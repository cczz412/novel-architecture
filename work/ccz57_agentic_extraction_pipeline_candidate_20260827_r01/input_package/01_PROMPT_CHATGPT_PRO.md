# 给 ChatGPT Pro 的任务

你收到的是一份只读的独立咨询材料包。请完整阅读 00_READ_ME_FIRST.md 和 01_BACKGROUND_AND_BOUNDARIES.md，再按需要下钻五份 Deep Research 原件和本地 API 探针的冻结输入、原始请求、原始回复、运行回执与观察记录。

## 你的核心任务

请为中文长篇小说的事实抽取设计一套“可迭代、可纠错、可停止、可审计”的候选模块管线。不要把它简化成“同一个模型再想一次”，也不要假定一次调用必须直接交付最终正确结果。

请围绕下面几条相互影响的判断做完整设计：

1. 哪些失败能由确定性程序发现和处理，哪些需要定向补抽、关系／说话人专项处理、独立 verifier 或人工。
2. 原始抽取、诊断、修复候选、验证和正式合并应该怎样分开，避免修复无痕覆盖原本正确内容。
3. 一次抽取、任务分解、打开思考、多轮补漏、独立模型互审分别适合什么错误，不适合什么错误。
4. 怎样保存每轮状态、输入、输出、Patch、证据、预算和错误指纹，怎样发现没有进展、震荡或回归。
5. 在当前证据很少、没有正式 Gold 的情况下，下一轮最小本地消融应先验证哪些单变量，才能决定是否值得组建正式产品模块。

## 必须交付的内容

### A. 证据判读

- 列出本地探针已经直接证明的现象，并给出对应包内文件路径。
- 列出只有五份研究报告支持、但原始来源没有随 Markdown 保留的候选。
- 列出当前材料无法回答的问题。
- 区分“格式合法”“值正确”“证据承托”“覆盖完整”“关系正确”“产品可用”，不要合成一个总 PASS。
- 不要凭本包计算正式模型排名或准确率；当前四题不是 Gold。

### B. 候选管线图

请给出一张从输入到保存结果的完整流程图。每个模块都要用大白话和工程字段分别写清：

- 读取什么；
- 输出什么；
- 是否允许修改已有结果；
- 保存哪些版本和证据；
- 哪些机器信号触发它；
- 谁负责：程序、主抽模型、专项模型、独立 verifier 或人工；
- 怎样证明它带来净改善；
- 什么情况下必须停。

至少判断这些候选层是否应该存在，以及它们应合并还是分开：

- 输入冻结与运行身份；
- 一次主抽取；
- JSON／Schema 机械检查；
- 纯格式的确定性派生修复；
- 证据定位与承托检查；
- 源文反向覆盖和显式事实补漏；
- 说话人专项；
- 因果／时间／指代／关系专项；
- 动机、伏笔和暗示的独立解释层；
- Patch 提案；
- 独立验证；
- 合并与版本保存；
- 预算、无进展、震荡和人工停损控制器。

### C. 错误路由表

针对运输失败、截断、模型身份异常、坏 JSON、代码围栏、非法空值、证据找不到、证据不承托、漏显式事实、漏说话人、漏关系边、跨句指代、状态变化、动机／伏笔推断、多轮回归，分别给出：

- 可观察的触发信号；
- 推荐处理器；
- 处理器只允许改变什么；
- 验证方法；
- 最大尝试和停损；
- 失败时交给谁。

如果证据不足以确定唯一处理器，请保留候选，不要为了表格整齐硬选。

### D. 状态与数据结构

请提出最小必要的数据结构，至少覆盖：

- 不可变原始 attempt；
- parser／Schema／证据／覆盖／关系等诊断；
- 局部 Patch 和被触碰字段；
- 修复前后 diff；
- 验证结论与争议；
- 模型、供应商、思考档、Prompt／Schema／输入版本；
- Token、耗时、费用、重试、调用身份；
- 合并版本和人工决定；
- 停止原因。

字段应足够让后续程序实现和测试，但不要直接把候选写成正式产品合同。

### E. 两级实施方案

请分别给出：

- 一个最小可运行版本：尽量少的模块和调用，能先解决当前最清楚的失败；
- 一个演进版本：只有当本地消融证明净收益后才加入的能力。

明确哪些模块现在不该做，避免为了“像 Agent”制造复杂循环。

### F. 下一轮最小消融

请设计 4～8 个按优先级排列的冻结 A/B。每个实验只改一个变量，并写清：

- 冻结什么；
- 只改变什么；
- 用哪类合成题或未来获批 Gold 切片；
- 观察哪些指标；
- 什么结果支持继续；
- 什么结果应停止该路线；
- 预计新增调用数、Token／耗时级别和人工工作。

至少单独测试：

- 纯格式修复是否保持所有叶子值不变；
- 源文反向覆盖是否提高显式事实召回且不过度增加假项／重复；
- 说话人专项是否只在明确触发子集上净改善；
- 已有因果两端时，关系专项是否比“整包再想一次”更有效；
- Patch-only 修复是否比整包 regenerate 更少破坏正确项；
- 4096 到 8192 的变化到底只是缓解截断，还是产生语义改善。

## 评价规则

不要只给一个总分。至少并排保留：

- 请求成功、截断和模型身份；
- JSON 解析与 Schema；
- 字段值；
- 证据定位与承托；
- 显式事实覆盖；
- 说话人、因果、时间、指代、状态变化等关系切片；
- 错误变正确、正确变错误、正确项保留、重复和矛盾；
- Token、耗时、费用、调用次数和人工升级率。

## 硬边界

- 不把本地合成探针叫 Gold，不宣布模型整体可用，不替代 CCZ-84 或 CCZ-57 正式验收。
- 不把 Deep Research 内部引用编号写成已核实的一手来源。
- 不要求披露或依赖模型隐藏思维链；只使用可观察输入、输出、工具结果和状态。
- 不授权新的 API 调用、训练、扩样、Gold 生成、Linear／GitHub 写入或产品施工。
- 不把你的建议写成已经批准的产品合同。
