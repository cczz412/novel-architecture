# CCZ-57 Agent 式抽取纠错管线｜Pro 回包本地采用审查 R01

## 结论

这份回包可以作为**候选管线设计底稿**，不能直接当成产品合同或施工许可。

最适合现在采用的是“程序控制、保留原件、分层检查、局部修改、独立验证、能停就停”这套骨架。最不适合现在直接照搬的是自动语义修复、同模型反复自审、默认开思考、整包重写和多数票。

下一步应先做一轮 **0 次新增 API 调用的离线骨架验证**。跑通以后，再由 CZ 单独批准一个 6～8 例的小型 API 对照；不直接启动报告里每组 24 对样本的大实验。

## 回包和本地证据是否对得上

机械核对结果：

- 返回 ZIP 的 SHA-256 与 ChatGPT 给出的值完全一致；压缩包测试通过，根目录只有约定的四份 Markdown。
- 输入包的 `MANIFEST.sha256` 有 504 条，整个包有 505 个文件。多出来的一个就是清单文件自己，不是漏算或夹带。
- 40 组 4096／8192 请求逐组归一化比较后，差异只有输出 Token 预算值，没有偷偷改 Prompt、材料、模型或思考档。
- Doubao Mini Q2 的接口外层 JSON 能解析，但 `content` 字符串里的某条事实确实有两个同名 `status`。一般解析器很可能只留下后一个值，前一个值会被静默覆盖。

所以，回包抓到的“成功响应、JSON 可解析、合同合法、语义正确是不同层次”有本地原始证据支撑。

## 可以直接采用为设计纪律的内容

| 候选纪律 | 本地判断 | 现在能做什么 |
|---|---|---|
| 原始请求和原始回复不可覆盖 | 直接支持 | 每次尝试只新增证据，不回写原件 |
| 运输、身份、截断、JSON、Schema、证据和语义分开判断 | 直接支持 | 不再用一个总 PASS 掩盖失败位置 |
| 诊断、修复、验证、合并分成四步 | 直接支持 | 每一步留下单独输入、输出和责任边界 |
| 纯格式问题优先由程序处理 | 直接支持 | 只处理外层代码围栏等可证明不改叶子值的情况 |
| 模型只交局部 Patch，程序负责合并出新版本 | 方向支持 | 先离线定义 Patch、diff、父子版本和作用域检查 |
| 重复错误、A→B→A、正确项回归、预算耗尽就停 | 方向支持 | 先实现错误指纹和停止原因，不让循环无限跑 |

这些是工程护栏，不等于它们已经证明能提高小说事实抽取准确率。

## 不能直接照搬的地方

### 1. 因果边还不在 v2.1 合同里

当前抽取模块读取“背景卡＋当前章节”，输出的是 `facts` 数组。现行 v2.1 没有正式的 `relations` 字段。回包提出让因果专项处理器写 `/relations`，这不是普通局部修复，而是新增一种输出。

推荐先做旁路候选：`RelationCandidate` 只保存“原因事实 ID、结果事实 ID、关系类型、证据、置信边界”，不写回现行事实库。等实验能证明净改善，再决定是否改正式合同。

### 2. 不能拿数组下标当长期身份

JSON Patch 标准适合表达局部变更，但当前事实是数组，数组下标会随着增删移动。回包自己也提醒了这个风险。离线试验应给事实生成旁路稳定 ID，例如“原始尝试 ID＋原顺序＋内容摘要”，Patch 指向稳定 ID，由程序解析成当时的数组位置。原始回复仍不改。

### 3. 报告里的数字是候选预算，不是已经批准的预算

“每个语义实验 24 对”“运输错误重试 1～2 次”“一次主抽取＋一次修复＋一次验证”等数字没有被本地实验验证，也没有得到 CZ 的新授权。它们只能当设计起点，不能直接变成运行默认值。

### 4. 4096→8192 先分析旧回件，不急着再花调用

本地已经有 40 组严格配对请求和对应回件。先把“是否截断”“A/B 都完整时语义有没有变化”“Token、耗时和坏 JSON”机械整理出来。旧证据答不出来的部分，才进入新的小型对照。

### 5. ChatGPT Pro 身份只得到用户侧说明

本轮返回材料由 CZ 标明来自 ChatGPT Pro，但没有一并提供页面模型标签或发送回执。因此可以确认“回包与输入包绑定、内容完整”，不能独立证明网页当时显示的精确模型身份。

## 先做的 0 API 离线切片

这轮只使用已经保存的 Q1～Q4 原始请求和回复，不调用模型：

1. 建立不可变 Attempt 记录，保存请求、原始字节、模型身份、耗时、Token、截断和错误。
2. 增加重复 JSON key 检查、普通 JSON 解析、v2.1 Schema 检查和 evidence 原文定位。
3. 实现唯一允许的格式派生：剥除单层代码围栏；派生前后所有叶子值和数组顺序必须完全一致。
4. 定义旁路稳定事实 ID、PatchProposal、父子版本和 touched paths；不修改原始回复。
5. 用现成的空 `speaker`、重复 `status`、坏 JSON 和 Q4 因果缺边重放错误路由。
6. 实现重复错误指纹、无进展、A→B→A、未触碰字段变化和正确项回归的停止记录。

这轮通过，只能证明管线骨架能正确保存、发现、路由和拒绝问题，不能证明自动语义修复有效。

## 以后才需要 API 的小型验证

离线骨架通过后，再从获批材料里挑 6～8 例，单独批准并冻结：

- Patch-only 与整包重写谁更少破坏正确项；
- 因果两端已经存在时，只补边能不能净改善；
- 说话人专项是否只在明确触发的子集上有效；
- 独立验证器是否比同模型自审更可靠；
- 关闭思考和最低思考的差异是否能复现。

必须并排记 `错→对`、`对→错`、正确项保留、重复、矛盾、Token、耗时、费用、调用次数和人工升级率。不能只报“修完以后有几条”。

## 小说辅助产品现在真正缺什么

当前模块读取背景卡和章节正文，能输出一份事实数组。小说辅助产品还缺少三块能力：

- **长期保存和版本判断能力**：不能把原始尝试、派生版本、Patch、验证结论和当前可用版本稳定地串起来。作者改稿或重新抽取后，产品就难以说明哪份结果从哪次请求演变而来。
- **生成能力**：产品还不能把已抽出的两个事件安全生成为“候选因果边”，也不能证明自动补出的说话人或关系是对的。作者仍要自己重读原文找遗漏关系。
- **传递和使用能力**：即使诊断器发现空说话人、重复字段或因果缺边，产品还不能把最小问题安全交给对应处理器，再让独立验证器判断能否进入新版本。作者无法放心把抽取结果交给后续检索和续写模块。

0 API 离线切片主要补“保存、版本判断和安全传递”的骨架；语义生成能力仍需后续小样本实验。

## 外部资料能支持到哪里

- [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core.html)支持把结构断言独立检查，但结构通过不能代替小说语义判断。
- [RFC 6902](https://www.rfc-editor.org/rfc/rfc6902.html)支持用标准操作表达局部 JSON 变更，但不会替我们解决数组身份和语义真值。
- [LangGraph 的持久化与故障恢复](https://docs.langchain.com/oss/python/langgraph/persistence)以及[中断恢复说明](https://docs.langchain.com/oss/python/langgraph/interrupts)支持保留检查点和注意节点重放；[Temporal 的 Activity 说明](https://docs.temporal.io/activity-definition)也强调可能重复执行，因此有副作用的步骤要能幂等。
- 关于模型自己审自己，[Self-Correction Without External Feedback](https://arxiv.org/abs/2310.01798)报告了缺少外部反馈时可能不升反降；[CRITIC](https://arxiv.org/abs/2305.11738)说明外部工具反馈在它研究的任务上有帮助。两者都不能直接证明中文长篇小说抽取会得到相同结果。
