# 大纲结构模板 v1｜填空表（外发实拆用）

用途：把这张表＋真实小说前 N 章发给 ChatGPT，让它逐章填空，并全程复述思考过程。
依据：R10 v0.1＋修订草案 v0.2 全部拍板（改判①～⑦、⑪⑫方向、D-HOOK-002、D-TIME-001、D-ADAPT-001）。
地位：**v1 初稿，待 CZ 过目定稿后才外发**。

---

## 填表总规则（写给 ChatGPT 的）

1. 逐章填写；每填一个区块前，先用一段话说明你打算怎么填、依据正文哪里。
2. 凡是从正文抽出来的条目，必须带证据锚（引用原文短句或段落位置）；没有依据就留空并写"无依据"。空值合法，不许硬编。
3. 分清三种性质再落笔：读者亲眼看到的／角色的推测或误信／系统（世界规则）宣告的。谣言和真相分两条记，不许合并。
4. 全程复述你的工作顺序（见表末"过程复述区"），这部分和填表本身同等重要。

---

## 第一部分｜书级信息（整本填一次）

| 栏 | 填什么 |
|---|---|
| 书名／题材 | |
| 导入来源声明 | 这书是自有／授权／仅摘录分析？（本次实验统一填"仅摘录分析"） |
| 世界时间体系 | 这本书故事内时间怎么记？（真实历法／虚构朝代纪年／副本内计时／第几世…可文字＋数字） |
| 世界线清单 | 有几条线/几层现实/几个副本/几世？各起个名（重生文必填第一世/第二世） |
| 世界规则（金手指） | 每条：触发条件／效果／代价／限制／例外；标"读者已知/未知" |

## 第二部分｜章级账本（每章一份）

### 2.1 章内变化流（唯一权威原始账）＝有序阅读节拍

按读者阅读顺序列节拍，每拍一行：

| 拍号 | 读者这一拍看到什么（一句话） | 发生的事件/事实变化 | 这拍揭露了什么信息（性质：读者所见/角色推测/系统宣告） | 知情变化（谁从不知道→怀疑→知道） | 视觉锚（若这拍是名场面/关键画面，起名并一句语义） | 手法标签（大类→二级） | 证据锚 |
|---|---|---|---|---|---|---|---|

- 揭露闸：如果某条信息刻意压到后面的拍才揭晓，标"压至第 X 拍"。
- 视觉锚每章最多挑 1～3 个高优先级，不许把每拍都当名场面。

### 2.2 事件/事实登记（从变化流沉淀）

| 条目 | story_time（故事内时间，支持文字纪年） | context_ref（哪条线/哪层现实/第几世） | assertion 性质 | known_by（谁：知道/怀疑/误信/部分知道/特意标注不知道） | 证据锚 |
|---|---|---|---|---|---|

- known_by 名单外＝没追踪，不代表不知道。
- 群体可整体记（"赵家全族知道"），个别例外单列。

### 2.3 钩子与债（分三种，别混）

| 类型 | 填什么 |
|---|---|
| hook_occurrence（本章已发生的钩子事实） | 正文里明确挂出的悬念/威胁/承诺/倒计时，带证据锚 |
| candidate_obligation（候选读者债） | 跨章存在＋不回应读者会明显失望的才填；**只登记不排期**；标"章末可观测"还是"后文才确认" |
| 章末悬念（吊胃口用） | 本章结尾的钩子类型；普通转场悬念只记这里，不进上面两栏 |
| 故事内触发器（若有） | 锚定故事内事件/时间/条件的未来安排（如"X 与 Y 相遇必触发 Z"），不锚章节号 |

### 2.4 章末快照（从变化流推算的缓存）

主要角色状态／位置／关系／资源／进行中冲突，一览。注明：本表可由 2.1 重算得出，如与 2.1 矛盾以 2.1 为准。

### 2.5 章间交接

交给下一章什么：未闭合的场面、进行中的对话/战斗、悬着的承诺。只向前传，不回改历史。

## 第三部分｜体验合同（每章一张，反向填写）

从正文倒推"如果当初要生成这一章，合同上必须写死哪几条"。**稀疏原则：只填真要卡死的三五件，其余留空。**

| 组 | 填什么 |
|---|---|
| 硬约束 | 不守住这章就废的（如：主角身份必须压到第 X 拍才揭；某高光台词必须原样出现） |
| 软偏好 | 有更好，没有不算错（节奏/氛围倾向） |
| 控制 | 避开近期用过的手法标签（引用 2.1 标签列） |

## 第四部分｜弧线级观察（每 3～5 章填一次）

- 这几章的读者情绪走势（蓄压/爆发/喘息）？
- 有没有手法标签用得过密（同一二级标签近几章反复出现）？哪些是套路该轮换、哪些其实是人物招牌该豁免？
- 长线债务健康度：哪些候选债在靠近兑现、哪些在被遗忘？

## 第五部分｜过程复述区（每章填完后写，最重要）

1. 你这章的实际工作顺序是什么？（第一遍读时干了什么→第二遍…；先抽事件还是先排节拍？合同是最后倒推的吗？）
2. 一共过了几轮？每轮各解决什么？
3. 遇到岔路怎么办的？（如：一句话分不清是推测还是事实→你按什么规则裁的？信息量太大→你怎么取舍的？）
4. 你做了哪些自检？（填完回头查了什么？发现并改掉了什么错？）
5. 如果让你把这套活拆成 7～8 次独立的 API 调用（每次一个模型只干一件事），你会怎么切？先后顺序？哪步依赖哪步？哪步该由程序而不是模型做？
