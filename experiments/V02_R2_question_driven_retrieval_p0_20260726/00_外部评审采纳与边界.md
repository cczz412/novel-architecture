# R2 P0｜外部评审采纳、暂缓与施工边界

## 结论

这份 ChatGPT 报告不是施工令。它抓出的三个工程缺口能在现仓复算，另有一个合同迁移边界须在 R2 单独处理：

1. R1 预注册写明“开放题不自动得分”，实际计分器却把开放题直接记成功；
2. R1 的主读数只看事实行是否出现指定来源编号，没有真正检查作者问题的完整答案；
3. C15 的句子切分会产生只含闭引号和空白的来源单元；
4. C15 五个新诊断标签按既定政策借用旧失败码、保持冻结码谱不扩展；这不是 C15 缺陷，但这些码不能直接充当 R2 的题级错误合同。

所以 R2 不能直接发网。先做 0 API 的 P0 地基件，再决定题级路线。

## 改后采纳

| 外部建议 | 本地改法 |
| --- | --- |
| 推荐路线叫 R3 | 为避免和当前 R2 道次混淆，本地不使用 R0～R3 命名；改成“整章直读基线／机械检索回取／薄底账回取” |
| 双层惰性缓存 | 证据窗口缓存可进开发实验；“确认事实缓存”推迟到路线已达标以后，不把它塞进第一轮 |
| 句子作为最小检索单元 | v2 同时保留段落和修复后的句子；第一轮以完整段落扩窗，句子只作索引定位 |
| Pro 窄补丁 | 只设计问题单和字段白名单；调用上限与是否启用等开发集主路线出数后由本地另冻合同 |
| R1 30 题继续开发 | 保留为章级盘点压力集；另外补点查、错误前提和无答案开发探针，不能把旧十题直接冒充全部作者需求 |
| source 编号映射 | 只作隐藏召回参考，不进入模型输入，也不直接决定题级成功 |
| 更严的质量门槛 | “硬错误 0、其他重大错误不多于 3”只作诊断建议；本道正式过闸仍照目标令的完整回答不少于 15／30、关键错误不多于 10 |

## 暂不采纳

| 项目 | 暂缓原因 |
| --- | --- |
| 向量检索 | 当前三章足够先做本地机械召回曲线；现在加入会多一个不可解释变量 |
| 模型生成冷索引 | R1 已证明它会把包做大，还曾污染计分 |
| 丰富长期状态账 | 会重新回到“先做万能章节记忆”的旧路；只在题级路线过闸后议 |
| 事实缓存自动写入 | 模型和程序都没有资格自行把候选升级成长期事实 |
| 旧 Q3 后继分支 | 目标令已经把它冻结；R2 新执行链不接这条历史分支 |
| 删除历史文件 | “删除出新路线”只表示不接新执行链；历史证据继续只读保留 |

## 本地已经获得的施工裁量

R2 目标令已经明确：打法、路线、次数由本地自定，不设中途核签。下面这些不再作为新的 CZ 等待项：

1. 开发阶段可以多路线；进入终验的路线必须在看不到终验结果前一起冻结，每条路线只跑一轮，同一批全部输出封存后再统一解锁评分；
2. 终验继续使用目标令要求的“同模板新 30 题”；顾问提出的十风险桶只用来补开发探针和诊断覆盖，不擅自替换终验模板；
3. 正式过闸仍是完整回答不少于 15／30、关键错误不多于 10；更严指标随账并列，不顶替现役门槛；
4. R2 新建题级错误合同，C15 冻结码谱一字不动；
5. Pro 只在开发集证明窄补丁有净收益后才进入候选终验路线，调用帽由本地在冻结实验合同时写死；
6. “确认事实缓存”不进入第一轮 R2；未来若做，接受票权限另行设计。

这段是本地对现有目标令的施工解释，不是新增拍板，也不增加新的中途核签。

## P0 停点

R2 第一次模型请求前，至少要交付：

1. 来源目录 v2 与逐字重建测试；
2. 题级金标合同：逐题冻结原子事实头、可回答／无答案／错误前提三种终态、必要限定与合法来源组；
3. 题级答案／部分回答／正确拒答／错误拒答／证据不托／限定错误／问题单／逐题成本合同；
4. 新题级计分器的合成夹具，证明开放题不会自动得分，且六种题级结果互不混账；
5. R1 开发锁箱迁移票，明确哪些题有完整语义真值、哪些仍缺人工判词；
6. 召回、回答、承托三张独立结果表；
7. 本地机械索引与召回—材料量曲线；
8. 终验封印包：题集、金标、计分器、检索参数、提示词、模型版本、重试规则分别报 SHA；
9. 运行器正式跑题时不可读取金标或答案锁箱，全部输出先封存，随后由隔离评分器解锁评分；
10. 证据承托不能由程序自签的边界票；
11. R2 题级失败码合同，未知码拒收；C15 原失败码绑定保持只读。

P0 机械全过也只代表“具备开实验的地基”，不代表推荐路线已经有效；它是本地施工前置检查，不是新增的 CZ 核签闸。
