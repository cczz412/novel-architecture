# V05｜作者体验层与新形态调查

## 总结论

✅ **T1～T12 没有整体走歪。**
“大纲唯一真账＋具名视图合同＋画布工作流＋黑盒流程／挂靠点”这套骨架，能承载商业网文、AI 漫剧和两个新形态。

但现在只能说**骨架能装**，还不能说功能已经完整。V05 暴露出三块必须补的东西：

1. **视图回提补丁协议**
用户在分镜、画布、互动试玩里改了东西，不能直接偷偷改大纲，也不能只留在下游形成第二本账。正确做法是：下游生成一份“建议怎样改大纲”的补丁，由作者确认后入真账。
2. **视觉生产适配包**
要补角色／场景／道具的资产身份、镜头语义、时长节奏、画面一致性检查、批量任务与成本控制。实际图片和视频不用塞进大纲，大纲只记资产 ID、版本、约束和使用关系。
3. **互动运行适配包**
要补玩家状态、世界状态、选项前置条件、选择后果、随机判定、分支汇合、存档回退和运行日志。否则“大纲”只能写出分支文案，不能真正跑成一个可玩的世界。

按产品承载能力粗估——**这不是测试结果，只是架构判断**：

| 场景 | 当前承载度 | 判断 |
| --- | --- | --- |
| 商业网文正文／大纲互转 | 约 85% | 主骨架已经成立 |
| 大纲转 AI 漫剧 | 约 75% | 缺视觉资产与生产控制 |
| 想法转 SVG 火柴人动画 | 约 85% | 不用改核心架构 |
| AI 互动叙事 | 约 60% | 必须补运行态和分支状态 |

🔥 **最该先做的画像：AI 漫剧创作者，具体瞄准个人及 1～5 人小团队。**

原因很直接：他们有明确产出任务、愿意为效率和算力付费、结果是否有用当天就能验证，而且你们的“爽点／期待／Hook／规则”能力，正好补上现有漫剧工具普遍偏生产、弱故事的问题。行业公开讨论也把剧本拆分、资产复用、人物场景一致性列为生产难点，同时指出真正拉开成绩的仍是故事和情绪调度。阅文近期的工具与扶持计划也在直接覆盖个人创作者和小型工作室。 ([中国青年报](https://zqb.cyol.com/pc/content/202601/27/content_421675.html))

**小白作者不是第一付费画像，而是第一获客入口。**
“想法→SVG 火柴人定格动画”很适合让陌生用户第一次体验产品，但不要单独做成一个大而全的小白写作平台。

# 二、四类画像逐个判断

## 1. 小白作者

### ✅ 结论

**来用理由只成立一半。**

“我不会写，请 AI 给我一个大纲”不够强，因为平台自带工具已经能帮用户构思和续写。真正成立的理由应当是：

> **我脑中只有一个画面或念头，几分钟后就能看到它变成一个可播放、可选择、还能继续写成小说或漫剧的故事。**
> 

### 可操作方案

推荐工作流：

> 一句话想法
→ 系统只追问 2～3 个决定故事方向的问题
→ 自动生成 6～10 格 SVG 火柴人动态分镜
→ 给出 3 条明确不同的后续路线
→ 用户选择或自然语言修改
→ 生成前三章／前三集小大纲
→ 再询问是否扩成长线项目
> 

**最容易流失的地方：看到第一个有趣结果之前。**

因此不要让小白先填写这些东西：

- 世界观表
- 人物卡全集
- 故事线里程
- Hook 类型
- 规则对象
- 大纲字段

这些都应当由黑盒流程先推断，缺口再用大白话问。

必须可视的内容：

| 可视化 | 用户能看懂的问题 |
| --- | --- |
| 火柴人故事条 | “我的想法已经变成什么了？” |
| 人物欲望／阻力卡 | “主角想干嘛？谁在拦他？” |
| 三条路线预览 | “我选哪条会更爽、更虐或更刺激？” |
| 爽点与悬念标记 | “精彩点大概在哪？” |
| 一句话修改前后预览 | “AI 到底改了什么？” |

### 代价与风险

⚠️ 最大风险不是技术，而是**新鲜感消费**：用户玩一次觉得有趣，但没有继续创作的理由。

另一个风险是模板味。每个想法都变成“受辱—觉醒—反杀”，短期看爽，第二次就腻。

### 反面核查

用同一批完全没写作经验的用户，对比：

- 普通聊天框生成故事；
- 你们的火柴人可视流程。

若后者不能明显提升以下表现，来用理由就不成立：

- 完成第一次故事的比例；
- 用户是否知道下一步该做什么；
- 是否主动修改或选择了一次剧情；
- 7 天内是否创建第二个故事；
- 是否把低清原型继续扩成大纲／正文／漫剧。

## 2. 网文老作者

### ✅ 结论

**来用理由成立，但必须定位成“接管旧稿、检查风险、辅助改编”，不能定位成代写。**

公开调查里，小说作者使用 AI 时最常见的是构思、搜索和找措辞，真正直接拿 AI 文本发表的比例很低；作者也普遍担心事实错误、内容乏味、署名和训练授权问题。 ([PublishersWeekly.com](https://www.publishersweekly.com/pw/by-topic/digital/copyright/article/99019-new-report-examines-writers-attitudes-toward-ai.html))

老作者最可能为了这些事来：

- 导入几十万字旧稿，自动接管人物、规则、伏笔和状态；
- 找出吃设定、时间线冲突、长期未兑现期待；
- 规划接下来几章，但不改变他的创作意图；
- 把旧书快速改编成漫剧／短剧；
- 保持作者自己的口吻和套路边界。

### 可操作方案

推荐工作流：

> 导入正文
→ 自动提取大纲
→ 只让作者审核高风险项
→ 显示证据原文
→ 给出问题与影响范围
→ 作者选择“忽略／纠正／加入计划”
→ 生成未来 3～5 章方案或改编视图
> 

**最容易流失的地方：第一次提取审核。**

只要出现下面任何一种情况，老作者会立即不信任：

- 人物关系抽错很多；
- AI 无法指出判断来自哪段正文；
- 作者要逐条补几十个字段；
- 系统没问就改掉设定；
- 修正一次，别处又跟着乱掉。

必须可视的内容：

| 可视化 | 作用 |
| --- | --- |
| 原文证据卡 | 点一下看到系统为何这样判断 |
| 改动影响图 | 改一个规则会影响哪些章、人物和分镜 |
| 已发表锁定带 | 清楚区分不能改的历史与可调整的未来 |
| 期待／兑现时间线 | 哪个读者承诺拖太久、哪个即将到期 |
| 金手指规则状态 | 当前等级、代价、冷却、已暴露信息 |
| 套路重复提示 | 最近几章是否连续用了同一种打脸或钩子 |

### 代价与风险

⚠️ 最麻烦的地方在于“校对税”。

如果作者修正系统的时间，接近他自己整理设定的时间，整套结构再先进也没用。

来源、模型使用和作者控制也应当做成前台信任能力，而不是只藏在日志里。

### 反面核查

拿 5 本已连载、至少几十万字的商业网文试：

- 人工整理一份可续写账；
- 系统提取后由作者修正一份。

若系统版不能明显减少整理时间，或作者在完成审核后仍不敢让系统规划后续，这个画像就暂时不成立。

## 3. 工作室：多人协作、批量产出

### ✅ 结论

**来用理由很强，但当前架构只解决了“大家看同一本账”，还没完全解决“大家同时改这本账”。**

团队类写作和分镜产品普遍把角色权限、评论、审批、历史版本和恢复能力当作标准功能，因为多份稿件和同时编辑很容易造成“谁的是最新版”以及覆盖冲突。 ([Celtx Blog](https://blog.celtx.com/collaborative-screenwriting-software/))

工作室会为了这些事来：

- 一本 IP 同时跑正文、剧本、分镜、素材和成片；
- 统一人物、规则、画面资产；
- 把任务批量分给编剧、分镜、生图、后期和审核；
- 减少返工；
- 看清成本、卡点和交付进度。

### 可操作方案

推荐工作流：

> 导入／立项
→ 负责人锁定故事底稿
→ 系统按集／章拆工作包
→ 不同角色只看自己的具名视图
→ 提交修改补丁
→ 审核人合入大纲
→ 批量生成低清预演
→ 锁资产
→ 高成本生成
→ 质检与导出
> 

**最容易流失的地方：第一次跨角色交接。**

例如编剧改了人物动机，分镜师还在使用旧版本；或生图组锁定了角色形象，剧情组又修改年龄和服装。

必须可视的内容：

| 可视化 | 作用 |
| --- | --- |
| 制作看板 | 每集处于大纲、分镜、素材、视频还是审核 |
| 依赖关系 | 这个修改会让哪些已做素材失效 |
| 版本对比与审批 | 谁改了什么，谁批准的 |
| 资产复用图 | 哪些角色、场景、技能特效可以重复调用 |
| 异常队列 | 只集中展示冲突、失败和待人工判断项 |
| 成本／耗时面板 | 每集、每镜头花了多少生成次数与算力 |

### 代价与风险

⚠️ “唯一真账”可能反过来成为团队瓶颈。

如果任何小改动都要等待中央大纲锁，团队会绕开系统，用文档和群聊继续干活，随后产生影子版本。

### 反面核查

做一次真实三角色试产：编剧、分镜、生图／后期共同制作 10～20 集。

失败信号包括：

- 大量修改只存在聊天记录；
- 团队仍靠文件名判断最新版；
- 一个小修改导致整集重新生成；
- 大纲成为审批堵点；
- 负责人无法追溯成本和返工原因。

## 4. AI 漫剧创作者

### ✅ 结论

**这是最该先做的画像，来用理由最完整。**

现有工具已经能做剧本拆分、分镜、角色一致性、资产生成和批量导出；但行业公开反馈仍把故事质量、情绪节奏、角色场景一致性和资产复用列为主要问题。 ([中国青年报](https://zqb.cyol.com/pc/content/202601/27/content_421675.html))

你们的差异可以说得很清楚：

> 别的工具主要让画面生产更快；
你们要让“读者为什么继续看”一路传到镜头和成片里。
> 

### 可操作方案

推荐最小工作流：

> 导入网文／大纲
→ 自动拆成集级故事节拍
→ 生成 SVG 低清动态分镜
→ 作者确认剧情与节奏
→ 锁定角色／场景／技能资产
→ 批量生成高质量画面和视频
→ 一致性与剧情忠实度检查
→ 导出
> 

**最容易流失的地方：第一次高成本画面生成之后。**

用户最怕的是：

- 人物不像同一个人；
- 画面好看但剧情意思错了；
- 一段简单镜头反复抽很多次；
- 不知道修改大纲会报废哪些素材；
- 生成费用不可预期。

必须可视的内容：

| 可视化 | 作用 |
| --- | --- |
| 故事节拍／镜头双层时间线 | 同时看“剧情发生什么”和“画面怎么表现” |
| 角色一致性板 | 正面、侧面、表情、服装、受伤等状态 |
| 场景／道具／技能资产库 | 复用而不是反复生成 |
| 镜头剧情目的标签 | 这一镜是在铺垫、展示规则、制造爽点还是留钩子 |
| 镜头成本与重抽次数 | 及时发现生产黑洞 |
| 修改影响预览 | 改剧情后哪些镜头需要重做 |

### 代价与风险

⚠️ 视觉模型变化很快，不能把产品价值绑在某一家模型效果上。

你们应当稳定拥有的是：

- 大纲和镜头语义；
- 资产身份；
- 生成任务；
- 评价记录；
- 用户选择；
- 失败原因。

具体调用哪一个图像／视频模型，应当可以替换。

### 反面核查

第一阶段不要只测“能否生成视频”，要测：

- 第一次结果中有多少镜头可以直接用；
- 每镜头平均重抽次数；
- 人物／服装／场景漂移率；
- 画面是否准确表达大纲中的剧情变化；
- 每分钟内容成本；
- 用户是否真的发布，而不只是生成试玩。

# 三、新形态①：想法→SVG 火柴人定格动画

## ✅ 结论

**需求成立，现有架构大体能承载。推荐把它定义成“故事原型机”，而不是低配漫剧生成器。**

Storyboarder 直接用“像画火柴人一样快”来描述故事验证；Boords、Firefly 等产品也都把文字快速变成可播放分镜作为低门槛入口。 ([Wonder Unit](https://wonderunit.com/storyboarder/))

用户买的不是火柴人，而是：

- 不会写也能把想法讲出来；
- 很快发现故事是否无聊；
- 很快改方向；
- 可以把这个低清结果继续升级成正文或漫剧。

## 可操作方案

推荐流程：

> 想法输入
→ 黑盒补齐最少信息
→ 生成临时大纲
→ `stick_animatic.v1` 具名视图
→ 组件化 SVG 播放
→ 用户改画面／台词／方向
→ 生成大纲修改补丁
→ 用户确认入账
> 

这里应优先用**确定性的 SVG 组件库**，不要一开始就调用不稳定的生图模型：

- 固定人物骨架；
- 常见姿势；
- 表情；
- 前中后景站位；
- 推拉摇移等简单镜头；
- 对话框、旁白和音效；
- 受击、爆炸、升级、闪回等商业网文高频表现。

这样速度快、成本低、修改可控，特别适合小白第一次体验。

## 还缺什么件

| 缺件 | 挂载位置 |
| --- | --- |
| `stick_animatic.v1`：人物、站位、动作、表情、镜头、时长、字幕、音效的输出约定 | **具名视图合同** |
| SVG 人物／场景／道具组件身份与版本 | **本体的题材／视觉适配层** |
| 逐帧编辑、播放、拖动时长、替换动作 | **画布** |
| “改这一帧后，大纲应怎样变”的补丁协议 | **具名视图合同＋画布** |
| 故事方向确认、角色确认、低清预演确认、正式导出 | **黑盒挂靠点** |
| 低清预演里仍要显示本集推进、爽点与末尾钩子 | **体验合同** |

## 代价与风险

- 火柴人效果过于简陋，用户误以为这是最终成品；
- 用户只玩一次，不进入长期创作；
- SVG 动作库积累会逐渐变成一项内容资产工程；
- 编辑画面后若不能同步回大纲，会马上出现第二本账。

解决方式是在界面上始终把它叫做**“剧情预演”**，并提供一条明确升级路径：

> 剧情预演 → 漫画分镜 → 高质量画面 → 动态漫剧
> 

## 反面核查

若用户看完火柴人预演后：

- 不能复述主角目标；
- 不知道高潮和钩子在哪里；
- 很少选择或修改剧情；
- 很少继续扩成大纲／正文／高质量画面；

那它只是一个有趣演示，不是产品入口。

# 四、新形态②：AI 互动叙事，故事当虚拟世界来闯

## ✅ 结论

**方向成立，但当前架构只能承载“互动内容设计”，还不能独立承载“互动世界运行”。**

说白了就是要分清两种东西：

- **设计态大纲**：作者写好的可能性空间，仍然是唯一创作真账；
- **运行态存档**：某个玩家具体走了哪条路、拿了什么东西、谁对他好感多少。

运行态存档不是第二套创作格式，它更像游戏存档。互动引擎仍只消费大纲导出的具名视图；只有作者决定把某次玩家经历升格成正式剧情时，才通过补丁写回大纲。

## 可操作方案

不要一开始就做“用户随便输入什么，AI 都接着编”。

更稳的首版是：

> 每张定格画面
→ 2～3 个作者／AI 编排过的选择
→ 额外一个受世界规则约束的自由输入
→ 系统判断条件和后果
→ 更新状态
→ 播放下一张画面
> 

Hidden Door 的经验说明，允许自由输入但又维持世界规则，比无限迎合玩家更有挑战；可它也暴露了等待时间和叙事跳脱会迅速让用户离开的风险。 ([The Verge](https://www.theverge.com/games/757816/hidden-door-early-access-ai-story))

推荐第一批只做**半开放互动**：

- 大方向由大纲保证；
- 小行动允许玩家自由发挥；
- 关键节点重新汇合；
- 失败也要产生有趣后果，而不是“失败，请重来”；
- 每次选择都应让至少一个状态、信息或关系发生变化；
- 每段都继续维护商业内容所需的短期目标、兑现和悬念。

Dorian 的商业互动创作指南同样强调早期目标、频繁选择和结尾悬念，说明你们现有期待账、爽点账和 Hook 账有明显复用价值。 ([Dorian: The Social Fiction Platform](https://home.dorian.live/dorianacademy/quickstart-guide))

## 还缺什么件

| 缺件 | 挂载位置 |
| --- | --- |
| 玩家状态、关系、资源、背包、身份、世界状态 | **本体适配层** |
| 选择节点、前置条件、状态变化、成功／失败、随机判定、不可逆标记、分支汇合 | **本体适配层** |
| “这次选择给玩家什么感受”的合同：风险、诱惑、信息差、短期／延迟回报、失败乐趣 | **体验合同** |
| `interactive_story.v1`：画面、选项、条件、结果、降级方案、状态展示 | **具名视图合同** |
| 分支图、可达状态、死路、永远触发不了的选项、试玩路径 | **画布** |
| 世界规则锁定、关键选择前、重大剧情段结束、异常路线出现后 | **黑盒挂靠点** |
| 叙事导演、状态裁决、存档、回退、运行日志、延迟与成本控制 | **黑盒运行服务** |
| 将玩家生成的新剧情提议升格为正式大纲 | **视图回提补丁协议** |

🔥 **最关键的新对象不是“更多分支”，而是“状态转移”。**

Twine、ink、ChoiceScript 和 Yarn Spinner 的共同结构都是变量、条件、状态更新和运行接口；这也是现有 T1 单一章末快照无法完整表达的部分。 ([Twine](https://twinery.org/))

## 代价与风险

- 分支越走越多，内容量失控；
- 玩家感觉三个选项其实都会回到同一个结果；
- 自由输入破坏金手指或世界规则；
- 生成等待数秒，用户直接离开；
- AI 忘记玩家之前做过的事；
- 玩家靠一句话绕过所有挑战；
- 每条路线都临时生成画面，成本不可控。

## 反面核查

建议拿一个 5～8 分钟的小世界做试玩，不要先做长篇：

- 至少有一次选择立即生效；
- 至少有一次选择延迟兑现；
- 至少有一次失败仍产生新剧情；
- 至少有两条路线中途汇合但保留不同状态；
- 回退后能稳定重放；
- 玩家能解释“我的选择改变了什么”；
- 等待时间没有明显打断沉浸。

若玩家只说“文案不一样，但选什么都一样”，互动形态就失败了。

# 六、画像优先级与产品顺序

## ✅ 推荐顺序

### P0：AI 漫剧创作者

精确瞄准：

- 个人创作者；
- 1～5 人小团队；
- 已有网文、小说推文或短剧想法；
- 要快速做 1～3 分钟试片；
- 当前正在多个 AI 工具之间复制粘贴。

首发承诺不要写成“全自动做漫剧”，而应写成：

> **一份故事大纲，自动管住剧情、分镜、角色资产和批量生成；修改一次，知道哪里受影响。**
> 

### 同期获客入口：小白 SVG 故事原型

它负责让新用户几分钟内看到结果，然后把有继续意愿的人带入大纲项目。

### P1：工作室包

补齐：

- 权限；
- 审批；
- 版本；
- 批量队列；
- 成本；
- 资产库；
- 异常处理。

这会把个人漫剧创作者自然升级成团队客户。

### P2：网文老作者

主打：

- 旧稿提取；
- 证据核对；
- 续写诊断；
- 漫剧改编；
- 不改作者原意。

老作者价值高，但信任建立慢，应该在提取准确率和证据锚经过大量漫剧项目磨过之后再重点攻。

### P3：AI 互动叙事

这应当视为一条新产品线，而不是在大纲页面旁边加一个“互动模式”。

它需要独立的运行服务、存档、状态裁决、内容安全、延迟控制和玩家数据分析。架构能共用，产品开发量不能低估。

# 七、质疑清单

## T1｜厚描三件套作为唯一真账

**质疑：对线性作品成立，对互动叙事不够。**

章末快照默认存在一个实际章末状态；互动世界同时可能存在多组可达状态。`story_time＋narration_order` 也不能表示“玩家走了哪条路径、什么条件导致这条路径可达”。

**建议：** T1 不推翻，但互动适配层增加：

- `branch_context`
- `state_transition`
- `reachable_state_set`
- `rejoin_key`
- `session_state_ref`

**证伪方式：** 用当前 T1 原样装入一个包含 20 个选择节点、6 个状态变量、3 次分支汇合、一次随机失败和一次回退的故事。如果能稳定恢复任何路径，并保证后续选项完全一致，此质疑可撤回。

---

## T7｜每章一份体验合同

**质疑：合同范围过度绑定“章”。**

网文章节改成漫剧时，可能一章拆三集，也可能五章并成一集；互动内容还会以任务、场景段或选择段为体验单位。只有章合同，容易出现“原章有 Hook，但拆出的前两集没有结尾钩子”。

**建议：** 保留章合同，但增加：

- `scope_type = chapter / episode / interactive_segment`
- 父合同与子合同继承；
- 改编视图允许重新分配推进、爽点和 Hook，但不能丢失 `must_preserve`。

**证伪方式：** 取 5 章网文改成 10～15 集短漫剧。若不增加集级合同也能保证每集推进、爽点和钩子，此质疑可撤回。

---

## T8｜下游只读具名视图合同

**质疑：读边界拍对了，写回边界还没拍。**

实际用户一定会在分镜或互动画布上直接说：

- “这一镜让主角先忍一下。”
- “这个选项改成背叛队友。”
- “这集不要在这里揭晓。”

这些改动已经触碰故事含义。若只能在大纲里修改，体验很笨；若分镜直接回写，又会破坏唯一真账。

**建议：** 补 `proposed_outline_patch`：

- 修改来自哪个视图；
- 用户想改什么；
- 建议改动哪些大纲对象；
- 会影响哪些下游；
- 是否与已发表／已锁资产冲突；
- 作者确认后才入账。

**证伪方式：** 让漫剧创作者完成 30 次逐镜修改。若不需要补丁协议，也没有任何修改留在分镜侧形成影子真账，此质疑可撤回。

---

## T9｜固定八个逻辑阶段、两程序＋三到四模型

**质疑：过早拍死实现数量。**

用户关心的是准确率、成本、速度、可追溯和可恢复，不关心内部恰好几阶段、几个模型。模型能力变化后，固定数量可能变成维护负担。

**建议：** 冻结的是：

- 阶段输入输出；
- 工件信封；
- 质量门槛；
- 回退策略；
- 证据覆盖；
- 成本／延迟预算。

阶段数和模型数作为可替换执行计划。

**证伪方式：** 若八阶段在多题材、多长度和不同模型组合下，长期稳定优于更短或动态流程，且没有明显成本劣势，可以继续冻结。

---

## T10｜黑盒外不可插手

**质疑：对低成本抽取可行，对高成本视觉生成过硬。**

我不反对黑盒。用户不应该看见内部模型串联。问题在于：从故事直接一键跑到昂贵成片，中间只要方向错一点，就会造成大批返工。

**建议：** 至少保留这些作者可理解的挂靠点：

- 故事方向确认；
- 集级拆分确认；
- 角色／场景资产确认；
- SVG 低清预演确认；
- 高成本批量生成前确认；
- 导出／发表前确认。

**证伪方式：** A/B 测试无停点版与上述停点版。若无停点版完成率更高，同时重抽成本、弃稿率和剧情错误不增加，此质疑可撤回。

---

## T11｜推进力作为建议层主秤

**质疑：主方向正确，但不能成为压倒性单指标。**

商业网文确实要快，可“每章都强推进”容易变成：

- 连续升级；
- 连续打脸；
- 连续揭密；
- 角色没有喘息和依恋空间；
- 签名套路快速重复。

推进力应当是主秤之一，还要受到以下约束：

- 期待是否更强；
- 爽点是否真正兑现；
- 人物关系是否积累；
- 新鲜度；
- 情绪疲劳；
- 金手指规则是否被透支。

**证伪方式：** 让读者盲测“只按推进力推荐”与“推进力＋期待／人物／疲劳联合推荐”的连续 20 章。若前者留存更高且没有更强重复感，此质疑可撤回。

---

## 无重大质疑的部分

- **T2：** 九类对象＋可选池＋适配层方向正确。视觉和互动缺件先进入适配层，不必立刻污染固定核心。
- **T3：** Hook 生命周期登记很适合商业网文与互动任务追踪。
- **T5：** 暗稿放编排侧是对的，不能与已发生事实混账。
- **T6：** 故事线实况与全书目标双层规划，正好服务老作者和工作室偏航检查。
- **T12：** harness 和画布工作流复用方向没有重大问题，前提是四类画像看到的前台不同；小白不能直接看到工作室生产画布。
- **T4：** 已退役重造，格式尚未拍，当前没有足够对象可质疑。

# 八、第五节必答题：本轮有把握的推荐

## 1. 证据锚保留与否

### ✅ 结论：保留，而且属于高优先级能力

**置信度：0.97**

### 可操作方案

按内容来源分级：

| 内容 | 锚要求 |
| --- | --- |
| 正文提取出的事件、状态、规则、期待 | 必须能回到原文范围 |
| 作者手工规划的目标、Hook、暗稿 | 标记为“作者声明”，不伪造原文证据 |
| AI 新生成的建议 | 记录输入对象、工作流、模型／版本、生成时间 |
| 视觉素材 | 记录参考资产、生成模型、版本及授权信息 |
| 程序派生切片 | 指回派生所用的真账对象和版本 |

### 代价与风险

会增加存储、索引和迁移成本；如果每个无关小字段都强制精确到字，系统会变重。

### 反面核查

随机抽 100 个高风险判断，让作者追问“为什么”。若证据锚无法帮他快速接受或纠正判断，说明锚的粒度或展示方式错了，而不是说明不该保留。

---

## 2. 新逻辑句条目格式

### ✅ 结论：用“变化＋读者效果＋后续债务”，不要只写剧情摘要

**置信度：0.86**

### 可操作方案

推荐骨架：

> **触发／条件 → 主体目标 → 行动与阻力 → 状态变化 → 读者获得什么 → 留下什么后续义务**
> 

例子：

> 拍卖会当众羞辱
→ 林渊要保住妹妹的入场资格
→ 他冒险公开系统奖励、压过世家少主
→ 身份从“可随意欺负的废柴”变成“背景可疑的强者”
→ 读者得到第一次公开反杀
→ 欠下“系统奖励为何需要付出寿命”的解释义务
> 

结构化字段藏在后台，作者前台仍可以看到一句自然语言。

### 代价与风险

句子会比普通摘要长；模型也可能机械地给每件小事都加一个读者效果。

### 反面核查

同一条逻辑句分别交给正文、分镜和互动三个下游。如果三边对“发生了什么变化、爽在哪里、后面欠什么”理解明显不同，格式仍然不够明确。

---

## 3. 体验合同格式定稿

### ✅ 结论：分成硬约束、软偏好、控制字段三组

**置信度：0.90**

### 可操作方案

建议最小结构：

```
scope:
  chapter / episode / interactive_segment

hard:
  progression_target
  promise_or_payoff
  rule_must_show
  must_preserve
  ending_hook

soft:
  setup_refs
  desired_pattern
  emotional_temperature
  novelty_avoid

control:
  priority
  confidence
  valid_range
  source_intent
```

“章章有钩子”不代表每个字段都必须填满。没有需要展示的金手指规则时，可以明确为空，而不是硬塞一次规则解释。

### 代价与风险

合同过硬会让输出像流水线模板，意外感和人物自然反应会下降。

### 反面核查

拿连续 30 章做盲测，比较：

- 完整合同；
- 只给剧情目标；
- 硬约束＋软偏好合同。

若完整合同明显增加套路重复，说明字段或约束等级过重。

---

## 4. 字段版本化机制

### ✅ 结论：至少明确三种版本，不要只放一个 `version`

**置信度：0.88**

### 可操作方案

- **schema_version**：字段定义变了没有；
- **record_revision**：这条人物／事件／规则被改了几次；
- **view_contract_version**：下游接口属于哪个版本；
- 已发表或已正式生产的批次再锁一个 **published_snapshot_id**；
- 所有变化通过变更集记录，保留改前、改后、操作者和原因。

### 代价与风险

实现与迁移成本会上升，作者前台不能展示一堆版本号，只展示“已发表锁定／有新修改／下游需更新”。

### 反面核查

半年后打开旧项目，用当时版本重新生成具名视图。若无法复现，或系统无法明确告诉用户为何不同，版本机制不合格。

---

## 5. 暗稿可见性闸

### ✅ 结论：默认隐藏，按角色授权，明确“不会自动当成已发生事实”

**置信度：0.93**

### 可操作方案

- 个人作者：默认折叠，可主动打开；
- 工作室：作者、主编可见，分镜／生图角色默认不可见；
- AI 使用暗稿前必须检查权限；
- 暗稿转正式计划需显式“升格”；
- 导出、改编和互动运行默认不消费未升格暗稿。

### 代价与风险

隐藏过深会让作者忘记自己存过什么；权限过宽又可能提前泄露结局或让下游误用。

### 反面核查

让不同角色查看同一项目，检查是否有人看见不该看的结局，以及下游是否曾把暗稿当既成事实生成。

---

## 6. 偏航判定口径

### ✅ 结论：不要汇总成一个神秘分数，分三档告诉作者“偏在哪里”

**置信度：0.87**

### 可操作方案

| 偏航类型 | 示例 |
| --- | --- |
| 硬冲突 | 吃设定、人物状态冲突、已发表事实被改 |
| 商业体验偏航 | 期待过期、爽点迟迟不兑、连续同类 Hook、主角长期不推进 |
| 作者规划偏航 | 偏离故事线里程、结局方向、人物命运或全书大爆点 |

再结合：

- 已发表／未发表；
- 可动／不可动；
- 作者是否主动改计划。

### 代价与风险

提醒太多会形成告警疲劳，尤其不能把作者有意制造的压抑段落直接判成错误。

### 反面核查

拿成功连载中真实存在的“蓄压期”“换地图期”“感情沉淀期”测试。若系统大量误报为拖沓，偏航口径太单一。

---

## 7. 产出方标记字段

### ✅ 结论：必须定义，并与 provenance 配套

**置信度：0.96**

### 可操作方案

建议至少能回答：

- 来自正文提取、作者填写、AI 生成、程序派生还是多人合并；
- 谁或哪个工作流产出；
- 使用哪个输入版本；
- 置信度；
- 谁人工确认；
- 何时产出；
- 证据或上游对象在哪里。

前台只显示“正文提取／作者设定／AI 建议／程序派生／已人工确认”这类人话标签。

### 代价与风险

元数据会增多，但这是老作者信任、团队追责和模型替换的基础。

### 反面核查

发生错误时，若无法在一分钟内判断是原文冲突、提取错误、作者改动还是生成错误，字段定义不合格。

---

## 8. 建议层工况分型

### ✅ 结论：按“用户任务”分，不只按作者水平分

**置信度：0.91**

推荐至少分这些工况：

- 小白想法孵化；
- 新书开篇；
- 连载续写；
- 已发表内容后的未来规划；
- 未发表内容修订；
- 旧稿提取与诊断；
- 网文转漫剧；
- 工作室批量生产；
- 互动世界设计；
- 互动试玩异常处理。

同一个老作者在“续写”和“改漫剧”时，需要的建议轻重完全不同。

### 代价与风险

分型太多会让用户选不明白，因此应由系统按当前动作自动判断，用户只在判断错时切换。

### 反面核查

若作者需要频繁手动切工况，说明自动识别没做好；若不同工况最后给出的建议几乎一样，说明分型只是名称变化。

---

## 9. 挂靠点／停点清单

### ✅ 结论：只在“方向难逆转”或“接下来成本明显增加”的地方停

**置信度：0.95**

推荐挂靠点：

1. 正文提取完成后，只审核高风险项；
2. 故事核心方向确定；
3. 长线大纲锁定；
4. 章／集拆分完成；
5. 角色和场景资产锁定；
6. SVG 低清预演完成；
7. 高成本批量生成之前；
8. 正式发表／导出之前；
9. 互动试玩出现规则冲突、死路或异常高成本之后。

普通润色、小字段补全、低风险派生不应打断作者。

### 代价与风险

停点过多，黑盒失去爽感；停点过少，返工成本暴涨。

### 反面核查

记录每个停点上用户“直接通过／修改／退出”的比例。长期几乎没人修改的停点应删除；经常在停点之后大规模返工的地方，应向前移动。

# 最终拍板建议

✅ **保留 T1～T12 总方向，不重开整套架构。**

本轮应追加三项正式挂账：

1. **视图回提补丁协议**
这是四类画像都会碰到的共同缺件，优先级最高。
2. **视觉生产适配包**
与 AI 漫剧首发画像一起定义，覆盖资产身份、镜头合同、一致性、任务成本和审核停点。
3. **互动运行适配包**
先定义设计态大纲与运行态存档的边界，不急着开发完整开放世界。

🔥 商业落地顺序建议固定为：

> **AI 漫剧个人／小团队付费产品**
＋ **小白 SVG 故事原型获客入口**
→ 工作室协作包
→ 老作者旧稿／改编包
→ 半开放互动叙事
→ 更自由的虚拟世界玩法
> 

这条顺序既保住“大纲唯一中枢”，又能让用户一上来看到真正有用的结果，而不是先面对一套漂亮但难用的结构。
