# 新大纲格式的评测与金标体系设计建议

## 金标制作

**结论先行：**最省人力的金标做法，不是全量人工从零写，而是做成“**LLM 预标 + 人类改错 + 难例双标 + 冲突裁决**”。协议上要抓住一条：**凡是要进入提取质量秤的内容，必须是可观察、可对证、可回放的**。这也是我对“证据锚保留与否”的直接推荐：**必须保留，而且是强制保留**。现有研究里，数据集质量管理最常见的问题之一就是 agreement 和 error rate 算得不稳、不透明；而在人类或 judge 都容易飘的任务里，人写参考答案或明确证据，会明显提高对齐度、降低偏差。citeturn18view2turn18view5turn12view7

**可操作方案：**提取金标建议按“章节包”来标，不按单章孤立标。一个最小标注单元建议包含：**当前章正文、上一章末、下一章开头、最近一次状态快照、基础实体表**。这样才标得动“章内变化流”和“章间交接”。对象层面上，建议这样分：

| 对象 | 金标方式 | 省人力做法 | 是否强制证据锚 |
| --- | --- | --- | --- |
| narrative_units | 穷举 | LLM 预切分，人只修边界与功能 | 是 |
| entities | 穷举 | 先合并别名，再修角色功能 | 是 |
| events | 穷举 | 只标推动状态变化的事件，不标纯修辞动作 | 是 |
| state_facts | 穷举 | 只标“章末有效状态”与“中途关键变更” | 是 |
| rules | 穷举 | 只标规则本体、触发条件、限制、例外 | 是 |
| 章间交接 | 穷举 | 只标真正影响下章起跑线的交接 | 是 |
| reader_promises / payoffs | 重点抽样 | 每章只标 **Top 3–5** 个最影响追更的承诺/兑现 | 是，允许多证据 |
| future_obligations / Hook | 重点抽样 | 只标本章新挂出的与状态变化的 | 是 |
| provenance | 纪律层 | 自动携带，不单独评分但参与严格秤 | 本体就靠它 |

这样做的意思很清楚：**把最贵的人力，留给下游损伤最大的对象**。对商业网文口径来说，最怕的不是某个普通实体漏了一个别名，而是**规则抽错、状态抽错、钩子和兑现关系抽错、章间交接抽错**。这些一旦错，会直接砸到爽点、规则感和连续追更的体验。citeturn18view2turn18view5

**难章型覆盖**不要按“好不好看”分，而要按“**一旦抽错，下游会不会整体翻车**”分。我建议固定覆盖下面这组难章型，并把它们显式写进金标抽样计划：

| 难章型 | 最低固定样本数 | 为什么必须单列 |
| --- | --- | --- |
| 开书立钩章 | 30 | 决定承诺、主欲望、首轮钩子是否被正确挂账 |
| 规则讲解密集章 | 30 | 最容易把规则、限制、例外抽混 |
| 爽点兑现章 | 30 | 最容易把 promise / payoff 配对做错 |
| 章末强钩章 | 30 | 最容易高估“悬念感”，低估可兑现性 |
| 章间交接章 | 30 | 最考验你们的交接账和状态快照 |
| 时间跳跃 / 回忆章 | 25 | 双时间轴最容易漂 |
| 多线并进 / 群像章 | 30 | narrative_units 与实体关系最容易乱 |
| 高动作战斗章 | 25 | 事件多、状态变化密，漏抽率高 |

**多标注人分歧裁决**这块，别一上来全量双标，太烧人。更省的办法是“三段式”：

| 阶段 | 做法 | 目的 |
| --- | --- | --- |
| 协议试桩 | 30 章全双标 + 主审裁决 | 把 guideline 打磨到能用 |
| 主集生产 | 全量单标；100% 难章双标；常规章抽 20% 双标 | 控成本同时盯住高风险区 |
| 版本变更期 | 任何 schema / rubric 变更后的 50 章回归双标 | 防“规则一改，全线漂” |

裁决时要把分歧分成两类看。**可证伪分歧**，比如事件边界、状态极性、规则是否生效，直接主审裁单值；**主观分歧**，比如某个钩子到底更偏“悬念型”还是“爽点延迟型”，不要硬捏成一个答案，应该保留 `alt_valid_labels` 或 `ambiguity_tag`。研究里对高主观任务的结论很一致：低一致度不一定是脏标，很多时候恰恰是“真实难例”；把这些例子从测试里删干净，会让系统分数虚高、鲁棒性变差。citeturn17search2turn15view0turn16view1

**代价与风险：**这套协议最麻烦的地方在于，`reader_promises / payoffs` 和 `future_obligations` 很容易被标注员带入个人阅读趣味。你们如果不设“Top-K + 证据句 + 重要性等级”的硬框，后面建议层评测会越来越像“谁更会写点评”，而不是“谁更会保住商业网文读者要的推进力”。citeturn13view5turn12view6

**反面核查：**如果试桩后发现 `reader_promises / payoffs` 的双标一致度始终很差，且保留分歧信息也救不回建议层效果，那就别硬把它们算进“提取金标主秤”，而是降为“编排辅助层标签”。**需补材料：**你们现有 20–30 章的 reader promise / payoff 手工样例，以及作者侧到底认不认这类标签。

## LLM Judge 的边界

**结论先行：**LLM judge 在你们这里**能用，但只能用在“可观察、可枚举、能对证”的环节做加速**；凡是涉及**长期读者结果、作者偏好、强主观审美**的地方，都不能让它单独拍板。公开研究里，GPT-4 这类强 judge 在某些开放任务上和人类有不错的一致性，G-Eval 这类 rubric 化做法也能比传统自动指标更贴近人类；但同一批研究也同时指出，它会受**位置顺序、冗长度、模型自偏好、任务难度**影响，而且不同 judge、不同 prompt、不同 benchmark 之间稳定性并不好。尤其关键的一点是：当 judge 自己都答不对题时，它判别别人的答案质量也会明显失真；给到人类写的参考答案后，一致性才会改善。citeturn12view8turn12view0turn12view6turn13view0turn12view9turn13view1turn12view7

**可操作方案：**我建议你们把 judge 分成三档用：

| judge 用途 | 可以让 LLM 单独干 | 不能让 LLM 单独干 |
| --- | --- | --- |
| 提取评审 | 字段完整性、证据锚覆盖、明显矛盾筛查、格式合法性、 pairwise 对比两个提取结果谁更接近 gold | 最终 release gate 分数 |
| 建议评审 | 诊断是否命中已知问题、建议是否可定位、是否给出可执行动作、是否碰禁区 | “作者会不会真采纳”“读者会不会更爽” |
| 影子运行 | 大样本预筛、难例聚类、异常报警、同/异源 judge 对照 | 胜出单一裁定 |

具体落法上，**提取评审优先用 pointwise 二值/多值核查**，比如“这条规则是否有证据锚”“这个 state_fact 时间索引是否正确”；**建议质量比较更适合 pairwise**，也就是把新建议和旧建议并排，让 judge 比哪条更可执行、更贴近给定问题。原因是 pairwise 在弱 judge 也判不太动“绝对正确”时，往往仍能给出更靠谱的相对排序；但也要看到另一面：对小模型来说，pairwise 不一定总赢，很多小 judge 需要更强的推理提示或干脆做 pointwise 才稳。所以这里不要一刀切，**强 judge 用 pairwise 做比较，弱 judge 用 pointwise 做局部可观察标签**。citeturn11view9turn13view2turn10search13

**同源怎么办：**如果 judge 和被评模型同一家、同一族，别简单理解成“完全不能用”，也别天真地当成“反正一样懂业务就更准”。更靠谱的做法是：**同源 judge 只保留在局部二值检查和解释性回看里；最终排名、release gate、改判证据，必须引入异源 judge 或人类校准。**因为已有研究表明，LLM 不只是会“偏爱自己”，它们还可能识别自己的文风；自识别能力和自偏好强度还有线性关系。另一条线的研究也说明，强 judge 会系统性地给更“熟”的文本更高评价。citeturn19view0turn13view1

我建议你们用一个很实操的结构：**“二异源 + 一同源” 三裁判制**。同源 judge 留给你们做业务贴合和解释；两个异源 judge 负责抗家族偏差。最终用多数票或加权投票，但必须把**模型名、提供商名、系统提示来源、输出格式装饰**先做盲化处理，至少要把“这是哪家模型写的”这层信息从 judge 输入里拿掉。再叠一个**顺序对换**：任何 pairwise 评审，A/B 和 B/A 都跑一遍，只有两次都给同向结论，才记为高置信。位置偏差研究已经很明确：顺序变化会改变裁判结论，而且这种偏差不是随机噪声。citeturn12view4turn13view0

**防漂移**这块，不要只盯主模型漂，judge 也会漂。我建议固定四个监控件：**judge 版本钉死、rubric 版本钉死、50 题 canary 集周跑、低置信自动升级**。低置信升级这件事，不要靠“模型自报我不确定”四个字，最好做成**selective evaluation**：judge 先打分，再估一个“人类会不会同意我”的置信度；置信不够就升级到更强 judge 或人工复审。已有工作表明，这种“先判断、再决定要不要相信”的级联方式，比盲信单个最强 judge 更稳，也更省钱。citeturn13view3

**代价与风险：**三裁判、顺序对换、置信升级都会加成本，单条评审费用会明显上去。可这笔钱能直接买到三样东西：**更低的家族偏差、更低的位置偏差、更少的线上误改判**。如果你们把 judge 只当一个廉价打分器，前期看着省，后面会在错误优化上加倍还债。citeturn13view0turn13view1turn13view3

**反面核查：**如果你们做过 100–200 个已有人类裁定的建议 case，对比下来发现三裁判制和单强 judge 的一致性、召回、误报几乎没差，那三裁判权重可以下调，保留在 release 前抽检层，不必全量跑。

## 影子运行判据

**结论先行：**影子运行不能问“新流水线总分是不是更高”，而该问三件事：**有没有踩硬雷、核心价值有没有真涨、涨幅是不是跨题材/跨难章型都站得住**。单一指标一定会误导，尤其在你们这种商业网文口径里，模型很容易靠“更会说”“更会补字”把某些主观分抬上去，但真正决定体验的规则感、钩子兑现、章间交接反而掉了。研究上，静态 benchmark 很容易饱和；agreement 也并不等于 judge 和人类在评同一个构念。你们的影子运行如果不做分层和 veto，最后很容易优化成“会涨分，不会涨体验”。citeturn18view6turn13view5turn7search12

**可操作方案：**推荐你们用“**veto 门槛 + 组合分 + 分层稳健性**”三层判。

先放硬门槛，任何一条不达标就直接不算赢：

| veto 指标 | 建议阈值 | 说明 |
| --- | --- | --- |
| schema 合法率 | ≥ 99.5% | 下游只认一种大纲格式，这条不能松 |
| 严重事实幻觉率 | 不高于旧系统 | 针对 state_facts / rules / handoff |
| 严重连续性错误率 | ≤ 0.5 / 100 章 | 规则、时间、人物状态打架 |
| 证据锚缺失率 | ≤ 2% | 没锚就很难改判 |
| 关键对象漏抽率 | 不高于旧系统 | rules、state_facts、章间交接三类单独看 |

过了 veto，再看组合分。我建议影子运行主分不要直接拿读者结果，按你们口径，读者结果只做校准。主分公式可以直接这么落：

[
ShadowScore = 0.35 内容秤 + 0.30 严格秤 + 0.15 诊断命中 + 0.10 建议可执行 + 0.10 作者认可净值
]

这里的**作者认可净值**建议定义成：

[
作者认可净值 = 即时采纳率 - 0.5 30天内撤销率
]

这样做是在防一种很常见的假提升：建议看上去很会说，作者当下点了“采纳”，过两三天又改回去。你们自己也已经把“稍后撤销率”挂进四层秤了，这个信号一定要进主分。至于**内容秤**和**严格秤**，建议这样算：

[
内容秤 = _k w_k Recall_k
]

[
严格秤 = _k w_k StrictPrecision_k
]

其中 (k) 是对象类，权重我建议先按这版起跑：**rules 0.20，state_facts 0.20，章间交接 0.15，events 0.15，narrative_units 0.10，entities 0.08，reader_promises/payoffs 0.07，future_obligations 0.05**。这不是学术唯一答案，是按“商业网文 + 下游改编”损伤成本排出来的工程初稿。citeturn12view7turn18view6

第三层一定要做**分层稳健性**，不然平均分没有意义。建议设三条：

| 稳健性条件 | 建议阈值 |
| --- | --- |
| 12 类难章型里，非负增益占比 | ≥ 9 / 12 |
| 任一关键难章型回撤 | 不低于 -3 分 |
| 6 个主题材里，非负增益占比 | ≥ 5 / 6 |

再加一个统计检验：对 `ShadowScore`、`内容秤`、`严格秤` 至少做 **bootstrap 95% CI**，只有当核心指标的增益置信区间下界都大于 0，且 veto 全过，才算真正赢。这个逻辑很接近“可信改判证据”而不是“跑分赢了”。citeturn13view5turn4search13

**代价与风险：**这样判输赢会让一部分“平均分微涨”的版本过不了，因为它们常见的问题就是：在简单章、常规章涨了一点，在难章和关键对象上掉得更厉害。短期看会显得你们版本升级变慢，长期看反而是在保护唯一中枢格式不被污染。citeturn18view6turn7search12

**反面核查：**如果后面你们拿真实线上结果对齐，发现某些 veto 项对读者结果并不敏感，比如 `entities` 某类严格率掉一点并不影响任何下游，那些 veto 应该降成观察项，而不是一直堵门。

## 评测集规模与防过拟合

**结论先行：**对你们这类系统，**“一个固定大测试集”不够，得是“固定核心集 + 隐藏挑战集 + 滚动新样本”**。不然很快就会出现两种假进步：一种是模型背会了题型，另一种是团队把系统往公开分上调，却没把真实线上难例吃掉。Dynabench、LatestEval 和后续一系列 benchmark 研究，核心都在提醒同一个问题：静态集会饱和，公开集会污染，动态难例和时间敏感新样本更能测到真实鲁棒性。citeturn11view5turn11view6turn2search18turn7search12

**可操作方案：**样本量我给你一版能直接落的表。这里的数字不是论文统一结论，而是按你们业务复杂度、比例型指标希望落到某个置信区间宽度去配的工程建议值。

| 评测包 | 建议规模 | 用途 |
| --- | --- | --- |
| 提取协议试桩集 | 30 章包 | 只用来改 guideline，不报最终分 |
| 提取固定开发集 | 150 章包 | 模型迭代可见 |
| 提取 judge 校准集 | 90 章包 | 校准 LLM-as-judge 与阈值 |
| 提取隐藏核心测试集 | 240 章包 | release gate 主集 |
| 提取隐藏挑战集 | 120 章包 | 难章、极端章、下游高损伤章 |
| 建议层固定集 | 240 case | 四层秤主评测 |
| 建议层滚动新样本 | 40 case / 月 | 防套路化、盯漂移 |
| 影子运行在线采样 | 200–500 live case / 周 | 实盘监控，不进固定分 |

如果你们要更省，**提取 release gate 最少也别低于 360 章包**；想把主要比例指标的误差压到更稳，**600 章包是舒服线**。建议层因为更贵、主观性更强，**240 case 固定集 + 每月 40 个滚动案例**，通常比一口气攒 1000 个更划算；前者更能防过拟合。citeturn11view6turn18view6turn7search12

防过拟合这块，我建议你们立四条死规矩。**一是按“书”切分，不按“章”切分。**同一本书前后章节共享角色、规则、叙事套路，按章切会虚高。**二是固定集隐藏，不把分层明细全放给调参人。**给总览与异常方向就够，别把 challenge 子集做成刷榜场。**三是每月从影子运行失败样本里回收 20–40 个新难例，进“滚动挑战池”。**这一步本质上就是把 Dynabench 的“人和模型一起产难例”思路搬到你们内部。**四是退休机制。**任何一批 challenge case 连续三个月被轻松打穿，就进退休库，留作回归，不再担当主 gate。citeturn11view5turn18view6turn11view6turn7search12

**代价与风险：**隐藏集、滚动集、退休集都意味着你们要做版本管理和访问控制，工程上会复杂一点。另一个风险是，滚动新样本如果只从“最离谱的失败”里抽，会把集子越做越偏激，普通章反而代表性下降。所以建议滚动池里保持 **70% 问题驱动 + 30% 随机抽样**。这样既能追着痛点打，也不至于把基线分布丢了。citeturn11view5turn11view6

**反面核查：**如果跑三个月后发现滚动 challenge 和固定集排序高度一致，且没有额外暴露出关键难例，那滚动池规模可以下调，重点改成季度刷新，不必月月大动。

## 必答题里我有把握先给的推荐

**结论先行：**第五节里，我对下面这些题有把握给方向；没把握的，我会直接写“需补材料”。总体原则就一句：**凡是进入唯一中枢格式、会被多个下游消费的字段，都要优先考虑“可评测、可回放、可改判”，再考虑省字段。**这和数据集质量管理、judge 校准、人类参考答案提升对齐度的结论是一致的。citeturn18view2turn18view5turn12view7

| 必答题 | 推荐 | 置信度 | 依据 |
| --- | --- | --- | --- |
| 证据锚保留与否 | **保留，且强制随行** | 高 | 没锚就很难做严格秤、裁决、改判；人类参考能明显提升 judge 可靠性 |
| 体验合同格式定稿 | **做成可观察字段，不写抽象感受词** | 高 | judge 与人都更适合评“有没有做到”，不适合评“像不像会爽” |
| 字段版本化机制细则 | **三层版本：core_schema / view_schema / rubric_version** | 高 | schema 变了、视图变了、评测规则变了，要分开追 |
| 偏航判定口径 | **按“故事线里程偏离 + Promise 债务逾期 + 规则违背 + 疲劳超限”联合判** | 中高 | 更贴你们的商业连载口径，不按文学向抽象主题漂移判 |
| 产出方标记字段定义 | **至少区分 extracted / human_authored / model_inferred / derived / adjudicated** | 高 | 不然回头追责任、算误差、做回归都很痛苦 |
| 规则是否单列第八件 | **建议单列** | 中高 | 规则是商业网文的高损伤对象，混在别处评测会失焦 |
| 爽点账 / 钩子账细目 | **建议分账，不要混账** | 中高 | 生命周期不同：爽点看兑现，钩子看牵引与兑付节奏 |
| 建议层工况分型清单与搭配 | **至少四型：未发表可动、已发表可动、已发表不可动、改编约束下可动** | 高 | 这四型会直接改变建议可执行性定义 |
| R12 衔接：新格式金标与秤重建 | **按“提取双秤 + 建议四层秤 + judge 校准 + 影子运行”落地** | 高 | 这正是本报告主方案 |

再补一条我觉得很关键的细节：**体验合同**的字段不要写成大段自然语言，建议固定为可观测槽位，比如：`promise_advanced[]`、`setup_used[]`、`rule_shown[]`、`hook_type`、`must_preserve[]`、`avoid_recent_signature[]`、`desired_pattern`。这样它既能被下游消费，也能被 judge 评审。说白了就是：**合同要像检核表，不要像赏析文。**citeturn12view6turn13view5

下面这几题我暂时不建议拍死：**新逻辑句条目格式设计、Hook 冲突裁决七序落地、暗稿可见性闸、挂靠点/停点清单。**不是说不能做，而是**需补材料：**旧逻辑句样例 50 条、真实 Hook 冲突 case 30 条、作者工作台交互录像 10–20 段、分镜/互动叙事的实际停点需求表。没有这些，格式很容易拍成“看着完整，用起来别扭”。

**代价与风险：**把证据锚、版本层、产出方字段都加进去，会让格式显得更重。可你们的前提不是“让 JSON 好看”，而是“让唯一中枢格式能扛六个下游和长期迭代”。这类重字段在前期看着烦，后期会变成最省命的东西。citeturn18view2turn18view5

**反面核查：**如果后面发现某些字段长期只被单一工具用、从不参与评测与改判，也不影响任何一个下游，那就该从本体降级到适配层，不要为了“以后可能有用”一直塞在核里。

## 质疑清单

**结论先行：**我有几条明确怀疑，而且都属于“做歪了会后面很难补”的那种。不是说这些决策一定错，而是它们现在都还缺**可证伪的验证设计**。其余条目里，像 T3 Hook 账分离、T5 暗稿挂编排侧、T6 作者规划层、T8 具名视图合同、T11 建议层按工况分层、T12 harness 借结构不重造，方向上我暂时没有重大反对，原因是它们都在做同一件对的事：**把核心账、编排账、消费视图、工具工作流分层，减少互相污染。**citeturn11view5turn18view2
