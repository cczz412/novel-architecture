# 商业网文大纲中枢系统的深度研究判断

你们现在最该定下来的，不是某个漂亮的 JSON 长什么样，而是**把“大纲”定义成一种兼顾时间、状态、爽点、承诺兑现、下游投影的叙事操作系统**。对起点／番茄式连载和同源 AI 漫剧来说，读者买单的从来不是“结构化本身”，而是更稳地保爽点、更快地接期待、更少地掉钩子。行业侧也说明了这个方向：到 2024 年底，中国网络文学用户到了 5.75 亿，网文 IP 已经是影视、动漫、微短剧等赛道的重要增量来源；到 2026 年 2 月，短剧行业月活已到 7.18 亿，内容形态已经分成竖屏短剧、横屏短剧和 AI 漫剧三条主流赛道，说明“同源内容、跨端再利用”已经不是概念，而是现实生产方式。微短剧用户对“快节奏、强情绪、末尾悬念”的偏好也非常明确，公开报道里甚至直接总结成“15 秒一个反转，30 秒一个冲突，最后 10 秒留悬念”。这决定了你们的中枢格式必须把“追读驱动力”记成硬账，而不是旁注。citeturn16view0turn9view9turn10view5turn17view0turn9view6

## 长篇叙事中间层形态

✅ **结论**：你们的中间层不该在“厚描”和“薄切片”里二选一，**该用“厚描做真账本，薄切片做派生视图”**。也就是：把“章末快照＋章内变化流＋章间交接”作为唯一真相源，再从它派生出“高光关键帧／分镜 Beat 卡／检索索引卡”。这样提取、续写生成、分镜脚本三条线能共用一份账，而不是各自偷改口径。这个判断和 Event Sourcing 很接近：Fowler 把它定义成“把状态变化记录为事件序列”，同时用快照减少重放成本；Azure 的架构文档也明确说，长事件流会让重建状态越来越贵，所以要定期做 snapshot。对你们来说，**厚描=事件流+阶段状态**，薄切片=面向下游的 projection。citeturn8view4turn8view3

✅ **可操作方案**：建议把每章的 canonical package 固定成四层。第一层是 `chapter_end_snapshot`，记“这一章结束时，重要角色/关系/规则/资源/外部局势分别处在什么状态”；第二层是 `change_flow`，记“本章真正发生了哪些变化、按什么顺序发生、变化是谁触发的、证据在哪”；第三层是 `handoff`，记“这一章把哪些未了问题、已点燃冲突、待兑现承诺交给下一章”；第四层是 `salient_beats`，这是从厚描里派生出来的高光卡，专门给正文生成控制节奏、给分镜挑镜头、给工作台做巡检。这里的 `salient_beats` 不该反客为主，只负责把厚描里最值得视觉化、最值得章末挂钩、最值得续写延续的点抠出来。Yarn Spinner 对 storylet/saliency 的说明很有参考价值：它把内容块和“当前最该出现哪块内容”的选择机制分开处理，你们完全可以借这套思路，让厚描负责“账”，薄切片负责“调用优先级”。citeturn11view0turn9view4

✅ **为什么这套更适合商业网文/AI 漫剧**：薄切片关键帧对“入场/出场明确、场景转换清楚”的章节很省事，但一碰到你们列出来的难章型——纯对话、回忆插叙、弱变化、信息倾泻、转线——就会变成假稳定。因为这些章的核心价值常常不是“谁出现了”，而是“读者期待被推进了多少”“规则被解释清楚没有”“角色关系是升温还是降温”“金手指的边界有无被重写”。文档级信息抽取本来就容易死在共指、跨段依赖、长尾实体和标签噪音上；到了长篇网文这种长上下文、长尾人名/法宝/规则术语密集的文本里，单靠薄切片更容易把真正重要的“变化”漏掉。已有综述和长文抽取研究都指出，长文 IE 的难点正是跨段依赖、核心指代和长尾对象召回；专门做长文本长列表抽取的 L3X 甚至把“先冲召回、再做精筛”当成必要设计。citeturn8view1turn19view0turn18view0

⚠️ **代价与风险**：厚描的麻烦不在“能不能提出来”，而在“后面会不会越攒越厚，查一条状态要回放半本书”。这风险是真有的。Event Sourcing 的标准处理方式就是：别让所有消费方直接读全事件流，而是 **按实体、按卷、按章节区段做快照和索引**。你们这里建议多加三张派生索引：`entity_timeline_index`、`promise_payoff_index`、`rule_revision_index`。前者解决“第 873 章某角色那时有没有受伤”；中间这张解决“某个钩子什么时候种下、什么时候推进、什么时候兑了”；后面这张解决“规则是不是被偷改了”。如果不做这三张索引，厚描会在两种规模下开始明显崩：一是单实体跨章变化过密，二是长线 hook 过多但没有冷热分层。更具体的阈值我只能给工程经验值，不能当通用真理：**当一次查询需要重放超过 20–30 个章节快照或 200+ 条该实体变更项时，就该强制做中间快照和实体时间线压缩**。需补材料：你们平均“每章活跃实体数、每卷长线 hook 数、检索 SLA”。citeturn8view3turn8view4

✅ **反面核查**：厚描形态在“跨千章检索某一时刻某实体状态”会不会崩？会，但不是因为厚描本身错，而是因为**把 canonical 和 query view 混用**。预防办法很明确：真账本保厚描；检索只读快照与索引；给每个实体建立“最近快照指针＋自上次快照后的变化链”；分镜和生成永远读 `salient_beats` 等投影视图，不要直接扫全量变化流。说白了就是：**厚描负责存真相，薄切片负责快查快用**。citeturn8view3turn8view4turn11view0

## 中枢 schema 设计

✅ **结论**：三层切法应该是 **固定核心管“跨体裁、跨下游都离不开的叙事真账”**，**题材可选池管“玄幻/都市/电竞各自的世界规则和资源类型”**，**适配层管“正文、分镜、互动、作者工作台各自的取数视图”**。不要把面向某一端的字段硬塞进核心，也不要把所有自由度都扔给可选池。大纲一旦被定义成唯一中枢，schema 就不是“给模型填空的表单”，而是“给所有下游守兼容的协议”。JSON Schema 官方近年的方向已经把升级兼容性放到非常高的位置；Confluent、Protobuf、Google Cloud 的版本演进文档也都在强调一件事：**安全的演化方式是加可选字段、做弃用标记、保持旧消费者还能读，新旧版本并存过渡**。citeturn9view0turn9view1turn8view5turn14view0turn14view1

✅ **可操作方案**：固定核心建议只保六类对象。`chapter_package` 记章节级账；`entity` 记角色/组织/地点/法宝/系统等叙事对象；`world_rule` 记规则及修订；`promise_payoff` 记期待到兑现链；`hook` 记未来事件；`evidence` 记来源片段和置信度。你们最容易犯的错，是把核心定成“人物入场/出场/所在场景/说了什么”这种低层视角，因为它看起来最稳，实际却最容易在商业网文里失真。真正该进核心的，是**状态、变化、规则、承诺、兑现、证据、时间、因果**。这也是为什么 schema 写完后，一定要同时服务提取、生成、分镜、互动——不是靠大家都读同一堆字段，而是靠核心稳定、适配层各拿各的 projection。Schema-Driven IE 和 Amazon PARSE 的研究都说明，schema 一旦写得模糊、静态、面向人类而不面向模型，抽取就会更容易幻觉、漏项和不稳定。citeturn8view2turn10view0

✅ **字段演化与版本化**：每个对象都建议带上 `schema_version`、`producer_version`、`projection_version`。升级规则用最简单也最不容易翻车的方式：**加字段=minor，改语义/改必填/改层级=major**。旧字段不要直接删，用 JSON Schema 的 `deprecated` 挂弃用标记；破坏兼容的 major 版本，要允许 v1/v2 同时存在一个过渡窗口，直到所有下游合同都更新。Google Cloud 的 OpenAPI 文档就是这么建议的：向后兼容改动升 minor，不兼容改动升 major，并允许多 major 并存；PactFlow 的 consumer-driven contract testing 也强调，要拿“消费者真正依赖的合同”去跑自动验证，别只看提供方觉得自己没改坏。对你们来说，这意味着每个下游都要有自己的“消费合同测试”。citeturn14view0turn14view1turn14view2turn8view5

{

⚠️ **代价与风险**：固定核心一旦定错，真会全线返工。一个典型死法就是：**把“场景 scene”定成核心原子单位，而不是“章节中的状态变化包”**。这看上去很像影视脚本，分镜端会很开心，但正文导入提取会在纯对话、回忆插叙、弱变化章里大量失真；正文生成为了迎合 scene，会硬拆自然的章节节奏；互动端做条件分支时又会发现缺真正的状态/规则/承诺链，只能往 scene 里补脏字段，最后整个协议烂掉。预防手段只有一个：**核心字段只能收“跨端不可替代”的信息，不能收“某一端好用但别端未必需要”的信息**。上线前要跑你们那 8 类难章型、再加 3 种下游 projection 回放，任何一个字段如果只有 1 个下游真依赖，就不该进核心。citeturn11view5turn10view0turn8view1

✅ **反面核查**：固定核心定错的典型案例，我认为不是“字段少了一个”，而是**把真正的叙事不变量定错成展示层变量**。预防办法别靠拍脑袋评审，直接上三道闸：一是“8 类难章型回放”；二是“4 个下游消费合同测试”；三是“旧版本样本自动迁移测试”。只要有一个下游必须靠读自由文本补语义，核心就还没定稳。citeturn14view2turn9view1turn8view5

## 多遍提取流水线工程学

✅ **结论**：就你给的现状看，**提取必须改成多遍，而且要“强流程、弱自治”**。主力模型不够聪明时，最怕把“理解、记账、校验、补漏、对齐格式”全塞进一轮；这会把最难的几种误差——漏召回、共指错、规则错、时间错、字段错——混成一锅。长文 IE 的公开研究也几乎都在往模块化、迭代式流程走：SciEx 直接把 PDF 解析、检索、抽取、聚合拆开，并在中间放了 retrieval–extraction–verification；L3X 在长文本长列表抽取上用“召回优先→精筛优先”的两阶段；PARSE 提到 schema 模糊时会导致幻觉和不可靠行为，所以要用 reflection 和 guardrails 去约束。citeturn18view0turn19view0turn10view0

✅ **可操作方案**：我建议你们用 **七遍主线＋两条旁路**。

主线七遍可以这样切：

- `Pass A`：章型识别与粗切块。先判断这是开篇、转线、高潮、回忆、纯对话还是信息倾泻章，决定后面用哪套抽取策略。
- `Pass B`：高召回捞候选。只捞人、物、规则、冲突、承诺、爽点、悬念、时间锚点，不要求整理干净。
- `Pass C`：实体归一与共指消歧。把“他/老爷子/会长/系统提示里的称呼”合并。
- `Pass D`：状态快照重建。只回答“章前是什么、章后变成什么”。
- `Pass E`：变化流重建。把真正造成变化的动作、揭露、冲突推进串起来。
- `Pass F`：爽点/Hook/兑现链记账。把商业网文真正值钱的东西落账。
- `Pass G`：合同校验与缺口追问。程序检查必填、有无引用证据、时间顺序、规则矛盾、是否欠产出。

旁路一条做 `evidence_span` 回填，任何关键字段都尽量绑定原文证据；另一条做 `cross_chapter_reconcile`，拿上一章快照和这一章输入做对齐。这样你们的“章末快照＋变化流＋交接”会天然长出来，而不是靠单轮模型临时想起来。这个设计也更贴合你们现在观察到的自由生长结果。citeturn18view0turn19view0turn10view1

✅ **程序钩子该放哪**：最有价值的钩子不是“再问模型一遍”，而是**在模型之间插程序化守门**。建议至少放六个：`coverage_alarm` 看是否明显欠产出；`alias_merge` 做别名合并；`temporal_checker` 查时间矛盾；`rule_consistency_checker` 查金手指与世界规则互撞；`promise_payoff_gap_checker` 查上章 promise 本章是否推进；`patch_router` 决定该重跑哪个 pass。弱模型适合干“局部、窄任务、格式强约束”的活，不适合自己决定整个流程。OpenAI 的函数调用文档强调工具描述要清晰；Anthropic 也明确建议，把经常连着发生的操作合并进一个工具底层做掉。换成你们场景，意思就是：**模型可以在某个 pass 里提出‘我想补查 xxx’，但不能自己改总拓扑**。citeturn9view2turn9view3

⚠️ **主动与被动怎么拿捏**：我的判断是 **七成被动、三成主动**。被动，是主流程、输入输出格式、重试条件、校验规则都由 harness 写死；主动，只给模型三种自治权：提出局部补召回、提出低置信冲突、提出“需更多上下文”的位置。别让弱模型自主决定“下一遍我该干嘛”，因为它很容易把没做好的前一步当既定事实，越想越偏。文档级 IE 里，本来就有共指、 reasoning、标签噪音这些系统性坑；一旦早期 pass 出错又被后续 pass 当真，误差会连锁放大。citeturn8view1turn10view1turn18view0

⚠️ **多遍什么时候反而更差**：有三种情况会翻车。**一是章节本来很简单，却被拆成太多遍，信息在传递中被压扁；二是早期 pass 产物太硬，后续只会补充不会推翻，导致“错误冻结”；三是成本压力逼得每遍上下文更短，结果全局依赖反而比单轮更差。** 长文本抽取研究已经反复提到，长上下文、跨段依赖和 schema 变化都会让系统稳定性下降；L3X 也说明，长文本里就算是长上下文模型，复杂关系任务依然会明显掉性能。所以多遍不是越多越好，**标准应该是每一遍都只解决一种主要误差，并且允许后面推翻前面**。citeturn18view0turn19view0turn8view1

✅ **反面核查**：什么时候多遍比单轮更差？当你们把多遍做成“流水账接力”而不是“可回滚的审计管线”时。预防方式很硬：每遍输出都带 `confidence`、`evidence_span`、`can_override_previous=true/false`；任何关键主张如果没有证据、没有可回滚标记，就不能升格为 canonical。citeturn18view0turn10view0turn10view1

## 作者建议层

✅ **结论**：作者建议层不能只做“这章哪里不好”，而要做成 **“问题—证据—对追读的影响—最小改法”**。商业网文作者最烦的是模型自嗨：一会儿说升华主题，一会儿说再丰满心理，一会儿说补环境描写，看着都对，实际不解决“这一章读者为什么不想追下一章”。你们的建议层得紧贴平台已经在看的东西：番茄官方写明会给作者看章节读完率、流量变化、互动数据；阅文作家助手也把大纲设定、全文检索、读者互动和可视化统计放在核心功能区。也就是说，作者工作的现实语境，本来就是“剧情账本 + 平台反馈”双输入。citeturn9view8turn9view7turn11view3

✅ **可操作方案**：建议层的输出模板，建议固定成五格，不要散谈。

`诊断对象`：哪一段、哪个 beat、哪个 promise。

`证据`：引用大纲账本或原文片段。

`对追读的影响`：是爽点太晚、章尾无钩、规则没说清，还是情绪起不来。

`最小修改动作`：删、移、并、提早兑现、换章尾、补规则锚点。

`替代方案`：给 2 个不同强度的改法。

比如不是说“本章节奏偏慢”，而是说：**“这章用了大量解释交代，但上一章种下的‘系统首次公开惩罚’直到章末还没形成体感，所以读者只收到信息，没收到压迫或期待。建议把惩罚样例提前到中段，用一个可视化后果代替半页口头解释，章尾再挂‘主角要不要硬闯’。”** 这种建议才真能改稿。Rubric 研究也支持这个思路：LLM-RUBRIC 用多维度人工 rubric 做校准；相关反馈研究则反复指出，高质量 AI 反馈依赖清楚的 prompt 和 rubric，而且“泛泛而谈、缺例子”的反馈很难真正帮人改稿。citeturn10view2turn10view3turn10view4

✅ **建议质量怎么立秤**：别拿“像不像编辑”评分，要拿“改完有没有用”评分。建议至少立四个秤：`可执行率`，作者能不能立刻按它改；`证据充分率`，有没有明确指向账本或原文；`采纳后指标提升`，改稿后读完率/次章点击/评论情绪有没有改善；`误伤率`，有没有明显把作者原本强项改没了。因为研究里已经很清楚，AI 反馈可以高效、覆盖广，但经常“泛”“空”“没例子”，这类建议看上去多，实际转化差。你们可以把作者采纳后的改稿，再用 rubric 和平台数据回灌成训练信号。citeturn10view3turn10view4turn10view2

⚠️ **代价与风险**：最伤作者的建议有四类。**一类是把所有书都往同一种热点模板里捏；一类是只盯短期点击，不顾长线规则和人物信用；一类是直接替作者重写，声音越改越像模型；一类是用文学向意见压商业连载——比如逼他“留白”“克制”“慢炖”，结果把爽文的核心体感洗没了。** 这类建议不是没道理，而是口径错了。识别办法也不复杂：凡是建议里没有“影响哪条 promise/payoff 链”、没有“读者体感会怎么变”、没有“最小修改动作”，一律降级。凡是建议要求改超过本章 30% 内容，却没有明确收益预估，也要拦。citeturn10view4turn10view3turn9view8

✅ **反面核查**：什么建议会伤害创作而不是帮助？我给一个硬标准：**只提高“表面刺激”，却降低“世界规则可信度、人物行为可信度、长线兑现概率”的建议，都属于伤害型建议。** 拦截策略是给建议层加“反效果审查”：它每提一个改法，就必须同时回答“会不会伤到已有长线、会不会让角色降智、会不会增大后续账本负担”。答不出来，就不能给作者。citeturn10view2turn10view3

## Hook 式未来事件

✅ **结论**：Hook 不能再当“备注”存，必须当 **可触发、可巡检、可降级的计划对象** 存。也就是把“30 天后”“节日到来”“进入副本”“得到宝物后触发”“某人达到某境界后追债上门”都记成统一的 hook 实体，绑定触发条件、有效窗口、预期兑现、优先级和替代方案。这个做法和互动叙事系统里的变量/条件触发很一致。Yarn Spinner 把变量分成数字、字符串、布尔值，还专门提供 smart variables，把复杂条件集中定义后到处复用；它甚至直接给了 time-based event 的例子。对你们来说，这很适合做“有机会就检查”的巡检底座。citeturn9view5turn12view0

✅ **可操作方案**：每个 hook 建议至少有这些字段：`hook_id`、`origin_chapter`、`hook_type`、`condition_expr`、`earliest_due`、`latest_due`、`salience`、`payoff_expected`、`fallback_plan`、`current_state`、`related_entities`、`evidence_span`。`condition_expr` 不要写自然语言，写成半结构化表达，比如：

`story_day >= 30`

`festival == "宗门大比"`

`entered_instance("黑渊副本") == true`

`has_item("天机残页") && item_resonance_count >= 3`

然后每章收尾时跑一个 `hook_inspector`：先看哪些 hook 被本章激活了，哪些进入了“有机会兑现”的窗口，哪些正在变热，哪些已经过期。Yarn 的 smart variables 强调“把复杂条件集中定义，逻辑改一处，全局生效”，这点正适合你们把各种触发逻辑统一挂到 hook 表达式层。citeturn12view0turn9view5

✅ **和逐章账本联动**：Hook 最怕散在角落里没人管，所以它必须和 `chapter_package` 双向联动。每章账本里要有 `hook_updates`，专门记本章对哪些 hook 做了点燃、推进、延期、兑现、废弃；每个 hook 自己再反向挂 `last_seen_chapter`、`next_check_reason`。这样作者工作台就能很直观地看到：哪些钩子在发热，哪些拖太久会掉信用，哪些明明有机会却连续多章没碰。Emily Short 讲 QBN/storylet 的时候提到两个很要命的规模问题：内容少时没意思，内容多时可选项会压死人；而且作者得自己大量记手工进度账。你们如果不把 Hook 做成第一类对象，也会很快掉进这个坑。citeturn12view1turn11view0

⚠️ **代价与风险**：Hook 账一旦开得太猛，会出现两个坏结果。一个是**兑现窗口互撞**，读者只会觉得乱；另一个是**兑现债务滚大**，作者后面每章都在还账，爽点反而被挤没。这个时候不能只做“冲突提示”，要有裁决规则。建议按四个维度排队：`兑现收益`、`过期风险`、`前文铺垫强度`、`对主线推进的必要性`。排低的 Hook 不一定删，可以降级成旁敲侧击：先回声式提醒、先给线索、先给传闻、先做小兑现，别都抢主舞台。citeturn12view1turn9view6

✅ **反面核查**：Hook 堆积过多且互相冲突时，怎么裁决与降级？我建议一条硬规则：**同一章最多允许一个主兑现、一个副推进、一个新挂钩。** 其他 Hook 只做轻触达或延后说明。再加一条软规则：任何 Hook 若连续 3 个“有机会章”未被触达，必须在工作台里亮黄灯；连续 5 个亮红灯。需补材料：你们现有小说样本里，长线伏笔平均兑现跨度是多少章。citeturn12view0turn12view1

## 创作 Agent 的工具化拆分

✅ **结论**：Tool 不该按“技术动作”切，而该按 **作者心智里的业务能力** 切。也就是作者眼里看到的是“导入提取”“查漏补账”“生成下一章”“出分镜”“巡检 Hook”“查一致性”“给修改建议”，而不是十几个彼此抢活的细碎函数。Fowler 讲微服务时反复强调，边界应该围绕 business capability；同时也提醒，服务拆开会带来分布式复杂度。对 agent tool 也是一样：切太碎会相互推皮球，切太粗会变成黑盒大泥球。OpenAI 的函数调用文档明确要求工具名、参数说明、说明文字都要清楚；Anthropic 还明确说，频繁连用的多步操作可以在工具内部合并。这个组合起来，就是你们最适合的切法：**外部粗颗粒、内部细流程。** citeturn11view4turn11view5turn9view2turn9view3

✅ **可操作方案**：我会建议把外露工具收敛到八个能力面。`导入/提取`、`大纲巡检`、`补账修账`、`正文生成`、`分镜投影`、`Hook 管理`、`一致性校验`、`作者建议`。它们统一只吃 `outline_ref + scope + intent`，统一返回 `patch / projection / diagnosis` 三种东西之一。比如“分镜投影”别再让它自己理解全文，它只读大纲里的 `salient_beats + visual_cues + character_state + rule_effects`；“作者建议”也别直接碰正文生成，它只产诊断和 patch 建议。这样下游都只认大纲，不相互偷读。citeturn11view4turn9view2turn9view3

✅ **自描述怎么写才不被误用**：每个 Tool 的说明都要写清四件事：`它解决什么问题`、`它不会做什么`、`它要求的最小输入`、`它保证输出什么`。比如：

**Hook 巡检**：解决“未来事件是否漏检、撞车、过期”；不负责生成正文；最小输入是 `outline_ref + active_hook_set + chapter_scope`；输出一定是 `hook_status_patch`。

**分镜投影**：解决“把章节大纲变成镜头级 Beat 顺序”；不负责改剧情；最小输入是 `outline_ref + target_medium`；输出一定是 `storyboard_projection_vX`。

工具说明越像合同，越不容易被大模型乱用。citeturn9view2turn14view2

✅ **网页端画布怎么摆给作者**：别把 Tool 名字平铺给作者选，作者不会按技术边界思考。更好的方式是按创作阶段摆：**导入已有正文 → 看提取结果 → 看风险/爽点诊断 → 选择补账或修账 → 选择生成正文或出分镜 → 跑一致性和 Hook 巡检 → 发布或回退。** 也就是画布外显的是流程选择，底下真正调哪个 Tool 由系统判断。这样既降低误用，也更符合连载作者“我现在想干嘛”的节奏。番茄和阅文作家工具都把写作、统计、消息、设定这些能力做成围绕任务的工作台，而不是暴露底层接口；你们完全可以借这种产品心智。citeturn9view8turn9view7turn11view3

⚠️ **代价与风险**：工具切太碎，死法是**模型不停跳转、参数来回搬、上下文丢失、同名相近工具互相抢**；切太粗，死法是**一次调用要干五件事，结果任何一件错了都没法精修，也没法做 patch 级回滚**。检验粒度对不对，我建议看三个指标：真实任务平均要跳几次工具、是不是经常同一任务必须人工改调用顺序、失败后能不能只重跑局部。经验上，**一个作者真实任务如果平均要跨 3 个以上外露工具，说明太碎；一个工具如果内部常年分支到 5 种以上互不相干的结果，说明太粗。** 这个阈值是工程经验，不是行业定理。需补材料：你们网页端当前计划暴露给作者的节点数。citeturn11view5turn11view4turn9view3

✅ **反面核查**：工具切太碎和切太粗各自的死法，上面已经说透了。真正的检验法就一句：**作者提出一个明确意图后，系统能不能在不让他理解内部结构的前提下，稳定走到正确的 projection / patch / diagnosis。** 做不到，就说明边界还没切准。citeturn11view4turn9view2

## 爽点与追读的结构化

✅ **结论**：这块必须进核心，而且得是 **“承诺—推进—兑现—余波”链条式记账**，不能只做一个“本章爽点数”指标。对你们这种系统，真正该进固定核心的不是“玄幻有打脸、都市有逆袭、电竞有翻盘”这些题材外壳，而是**任何商业连载都会用到的读者驱动因子**：`hook`、`promise_payoff`、`emotion_curve`、`rule_basis`、`pacing`、`highlight_salience`。AI 漫剧和网文的差异，不在要不要这些账，而在调用口径不同：微短剧/AI 漫剧更看重单位时间内的冲突、反转、视觉高光和结尾悬念；网文则允许铺垫更长一点，但章章仍得有推进和挂钩。新华网对微短剧用户偏好的总结已经非常直白；QuestMobile 也显示 AI 漫剧 2026 年已经从概念赛道走到爆发赛道。citeturn9view6turn17view0turn11view2

✅ **可操作方案**：你们至少要建四本账。

**爽点账**：不是只记“爽没爽”，而是记 `爽点类型`、`触发前提`、`规则依据`、`受益角色`、`代价/风险`、`执行方式`、`强度`、`新鲜度`、`余波`。

**钩子账**：记 `章尾悬念`、`未完成动作`、`新问题`、`高风险承诺`。

**期待→兑现账**：把“读者被种下的期待”当显式对象，状态至少有 `seeded / advanced / delayed / twisted / paid_off / abandoned`。

**情绪曲线账**：不是文学向的细腻情感史，而是商业阅读体感：压迫、期待、释放、反打、回甜、回压。

这样提取端才能诊断“本章有推进但没释放”“规则有解释但没体感”“打脸来了但没前置期待所以不爽”；生成端也才能控制“每章至少一种主爽点 + 一次期待推进 + 一个章尾挂钩”；分镜/漫剧端则直接读 `highlight_salience` 选高光镜头。citeturn9view6turn17view0turn9view8

✅ **网文口径和 AI 漫剧口径差多少**：我的判断是 **底层账本同一套，节奏标尺分两档**。网文版偏“章级体感”：每章有没有推进、有没有爽点、有没有钩子，允许在 1500–3000 字内做一个相对完整的小起伏。AI 漫剧版偏“Beat 级体感”：同一段内容里，镜头高光、视觉反差、反转频率、句尾包袱、集尾悬念都要更密。新华网引用业内观点时说得很清楚，微短剧要在更短时长里把梗、冲突、悬念排得更密；QuestMobile 也把 AI 漫剧单独列成主流赛道，显示它已经不是单纯“看图版小说”，而是独立节奏物种。**所以：promise/payoff/hook/rule_basis 放固定核心；视觉爽点类别、镜头反转密度、单集结尾 cliff 权重放适配层。** citeturn9view6turn17view0turn10view5

✅ **怎么让提取、生成、分镜三端都能直接用**：提取端要输出 `chapter_fun_scorecard`，但这里的“分数”只做诊断，不做目标；它至少回答五个问题：

这章有没有明确推进上章期待？

这章有没有读者能立刻感到的释放点？

这章的爽点有没有规则作为支撑？

这章章尾有没有新悬念或旧悬念升级？

这章有没有信息过载挤压体感？

生成端则把它改成约束：例如“卷中期每章至少 1 个主爽点、1 个推进、1 个章尾钩；卷末可允许多次连续推进、集中大兑现”。分镜/漫剧端再把 `highlight_salience` 高的 beat 自动投成镜头候选，优先选“可视化后果强、关系反差强、身份揭露强、规则打击面直观”的内容。公开资料里，微短剧用户偏好本来就是“情绪价值强、冲突密、末尾想接着看”，所以你们的结构化目标不该是抽象“叙事完整”，而是可直接服务这些体验。citeturn9view6turn11view2turn9view8

⚠️ **代价与风险**：爽点一旦量化，模型就会刷指标——这事几乎一定发生。常见刷法有三种：**为爽而爽，根本不铺；反转过密，读者麻木；情绪总在高位，失去起落。** 另外还有一种更阴的：看起来“每章都有亮点”，其实都是同一个模板循环。公开的 AI 反馈研究已经提醒过，系统很容易产出高覆盖但泛化、套路化的反馈；同样道理，爽点指标如果太单薄，也会把生成推向机械重复。citeturn10view4turn10view3

✅ **防刷指标的办法**：别把目标设成“爽点数量”，要设成 **“兑现质量和分布质量”**。建议加五个反作弊检查：

`freshness_check`：近 20 章同类爽点模板重复率。

`rule_grounding_check`：爽点是否有规则和前置因果支撑。

`cost_ratio_check`：爽点是否伴随代价、风险或后续余波。

`promise_conversion_check`：种下的期待有没有真兑现，而不是换个更大的空头。

`saturation_check`：过去 5 章情绪是否持续高烧没有回落。

真正好看的商业连载，不是每章都最大化刺激，而是**让读者形成“这书准会给我想看的，而且给法越来越会”** 的信任。这个东西只能靠链条账来守，靠单指标守不住。citeturn9view6turn16view0turn17view0

✅ **反面核查**：爽点量化后模型刷指标，怎么识别和防止？识别看三件事：**是否缺前置铺垫、是否重复用同一模板、是否把情绪一直顶满。** 防止也看三件事：**用 promise→payoff 链替代“爽点数”；把规则依据做成硬约束；把新鲜度和情绪恢复窗口一起计入诊断。** 这样它刷“数量”没用，必须刷“兑现质量”。citeturn9view6turn10view4turn10view2
