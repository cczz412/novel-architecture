# V01｜结构承载复检

## 总判定

✅ **“大纲作为唯一中枢”可以继续，但设计稿 v0 不宜原样冻结。**

方向没有做反。真正要改的是“唯一真账”的定义：

> **唯一的应该是语义权威、统一 ID 和提交入口，不是让变化流、快照、章间交接、Hook、暗稿、规划都拥有同等真相权。**
> 

我建议把总纲改成：

> **所有下游只消费版本化的具名大纲视图；所有有效改动，都通过同一个分支化语义内核提交。**
> 

推荐的权力关系是：

```
已发表正文／导入材料
        ↓ 提取、证据、人工确认
【已发生事实层】←—— ChangeSet 变更提交 ——→ 作者修改／下游回流
        ↓
【状态快照】         只读、可重建
        ↓
【章间交接】         下一章续写上下文，不是历史事实

【未来计划层】
Hook 义务／暗稿／里程碑／结局规划
        ↓
【体验合同＋具名视图】
        ↓
正文／分镜／画面／互动叙事／作者工作台
```

这里不要求真的采用“事件溯源”数据库，但可以借它的权威划分：变化记录是权威来源，快照是为了查询方便生成的只读结果，纠错通过新增更正记录完成，而不是偷偷覆盖旧记录。微软的事件溯源架构也采用“事件记录为权威、物化视图为派生结果”的划分。([Microsoft Learn](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing))

长篇也不能只靠“大上下文窗口”硬撑。研究显示，模型会漏掉长上下文中部的信息；任务复杂度和上下文长度上升时，表现明显下降。2026 年的长故事一致性评测还发现，事实和时间错误最常见，并容易出现在故事中段。也就是说，你们的索引、快照、证据链方向是对的，但还缺“谁有最终解释权”和“改一处会影响哪里”。([arXiv](https://arxiv.org/abs/2307.03172))

**需补材料：v1.5／v1.6 中关于写入权、已发表正文权威、冲突优先级、分支与版本的现有条款。**下文按 v0 能看到的口径判断。

---

## 六个下游的承载结论

| 下游 | v0 当前承载力 | 主要判断 |
| --- | --- | --- |
| 正文导入→提取大纲 | 🟡 条件可承载 | 对象覆盖不错，但缺身份归一、更正链、角色／读者知情状态、导入后冲突裁决 |
| 大纲→正文 | 🟡偏绿 | 厚描、交接、规则、体验合同都有效；补上知情差、检索包和人工改稿回流后可长期使用 |
| 大纲→分镜脚本 | 🟡 | 缺“卷／章／场／节拍”的层级与可视化转换语义；章节不能直接等同于场次 |
| 分镜→剧情画面 | 🔴 当前不能长期承载 | 缺人物外观状态、服装、地点、道具、视觉资产引用和连续性视图 |
| AI 互动叙事 | 🔴 当前不能长期承载 | 线性真账没有分支、状态转移、选择前置条件、分支义务和汇合政策 |
| 作者工作台 | 🟡偏绿 | 诊断与挂靠点方向对，但缺“建议—预览—提交—冲突处理”的统一改动协议 |

🔥 **最危险的两个缺口：**

1. **互动叙事和改编分支没有独立 canon。**短剧合并人物、调整事件顺序、删支线甚至换结局时，已经不是“只读视图”，而是一条改编分支。
2. **人工改稿后没有回写协议。**正文生成出来后，只要作者手改过，大纲就可能不再是真账；已发表正文更是读者已经看到的事实，不能继续让旧大纲压着它。

# 一、厚描三件套

## 结论

✅ **厚描优于薄切片，这个方向保留。**

⚠️ **“章末快照＋章内变化流＋章间交接均为唯一真账”的表述必须改。**三者承担的职责不同，不能同权：

- 章内变化流回答“发生过什么、什么被更正了”。
- 章末快照回答“此刻状态是什么”。
- 章间交接回答“下一章别忘什么、可以往哪走”。

交接里可能含作者意图、节奏偏好和未来建议，它天然不是历史事实。

## 可操作方案

把三件套明确成三级：

| 结构 | 定位 | 能否单独改写事实 |
| --- | --- | --- |
| **事实变化记录** | 权威层；记录已确认事件、事实、规则变化与更正 | ✅ 只能走正式提交 |
| **章末状态快照** | 查询缓存；从事实记录重建 | ❌ |
| **章间续写交接** | 事实＋当前义务＋计划边界拼出的续写上下文 | ❌ |

再加三条写入纪律：

1. **已发表正文具有公开事实纠错权。**正文与大纲冲突时，不是正文自动覆盖，也不是大纲继续装作没发生；系统生成差异单，让作者确认后更新大纲。
2. **更正不覆盖旧事实。**使用 `supersedes／corrects` 关系，保留“之前为什么会判断错”。
3. **每条数据声明所属分支与确认版本。**至少要有 `branch_scope` 和 `canon_revision`。

现有 `story_time＋narration_order` 保留。再补两种时间含义即可：

- 故事里什么时候为真。
- 系统在哪个版本确认它为真。

不必现在就上很重的双时间数据库。

快照频率也别写死成“每 10～20 章”。推荐由以下条件触发：

- 回放时间超过设定上限；
- 累积有效变化过多；
- 一个大情节结束；
- 即将分支、改编或发布；
- 人工要求保存检查点。

“回放 100～200 条”同样应是运行参数，不是格式规则。

## 代价与风险

结构上会多出“更正记录、权威等级、提交版本”，早期看起来比直接覆盖麻烦。

但不这么做，100 章以后最常出现的不是存储不足，而是：

- 快照说人物活着，变化记录说人物已死；
- 交接还在要求兑现已经删掉的伏笔；
- 作者改了正文，大纲却不知道；
- 改编分镜反过来污染小说正史。

## 反面核查

用四组测试证伪我的质疑：

1. 删除全部快照，仅靠变化记录能否重建任意章节状态。
2. 故意制造快照、交接、事实三方冲突，系统能否稳定判断谁赢。
3. 对第 30 章做一次身份反转，对第 80 章做一次规则更正，六个下游是否得到一致结果。
4. 作者手改并发表一章后，大纲能否在一次可审查提交中追平公开正文。

若现有 v1.6 已完整规定这些优先级，我对 T1 的质疑可下调。

# 二、九类对象

## 结论

✅ **内容覆盖面够大，问题不在“少一个对象”，而在九类对象被放成了同一层。**

现在至少有四种完全不同性质的东西：

| 性质 | 对象 |
| --- | --- |
| 已发生故事语义 | narrative_units、entities、events、state_facts、rules |
| 读者体验推断 | reader_promises、payoffs |
| 未来计划与债务 | future_obligations、章间交接、规划、暗稿 |
| 治理信息 | provenance、版本、field_status、产出方 |

`provenance` 不是故事对象，它是每条记录都要带的治理外壳；章间交接也不应被当作一种 narrative unit。

## 可操作方案

九类可以继续作为九种**逻辑视图**，但底层分成三种权威层：

### A. 已发生层

- narrative_units
- entities
- events
- state_facts
- rules

### B. 未发生层

- future obligations
- milestones
- dark drafts
- ending／命运／大爆点规划

### C. 推断与派生层

- reader promises／payoffs 的推断
- chapter snapshot
- chapter handoff
- consumer views

所有层统一套一层治理字段：

- 分支与版本
- 来源和证据
- 产出方
- 置信度
- 权威状态
- 更正关系
- 字段状态

还要补五个横向能力，但不一定都新建顶级对象：

**1. 身份归一**

同一人物的本名、假名、易容、附身、分身、前世、身体交换，必须指向稳定实体 ID。

**2. 知情状态**

同一事实至少要区分：

- 世界实际情况；
- 哪个角色知道／相信什么；
- 读者已经知道什么；
- 信息是否可靠。

没有这个，悬疑、身份隐藏、反派设局、误会流会频繁穿帮。

**3. 叙事单元层级**

至少能表达：

```
全书 → 卷／大篇章 → 故事线阶段 → 章 → 场景 → 剧情节拍
```

不是每本书都必须填满所有层，但 ID 和父子关系要稳定。镜头仍放在分镜视图，不进核心。

**4. 依赖关系**

关键记录至少支持：

- caused_by
- requires
- reveals
- contradicts
- fulfills
- preserves
- adapts_from

不用给每句话建完整因果图，只给规则、身份、承诺、关键事件和改编关系建高价值边。

**5. 分支作用域**

每条事实、计划、义务都要知道自己属于：

- 小说主线；
- 短剧／漫剧改编线；
- 互动会话分支；
- 沙盒试写；
- 全分支共有规则。

EACL 2026 的叙事检索研究发现，把实体和事件全部压进单一实体节点会抹掉角色与情境随时间变化的信息；分开维护实体和事件关系，对时间、因果和人物一致性查询更有效。这与 T2 把 entities、events 分开是同向的，但也说明两者之间的映射和时间关系不能省。([ACL Anthology](https://aclanthology.org/2026.eacl-long.90/))

## 代价与风险

关系和作用域越多，模型误连边的概率越高。

控制办法不是删掉关系，而是：

- 模型提议；
- 高置信关系自动收；
- 关键关系进人工核查；
- 低置信关系保留为候选，不进入权威层。

“固定核心入场门槛＝两题材＋两下游”对故事内容字段可继续用，但**不应套在治理轴上**。分支、版本、来源、权威状态即使暂时只服务一个战略下游，也不能因为没凑够“二乘二”而被拒绝。

## 反面核查

至少用这些结构试装：

- 主角用假身份活动 40 章；
- 双胞胎或分身交换身份；
- 角色失忆，但读者知道真相；
- 不可靠叙述者故意说假话；
- 倒叙中先讲结果、后讲原因；
- 小说五章合成一集漫剧，并合并两个配角；
- 互动分支里一条线角色死亡，另一条线仍存活。

只要其中一个必须靠自由文本备注才能解释，核心结构还没接住。

# 三、读者体验层与接口

## 结论

✅ **这是整套系统最有商业差异的部分，应该保留。**

⚠️ 六本账不宜做成六套各自写入的数据。更好的形态是：

> **一张体验关系网，六种查询视图。**
> 

核心关系应是：

```
读者期待
   ↓
铺垫／压力积累
   ↓
局部兑现／完整兑现／反转兑现
```

章末钩子是“本章怎么制造未完成感”的呈现手法；Hook 义务是系统内部未来要处理的债；两者不是同一个东西。

## 可操作方案

### 1. 体验合同改为稀疏合同

不是每章都填满所有字段。推荐最小内容：

| 字段 | 回答的问题 |
| --- | --- |
| `chapter_job` | 本章主要做推进、兑现、揭示、施压、喘息还是转场 |
| `advance_promises` | 推进哪些读者期待 |
| `planned_payoffs` | 本章兑现什么，部分还是完整 |
| `rule_display` | 展示或利用哪条金手指／世界规则 |
| `reader_state_before_after` | 读者看前和看后，应该多知道／多期待／多担心什么 |
| `ending_open_loop` | 结尾留下的核心问题 |
| `must_preserve` | 正文、分镜不能损失的语义 |
| `avoid_recent_patterns` | 避免哪些近期重复套路 |
| `contract_strength` | hard／soft／advisory |
| `waiver_reason` | 为什么本章可以不满足常规要求 |

`desired_pattern` 默认放在 advisory，不要成为硬指令。

`chapter_job` 里的“喘息”也应算有效推进。商业网文不是每章都必须打脸或升级；人物关系变化、信息揭示、情绪回收、兑现后的短暂放松，同样会改变读者状态。

### 2. 六本账共享同一组 ID

例如：

- 一个 promise 可以对应多个 setup；
- 一个 payoff 可以同时兑现多个 promise；
- 一个章末 hook 可以激活一个 obligation；
- fatigue 只读取最近窗口，不拥有新的剧情事实。

### 3. 具名视图合同增加四项

T8 的必填／降级／限额保留，再补：

- 来源分支与 canon 版本；
- 语义不变量；
- 已声明的信息损失；
- 是否允许写回，以及写回走什么 ChangeSet。

消费者合同测试的方向很稳。软件接口领域的实践也会把消费者期望、版本兼容和真实交互样例一起管理，避免上游改字段后悄悄弄坏下游。([Pact 文档](https://docs.pact.io/pact_broker))

### 4. 不把“钩子存在”当成追读率代理

对故事期待的研究发现，读者对后续发展的前瞻预期，与继续阅读等参与行为存在关联，这支持你们维护期待账。([arXiv](https://arxiv.org/html/2412.15239v4))

但一项 133 人的连续剧实验里，悬念式结尾提高了唤醒程度，却没有提高喜爱度或继续观看意愿。它不能直接外推到起点／番茄，但足够否定“只要断在半截就一定提高追读”的简单公式。([Sonar](https://sonar.ch/global/documents/319990))

所以系统应评价：

> **读者是否产生一个有价值、相信会被兑现的问题，**而不只是检查“本章有没有钩子标签”。
> 

## 代价与风险

最大风险是模型刷指标：

- 每章都硬塞钩子；
- 永远只做部分兑现；
- 把题材标志性套路误判成重复；
- 为了“推进力”把所有喘息章删掉；
- 合同越来越长，正文变成填表作文。

应把体验合同当作生成约束和诊断依据，不当作统一总分。

## 反面核查

做双组试写：

- 一组使用强制满字段合同；
- 一组使用稀疏合同＋允许豁免。

比较：

- 作者重写比例；
- Hook 被人工删除比例；
- 章节套路重复度；
- 期待的实际兑现率；
- 测试读者的继续阅读意愿；
- 规则穿帮率。

若满字段合同在这些指标上都更优，而且不降低题材特色，才考虑加强硬约束。

# 四、编排侧四件

## 4.1 Hook 登记账

### 结论

✅ Hook 账要保留。

⚠️ 当前生命周期把“idea”放进 Hook，会和暗稿重复；“未来义务不抽取”也接不住导入作品和作者临场埋下的承诺。

### 可操作方案

推荐生命周期：

```
candidate
→ active
→ due_window
→ scheduled
→ partially_paid
→ paid
```

异常态：

```
superseded
cancelled_with_compensation
invalidated_by_revision
blocked_by_conflict
```

关键调整：

- `idea` 留在暗稿；
- 正文导入时允许半抽取 `obligation_candidate`；
- 人工或规则确认后才进入 active；
- 增加 `due_window`，不要只有一个死日期；
- 增加 `satisfaction_criteria`，说明怎样才算真兑现；
- 部分兑现后必须留下 `remaining_obligation`；
- 每条义务声明 reader visibility 和 branch scope。

### 代价与风险

半抽取会产生误报，尤其是随口一说、假伏笔和气氛性描述。

所以候选 Hook 不应直接影响生成，只在置信度足够或作者确认后进入 active。

### 反面核查

抽取一批含有誓言、系统任务、身份伏笔、感情承诺、误导线索的真实章节，检查：

- 候选义务漏掉多少；
- 普通描写误报多少；
- 同一义务是否重复登记；
- 取消后是否存在读者可接受的补偿。

---

## 4.2 暗稿

### 结论

✅ 挂编排侧是对的。

单一 `visibility` 布尔值不够，它会把“作者能看”“模型能用”“已经承诺”混成一件事。

### 可操作方案

拆成三个独立闸：

| 闸 | 示例状态 |
| --- | --- |
| 作者可见性 | 系统隐藏／作者可见／团队可见 |
| 生成可用性 | 禁止使用／仅供灵感／允许调用 |
| 承诺程度 | 灵感种子／候选／已锁定／已否决 |

暗稿只有被提升为 active obligation 或 committed plan 后，才可以影响正式生成。

### 代价与风险

状态会变多，但这比“暗稿里的结局突然被正文模型泄漏”代价小得多。

### 反面核查

连续运行大量正文和分镜生成，检查：

- 禁止使用的暗稿是否被泄漏；
- 已否决路线是否重新出现；
- 作者能否看懂某条暗稿为什么进入了正式计划；
- 团队协作时，不同权限是否看到正确内容。

---

## 4.3 作者规划层

### 结论

✅ “故事线实况＋全书目标”双层成立，没有重大方向问题。

需要补的是**承诺强度、分支作用域和计划—实况对账**。

### 可操作方案

规划项统一带：

- `scope`：全书／某故事线／某改编分支；
- `commitment`：hard／soft／aspirational；
- `repairability`：还能不能向前修；
- `locked_by_author`；
- `supersedes`；
- `actual_alignment`：当前实况与计划的关系。

商业网文里建议这样分：

- 结局、核心金手指底线、已公开大承诺：可设 hard；
- 大篇章路径、角色阶段目标：多为 soft；
- 主题表达、某个理想名场面：多为 aspirational。

“主题”不应默认和“结局”同权。

详细层级大纲配合人物、地点和未来节点，确实能改善长故事的一致性与大纲贴合；但动态大纲研究也指出，完全固定的规划难以适应生成过程中的变化，因此计划与实况之间要允许有审查过的偏离。([arXiv](https://arxiv.org/html/2212.10077))

### 代价与风险

目标锁得太硬，会让系统为了守旧计划，放弃连载中实际更受欢迎的人物和支线。

锁得太松，又会出现大爆点、人物命运和前期承诺随时漂移。

### 反面核查

拿有真实作者规划稿与连载结果的作品，检查：

- 哪些偏离属于质量提升；
- 哪些偏离造成读者债务；
- 系统是否把所有偏离都误报成错误；
- 已发表作品能否只做“向前修”，不建议重写读者已经看过的事实。

---

## 4.4 新逻辑句

### 结论

✅ 应重造，但不能成为事实、事件、规则之外的第四套可写真账。

推荐改名为 **NarrativeClaim，叙事断言**。

### 可操作方案

它作为提取和模型交换的原子格式，最少表达：

- 谁／什么；
- 做了什么、是什么状态或受什么规则约束；
- 肯定还是否定；
- 已发生、计划、假设、传闻还是角色相信；
- 谁知道；
- 适用的故事时间；
- 所属分支；
- 关联因果；
- 来源证据；
- 当前状态。

同时保留一条自然语言 `surface_text`，让作者看得懂。

关键纪律：

> 模型先生成 NarrativeClaim；核查通过后编译进 event／state_fact／rule 等正式对象。正式提交后，不允许逻辑句和正式对象两边独立修改。
> 

### 代价与风险

结构太细会增加提取成本；结构太松又会退化成普通摘要句。

### 反面核查

进行往返测试：

```
正文 → NarrativeClaim → 正式大纲对象
→ 再生成正文 → 再提取
```

检查人物、规则、时间、承诺和因果是否仍能对齐。再随机修改一条 NarrativeClaim，确认不会留下两套互相矛盾的记录。

---

# 五、流程与工具

## 5.1 八阶段提取流水线

### 结论

✅ 八个逻辑阶段可以保留。

❌ 不建议冻结成“永远八次处理、固定三到四个模型”。

### 可操作方案

把它定义为**有条件流程图**：

- 对话密集章加强说话人、关系和知情状态核查；
- 战斗章加强状态变化、道具和规则核查；
- 设定章加强规则与例外；
- 倒叙章加强故事时间与叙述顺序；
- 短小过渡章可跳过部分阶段。

工件信封至少带：

- 输入分支与版本；
- schema／stage／prompt／model 版本；
- 证据引用；
- 覆盖情况；
- 置信度与冲突；
- 跳过了哪些阶段及原因；
- 是否允许重试；
- 是否需要人工升级。

固定“八阶段”可以是产品说明，内部实际执行应按章型条件运行。

### 代价与风险

条件流程比固定串行流程更难调试。

所以必须让每一步可重放、可重试、可比较新旧版本。长期运行的流程系统也通常要求编排逻辑可重放，并把模型调用、数据库查询等不确定工作隔离成可重试活动。([Temporal 文档](https://docs.temporal.io/develop/go/workflows/versioning))

### 反面核查

选五类章：密集对话、连续战斗、规则揭示、纯情绪、非线性叙述。比较：

- 固定八阶段；
- 条件跳阶段；
- 单模型一次抽取。

同时看覆盖率、错误率、成本、等待时间和人工修正量。不能只看字段填满率。

---

## 5.2 工具边界

### 结论

🟡 作者端“外粗内细”的方向对。

⚠️ “只有主窗口 AI 单独可调用才算 Tool”可以作为产品露出规则，不能成为内部治理规则。

### 可操作方案

分两本登记：

| 登记 | 管什么 |
| --- | --- |
| 作者可见 ToolCatalog | 作者／主窗口能主动调用的能力 |
| 内部 OperatorCatalog | 提取器、核查器、迁移器、视图生成器等内部环节 |

内部模块即使不叫 Tool，也要登记：

- 输入输出；
- 版本；
- 所属阶段；
- 超时与重试；
- 负责人；
- 可否重放；
- 失败时如何降级。

还有一条硬限制：

> 主窗口 AI 也不能绕过具名视图直接乱读或乱写内核。
> 

### 代价与风险

登记项会增加，但可避免“不是 Tool，所以没人记录它改过什么”。

### 反面核查

更换主窗口模型或工作流调度器，检查：

- 内部环节是否仍可独立运行；
- 历史结果是否可复现；
- 是否丢失调用追踪；
- 是否出现某个模型拥有隐藏特权。

---

## 5.3 作者建议层

### 结论

✅ 建议层结构可用。

⚠️ “推进力”不能只理解为事件速度，否则系统会持续催作者加冲突、升级和打脸。

### 可操作方案

推进力改成：

> **本章是否让读者的认知、期待、压力、关系判断或兑现状态发生了有价值的变化。**
> 

建议层只产出 Suggestion／ChangeSet 提案，不直接修改事实或计划。每条建议显示：

- 发现的问题；
- 证据；
- 为什么影响读者体验；
- 两到三个可选处理；
- 不处理的后果；
- 改动范围；
- 置信度；
- “保持不变”选项。

不同工况：

| 工况 | 建议力度 |
| --- | --- |
| 已发表连载 | 只做向前修复，避免要求重写既成事实 |
| 未发表规划 | 可提出结构重排 |
| 草稿修订 | 允许局部重写 |
| 漫剧／短剧改编 | 重点看可视化、时长和保真冲突 |
| 互动叙事 | 重点看分支安全、状态可达和义务爆炸 |

### 代价与风险

系统可能把自己的偏好包装成诊断，作者逐渐失去判断权。

因此建议必须带证据、影响范围和不改选项。

### 反面核查

专门测试：

- 大战后的喘息章；
- 完成一次大兑现的收尾章；
- 只推进感情关系的章节；
- 读者已知、角色未知的悬疑章。

若它们频繁被判为“推进不足”，推进力口径就错了。

---

## 5.4 Harness

### 结论

🟡 “大部分被动、关键点主动”合理。

❌ 9∶1 不能成为架构常量；它应由实际触发数据跑出来。

### 可操作方案

主动介入只在这些情况发生：

- 硬事实、规则、身份或知情状态冲突；
- Hook 进入到期窗口；
- 模型低置信或证据互相打架；
- 即将发表、导出、合并分支；
- 暗稿要提升为正式计划；
- 改编操作会改变因果或结局；
- 作者主动要求检查。

作者管道四种方案与 AI 管道单方案，可以保留，但底层必须产生同一种 ChangeSet，并带同样的：

- base revision；
- 变更列表；
- 影响范围；
- 验证结果；
- 回退点。

AI 默认给一个推荐方案没问题；低置信或重大冲突时应允许“无法可靠决策，转人工”，不能为了省 token 假装确定。

NVM 画布的数据结构可以借用，作者界面不要因为“已有画布”而强行同形。小白作者、老作者、工作室和漫剧制作者看到的信息密度会明显不同。

### 代价与风险

主动闸过多会打断创作，过少又会让错误一路传到发布或资产生产。

### 反面核查

用四类用户记录：

- 每一万次操作中主动打断次数；
- 用户接受／忽略比例；
- 打断后避免的实际返工量；
- 误报造成的时间损失；
- 不同用户是否都适合相同画布。

9∶1 只有在这些数据长期稳定后，才适合作为运行目标。

# 六、不补会在 100 章／1000 章尺度上崩的缺件

| 缺件 | 约 100 章时的表现 | 约 1000 章时的表现 | 优先级 |
| --- | --- | --- | --- |
| **分支／正史／修订层** | 改编和试写开始污染主线 | 互动分支、改编版、小说版互相覆盖 | P0 |
| **下游改稿回流 ChangeSet** | 作者手改正文后大纲失真 | 大纲与已发表内容长期分叉 | P0 |
| **角色／读者知情状态** | 身份隐藏、误会、悬疑开始穿帮 | 角色全知、秘密提前泄露、旧认知无法追踪 | P0 |
| **叙事单元层级与跨媒介映射** | 章拆场、场合并时靠手工备注 | 小说章、短剧集、漫剧场次大量错位 | P0 |
| **依赖与影响范围** | 改规则后漏改少量 Hook | 改一条世界规则，数百处状态、画面资产和互动条件变旧 | P0 |
| **视觉连续性视图** | 换装、道具、地点状态偶发漂移 | 大量重绘，人物与场景资产失控 | P0，若漫剧是主线产品 |
| **版本迁移与旧流程重放** | 新旧字段偶尔不兼容 | 历史作品无法重跑，旧视图无人敢升级 | P0 |
| **暗稿／分支归档与压缩** | 候选方案开始变多 | 互动分支和废案无限膨胀 | P1 |
| **人物声纹档案** | 主要角色偶尔说话同质 | 长连载与漫剧台词大量同声 | P1 |
| **套路 signature 高级去重** | 暂时可人工发现 | 数据足够后才有稳定价值 | P1 |

近期视觉叙事研究把人物身份、服装状态、地点稳定性和物件状态变化列为长序列分镜连续性的核心问题。([arXiv](https://arxiv.org/html/2604.13452v1))

阅文 2025 年报也披露，其漫剧工具已覆盖内容分析、资产生产以及从文本到视觉的完整流程，并公布了相应商业进展。公司自报数据不能代表整个行业效果，但足以说明视觉连续性已经是生产成本问题，不是展示型附属功能。([Moomoo Newsfile](https://newsfile.moomoo.com/public/NN-PersistNoticeAttachment/7781/20260423/12117307-0.PDF))

互动叙事方面，近期系统研究仍用“叙事状态节点＋玩家行动边＋状态转移”表达可能故事，并发现作者需要看见不同游玩路径之间的差异，才能控制 AI 扩张出来的故事空间。你们若真要长期接互动叙事，branch 和 transition 不是适配层小字段。([arXiv](https://arxiv.org/html/2601.15295v1))

# 七、块与块之间的打架点

| 打架点 | 问题 | 推荐裁决 |
| --- | --- | --- |
| T1 三件套内部 | 快照、变化流、交接可能互相矛盾 | 变化记录权威；快照可重建；交接无权改历史 |
| T1 与 T8 | 一边说三件都是真账，一边说下游只读派生视图 | 快照、交接归投影视图；内核事实另立 |
| T2 promises／payoffs 与 T3 Hook | 都在记录“未来要兑现什么” | promise 是读者期待；obligation 是内部债；hook 是章末手法；payoff 是兑现结果 |
| T3 idea 与 T5 暗稿 | 同一个点子可能出现两次 | idea 只进暗稿；升格后进入 Hook／计划 |
| T5 暗稿与 T6 规划 | 两边都可能记录未来路线 | 共用 PlanItem 底座，以承诺程度区分 |
| T4 逻辑句与 facts／events／rules | 两套都能写会出现双真账 | 逻辑句只做提取交换格式，正式对象唯一可写 |
| T7 体验合同与章间交接 | 两者都在告诉下一章怎么写 | 交接管连续性和不能忘；体验合同管读者要获得什么感受与期待 |
| T8 适配视图与改编 | 合并人物、换结局不再是只读视图 | 不改语义用 view；改语义就新建 adaptation branch |
| T9 Hook 不抽取 | 导入正文会漏掉作者临场埋下的义务 | 半抽取 obligation candidate，再审核升格 |
| T10 主窗口 Tool 与 T8 读写纪律 | 主窗口可能借“总控”名义绕过合同 | 主窗口也只读具名视图，只写 ChangeSet |
| T11 建议层与 T6 规划 | 建议可能偷偷改路线 | 建议只能提案，作者或规则提交后才进规划 |
| T11 推进力与疲劳账 | 一边催加速，一边又防疲劳 | 以读者状态变化判断推进，不以动作密度判断 |
| T6 全书目标与互动分支 | 一个结局无法覆盖多路线 | 目标带 global／branch scope |
| T12 AI 单方案与低置信冲突 | 强行单答案会掩盖不确定 | 默认单方案；冲突时允许停下与升级人工 |

# 八、哪里过度设计，可以删或缓

## 从硬规则改成可调参数

- 每 10～20 章物化一次快照。
- 回放上限 100～200 条。
- 固定八个物理阶段。
- 固定三到四个模型。
- 9∶1 被动／主动比例。
- 每章体验合同全部字段必填。

## 从多套实体账改成共享数据＋不同视图

- 六本体验账；
- Hook、暗稿、规划里的共通未来计划字段；
- snapshot／handoff 中重复保存的事实；
- 各下游重复复制的人物和规则资料。

## 可以等真实数据再加重

- 高级 signature 去重；
- 每个事件都建完整因果图；
- 复杂的爽点数值指数；
- 人物声纹单独成一本顶级账；
- 高光三连挑的核心化；
- 按固定章数判断情绪疲劳。

## ❌ 不建议缓的部分

- 证据锚；
- 权威与更正链；
- branch／canon／revision；
- 知情状态；
- 下游改稿回流；
- 具名视图合同；
- 版本兼容；
- 规则独立表达；
- 发布与导出前的硬闸。

# 九、质疑清单

| 条目 | 质疑 | 为什么 | 什么证据能证伪 |
| --- | --- | --- | --- |
| **T1** | 🔴 重大质疑：三件套同为唯一真账 | 快照和交接会与事实变化争夺权威 | 大规模更正、倒序和人工改稿测试中，三方零歧义，且能从任一部分无损重建 |
| **T2** | 🟠 九类对象平铺、核心入场门槛过硬 | provenance、交接、体验推断与故事事实不是同性质；治理字段不该受二题材二下游限制 | 六下游×多题材试装证明没有重复写入，也没有关键治理字段被门槛挡掉 |
| **T3** | 🔴 idea 进入 Hook、未来义务完全不抽取 | 与暗稿重复；导入正文会漏掉隐式承诺 | 金标章节中，依靠 promise 抽取就能覆盖所有有效未来义务，且不需要候选 Hook |
| **T4** | 🟠 新逻辑句可能形成双真账 | 与 events／facts／rules 重叠 | 随机修改与往返生成后，逻辑句和正式对象长期保持零分叉 |
| **T5** | 🟡 方向无重大质疑；怀疑单一可见性状态不够 | 作者可见、模型可用、正式承诺是三件事 | 大量生成中，未授权暗稿零泄漏，且作者可清楚控制全部使用边界 |
| **T6** | 🟡 方向无重大质疑；缺分支作用域与承诺强度 | 互动线、改编线和小说主线目标不同 | 多分支项目只用现有双层规划也能无歧义管理硬目标、软目标和实际偏离 |
| **T7** | 🟠 每章体验合同可能把作品推向公式化 | 模型会刷钩子、爽点和套路指标 | 真实 A/B 中追读与作者接受率提升，同时套路多样性、喘息空间不下降 |
| **T8** | 🟡 具名视图方向无重大质疑；“所有适配都是只读视图”有疑问 | 短剧改编常改变人物、顺序和因果 | 多个真实改编项目均能只靠无损视图完成，不需要独立改编正史 |
| **T9** | 🟠 固定八阶段可能把实验结果写成永久架构 | 不同章型需要的核查不同 | 固定八阶段在所有章型上同时优于条件流程，且成本和延迟不更差 |
| **T10** | 🟠 Tool 定义与主窗口运行方式绑得太紧 | 更换总控模型后，内部组件可能失去登记与治理 | 替换主窗口或调度器时，所有内部能力仍可复现、重试、追踪 |
| **T11** | 🟡 推进力可能被理解成持续加速 | 会误伤兑现章、情绪章、关系章 | 测试中这些章不会被系统性判弱，并获得作者与读者认可 |
| **T12** | 🟠 9∶1 和画布复用拍得偏早 | 不同用户和不同阶段的主动介入需求差异大 | 四类用户实测都证明同一画布更省时、更少错，且主动比例稳定接近 9∶1 |

# 十、第五节必答题建议

## 1. 证据锚保留与否

**结论（置信度：高）：保留，而且列为 P0。可操作方案：**每条正式事实、事件、规则和承诺保留来源片段引用、提取运行、产出者、确认者及派生关系。计划和暗稿没有正文片段时，锚到作者决定、父计划或生成运行。原始内容只存一次，其他记录保存指针，不重复复制长文本。W3C 的 provenance 模型也将实体、处理活动和责任主体分开，并通过生成、使用和派生关系形成追踪链。([W3C](https://www.w3.org/TR/prov-o/))
**代价与风险：**存储和索引增加；证据过细会拖慢查询。
**反面核查：**随机抽查冲突事实，若没有证据锚也能稳定定位来源、解释误判并局部重算，才可考虑减配。

---

## 2. 新逻辑句条目格式

**结论（置信度：中高）：采用 typed NarrativeClaim，但只作为交换原子，不另开真账。可操作方案：**至少表达主体、关系、值、否定性、情态、知情范围、故事时间、分支、证据和状态，并保留人能读懂的原句。
**代价与风险：**字段太多会让小事实成本过高。
**反面核查：**检查它能否统一表达“已发生事实、角色误信、世界规则、未来计划”，同时不与正式对象分叉。

---

## 3. 体验合同格式定稿

**结论（置信度：高）：稀疏合同，不做满字段表。可操作方案：**采用 `chapter_job＋推进期待＋计划兑现＋规则展示＋读者状态变化＋结尾开放问题＋must_preserve＋反重复＋强度＋豁免原因`。
**代价与风险：**稀疏合同可能让不同作者填法不一。
**反面核查：**没有合同字段的章节，能否仍通过章型模板和交接稳定生成；有合同的章节是否明显减少重写。

---

## 4. 字段版本化机制

**结论（置信度：高）：至少分五种版本，不能只放一个 `version`。可操作方案：**

- `schema_version`：字段长什么样；
- `semantic_profile_version`：字段含义和枚举口径；
- `view_version`：某个下游看到的合同；
- `record_revision`：这条故事记录改了几次；
- `pipeline／model／prompt version`：谁怎样产出的。

字段升级采用“先新增、让新旧消费者并存、确认无旧消费者后再删除”。旧字段名和枚举值不能换个意思继续用。JSON Schema 本身也要求明确声明采用的 schema 方言；消费者合同管理则强调不同版本之间的兼容验证。([json-schema.org](https://json-schema.org/understanding-json-schema/reference/schema))
**代价与风险：**迁移工具和兼容测试工作量明显增加。
**反面核查：**拿一份一年前的大纲，用新流水线生成正文和分镜；若不需人工修数据且结果可解释，机制才算过关。

---

## 5. Hook 冲突裁决七序＋降级

**结论（置信度：中高）：可先采用临时七序。**

**可操作方案：**

1. 已发表事实、硬规则、身份与知情约束；
2. 已向读者明确暴露的承诺和到期债务；
3. 作者锁定的结局、大爆点、角色命运；
4. 当前故事线的因果与角色行动合理性；
5. 本章必须完成的兑现、揭示或转折；
6. 疲劳、近期套路和节奏平衡；
7. 新点子、局部惊喜和新章末 Hook。

平台政策与安全要求放在七序之外，作为零号硬门。

降级依次考虑：

- 在 due window 内改期；
- 允许的部分兑现；
- 改变兑现形式但不改承诺含义；
- 拆章；
- 公开取消并给予补偿；
- 隔离冲突，转人工。

**代价与风险：**不同题材可能需要调整第 3～6 位。
**反面核查：**用系统流、感情线、悬疑线和升级线分别跑冲突案例，观察是否总偏向同一种爽点。
**需补材料：现有“七序”的原始定义及历史冲突案例。**

---

## 6. 暗稿可见性闸

**结论（置信度：高）：采用三闸，不用一个 visibility。可操作方案：**作者／团队可见性、模型可用性、承诺程度分别管理。
**代价与风险：**状态组合变多。
**反面核查：**检查未授权泄漏、已否决路线复活、团队权限错漏。

---

## 7. 偏航判定口径

**结论（置信度：中）：不要用“离原计划多远”单独判定。可操作方案：**分四类：

- 硬偏航：破坏事实、规则、身份或知情状态；
- 债务偏航：错过读者承诺的到期窗口；
- 规划偏航：偏离里程碑，但可能是好改动；
- 体验偏航：章节没有完成自己的 reader-state 任务。

严重度按：

```
读者是否已看见
× 是否不可逆
× 剩余修复窗口
× 影响多少下游
```

**代价与风险：**规划偏航很难只靠模型自动判好坏。
**反面核查：**让作者回看过去“改得更好”和“改崩了”的真实偏离，系统能否区分。
**需补材料：至少 3～5 本带原始规划、实际连载轨迹和作者解释的样本。**

---

## 8. 产出方标记字段

**结论（置信度：高）：必须有，而且“谁产出”与“是否权威”分开。可操作方案：**

- `origin_type`：human／extracted／model_proposed／program_derived／imported／migrated；
- `producer_id`；
- `run_id`；
- `source_refs`；
- `accepted_by／accepted_at`；
- `authority_status`：authoritative／accepted／proposed／inferred／derived。

**代价与风险：**字段较多。
**反面核查：**作者亲手输入但尚未确认的灵感，不能因为 origin 是 human 就自动变成正史。

---

## 9. 规则是否单列第八件

**结论（置信度：高）：语义上单列，物理上不必再开一本 UI 账。**

金手指和世界规则至少需要：

- 作用域；
- 触发条件；
- 前置条件；
- 效果；
- 代价；
- 冷却；
- 例外；
- 升级路径；
- 哪些角色知道；
- 读者何时得知；
- 生效与失效版本。

体验合同、正文、分镜、互动都引用同一 rule ID。

**代价与风险：**规则抽取会把一次性现象误判成通用规则。
**反面核查：**检查模型能否区分“角色猜测”“一次例外”“真正规则”和“规则升级”。

---

## 10. 爽点账／钩子账细目

**结论（置信度：中高）：四者必须拆开。**

- promise：读者相信未来会发生什么；
- obligation：系统认为以后必须处理什么；
- payoff：已经兑现了什么；
- chapter hook：本章末尾怎样制造开放问题。

**可操作方案：**通过 ID 连接，不共享同一个生命周期。爽点账记录 planned／actual、partial／full、满足条件与读者可见结果；钩子账记录开放问题、触发来源、预期价值和到期窗口。
**代价与风险：**账面数量增加。
**反面核查：**一个“系统奖励尚未领取”的案例中，四者能否各自表达而不重复抄同一句话。

---

## 11. 建议层工况分型

**结论（置信度：中高）：至少采用五类工况。**

- 已发表续写；
- 未发表规划；
- 草稿修订；
- 同源短剧／漫剧改编；
- 互动叙事。

每类再叠加：

- 可动／不可动；
- 作者明确意图；
- Hook 到期；
- 影响范围；
- 修复窗口。

**代价与风险：**细分过多会增加配置。
**反面核查：**同一个问题在“已发表连载”和“未发表大纲”中，建议是否明显不同。
**需补材料：四类目标用户的真实操作日志和建议接受／拒绝原因。**

---

## 12. 挂靠点／停点清单

**结论（置信度：高）：停在不可逆或高返工动作前。**

推荐停点：

- 提取发现身份、规则或时间冲突后；
- 暗稿升为 active Hook 前；
- 本章体验合同冻结前；
- 正文发表前；
- 小说语义转为改编分支前；
- 视觉资产大批量生产前；
- 互动分支合并前；
- schema／view 大版本迁移前。

普通低风险生成不应频繁停。

**代价与风险：**闸过多会破坏写作流畅感。
**反面核查：**每个停点统计“拦下了多少真实返工”和“制造了多少无效打断”，长期无价值的停点删除。

---

## 13. R12 金标与四层秤

**结论（置信度：中高）：金标至少分五个粒度，四层秤不要合成一个总分。**

金标粒度：

1. NarrativeClaim／事实级；
2. 章状态与交接级；
3. 50／200／1000 章长距一致性级；
4. 下游具名视图级；
5. 往返改稿级。

四层秤建议：

| 层 | 看什么 |
| --- | --- |
| 硬正确 | 事实、身份、时间、规则、知情状态 |
| 叙事功能 | 因果、推进、兑现、章节任务 |
| 读者体验 | 期待价值、爽点、疲劳、套路重复 |
| 生产可用 | 作者修正量、下游可消费度、成本与延迟 |

硬正确应是门，不应被其他层的高分抵消。

**代价与风险：**金标建设成本高，题材差异也大。
**反面核查：**一个事实严重穿帮但很刺激的章节，系统必须判失败；一个没有大战但完成大兑现的章节，不能因动作密度低而判失败。
**需补材料：六个下游各自至少 20～50 个真实成功／失败样例，以及可获得的追读、完读或作者修改数据。**
