# 商业网文大纲中枢系统的作者体验层与新形态评估

## 核心判断

✅ **结论先行**：你们这套“**大纲中枢 + 具名视图合同 + 画布工作流 + 黑盒工作流 / 挂靠点**”的方向，**对四类画像里三类半是成立的**。更准确地说，**网文老作者、工作室、AI 漫剧创作者**的来用理由都成立；**小白作者**也成立，但前提很苛刻：**第一次进来 5 到 10 分钟内，必须让他看见一个“真的像作品”的东西**，而不是先让他学结构、填字段、理解账本。市场侧的大背景也支持你们往“读者爱看点的结构化放大器”走：网络文学阅读与 IP 改编还在增长，漫剧、短剧、互动等多端转化在加速，短剧和微短剧用户规模也已经非常大。citeturn15view0turn15view2turn15view3turn6search5

✅ **最该先做的画像**：如果只能先打一个主画像，我建议你们**先做“网文老作者”**，更具体一点，是**有存量正文、在更、追求不断更和少返工的作者**。原因很直接：你们现有架构里“正文导入提取大纲 / 大纲生成正文 / 体验合同 / 作者建议层 / 具名视图合同”已经能直接命中这群人的核心痛点；反过来，**工作室虽然商业价值更高，但你们现在缺的多人治理件更多**，一上来就打工作室，会被权限、版本、审计、批处理和回滚拖慢。商业化第二阶段再冲工作室更稳。阅文和番茄自己的作者工具都在强调多端同步、数据看板、历史版本、发布与收益数据，这说明成熟作者接受“工具化”这件事，但他们接受的是**少添麻烦的工具化**，不是加重录入负担的工具化。citeturn15view4turn15view5turn5search0

⚠️ **最大的架构风险不在“能不能做”，在“哪几件东西没补就会做歪”**。我看到的最大缺口有三块：

一块是**互动分支状态**，你们现在的本体明显更偏线性连载；

一块是**镜头级视图合同**，AI 漫剧 / 分镜这条线要的不是文学摘要，而是可拍、可画、可复用的镜头语义；

一块是**多人协作治理**，工作室会把任何“单人脑内顺”的系统立刻拽进权限、锁定、审计、回滚、批量任务的泥里。微软和 Inworld 公开讲过互动叙事最麻烦的地方就是非线性依赖与玩家选择管理；Boords、StoryboardHero、Firefly 这类产品都把“脚本转分镜、角色一致性、评论审批、导出”当主卖点；协作写作工具也都把实时协作、批注、追踪变化、离线同步当基建。citeturn11view5turn11view1turn11view2turn14view2turn16view2turn16view3turn12view4

🧩 **我对你们的总判断**：这套架构**很像一个能做成“叙事操作系统”的底子**，而不是一个单点写作插件。这个方向值做。但如果产品第一触点还是“先让我理解十二个决策、九类对象、六本账”，你们会先把最容易转化的用户挡在门外；真正该先让用户看到的，是“我扔进一个点子 / 旧正文，系统立刻给我一个像样的章纲、节奏钩子和能继续写/能直接分镜的结果”。Sudowrite、StoryTribe、Vyond 这类产品在抢新手时，卖点全是“从一个想法开始”“不需要绘画经验”“几分钟看见成品”；你们不能在首屏输给这种直接感。citeturn13view0turn13view3turn14view4turn8search6

## 同类产品与市场信号

商业网文这条赛道，现在不是“写作工具内卷”这么简单，而是**上游内容生产和下游改编管线开始连起来了**。中国社科院与中国作协公开材料都在反复强调，网络文学 IP 改编在继续扩大，漫剧、短剧、游戏、衍生品都在吃上游叙事资产；2025 年网络文学 IP 改编市场规模达到 3676.1 亿元，同比增长 23.13%；2024 年微短剧用户规模达到 6.62 亿，占网民的 59.7%，市场规模 504 亿元，已经超过当年电影票房总额。对于你们来说，这意味着“大纲中枢”不是为了写作优雅，而是为了**把一份叙事资产反复变现**。citeturn15view0turn15view2turn6search5

## 四类画像的来用理由、流失点和可视化

### 小白作者

✅ **结论先行**：小白会来，但不是为了“学会大纲系统”，而是为了**把脑子里一个很模糊的爽点想法，快速变成像样的故事和画面**。如果你们把首轮体验做成“输入一句话 → 出一页章纲 + 三个钩子方案 + 一个能播放的低保真分镜”，这个理由成立；如果首轮体验是“请先补齐人物、世界、规则、状态、证据锚”，他会直接走。Sudowrite、StoryTribe、Vyond 这些产品都在抢“零基础、不想学复杂工具”的用户，它们卖的都是立刻有结果。citeturn13view0turn13view3turn14view4turn8search6

👉 **可操作方案**：小白入口不要从“大纲编辑器”进，要从**黑盒自动型工作流**进。最顺的路径应该是：

“我有个想法” → 选题材和爽点模板 → 生成 **一句话卖点 / 主角金手指 / 前三章推进 / 每章章末钩子 / 一个 lo-fi 分镜预演** → 用户只改“我喜欢哪个方向”。这个时候系统背后可以已经把大纲本体、体验合同、未来义务、Hook 账记好了，但前台只给他看**三块东西**：故事有没有爽、主角有没有代入、下一章想不想点。Sudowrite 的 Story Bible 就是把复杂的源数据藏在可引导的流程后面；StoryTribe 和 Canva Whiteboard 则说明“低保真视觉化”足够让非专业用户产生“我真的在创作”的感觉。citeturn13view0turn14view4turn14view3

⚠️ **最容易流失的一步**：**从第一次惊喜，切到第一次编辑**。说白了，小白能接受 AI 给他一版东西，但一旦要他自己改，他最怕两种事：一是**不知道改哪里**，二是**改完以后别的地方也乱了**。所以小白版必须可视化：

“这一改，会影响哪些角色 / 哪个伏笔 / 哪条规则 / 哪个钩子”；

“你可以直接改结果，不必先学结构”；

“系统已经替你补账了”。这类“改动影响可视图”其实比通用画布更重要。BookBub 的调研里，作者把 AI 当 brainstorming partner 和组织助手时更容易接受，把它当直接成文者时分歧更大，这跟小白的心理也很一致。citeturn10view0

❌ **反面核查**：如果小白入口上线后，用户大部分时间都停在“补资料”“选字段”“看不懂为什么有这几个账”，那就说明你们把专家后台端到了 C 端首屏。证伪方式很简单：看**首日从点子到第一章导出 / 第一个分镜导出的完成率**，再看第一次回访时用户是回到“继续写”还是回到“继续填设定”。如果回访多数都在补结构，不在推进故事，这个入口就偏了。这个判断是产品推断，**需补材料：你们打算给新手的首屏原型和首个任务链**。

### 网文老作者

✅ **结论先行**：这群人来用你们，理由最成立。因为他们真正要的不是文采辅助，而是**不断更、少穿帮、好断章、可控地往爽点推进，还能顺手给改编留料**。阅文作家助手和番茄作家助手都把重点放在多端写作、数据面板、版本历史、发布、收益、读者反馈上，说明成熟作者的工作流已经非常“生产化”；你们要补的不是“让他学会更专业写作”，而是**把他本来就在做的结构记忆活、伏笔回看活、节奏校正活给接过来**。citeturn15view4turn15view5

👉 **可操作方案**：老作者版本最该主打三条链路。

一条是**正文导入提纲**：把存量正文吃进去，直接抽出章节快照、状态事实、规则、Hook、读者承诺和兑现。

一条是**章前预飞检查**：下一章开写前，给出“上章到本章的必须保留、最好推进、风险点”。

一条是**连载安全网**：当作者准备改前文、挪章节、补规则时，系统先告诉他“哪几章会受影响、哪些后续 Hook 会漂”。这三条链路跟你们现有 T1 / T2 / T3 / T7 / T11 是对得上的。Sudowrite、Novelcrafter、Plottr 也都在证明作者愿意为“系列一致性、长线资料、可视结构”付费，但前提是不要把它变成额外一份工作。citeturn13view0turn12view0turn12view4

⚠️ **最容易流失的一步**：**第一次把旧书导进来后，系统提取得“不够像他自己”**。老作者不是没耐心，而是特别能感知“这个工具到底懂不懂我这本书”。如果提取出来的 reader promise、规则、伏笔、人物状态一看就假，或者系统总想把他的章法拉成通用模板，他会立刻把你归类成“写作玩具”。所以老作者可视化一定要做成**证据对照**：

“这条 Hook 是从哪段正文抽出来的”；

“这条规则为何被识别”；

“这章建议推进的是哪条期待”；

“你不采纳不会坏死，但采纳会解决什么问题”。

这是你们证据锚最有价值的用户面，而不是只留给研发排错。BookBub 的作者调研里，大量使用者都在强调“AI 给的是起点，不是定稿；我要保留我的 voice 和 vision”，这点跟成熟网文作者高度一致。citeturn10view0

💡 **需要什么可视化**：老作者最需要的不是炫酷，是**能一眼定位问题**。我会优先做五个板：

“全书 Hook 看板”“铺垫—兑现热力图”“角色 / 规则 / 资源状态时间线”“已发表锁定层”“章级体验合同条”。这五个板一旦做清楚，T11 的建议层才不会像空口说教，而像一个真的懂连载的人在提醒你。这个判断和作家助手 / 番茄作家助手把“数据、版本、发布、检索”摆到前台是一致的。citeturn15view4turn15view5

❌ **反面核查**：如果老作者必须手工修大量提取结果，或者系统每次都给出大而空的“加强人物成长”“提升戏剧冲突”，那他会只把你当临时 brainstorm 工具，不会把你放进日更主流程。证伪指标可以直接看：**导入后第一周仍持续用“章前预飞检查”的比例**，以及**提取后人工修账时间**。**需补材料：你们准备拿什么书做首批金标提取评测，尤其是连载中和已完本两类样本。**

### 工作室

✅ **结论先行**：工作室会是你们最容易付费、也最容易把需求拉满的一群人。因为他们天然在意**多人分工、批量产出、标准化复用、从网文到漫剧 / 短剧的同源资产复用**。你们“所有下游只认大纲一种格式”的中枢思想，对工作室特别有吸引力；这类团队最怕的是每条线都在重做一遍结构活。Arc Studio、Final Draft、Plottr、Novelcrafter 都把协作、评论、实时同步、版本与团队作为卖点，说明到了团队阶段，用户不再问“能不能生成”，而是问“谁改的、哪里变了、能不能回滚、批量能不能跑”。citeturn16view1turn16view2turn16view3turn12view4turn12view0turn12view3

👉 **可操作方案**：工作室版最好不要从“写作助手”卖，而要从**叙事生产管线**卖。最理想的流程是：

策划把 idea / 存量正文扔进来 → 系统生成标准大纲中枢 → 编排位在 Hook 看板和故事线里程上定方向 → 主笔只写正文或修正文 → 分镜位直接消费具名视图合同 → 画面位不碰正文，只认镜头包 → 审核位看的是改动 diff、发布锁和回滚点。

你们现在架构里已经有 T8 具名视图合同和 T10 黑盒工作流，这是最像“工作室资产系统”的地方；问题不是方向，而是件不够齐。citeturn16view3turn16view2turn12view4

⚠️ **最容易流失的一步**：**第一次多人同时写 / 同时改 / 同时导出时**。工作室用户不怕复杂，怕的是复杂以后不可靠。一个常见死法是：故事主笔改了某章的规则，分镜位导出的镜头包还是旧的，结果后面全错；或者一条 Hook 被两个编辑改成不同版本，系统不知道谁是准的。协作工具公开强调实时协作、按人查看变化、聊天注释、锁定和离线同步，不是因为它们炫，而是这几个东西不做就进不了生产环境。citeturn16view2turn16view3turn12view4

💡 **需要什么可视化**：工作室最该有的不是“大纲树”，而是**生产驾驶舱**。我建议至少有：

“书 / 线 / 章节 / 下游工单 Kanban”“版本 diff 轨”“异常队列”“消费者合同测试板”“批量导出队列”“已发表 / 已交付锁定图层”。

这里面“消费者合同测试板”尤其重要，因为你们已经定了“下游不直读本体字段”，那就必须把“视图合同是不是能稳定喂给分镜 / 画面 / 互动模块”做成人人看得懂的可视测试结果。这个思路和 Final Draft 的协作追踪、Arc Studio 的 writers’ room、Plottr 的 live collaboration 很一致。citeturn16view1turn16view2turn16view3turn12view4

❌ **反面核查**：如果工作室试用时还得靠飞书 / Excel / 群聊来确认谁改了什么、这条输出是不是最新、哪个版本能发，那你们虽然看起来“有 AI”，本质上还没形成生产系统。证伪方式看两件事：**一次多人并行的返工率**，和**从正文改动到下游视图同步的延迟 / 稳定性**。这两个指标扛不住，工作室不会把核心稿件交给你们。

### AI 漫剧创作者

✅ **结论先行**：这群人来用你们的理由也成立，而且和你们架构很合。因为 AI 漫剧 / 分镜线用户最缺的不是“再来一个生成器”，而是**一个能把故事、镜头、角色一致性、情绪节奏、导出格式串起来的中枢**。Boords、StoryboardHero、Adobe Firefly 都已经把“脚本转分镜”“角色一致性”“协作批注”“导出 PDF / PNG / MP4”作为核心卖点；Dashtoon 则证明“故事进来、漫画出去”这件事有真实消费场景。你们如果能把大纲中枢真变成镜头包的唯一上游，AI 漫剧这群人是很能感受到差异的。citeturn11view2turn11view1turn14view2turn14view1turn2search0

👉 **可操作方案**：对 AI 漫剧创作者，最顺的不是“大纲生成正文”，而是**大纲生成镜头视图合同**。这个视图合同至少要给出：

场景目的、情绪目标、出场角色、镜头类型、视角、动作节点、画面重点、道具 / 服装 / 关系状态、章末高光三连挑。

然后再由分镜线把它转成 storyboard cards、画面提示、角色 look references、镜头时长建议。Firefly、Boords、StoryboardHero 都在证明，用户会为“脚本直出分镜 + 一致性 + 可协作导出”买单，不会为“更花的 prompt 文案”长期买单。citeturn14view2turn11view2turn11view1

⚠️ **最容易流失的一步**：**从故事理解，切到画面生成**。最麻烦的地方在于，同一个章节的“好看剧情节奏”和“好画镜头节奏”不是一回事。如果你们的分镜输出还只是“这一章讲了什么”，没有给“这一格为什么要这么拍 / 这一格跟上一格关系是什么 / 画面里必须保留什么”，创作者会被迫回到手搓 prompt。Adobe Firefly 公开把“保持 consistent look and feel”“从 script 生成 storyboard”“协作反馈和导出”写得很重，正说明镜头层语义不能省。citeturn14view2turn14view1

💡 **需要什么可视化**：AI 漫剧版最该有四样：

“镜头带状时间线”“角色外观 / 道具一致性卡”“章节到镜头的高光映射”“分镜合同测试结果”。

这套可视化一旦做好，你们的 T8 具名视图合同就不只是研发协议，而是创作者真的能拿来审片、审镜头、审角色一致性的面板。citeturn14view2turn11view2

❌ **反面核查**：如果创作者导出镜头包后，还要大量手工补“镜头远近、角色朝向、动作节点、服装道具、情绪转场”，那你们的分镜线还停在“剧情摘要”阶段，不算真正进入漫剧工作流。证伪方式看**镜头包的一次可用率**，以及**从章纲到可审分镜的人工补写时长**。**需补材料：你们 D56 / D57 冻结项里，到底已经冻结到什么粒度。**

## 两个新形态的可行性

### 普通人扔一个想法进来，生成分镜式 SVG 火柴人定格动画

✅ **结论先行**：**能做，而且适合做成拉新壳层。** 这件事最像“给小白和泛用户一个低门槛的故事入口”，不是核心付费形态，但非常适合把“我不会写、也不会画”这群人拉进来。StoryTribe、Vyond、Canva Whiteboard 都在证明：**低保真、无需绘画经验、几分钟出结果** 本身就是强需求；用户并不要求第一版就电影级，他们要的是“我脑子里的梗终于被看见了”。citeturn14view4turn8search6turn14view3

👉 **可操作方案**：你们现有架构里，这个形态可以挂在**黑盒自动型工作流 + 分镜视图合同**上。建议把路径做成：

一句话点子 → 生成 6 到 12 格故事卡 → 每格有一句旁白 / 对白 + 角色位置 + 关键动作 + 简单镜头 → 输出 SVG 火柴人定格动画。

关键不是“画得好”，而是“节奏感出来了”。这和 Canva 的白板动画、Vyond 的文本到视频、StoryTribe 的无码绘 storyboard 是同一条用户心理线：**先看到故事被演出来，再决定要不要更认真创作**。citeturn14view3turn8search2turn14view4

⚠️ **代价与风险**：

一是**新鲜感很强，但长期留存未必强**。很多人会觉得好玩，但不一定留下来写长篇。

二是如果你们让这个壳层直接接触太多本体字段，用户会感觉突然从娱乐产品跳进专业后台。

三是 SVG 火柴人如果完全无统一动作语法，后面接互动叙事 / 分镜就会很乱。

也就是说，这个形态更像**需求创造器和 onboarding 壳**，不是最稳的主产品。相关产品之所以能成立，是因为它们把复杂制作包在简单表面后面。citeturn14view4turn8search6turn14view3

❌ **反面核查**：如果做出来以后，用户愿意玩两次，但很少继续写下一章、完善设定、升级成正式故事，那它只是一层 demo 皮。建议直接盯三件事：**首日导出率、次日续写率、从火柴人故事升级为正式大纲的转化率**。达不到，就别高估它的商业价值。

### AI 互动叙事，像养成 / 闯关那样看图选剧情，边选边生成大纲

✅ **结论先行**：**这件事你们现在的架构只能半做，不能说已经天然能做。** 原因很简单：你们当前设计明显是围绕“连载型、线性主链”搭的；而互动叙事真正难的，不是加几个选项，而是**管理分支状态、回收承诺、让每次选择既有后果又不把产能炸掉**。Episode 的核心卖点就是 choices shape your story；ChoiceScript 明说它适合写长篇 branching narrative；微软和 Inworld 公开讲互动叙事最复杂的是 non-linear plots、branching dependencies 和 player choices 管理。citeturn11view3turn2search15turn7search2turn7search13turn11view5

👉 **可操作方案**：如果你们真要做，这个形态不能只挂在“Hook 登记账”的边上，得补一层**互动世界状态模型**。最低要有：

`player_state`（玩家资源、身份、关系、已知信息）、

`branch_state`（当前分支节点、已选路径、可回收路径）、

`choice_consequence`（立即反馈 / 延迟反馈 / 假选择 / 真分流）、

`world_persistence`（世界变化哪些是不可逆的）。

同时，体验合同也得扩一件事：**choice contract**，也就是“这次选择承诺给玩家什么感觉，后面什么时候兑现”。否则你会做成“看起来能选，其实故事还是自动往前推”，而这种假互动在 Episode 这种平台里恰恰是用户最会吐槽的点。citeturn11view3turn2search15turn11view5

⚠️ **代价与风险**：

这条线最大的坑不是模型成本，是**分支爆炸**。ChoiceScript 之所以能让个人作者写很长的 branching narrative，是因为它把状态和分支当一等公民；AI Dungeon 之所以好玩，是因为它开放，但它的叙事稳定性天然难控；Inworld / Narrative Graph 走的是更工程化的世界状态管理。你们如果只靠现有章纲和 Hook 账硬撑，会很快碰到“选项越来越多，但后果越来越假”的问题。citeturn7search2turn7search13turn7search15turn11view5

❌ **反面核查**：如果玩家玩了几轮以后发现，不管怎么选，系统总在把他拉回同一条主线，或者早期选择对后面几乎没有可感知代价，那这条产品线就会沦为“带按钮的连环画”。我会把证伪标准定得很硬：**玩家能否在 3 到 5 次关键选择后，清楚感知自己的身份、关系或资源状态出现稳定差异**；做不到，就说明还没到该上线的时候。**需补材料：你们想要的是偏 Episode 式剧情互动，还是偏 AI Dungeon 式世界探索。两者本体设计完全不是一件事。**

## 架构适配结论与缺件挂载

✅ **结论先行**：你们已定架构**足够支撑四类画像中的主要流程**，也足够支撑新形态①；**新形态② 要补件**。这些缺件不是推翻 T1～T12，而是在已定层级上把“该有但现在还没落地的承重件”补齐。下面我按你要求，明确挂到**本体 / 体验合同 / 视图合同 / 画布 / 黑盒挂靠点**。

| 挂载层 | 我认为缺的件 | 为什么缺它会卡住 | 主要服务谁 |
| --- | --- | --- | --- |
| 本体 | **互动状态件**：`player_state / branch_state / choice_consequence / irreversible_world_change` | 互动叙事不是多几个 Hook 就行，没有这层会变成假互动 | 互动叙事 |
| 本体 | **视觉锚点件**：角色外观 ID、核心道具 ID、场景锚点、关系姿态锚点 | AI 漫剧要角色一致性，单靠正文语义很难稳定派生 | AI 漫剧、工作室 |
| 体验合同 | **弧线级合同**：不是只做“本章推进啥”，还要有 3～10 章滚动窗口的兑现压力 / 疲劳控制 / 套路去重预算 | 商业网文要章章有钩子，但也怕三十章后套路疲劳；只做章级合同容易近视 | 老作者、工作室 |
| 体验合同 | **Choice contract**：这次选择给玩家什么心理承诺、后续如何回收 | 互动叙事如果没有“选择体验合同”，用户会觉得被糊弄 | 互动叙事 |
| 视图合同 | **镜头包合同**：shot type、camera move、composition、emotion beat、must-show objects、continuity refs | 分镜 / 漫剧消费的是镜头语义，不是文学摘要 | AI 漫剧 |
| 视图合同 | **互动包合同**：可选项文案、门槛条件、可见不可见信息、失败转移、存档粒度 | 互动模块没这层就会把本体读爆，或者把选择做假 | 互动叙事 |
| 画布 | **Hook / Payoff 热力图、分支地图、团队工单看板** | 现在画布更像流程组织层，还缺“人人看得懂的叙事控制台” | 老作者、工作室、互动 |
| 黑盒挂靠点 | **提取证据复核点、章前预飞点、分镜预飞点、批量导出回滚点** | 黑盒不是不能黑，而是必须有可理解的插手点 | 四类画像全体 |

这张表背后的判断和市场侧需求是对得上的。老作者和平台作者工具已经证明，他们在意的是**数据、版本、发布、回看**；分镜工具证明画面创作者在意的是**镜头一致性、审批和导出**；互动叙事工具证明世界状态与分支管理是地基。citeturn15view4turn15view5turn11view1turn11view2turn14view2turn11view5turn7search2turn7search15

⚠️ **代价与风险**：补这些件最大的代价不是多几个字段，而是**要守住“大纲唯一真账”不被搞散**。我建议做法是：

本体只收“跨下游都不能丢的叙事事实和状态”；

镜头和互动这种强消费格式，尽量放在**具名视图合同**；

可视控制和人工复核，放在**画布与挂靠点**。

这样才不会把本体越做越肥，最后又回到“大纲什么都装，谁都看不懂”。这点从 Sudowrite 把 Story Bible 当 source of truth、再用 Canvas 和生成界面做用户入口，也能看出同样的经验。citeturn13view0turn13view1

## 质疑清单

你要求“有怀疑必须单列说清楚”，下面是我认为**值得认真怀疑**的点。我不是说它们一定错，而是说**现在就该压测证伪**，不然会在后面成本更大时爆雷。

| 条目 | 我的怀疑 | 为什么怀疑 | 用什么证据能证伪 |
| --- | --- | --- | --- |
| T1 中间层只保留“章末快照 + 章内变化流 + 章间交接”，薄切片全部派生 | **我有中度怀疑** | 这套对线性网文正文很顺，但对分镜 / AI 漫剧 / 互动叙事，部分“关键帧语义”未必能稳定从厚描派生出来，尤其是镜头重点、视觉锚点、选择瞬间的状态显著变化 | 拿同一本书跑“正文→大纲→分镜”，看镜头级关键帧的一次派生可用率；如果高于你们目标阈值，说明 T1 站得住，否则要补视觉锚点或镜头视图合同 |
| T3 Hook 账挂编排侧，本体只留引用和状态 | **我有中度怀疑** | Hook 是商业网文最值钱的“读者想看账”，如果它和事件 / 状态事实 / 规则之间耦合不够深，后续改文时很容易出现 Hook 活着、兑现条件却已经死了 | 做“改前文 / 挪章节 / 改规则”三类编辑压测，测 change_keys 巡检对 Hook 漂移的召回率；能稳定抓住大多数漂移，再说分离是安全的 |
| T7 体验合同是“每章出合同” | **我有中度怀疑** | 章级合同很适合连载，但商业网文的疲劳控制、套路去重和中期兑现，很多是跨 3～10 章窗口发生的；只做章级，容易把近一章写顺、把后面写紧 | 用 30～50 章中长样本做 A/B：纯章级合同 vs 章级 + 弧线级合同，比较套路重复、兑现延迟和作者改稿次数 |
| T10 黑盒外不可插手，只给挂靠点 | **我有轻到中度怀疑** | 小白可能不在乎，但老作者和工作室很在乎“我能不能看懂系统为什么这么改”。如果挂靠点不够“真能插手”，黑盒会被理解成不透明 | 看提取和生成的采纳率，以及用户是否频繁导出后去外部改，再导回；如果大量绕开主流程，说明黑盒边界画得太死 |
| T12 AI 管道单方案省 token | **我有中度怀疑** | 单方案对正文补写可以省，但对题材选择、章末钩子、分镜风格、互动选项这类高分歧任务，用户经常需要比较两个方向，不是一个方向 | 在“导入点子→首轮章纲 / 分镜”阶段做单方案 vs 双方案测试，测用户接受率和后续改动量；如果双方案明显更高，就别在关键决策点硬省 token |

🧩 **补一句总判断**：我**没有看到要推翻 T1～T12 的致命证据**。也就是说，我不是怀疑整套框架，我怀疑的是**某几条在新形态和多下游压力下，会不会少了中间承重件**。这属于“现在就该做证伪实验”的怀疑，不是“整套路子不对”的怀疑。你们“大纲为唯一中枢格式”的大方向，我认为仍然成立，尤其在 IP 多端转化背景下更有价值。citeturn15view0turn15view2
