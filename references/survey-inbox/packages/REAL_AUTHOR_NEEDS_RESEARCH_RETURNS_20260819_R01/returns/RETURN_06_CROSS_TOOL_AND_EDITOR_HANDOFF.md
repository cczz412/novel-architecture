# 小说项目建立后的往返交接事故：发布、返稿、外部 AI 与小团队边界

## 结论摘要

✅ **这轮研究能完成与现行 127 条预期的逐条排重。** 三个附件都可读；`CURRENT_ATOMIC_EXPECTATIONS_R01.json` 明确声明自己是 127 条现行原子预期的本地脱网排除表，规则也写得很清楚：同一个使用时机、作者目标和失败后果只是换个说法，不能算新需求；只有时机、目标或失败后果真的变了，才可以提候选。工作台同时明确，作者隔离、原子提交、崩溃恢复、本地/云存储替换、版本身份等已经在现有设计边界内。fileciteturn0file0 fileciteturn0file1 fileciteturn0file2

研究后的核心判断是：

**真正还没有被 127 条充分覆盖的，不是“再做一套版本控制”，而是“内容离开作者工作区以后，这一次外部交接到底发生了什么”。**

现有预期已经很强地覆盖了：

> `工作区里的哪一版 → 系统内部下一站拿到哪一版 → 作者确认 → 改稿后旧结果失效 → 原子保存与恢复`

现实事故集中在另一侧：

> `哪一版被交给了谁/哪个平台/哪个 AI → 对方基于哪一版做了什么 → 作者到底采纳了什么 → 哪一版真的发出去了 → 外部世界现在看到的是什么`

这两者不能混为一件事。现有 `revision + SHA + author confirmation` 能证明**内部对象身份**，却不能单独证明“编辑批的是不是你刚发给他的那一版”“平台定时队列里是不是你以为的那章”“AI 看过哪些未发布材料”“恢复本地备份以后线上章节有没有跟着恢复”。这是本轮最重要的增量。

我建议把本轮发现压成 **五个近期候选方向、两个团队分支方向**，但都只是候选需求，不是施工授权：

| 候选方向 | 适用路径 | 建议赛道 | 是否单人作者主路径 |
|---|---|---|---|
| **发布交接清单＋发布回执** | 作者工作区 → 平台 | 近期 | **是，中文连载最强** |
| **线上状态对账＋修订/撤回单独记账** | 作者工作区 → 平台 | 近期 | **是，中文连载最强** |
| **外部返稿“先比较、再应用”** | 作者 ↔ 编辑 | 近期 | **是，但取决于是否有编辑** |
| **外部意见从建议到采纳/拒绝的状态账** | 编辑、AI → 作者 | 近期 | **是，覆盖面比编辑单一路径更大** |
| **外部 AI 出入境记录＋敏感内容提醒** | 作者 ↔ 外部 AI | 近期条件分支 | **是，但仅 AI 用户** |
| **小团队交接单：谁交给谁、谁最终拍板** | 共同作者/合法小团队 | 未来分支 | 否 |
| **多人返稿按同一底稿合并，而不是“最新文件名赢”** | 编辑群/共同作者 | 未来分支 | 否 |

反过来，下面这些**不要因为本轮公开材料又出现，就重复加需求**：

**旧版不能冒充当前版、章节改稿后旧事实失效、作者可以反悔、事实确认留历史、故障后不能留下半套、备份恢复不能倒拨版本链、原始上传字节保留、不同作者隔离、JSON/Markdown/ZIP 导出不漏内容、AI 推断不能冒充事实**——这些都已经能在现行 127 条里找到直接对应项。fileciteturn0file1 fileciteturn0file2

公开证据也给出了一个很清楚的优先级差异：**中文连载作者的“工作区 → 发布平台”是主路径；2～5 人共同作者不是。** 番茄目前专门有官方帮助解释定时章节为什么持续审核、为什么发布时间改不了、为什么到了时间还没有发布；另有独立帮助处理章节发错卷、已定时章节能否调序等问题。这说明“本地稿写对了，但平台交接状态错了”已经是平台需要专门解释的一类现实问题，而不是抽象工程担忧。citeturn23view0turn23view1

研究执行时点是 **2026-08-18（America/Montreal）**；两个原子预期附件自身标记的快照日期是 **2026-08-19（Asia/Shanghai）**。公开网页只采用本轮已经实际可访问的版本，不把尚未可验证的 2026-08-19 新材料当作已发生事实。fileciteturn0file1turn0file2

## 与现行预期的逐条排重

这一步非常关键，因为很多表面上像“新需求”的事故，其实已经被现有库覆盖。

现行 JSON 共 **127 条：78 条核心、49 条附加，44 条要求真实小说材料**。工作台也明确说这批内容是“设计与验收候选库的本地镜像”，不是合同、施工票或产品完成证明。fileciteturn0file0turn0file2

下面按本轮最容易重复的主题排掉。

| 本轮外部研究看到的现象 | 现有直接对应 | 排重结论 |
|---|---|---|
| “别把旧稿当新稿” | `M1-E06`；`AE-X-C02` | **已有，只补证据** |
| 编辑回来一份旧底稿，可能覆盖当前稿 | `M1-E06` 只覆盖内部版本身份；`M4-C04` 覆盖章节改稿后事实失效 | **“旧版保护”已有；“外部返稿对哪一底稿”仍可新增** |
| 作者接受/拒绝某个结论 | `M5-C01/C02/C03` | **事实候选场景已有** |
| 作者以后改口 | `M5-C03` | **已有** |
| 改稿导致旧证据失效 | `M4-C04`、`M5-C05` | **已有** |
| 写一半崩溃、恢复不能半套 | `AE-AW-C03/C04`、`AE-X-C05` | **已有** |
| 恢复旧稿不能把版本史倒回去 | `M4-C04` | **已有** |
| 不同作者/小说不能串数据 | `M4-C06`、作者工作区隔离项 | **已有** |
| 外部 AI 的猜测不能成为事实 | `M4-C05` | **已有** |
| 导出 JSON/Markdown/ZIP 不丢卡片、不乱序 | `AE-M10-B01/C05` | **已有** |
| 导入 Word、ZIP 时不静默丢内容 | `M1-E01/B03` | **已有，但只覆盖“进入项目”** |
| Excel/CSV 材料 | `M1-N01` | **已有，不因本轮再出现而新增** |
| 灵感/建议是否进入正式规划由作者决定 | `M8-E06` | **已有内部语义** |
| 改动后概览过期 | `M9-E04` | **已有** |
| 团队交接这个大方向 | `M9-E09` 已点到团队 relay | **不能把“支持团队”本身算新需求** |

真正不同的地方在“使用时机”和“失败后果”。

举个最容易混淆的例子：

`AE-X-C02` 已经要求内部交接文件带版本和 SHA，不能靠“去目录里找最新文件”。fileciteturn0file1turn0file2

但作者把 `chapter_037 r18` 复制到平台草稿箱，平台后来显示审核中、定时失败，或者作者误把它放进了错误卷，这时问题已经不是“内部文件有没有版本号”，而是：

> **哪一个内部 revision 被提交给了哪个平台对象？平台现在实际是什么状态？**

番茄官方帮助当前确实把“章节发错卷”“已设置定时发布后调序”“后面的章节一直审核中”“到时间没有发布”列成具体问题。citeturn23view0turn23view1

所以“发布交接记录”可以成为新候选；再建一套内部 revision 则不能。

另一个容易误判的是编辑批注。

现有 `M5-C02/C03` 已经知道“作者确认/驳回/后来改口”应该有状态和历史；但这里的对象是**事实候选**。fileciteturn0file1turn0file2

真实编辑流程里的对象却可能是：

> “第三章铺垫太少，建议把父亲失踪的线索提前。”

这不是事实候选，也不能一键变成正文。它有一个独立生命周期：

> **外部建议 → 作者判断 → 全采纳 / 部分采纳 / 不采纳 → 某次正文 revision**

这就是不同对象、不同使用时机、不同失败后果，可以提新候选。

🔥 **所以排重后的边界可以浓缩成一句话：现有 127 条管得很好的是“项目里面的真值和版本”；本轮新增机会主要在“跨出项目边界的交接事件”。**

## 四类交接路径里的真实事故

### 作者工作区到发布平台

这是证据最强、也最应该放在单人作者主路径的一类。

番茄在 2025 年底专门发布章节调序帮助，直接列出“章节发错卷”“已设置定时发布的章节能不能调整顺序”等问题；2026 年的定时发布帮助又单列“后面章节一直审核中”“发布时间为何改不了”“到时间没发布”等避坑问题。2026 年的长篇发文规则还把“新增提交发布（含修改）”一起计入可提交发布字数。这说明对于连载作者，“写完稿”与“平台真正完成发布/修改”之间不是一个瞬间动作，而是有平台自己的对象、队列、审核和额度状态。citeturn23view0turn23view1turn23view2

公开作品中甚至能找到作者把章节标题直接写成“跳过这个章节哈，发布错了”的单例。它只能证明事故确实发生过，不能证明普遍率，但非常直接地说明“错误内容已经外显给读者”不是理论风险。citeturn21search4

最危险的混淆有四个：

**本地 current ≠ 平台草稿 current ≠ 平台待审核 current ≠ 读者已经看到的 live。**

如果产品只记“我的第 37 章现在是 r18”，仍然回答不了：

> 平台上的第 37 章到底是 r17 还是 r18？

也回答不了：

> r18 是已经提交、审核中、定时等待，还是已经真的对读者可见？

这就是为什么我把“发布交接清单”和“线上状态对账”分成两个候选。前者回答“我送了什么出去”，后者回答“外部世界后来变成了什么”。

当前作者能做的补救大多很笨：平台草稿箱里再确认一次、查看定时状态、检查章节顺序、发布后再去作者端或读者端核对；出错后再修改、调序或找平台帮助。这里“作者会逐项手工检查”是从现有平台状态和帮助入口推出来的工作流推断，不是一个有代表性的用户调查统计。番茄官方页面能证明这些状态和修复问题真实存在，却不能告诉我们有多少作者每天遇到。citeturn23view0turn23view1

**重复发布**这一项要诚实一点：本轮没有找到足够强的 2023–2026 中文作者公开材料，能证明它是高频普遍事故。重复提交/重试从机制上当然可能发生，但不能因为“工程上可能”就写成“作者经常这样”。因此应把“防重复提交”放在发布交接候选的验收反例里，而不是凭这轮研究单独升成高频核心需求。

**撤回与修改**则有更实的证据：至少在番茄现行规则里，“修改”也是发布提交的一部分，而不是纯本地操作；发布以后再改，已经触及平台状态。citeturn23view2

所以本轮新增真正重要的不是“自动发布”，而是：

> **作者点击外部发布前，知道送出去的是哪一版；送出去以后，知道平台实际上接收成了什么。**

这完全可以研究成立，而不产生任何平台接入或自动发布授权。

### 作者到编辑

这里的证据形态和网文平台不同。

中国作家网 2025 年《流转》改稿会记录得很具体：作者、责任编辑、出版社编辑和多名专家一起审读，一名专家从主题、情节架构、人物塑造、语言风格提出意见，另有人建议调整结构和叙述视角；作者表示会拿专家意见认真对照修改。2024 年《极顶》改稿会同样是多位编辑、专家对结局、人物动机、章节设计、结构和语言给修改方向，作者回应的是“认真思考修改方向、优化章节内容”，而不是“别人说什么就自动写进稿子”。citeturn23view3turn23view4

这给了一个很重要的产品边界：

**合法编辑合作的基本单位不是“多人都能改正文”，而是“别人可以提出修改，作者仍然要做决定”。**

这和“必须做多人协作平台”完全是两回事。

当这种意见通过 Word/WPS 文件往返时，工具机制本身会把问题暴露得更清楚。Microsoft 的官方 Word 支持文档直接假设了一种现实场景：文档发出去审阅后，可能收回很多含建议和修订的副本，因此要指定“原始文档”和“修订后的文档”合并；对于没有作者标记的改动，还允许人为给它填一个名字，用来知道是谁建议的；更多副本还可以继续合并。citeturn23view5

这只是英文通用工具的**对照证据**，不能直接推成“中国作者普遍都这样”。但它很好地证明了交接机制中的几个天然身份：

> 原始底稿是谁、返稿基于谁、这一处改动是谁提的、多个返稿如何保持各自身份。

WPS 公开用户问答里也能看到“文档被覆盖成旧版本”“云文件丢失/被其他版本覆盖”之后去历史版本或备份恢复的补救路线。WPS 自己注明这类页面是用户交流内容、不是官方筛选案例，所以证据强度只能算中低；不过它至少证明“去历史版本找回被覆盖内容”是现成的现实绕路。citeturn15view0turn15view1turn15view2

这里最麻烦的事故不是“Word 不能保存”，而是：

> `终稿.docx`、`终稿-编辑改.docx`、`终稿-编辑改-作者改.docx`、`终稿最终2.docx` 都是合法文件，但没有人能仅凭文件名保证哪个才是作者当前认可版本。

这正是现有内部 SHA/revision 很难单独解决的地方——因为文件一离开工作区，对方并不知道内部 revision 的意义；文件返回时也可能混入批注、修订、未开启修订模式的正文改动。

Microsoft 的另一份官方支持文档也说明文档可能包含隐藏数据和个人属性，并提供 Document Inspector 用于检查和移除它们。对小说作者来说，这意味着“发正文给外部”除了正文泄密，还可能存在作者姓名、属性或其他隐藏信息的外发风险；但公开材料不足以证明这在中国小说作者中属于高频事故，所以应作为**分享前风险检查项**，不能夸大为高频主诉。citeturn23view7

至于“批注在 Word/WPS/格式转换中丢失”的**中文小说项目级公开故障样本，本轮证据不够强**。工具存在批注、修订、合并功能能证明这些元数据重要，却不能证明小说作者经常因转换而丢批注。因此更稳妥的需求写法不是“必须解决高频批注丢失”，而是：

> **返稿如果包含系统无法完整识别的批注、修订或审阅元数据，就明确告诉作者哪些能保留、哪些不能，不静默把一份审阅稿当普通正文覆盖进去。**

这是候选，证据强度中等，而且与 `M1-B03/E01` 的首次导入损失报告有较高排重风险。它之所以仍可能成立，是因为这里发生在**项目建立后的审阅往返**，失败后果是“作者不知道编辑意见消失了”，不是“首次导入正文少了字”。

### 共同作者和合法小团队

这一条要明显降温。

本轮没有找到足够强的 2023–2026 中文长篇/网文公开样本，能支持“2～5 人共同作者频繁同时改同一本小说，因此需要完整权限系统”这样的结论。

现有附件自己也已经在 `M9-E09` 点到了团队交接，因此“以后能给团队看”这个大方向本身也不是新发现。fileciteturn0file1turn0file2

作为机制对照，Word 官方之所以提供多个返稿副本合并，是因为同一底稿可能返回多份不同修改；OneDrive 官方也说明，当多人或多台设备同时更改同步对象、尤其出现离线修改时，可能产生同步冲突，典型保存办法是把其中一个版本改成不同名字，让两个版本都留下。citeturn23view5turn17view2

这说明一个通用风险：

> “谁最后保存”不是“谁拥有最终创作决定”。

但这仍只是英文通用协作工具的对照，**不能外推为中国网文作者的高频需求**。

所以这里近期不应该做：

❌ 完整角色权限树  
❌ 实时多人共同编辑  
❌ 成员邀请、席位、组织管理  
❌ 复杂审批流  
❌ “编辑可以直接改作者真值”的多人写权系统

更合理的未来候选只是一个很轻的**交接单**：

> 谁把哪几章的哪一版交给谁；对方是建议者还是被授权改稿者；最终决定归谁；什么时候返还；回来的是建议还是正式替换稿。

当同一个底稿回来两三份返稿时，再有一个“每份返稿保持来源身份，作者自己决定如何合并”的分支即可。

这解决的是**身份混淆**，不是建协作平台。

### 外部 AI 工具往返

这一条与编辑有相似地方，但多了一个编辑没有的风险：**内容已经被交给另一个数据处理方。**

DeepSeek 当前可访问的官方隐私政策明确列出其可能收集用户输入的文本、提示、上传文件、反馈和聊天历史，并说明会用信息来提供、改进和开发服务及训练/改进相关技术和模型；政策同时提醒用户谨慎考虑自己发送的信息，并说明相关数据保留和服务器处理安排。citeturn23view8turn23view9

这不等于“作者上传的每一部小说一定会被拿去训练”，也不能把一个供应商的政策外推到所有 AI 工具。它能证明的是：

> **把未发布小说、秘密设定、编辑意见、合同备注复制到外部 AI，不再是纯本地处理。**

所以现有 `M4-C05` “AI 推断和作者事实身份不同”仍不够。fileciteturn0file1turn0file2

那条预期回答的是：

> AI 说的东西算不算故事事实？

新的问题回答的是：

> 我到底把什么小说材料交给了哪个外部 AI？回来这段文字又源自哪一次外部会话？

这两个目标不同，可以单独成候选。

中国平台还有一个特别重要的现实后果：AI 使用状态可能影响平台审核。晋江 2026 年公开作品页面已经出现系统处罚信息，明确标注“AI文字辅助—叙事级别”并要求章节清理，同时伴随黄牌和榜单限制；晋江公开论坛中也有作者围绕如何证明 AI 痕迹、AI 检测结果、原稿证据进行申诉讨论。直接作品系统通知的证据较强，论坛用户说法只算行为材料，不能拿来代替正式规则全文。citeturn18search0turn18search1turn18search10

论坛里还有作者担心把作品再次上传到 AI 检测服务本身会带来版权/数据暴露风险。这个只能证明**作者有这种顾虑**，不能证明检测平台真的把小说拿去训练。citeturn18search11

这使“AI 前原稿”出现了一个以前没有的外部身份意义：

> 它不只是备份，还可能成为作者解释创作过程、回到人工稿或处理平台争议时的重要参照。

但这里也要排重：**保存旧 revision、恢复时不倒拨版本链**已经属于现有预期。新增的只能是“这一版是否属于某次外部 AI 处理之前/之后、哪段输出被作者真正采纳”的外部来源标签，而不是再造备份系统。fileciteturn0file1turn0file2

反例也很明确：作者使用完全本地离线模型，或使用平台自身集成并已经有明确数据边界的助手时，外部披露风险会不同。因此这不该绑死在所有作者主路径里，而应该是**使用外部 AI 时自动出现的条件分支**。

## 一条意见从外部建议走到作者决定，哪里最容易乱

公开中文资料很少会把“某一条具体编辑意见 → 作者最终改了哪几个字 → 为什么没采纳另一条”完整公开，所以不能假装找到了一条全程可审计的真实生产日志。

但《流转》的公开改稿过程已经能追到很有价值的一段。

专家明确指出小说有些前后因果过于简单、关键处突兀，可以增加铺垫和伏笔；作者公开表示会对专家的意见认真对照修改。citeturn23view3

《极顶》的公开记录则给了一个很好的反例：专家给了很多具体结构、结局、人物、语言建议，作者的回应是接下来“认真思考修改方向”，并不是公开承诺“每条建议全部照做”。citeturn23view4

所以现实里最健康的一条状态链不是：

> 编辑建议 → 自动修改正文

而应该是：

> **外部建议 → 作者看到建议及其底稿 → 作者决定 → 如果采纳，产生新的正文 revision；如果不采纳，正文不变，但意见和决定仍有历史。**

拿《流转》那条“关键因果太突兀，需要增加铺垫”做一个**不伪造最终稿结果的结构追踪**：

| 环节 | 应该知道什么 | 最容易混淆什么 |
|---|---|---|
| 外发 | 作者发送的是 `第八章 r17` | 文件名叫“终稿”却不知道真实 revision |
| 建议产生 | 某编辑/专家针对 r17 的某一段提出“增加铺垫” | 评论人的身份与转发文件的人被混为一人 |
| 返稿 | Word 批注、修订，或微信一句话回来 | 批注锚已经因为作者同时改稿而漂移 |
| 作者判断 | 待定 / 采纳 / 部分采纳 / 不采纳 | “看过”误当成“采纳” |
| 采纳 | 从 r17 当前稿产生 r18；该意见关联到具体改动 | 直接覆盖 r17，后来不知道这段为何改 |
| 不采纳 | 正文不变，意见保留为 rejected/declined | 删除评论以后，看起来像从没讨论过 |
| 再改稿 | r19 又重写这一段 | 老批注被错误贴到相似句上 |
| 发布 | 平台收到 r19 或其他 revision | 本地 current 和线上 live 混为一版 |

其中 Word 官方的返稿合并机制也明确依赖“原始文档”和“修订文档”，还要求能标识是谁提出未标记的改动，这正好说明**建议身份和底稿身份必须同时存在**。citeturn23view5

🔥 整条链上最容易混淆的，其实不是文字，而是下面六种“谁是谁”：

**文件身份**：`最终稿.docx` 是文件名，不是版本身份。

**底稿身份**：一条批注是在 r17 上提出的，不代表它在 r19 仍然指向同一个意思。

**建议身份**：编辑提出“增加铺垫”，它仍然只是 proposal，不是作者已经接受的创作事实。

**决定身份**：作者今天接受，明天可以改变判断；现有 `M5-C03` 已经证明项目内部也需要保留这种历史。fileciteturn0file1turn0file2

**内容身份**：AI/编辑建议的文字，被作者采纳、重写后，不能继续简单标成“外部输出原文”；同时也不应把外部来源历史抹掉。

**发布身份**：工作区当前稿、平台待审稿和读者当前看到的稿，是三个可能不同步的对象。番茄的审核、定时发布和章节调序帮助已经直接展示了这种状态差异。citeturn23view0turn23view1

这里最有价值的产品原则不是“把所有工具连起来”，而是：

> **每一次跨边界交接都要能回答：谁把哪一版的什么交给了谁，对方回来了什么，作者后来怎么决定，外部现在是什么状态。**

## 候选需求与近期、未来赛道

下面的 `RC-*` 只是本研究为了方便讨论临时起的标签，**不是新增正式原子预期编号，也不修改现行 127 条权重。**

### 近期应继续验证的候选

| 临时候选 | 大白话定义 | 为什么不是现有条目换皮 | 证据判断 |
|---|---|---|---|
| **RC-PUB-A｜发布交接清单** | 每次准备发平台时，明确平台/作品/卷章、章标题与顺序、源 revision/SHA、准备立即/定时发布；留一份“我当时送出去的是什么” | `AE-X-C02` 只管内部文件交接；这里失败后果是**错误内容公开** | **强**：平台官方帮助直接出现发错卷、调序、定时问题。citeturn23view0turn23view1 |
| **RC-PUB-B｜外部实际状态回执与对账** | 区分“本地最新”“已提交”“审核中”“定时等待”“已公开”“修改中/已撤回”，发现不一致只报警，不自动重发 | 内部 revision 不能证明线上 live 是哪版 | **强-中强**：平台官方明确存在审核、定时、修改等独立状态；实际发生频率未知。citeturn23view0turn23view2 |
| **RC-REV-A｜返稿先比较、后应用** | 编辑返来的 Word/WPS 不是直接覆盖当前稿；先找它原来基于哪一版，再把正文改动、批注、修订分别展示给作者 | `M1-E01/B03` 管首次导入；这里是**已经建好的小说出去一圈又回来** | **中强**：中国长篇改稿过程真实；Word 有明确原稿/返稿合并机制；WPS 有旧版覆盖后的历史恢复行为。citeturn23view3turn23view4turn23view5turn15view0 |
| **RC-REV-B｜外部意见状态账** | 每条编辑/AI建议保留来源、底稿 revision、锚点、建议内容；作者决定待定/全采纳/部分采纳/不采纳；采纳后指向产生的正文 revision | `M5` 管事实候选审查，不管编辑对正文的修改意见 | **中强**：专业改稿会直接证明“外部意见→作者判断/修改”的工作方式；逐条最终采纳日志公开证据不足。citeturn23view3turn23view4 |
| **RC-AI-A｜外部 AI 出入境记录＋敏感提醒** | 送 AI 前说清这一轮要外发哪些正文/设定/未揭示秘密；记工具、时间、用途、材料范围；回来以后保留会话来源，作者只把明确接受的部分变成新 revision | `M4-C05` 只区分 AI 推断与作者事实；这里管**内容已经交给第三方**和返稿来源 | **中强**：AI 服务官方隐私政策直接证明输入/文件属于外部处理数据；中国平台的 AI 审核又让“AI 前后稿”具有额外意义。citeturn23view8turn23view9turn18search0 |

其中 **RC-PUB-A、RC-PUB-B** 最像中文连载作者的高频主路径。

**RC-REV-A、RC-REV-B** 对传统长篇、出版型作者和已经有责任编辑的网文作者很重要，但不能说每个连载作者每天都会用。

**RC-AI-A** 很可能越来越重要，但公开资料不足以估计“多少中文长篇作者经常把整章往外部 AI 来回搬”。所以它应该是条件分支，而不是强迫所有作者走一次“AI 审核流程”。

### 未来的小团队分支

| 临时候选 | 只解决什么 | 为什么暂时不升单人主路径 |
|---|---|---|
| **RC-TEAM-A｜交接单和最终决定人** | 发送人、接收人、交接范围、底稿 revision、对方是建议者还是被授权改稿者、最终拍板者 | 中国小说项目公开资料不足以证明共同作者是大多数人的高频模式；附件也已经有团队 relay 大方向 |
| **RC-TEAM-B｜多个返稿按底稿合并** | 两三个编辑/共同作者都从同一版返稿时，保留各自身份，不靠“谁文件时间最新谁赢” | 目前强机制证据主要来自 Word 等通用英文协作工具，只适合做对照，不能直接外推中国作者。citeturn23view5turn17view2 |

这两条即使未来成立，也**不等于多人权限系统**。

近期根本不需要因为它们去设计成员角色树。交接记录里先能表达：

> “编辑甲可以提意见，但作者 CZ 做最终决定”

就已经解决了很大一块真实混乱。

### 暂时不要提成正式候选的东西

**手机备忘录、表格、作者工作区之间自动双向同步。** 七猫等作者工具确实已经提供历史版本、多端同步和随记类能力，版本记录里甚至有过特定机型连接蓝牙后内容清空并修复的记录；这些足以证明作者端存在多端材料和恢复需求，却不能证明“手机备忘录 ↔ 表格 ↔ 小说项目自动双向合并”已经是中文作者的普遍主诉。竞品功能也只能证明功能存在。citeturn23view10

所以这里更合理的是**继续收真实作者样本**，不急着加“万能同步”。

**平台 API 自动发布。** 当前研究证明的是“发布交接事故存在”，不是“必须自动对接平台”。

**实时多人协作。** 证据不足，而且用户主路径不要求。

**细粒度多人权限。** 这已经越过本轮研究边界。

**AI 代写、AI 检测规避、平台规则规避。** 不在本研究合法工作流里，也不应从灰色讨论反推产品能力。

| 重要结论 | 原始来源与适用角色 | 失败后果 | 现在常见绕路 | 反例 / 限制 | 证据强度 |
|---|---|---|---|---|---|
| **平台发布是独立状态机，不等于本地保存成功** | 番茄官方定时发布帮助；连载作者。citeturn23view0 | 章节仍审核、到点未发、作者误以为已上线 | 作者端反复查看状态、等审核、人工排查 | 不是每次发布都会出错 | **强：官方当前帮助** |

| **外部 AI 会形成新的数据披露边界** | DeepSeek 官方隐私政策；使用外部 AI 的作者。citeturn23view8turn23view9 | 未发布正文、秘密设定、批注进入第三方处理环境 | 少传材料、只给必要片段、人工留原稿与会话记录 | 不同 AI 服务政策不同；本地 AI 不同 | **强：对该服务的数据边界** |

| **共同作者的并发合并需求存在机制风险，但中国普遍性未知** | Word/OneDrive 通用协作对照。citeturn23view5turn17view2 | 多人修改冲突、最新文件名覆盖别人的修改 | 保留副本、手动合并、指定一人收稿 | 缺中国长篇共同作者规模证据 | **中低，未来分支** |

一个很重要的反例也必须保留：

**并不是所有外部交接都值得“结构化管理”。**

作者把两段文字发给熟悉编辑，编辑回一句“这里节奏慢了”，作者当场改掉，生命周期十分钟，硬让他填写十个字段只会比微信更难用。

所以即使做 `RC-REV-B`，高频交互也应该极轻：

> 建议是谁提的 → 依附哪一版 → 作者点“采纳 / 部分采纳 / 不采纳” → 修改以后自动关联新 revision。

其余原因、备注、详细比较可以展开看，而不是强迫填写。

同理，发布清单也不应该变成“发一章填一张报关单”。系统已经知道平台、作品、章节和当前 revision 的情况下，应自动生成，作者只检查高风险差异。

## 研究边界、未知项与产品判断

这轮研究能下的结论，有几条很明确。

**中文连载作者近期最值得验证的是发布前后身份。** 官方帮助已经证明调序、发错卷、审核、定时失败、修改发布等问题存在。citeturn23view0turn23view1turn23view2

**长篇作者近期最值得验证的是返稿和意见状态。** 中国真实改稿项目证明，合法编辑关系通常是“多人给意见，作者再修改”，并不要求所有参与者直接拥有正文写权。citeturn23view3turn23view4

**外部 AI 应被看成一种特殊的“外部返稿方”，同时多一层数据披露。** 它给出的建议仍需要作者决定；而作者把材料发送出去这一动作本身需要能被理解和回溯。citeturn23view8turn23view9

**小团队可以研究交接，不应倒逼多人平台。** 现阶段够用的问题是“谁拿了哪一版、回来什么、谁拍板”，不是组织、席位和复杂权限。

有几件事仍然**未知，不能写成已经验证的高频需求**：

**重复发布到底多常见**：本轮有错发章节、错卷、定时/审核问题的实证，但没有足够公开样本估计重复发布率。

**中文作者批注丢失到底多常见**：格式和审阅元数据确实存在，返稿合并也确有机制需求，但中文小说项目公开事故样本不足。

**Word、WPS、手机备忘、表格之间谁才是多数作者的真实主稿中心**：竞品功能和零散支持材料不能回答分布。

**多少中国网文作者会把未发布全文送入外部 AI**：当前没有足够可靠样本，不能凭行业热度猜比例。

**共同作者规模**：本轮不足以证明 2～5 人共同写长篇是值得放进默认主路径的模式。

**编辑返稿的逐条最终采纳率**：公开改稿报道会公布建议和作者后续修改意愿，但很少公开“建议 A 最终接受、建议 B 拒绝、建议 C 部分接受”的生产日志。citeturn23view3turn23view4
