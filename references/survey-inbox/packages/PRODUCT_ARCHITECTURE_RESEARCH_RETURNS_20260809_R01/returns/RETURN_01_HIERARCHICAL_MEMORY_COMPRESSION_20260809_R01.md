## 结论

✅ 你们已定方向是对的，但要改一个关键定义：

> “远期历史压成一句带 ID 的事实”只能是常驻上下文里的导航视图，不能成为那段历史唯一剩下的记忆。

较稳的行业路线不是“摘要金字塔”和“事实库检索”二选一，而是：

**冻结原文与证据 → 结构化事实库 → 多粒度派生摘要 → 当前任务反向检索 → 必要时回捞原文。**

这与项目现有的[真值分层](sandbox:/workspace/scratch/de1104bdd5af/project_sources/08-02_SYSTEM_ARCHITECTURE_AND_TRUTH_LAYERS-2-.md)和[创作记忆管线](sandbox:/workspace/scratch/de1104bdd5af/project_sources/04-03_CREATION_AND_MEMORY_PIPELINES-2-.md)一致：压缩层负责省上下文，不负责改写真值。

公开研究没有给出通用的“旧 10 章压到多少字最好”。能找到的是特定任务、模型和预算下的数据。所以下面的比例应当视为起跑参数，再用你们自己的连续性任务调优。

## 递归摘要与事实检索怎么选

### 纯递归摘要金字塔

优点是上下文稳定、容易看全局故事弧、成本可预测。

风险是摘要不断重写后，细节、否定、知情范围、因果中间节点和人物状态最容易消失。[BooookScore](https://arxiv.org/html/2310.00785v4)发现，层次摘要比持续改写的运行摘要更连贯，例如 GPT‑4 为 89.1 对 82.5，但层次摘要保留的细节更少；运行摘要较详细，却更容易产生连贯性错误。

[FABLES](https://arxiv.org/html/2404.01261v2)在 26 本近期长篇小说、3,158 条摘要主张上发现，GPT‑4 只有 78.15% 主张被判为完全忠实，Claude 3 Opus 为 90.89%。不忠实内容中，人物／关系状态占 38.6%，事件占 31.5%，恰好是续写最不能丢的两类信息。

所以，根摘要适合回答“这条故事线大致讲了什么”，不适合回答“角色此时到底知道什么”。

### 纯结构化事实库＋检索

它在证据追踪、修订失效、时间有效期和状态覆盖方面明显更强，但也会丢掉语气、隐含动机及跨句语境；检索查询写错时，事实即使存在也捞不到。

[LongMemEval](https://arxiv.org/html/2410.10813v2)给出一个很有用的结果：

- 原始 round 作索引键：Recall@5 为 0.582；
- 只用抽取事实：0.530；
- 原始值＋事实作为多个索引键：0.644。

论文汇总显示，多键索引平均让 Recall@k 提升 9.4%，最终回答准确率提升 5.4%。这支持“事实句是检索键和紧凑证据”，不支持“事实句永久替代全部原语境”。

### 混合方案

推荐分工如下：

- 摘要、章节胶囊：让模型知道该往哪里找；
- 结构化事实：回答状态、规则、因果与连续性；
- 原文证据：处理争议、细腻语境和高风险生成；
- 当前任务包：只装本场真正需要的部分。

ReadAgent、RAPTOR、MemGPT、LongMemEval 和 DOME 的有效方案都具有这种多层保留特征。

## 旧伏笔和细节该怎么捞

小说场景没有单一检索方式能稳定最高召回。较合理的顺序是：

**实体/时间/故事线硬召回 → BM25 与上下文化向量扩召 → 一跳因果图扩展 → 重排去重 → 按故事时间送入模型。**

[NarCo](https://arxiv.org/html/2402.13551v1)用“当前段落由哪个早先段落解释”的回顾边，将《巴黎圣母院》检索 nDCG@10 从 23.97 提至 27.37。[SitEmb](https://aclanthology.org/2026.acl-short.5/)在七部长篇小说上，让 Recall@10 从普通 chunk embedding 的 43.57 升至 63.03，但它用了专门训练，不能把全部收益归因于上下文。[E²RAG](https://aclanthology.org/2026.eacl-long.90/)则发现一跳实体—事件扩展优于 2、4、8 跳，说明深扩图很容易带入噪声。

| 任务                     | 主检索通道                                | 补充通道                   |
| ------------------------ | ----------------------------------------- | -------------------------- |
| 人物身份、别名、物品归属 | `entity_id / alias_id` 精确匹配           | 向量召回不同表述           |
| 当前人物状态             | 实体＋`valid_from/to`＋`supersedes`       | 最近一次状态变化证据       |
| 旧故事线回归             | `storyline_id`＋上次离场/交接场景         | 故事线摘要、场景 embedding |
| 伏笔与回收               | 显式 `setup_id → payoff_id` 或 obligation | 一跳因果边、语义扩召       |
| 人物知情范围             | `knowledge_holder_ids`＋得知时间          | 对话／观察证据             |
| 时间与因果顺序           | `story_time`、叙事顺序、cause/effect      | 相邻场景和原文片段         |
| 作者记不起关键词         | 上下文化向量＋BM25                        | 实体、时间和故事线重排     |

对预先设计的伏笔，不应期待 embedding 自动猜中。作者或大纲确认伏笔时，直接建立 `setup_id`、预期 `payoff_id/storyline_id` 和生效条件。没有标注的旧细节才交给向量做候选发现。

现阶段也不必引入图数据库。关系表、边表、外键和递归 CTE 足够承载一至两跳因果扩展，这与项目的[当前工程决策](sandbox:/workspace/scratch/de1104bdd5af/project_sources/07-05_CURRENT_DECISIONS_AND_OPEN_QUESTIONS-2-.md)一致。

## 推荐的三层＋召回参数

下面所有“压缩比”只指送入模型的派生视图。事实记录与原文证据不删除、不按此比例压缩。

记忆包起跑上限可设为：

[
B_{\text{memory}}=\min(0.25\times \text{可用输入窗口}, 14{,}000\text{ tokens})
]

也就是 16k 输入约 4k，32k 约 8k，64k 以上先封顶约 14k，再画预算曲线。一个近期章节生成研究使用了约 6.4k–7.0k 的混合故事信息包，可作数量级参照；其中下一章梗概来自金标准未来章节，所以不能把其效果直接当生产结果。[论文](https://arxiv.org/html/2503.22828v1)

以 32k 输入、8k 记忆包为例：

| 区域       | 预算              | 建议内容                                                     | 迁移规则                             |
| ---------- | ----------------- | ------------------------------------------------------------ | ------------------------------------ |
| 当前层     | 3,200 tokens，40% | 本章已写部分、上一场结尾、本章完整事实、入场状态、当前人物知情范围 | 本章锁定后转入近期层；事实保持 1:1   |
| 近期层     | 1,600 tokens，20% | 默认最近 3 章；同一活跃故事线时扩至 5 章。每章保留 15–30 条状态差量、承诺、揭示和直接因果 | 起跑压缩约 4:1；测试 3:1、4:1、5:1   |
| 远期常驻层 | 800 tokens，10%   | 只载入 10–20 个当前相关胶囊；每个胶囊正文约 40–80 汉字，附覆盖 fact IDs | 起跑测试 20:1；同时比较 10:1、40:1   |
| 按需召回   | 2,000 tokens，25% | 最终 8–15 条事实＋2–6 段原文证据；保留时间顺序               | 每场重新编译，不永久写回真值         |
| 元数据余量 | 400 tokens，5%    | 标题、ID、排序、冲突提示和去重余量                           | 超额时先减弱相关软召回，不删钉住事实 |

远期层不应“一章永远只有一句”。更稳的做法是：

- 每章保存一条总览胶囊；
- 多故事线章节另存 1–3 条故事线／因果胶囊；
- 常驻上下文只载入当前相关者；
- 所有胶囊都带 `covered_fact_ids`，可以回到事实和原文。

### 固定钉住，不自动降级

以下内容即使相隔几十章，也不按距离自动移出：

- 不可逆人物或世界状态；
- 仍生效的世界规则、能力限制和禁令；
- 未履行承诺、债务、倒计时、触发条件；
- 活跃伏笔的起点和预计回收点；
- 与当前场景有关的知情差异；
- 当前故事线的上一次交接，即使发生在三十章前。

### 压缩与重建触发

- 正文章节锁定后：候选事实升格、生成近期视图和远期胶囊；
- 每个场景生成前：重新编译任务包；
- 事实修订时：按 `covered_fact_ids` 标记相关摘要过期并重建；
- 近期层默认在三个完整章节后降级，但同故事线仍活跃时延后；
- 不在上下文快满时临时递归改写旧摘要。

关键字段可包括：`fact_id`、`source_span`、`source_sha`、`chapter_id`、`scene_id`、`story_time`、`entity_ids`、`storyline_ids`、`cause_ids/effect_ids`、`setup_id/payoff_id`、`knowledge_holder_ids`、`obligation_id`、`valid_from/to`、`supersedes`、`irreversible`、`covered_fact_ids`、`view_version`、`stale`。

## 怎么量化压缩损失

不要只看生成出来的文章“读起来顺不顺”。应把损失拆开：

[
\Delta_{\text{write}}
= S(\text{金标准证据})-S(\text{完整压缩存储})
]

[
\Delta_{\text{retrieval}}
= S(\text{完整压缩存储})-S(\text{实际召回包})
]

也就是分别回答：

- 写入、抽取或摘要时，事实是否已经消失；
- 事实仍在库里，但任务检索是否没有捞到。

这是近期 [WhenLoss](https://arxiv.org/html/2605.24579) 采用的测量思路。另一项压缩引用研究发现，内容保留率降至 20% 时，ROUGE-Lsum 只下降 2.19 点，但引用召回从 50.10 跌到 10.95；只看文风和摘要分数会严重低估证据损失。[研究](https://aclanthology.org/2026.customnlp4u-1.19.pdf)

建议建立 80–120 个真实“未来依赖”样本，按距离分成 1–3、4–10、11–30、30 章以上，覆盖：

- 实体与别名；
- 状态更新和否定；
- 时间顺序；
- 人物知情范围；
- 规则与触发条件；
- 因果首尾；
- 伏笔和承诺回收；
- 无答案／应拒答。

对照组至少包含：

1. 金标准相关证据；
2. 全历史或截断全文；
3. 纯递归摘要；
4. 纯事实检索；
5. 三层＋混合召回；
6. 混合召回去掉因果边、去掉向量的消融组。

核心指标：

- Critical Fact Recall@固定 token 预算；
- 原文证据 span recall、fact-ID recall；
- 因果链首尾完整率；
- 人物知识泄漏率；
- 时间／状态／关系矛盾率；
- 伏笔或 obligation 命中率；
- 摘要无证据主张率、修改后的过期视图率；
- prompt tokens、成本和 P95 延迟。

可先采用这些工程门槛，明确它们不是论文给出的行业标准：

- 钉住事实载入率 100%；
- 关键远期事实 Recall@budget ≥95%；
- 全部依赖事实 Recall@budget ≥90%；
- 经人工裁决的远期胶囊无证据主张率为 0；
- 修改后过期视图残留率为 0；
- 相同 token 预算下，混合方案比纯摘要提高至少 5 个百分点关键事实召回，并显著降低硬连续性错误。

## 人类作者与商业产品怎么维护 Bible

人类行业要区分推介 Bible 和生产连续性 Bible。[Final Draft](https://www.finaldraft.com/blog/10-easy-steps-to-developing-your-tv-show-bible)给出的 5–20 页是推介材料尺度，不能当作长期记忆压缩比例。

生产 Bible 更像持续增长的台账：

- 人物、地点、物品、组织、规则各有独立卡页；
- 另有时间线、关系表、集／章摘要；
- 草稿事实先作为候选，最终正文或成片锁定后才成为 canon；
- 条目可细到生日、过敏、亲属和宠物名；
- 来源页码或剧本位置跟随事实保存。[Scriptation 指南](https://scriptation.com/blog/tv-show-bible-and-character-bibles-guide/)

Brandon Sanderson 团队的私人 wiki 为人物、地点、生物和魔法能力分别建页，并保留页码引用；其连续性编辑称通常约 30 秒可以查到答案。[官方 FAQ](https://faq.brandonsanderson.com/knowledge-base/how-do-you-remember-all-the-details-to-keep-all-the-little-bits-and-pieces-consistent/)

商业工具里最接近这套设计的是：

- [Novelcrafter Codex](https://www.novelcrafter.com/help/docs/codex/guidelines-for-descriptions)：简单实体建议 1–3 句，主角或核心地点约 3–4 段；[Progressions](https://www.novelcrafter.com/help/docs/codex/progressions-additions)让状态变化从指定场景起才对 AI 可见。
- [Sudowrite Saliency Engine](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/saliency-engine/4KL8gFeLZNvk8CEeXpfwB2)：从 Story Bible 中挑当前任务相关的卡和特征；Series Folder 支持跨书共享与里程碑版本。
- Plottr、Campfire、LivingWriter主要证明实体卡、时间线、关系和侧栏捞取已成为常见产品模式。

这些产品没有公开 Story Bible 压缩比、检索召回率或使用前后的连续性错误率。产品机制可以借鉴，效果宣称不能替代你们自己的实验。

## 较少争议的共识与待验证项

较少争议：

- 原文与证据必须可回溯；
- 摘要只能是派生视图；
- 原始值＋事实索引优于只保留其中一种；
- 时间有效期、故事线和人物知情范围要显式表达；
- 长上下文不能消除检索噪声；
- 证据召回比“文章看起来流畅”更能暴露压缩损失。

仍需用真实小说数据验证：

- 近期保留 3 章还是 5 章；
- 近期层 4:1、远期视图 20:1 是否合适；
- 8k 记忆包是否适配最终采用的模型；
- BM25／向量候选数和中文 embedding 阈值；
- 一跳还是两跳因果扩展；
- 自动重要性评分是否会漏掉低频但关键伏笔。

因此，当前方案可以继续推进，但产品定义应写成：

> 远期历史在常驻上下文中压成带 fact IDs 的短胶囊；完整事实与冻结原文始终保留并可按任务回捞。
