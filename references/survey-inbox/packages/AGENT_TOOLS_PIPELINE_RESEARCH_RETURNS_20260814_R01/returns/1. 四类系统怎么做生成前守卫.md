✅ 结论：你们 A、C、D 的方向是对的；B“事实句关键字”必须降级成召回器，只负责找可能相关的材料，不能直接判冲突。

还缺三块：

- 覆盖凭证：检查器到底查了哪些、没查哪些、用了哪个事实版本。
- 证据验真：事实编号和原文锚必须由程序复核，不能相信模型自己填写。
- 隐藏草稿复检：没有具体选项，就不可能检查这个选项撞没撞事实。生成前只能得到“允许范围”；生产模型产出隐藏草稿后，还要由另一套检查器复核，作者通过后才看见。

我没有读取附件。下面只采用你给出的“已拍”约束和外部公开资料。架构部分是我把这些机制迁移到小说生产场景后的工程判断。

## 1. 四类系统怎么做生成前守卫

| 系统          | 硬检查层                             | 相关资料核对层                       | 小模型适合放哪                 | 对你们的启发                    |
| ------------- | ------------------------------------ | ------------------------------------ | ------------------------------ | ------------------------------- |
| 游戏引擎      | 状态、标签、资源、冷却、动作前置条件 | 只调用声明“我能检查这个对象”的验证器 | 通常没有，小模型最多做体验建议 | “动作可执行”与“动作体验好”分开  |
| 叙事引擎      | 变量、条件、访问次数控制选项是否出现 | 只筛当前条件相关的 storylet/分支     | 可给剩余分支排序，但不改资格   | 先过滤不合法选项，再谈戏剧性    |
| 政策/规则引擎 | 结构化输入与确定性策略               | 规则索引、触发匹配、按请求切相关数据 | 不宜参与硬授权                 | 决策、执行、审计必须分离        |
| 代码 linter   | 语法树、变量作用域、控制流           | 只跑启用的规则、增量检查改动范围     | 风格、可读性等软判断           | 确定错误报 error，不确定报 warn |

Unreal 的验证接口会明确区分 `Valid`、`Invalid` 和 `NotValidated`，没执行验证不能冒充通过；其技能激活也会先检查资源和要求，但官方文档还明确说，激活尝试可能在后续阶段失败，甚至出现前置检查的假阳性。[Unreal 验证接口](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/EditorValidatorSubsystem?application_version=5.4)、[Unreal 技能激活接口](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AbilitySystemComponent?application_version=5.0)

Ink 用变量条件控制选项是否出现；Yarn Spinner 的 storylet 策略也是先剔除条件不满足的内容，再用 saliency——可以理解成“当前更值得出现的程度”——挑选剩余内容。[Ink 条件选项](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)、[Yarn Storylets 与 Saliency](https://docs.yarnspinner.dev/yarn-spinner-for-unity/samples/storylets-and-saliency/basics-storylets-and-saliency)

规则引擎也不会把全部规则塞进一次自然语言提示。OPA 建议使用索引语句和部分编译，Drools 会等规则所需输入齐全后再把它加入待执行队列。Cedar 更进一步：限制规则能沿关系访问多深，再从请求涉及的实体出发切出相关数据；在满足限制时，这个切片与读取全部数据会得到同一判断。[OPA 性能指南](https://www.openpolicyagent.org/docs/policy-performance)、[Drools 规则求值](https://docs.drools.org/8.38.0.Final/drools-docs/docs-website/drools/rule-engine/index.html)、[Cedar 数据切片](https://docs.cedarpolicy.com/policies/level-validation.html)

ESLint 把规则分成 `error` 和 `warn`：可能有假阳性、需要人工判断的规则适合 `warn`，不会阻断流程。[ESLint 严重程度](https://eslint.org/docs/latest/use/configure/rules)

### 延迟和漏报怎么取舍

🔥 不要用同一个阈值同时追求“少漏报”和“少误报”。正确做法是两段式：

1. 找线索时偏高召回：宁可多捞一些相关事实、规则和历史事件。
2. 升红灯时偏高精度：主体、时间、极性、状态都对齐，两端都有确认锚，才允许成为硬冲突。

具体分三条通道：

- 硬规则通道：字段、状态机、明确时间关系。放在阻断路径，超时或缺字段就返回“缺什么”，不能返回 OK。
- 检索核对通道：按人物、地点、物件、动作类别、秘密、时间窗切片。多捞出来的噪声交给后续复核，没捞到只能写“覆盖范围内未检出”。
- 小模型通道：动机、节奏、情绪、套路感。并行运行；超时写 `MISSING` 或 `UNCHECKED`，不能偷偷当 OK。

Kubernetes/Gatekeeper 也把这个取舍写得很直白：检查服务失败时，选择放过会提高可用性但削弱约束，选择拒绝会加强约束但可能阻塞工作；阻断式 admission 和周期性 audit 因而分开。[Gatekeeper 失败策略](https://open-policy-agent.github.io/gatekeeper/website/docs/v3.7.x/customize-admission/)、[Gatekeeper 审计](https://open-policy-agent.github.io/gatekeeper/website/docs/operations/)

建议长期盯五个数：

- 相关规则召回率：已知冲突案例里，该触发的规则有没有被叫到。
- 红灯准确率：红灯里多少真是硬冲突。
- 检查覆盖率：应查项目与已查项目的比例。
- 逃逸率：作者看到后才发现的硬冲突比例。
- 各层 P95 延迟：95% 请求能在多长时间内完成。

## 2. 子 Agent 只回 OK，怎样才可靠

结论很直接：让模型裸回一个 `OK`，无法证明它真的检查过。

可以让主 Agent 最终只看到 OK，但后台必须保存逐项回执。最稳的分工是：

- 编排程序提前给出必须检查的谓词清单，检查器不能自己缩小范围。
- 小模型逐项返回“支持 / 冲突 / 未知”和证据编号，不允许自己填写总结果。
- 普通程序核对事实编号是否存在、原文片段是否匹配、版本是否一致、检查项是否齐全。
- 普通程序再压缩成主 Agent 看到的 `OK / MISSING / ISSUES`。
- 放不放行由固定策略决定，不由任何检查器决定。

这是给主 Agent 看的最小回执：

```json
{
  "job_id": "J-2041",
  "result": "OK",
  "scope_note": "在 story_rev=R42、规则包=W17、12 个指定检查项内未检出",
  "coverage": {
    "expected": 12,
    "checked": 12,
    "unknown": 0,
    "not_run": []
  },
  "receipt_ref": "receipt://J-2041",
  "receipt_hash": "sha256:..."
}
```

发现问题时，每条问题建议保留这些字段：

```json
{
  "class": "HARD_CONFLICT",
  "predicate_id": "character.mobility.current",
  "proposal_anchor": {
    "option_id": "O2",
    "atom_id": "A3"
  },
  "fact_anchor": {
    "fact_id": "F-184",
    "source_rev": "R42",
    "source_span": "chapter_19:p_7",
    "quote_hash": "sha256:..."
  },
  "reason_code": "CURRENT_STATE_CONTRADICTION",
  "message": "选项写人物徒步追赶，但当前有效状态为无法负重行走"
}
```

不要给检查器这些字段：

- `allow_generation`
- `approved`
- `green`
- `block_recommendation`

这些都带有签字意味。检查器只报观察结果，编排程序按固定表处理。

### OK 也需要证据指针吗

需要，但不必把全部原文塞给主模型。

- 对硬规则：后台保存每个检查项读取过的事实 ID、事件 ID、状态值和版本。
- 对检索检查：保存查询条件、命中文档范围、遗漏或读取失败列表。
- 对语义检查：保存支持证据和反证证据的锚。
- 对主 Agent：只给覆盖摘要、回执地址和哈希。

问题项必须带短原文锚。OK 项不必把几十段原文展开，但必须能追溯到完整清单。

⚠️ “有引用”仍不等于“判断正确”。GopherCite 的研究明确指出，证据引用只是可信策略的一部分，被某段材料支持的说法仍可能不是真的；因此还要检查引用是否真的支持该判断。[GopherCite 论文](https://arxiv.org/abs/2203.11147) 将长输出拆成原子事实再逐项核对，也比整段打一个总分更可靠。[FActScore 论文](https://arxiv.org/abs/2305.14251)

### 防止编造 OK 的具体措施

- 回执的 `job_id`、快照版本和覆盖数量由程序注入，不让模型填写。
- 模型只能引用系统发给它的事实 ID；不存在的 ID 直接判回执无效。
- 原文锚由程序做精确片段或哈希校验。
- 任一项为 `unknown`、超时、读取失败，整体不能变成 OK。
- 回执与故事版本绑定；事实更新后旧 OK 自动失效。
- 抽取模型、质检模型、生产模型分别记录家族，编排程序拒绝不符合隔离要求的组合。
- 成对比较选项时交换顺序再跑一次；结论翻转就降为待复核。研究已确认模型评委存在位置偏差和偏爱同类模型文本的问题。[位置偏差研究](https://arxiv.org/abs/2406.07791)、[自偏好研究](https://arxiv.org/abs/2410.21819)
- 用人工标好的陷阱集定期测，不采用模型自报的置信度当准确率。

结构化 JSON 只能保证字段形状，不能保证字段里的判断是真的，官方文档也明确说明这一点。[Structured Outputs 局限](https://openai.com/index/introducing-structured-outputs-in-the-api/)

## 4. 关键字匹配与知情状态机

### 关键字只能拿来找候选材料

常见陷阱有：

- 同名和别名：“小林”可能是两个人，“先生”可能随场景变化。
- 否定范围：“他没有杀人”命中了“杀人”，含义却相反。
- 时间状态：“腿受过伤”不等于现在仍不能走；痊愈事件会终止旧状态。
- 假设、计划、梦境：“如果她死了”“他梦见她死了”都不是死亡事实。
- 归属对象：“她说弟弟受伤了”，受伤者不是“她”。
- 引语和传闻：人物说过不等于叙事确认。
- 指代和省略：“他把它交给她”必须先解出三方实体。
- 提及不等于动作：“想起那把枪”不等于持枪或开枪。
- 新事实覆盖旧事实：不能取最后一次出现关键词的句子，要按有效时间和确认状态选当前记录。

ConText 这类自然语言检查算法会把否定、假设、历史状态和“发生在谁身上”分开处理，说明单关键词远远不够。[ConText 论文](https://pmc.ncbi.nlm.nih.gov/articles/PMC2757457/)

建议把关键字流程固定成：

> 关键词／别名召回 → 实体消歧 → 极性与语气判断 → 时间定位 → 当前状态查询 → 两端证据核对

中间任一步不确定，都只能成为待复核线索。

### 知情状态不要做成一个超级枚举

“秘密已暴露／公开／A 误信／B 怀疑／读者不知道”混成一个字段，很快就会组合爆炸。

更稳的是把不同问题拆开：

| 记录               | 只回答什么                                 |
| ------------------ | ------------------------------------------ |
| `truth`            | 这条秘密的客观内容与确认状态是什么         |
| `disclosure`       | 在什么时间，通过什么事件，向谁披露过       |
| `reader_knowledge` | 某读者群当前是已知道、不知道、还是被误导   |
| `character_belief` | 某人物知道、明确不知道、怀疑或相信错误版本 |
| `valid_time`       | 这条状态从什么时候生效，何时失效           |
| `evidence`         | 原文锚、事实编号和版本                     |

读者硬账可以保持很小：

```json
{
  "audience_id": "reader_main",
  "secret_id": "S-12",
  "state": "KNOWN | UNKNOWN | MISLED",
  "believed_value": "仅在 MISLED 时必填",
  "anchor_id": "A-991",
  "valid_from": "chapter_18",
  "valid_to": null
}
```

人物账可以多一个明确的 `SUSPECTS`，但仍必须有显式台词、行为或事件锚。读者“大概猜到了”单独放进软提示表，不能进入 `reader_knowledge`。

状态变化用事件表达，例如：

- `DISCLOSE`
- `MISINFORM`
- `CORRECT`
- `MAKE_PUBLIC`
- `RETRACT`
- `RECOVER_FROM_INJURY`

当前状态由事件顺序和有效时间算出，不给每种组合单独命名。Statecharts 用分层状态和并行区域处理彼此独立的状态维度，正是为了避免平铺状态数量失控。[W3C SCXML 并行状态](https://www.w3.org/TR/scxml/)、[Harel Statecharts 原论文](https://www.wisdom.weizmann.ac.il/~harel/papers/Statecharts.pdf)

## 5. 哪些必须生成前，哪些可以稍后跑

| 时点                       | 必须完成                                                     | 可以推迟                                                     |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 生产模型动笔前             | 快照完整性、实体消歧、当前状态、时间线、人物与读者硬账、场景级世界规则、作者硬约束、证据切片 | 长周期风格审计、全书模板相似度                               |
| 隐藏草稿产生后、作者看见前 | 动作原子抽取、精确事实冲突、动作级世界规则、状态转移、明确泄密、硬回执完整性 | 动机细腻度、选项吸引力、轻微节奏问题                         |
| 作者看见选项时异步运行     | 不应再有尚未运行的硬检查                                     | 长距离情绪重复、机械套技巧、假选择、读者可能猜到多少、全库抽样审计 |

🔥 硬冲突检查不能等作者看见后再跑。可以晚跑的是黄灯和用于发现触发器漏报的全库抽样审计。

有一个边界必须说清：没有具体选项时，系统只能检查“这个场景允许人物做什么”，无法检查“这个选项具体撞了什么”。所以合理流程是：

> 生成前检查允许范围 → 生产模型写隐藏草稿 → 独立检查器核对具体动作 → 作者看见合格选项

主模型最终只需拿到：

- 当前允许的动作范围；
- 不得违反的硬约束；
- 触发的世界规则；
- 少量相关事实锚；
- 黄灯提示；
- 覆盖回执摘要。

不需要读取 200 多条事实，也不应得到一句未经证明的“确定无冲突”。
