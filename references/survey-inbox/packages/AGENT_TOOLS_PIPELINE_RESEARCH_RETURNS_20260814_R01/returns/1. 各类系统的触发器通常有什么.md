✅ 结论：**“同一套触发器外壳、不同业务载荷”可行，也很适合你们；但统一的是匹配与投影管线，不是把世界规则、义务、Hook、计划塞进同一张业务表。**

建议守住这几条边界：

- Hook 与义务必须分表。它们的状态、权限、完成含义都不同。
- 计划输入和已发生事实必须分通道。计划可以让 Hook 变得“相关”，但不能让义务“已兑现”。
- 触发器只负责：亮灯、进入执行包、提高材料优先级，以及在明确配置时阻止某个工作流动作。
- 触发器不能：写入故事事实、把计划标成发生、自动判定兑现/违约、自动开卡。
- 章号最多以后做导航位置，不能进入触发条件语义。

## 1. 各类系统的触发器通常有什么

公开系统没有一份统一的“触发器国际标准”，但结构非常相似。

| 系统          | 稳定的核心                           | 常见扩展                                               | 对你们最有用的启发                                     |
| ------------- | ------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------ |
| 规则引擎      | 输入事实、`when` 条件、`then` 后果   | 启用、优先级、规则组、互斥组、防循环、时间窗、定时重复 | 条件、范围、优先级、重复控制要分开                     |
| 事件路由      | 事件来源、类型、主题、字段模式、目标 | 过滤器、投递策略、状态                                 | 先按事件类型和对象缩小候选，再跑完整条件，不能全表扫描 |
| 游戏 Quest    | 追踪对象、目标值、作用玩家、完成结果 | 重置、持久化、个人/团队范围、HUD 显示、标题和描述      | “语义范围”和“谁看得见”是两回事                         |
| Ink           | 条件、变量、内容访问次数             | 默认一次性选择、可重复选择、距上次访问的回合数、标签   | 一次性/可重复不是条件本身，是激活策略                  |
| Twine/Harlowe | Storylet 条件                        | 紧迫度、互斥度、当前是否开放、调试面板                 | 作者应能直接看见“哪些条件现在开放”                     |
| 商业叙事工具  | 条件、变量、流程节点                 | 条件与修改指令分开、模拟、前值/现值、失败子条件        | 条件要可解释，不能只返回一个真假                       |

具体来看：

- Drools 的规则最少是条件和动作；另外提供 `enabled`、优先级、规则组、互斥组、`no-loop`、生效/失效时间、延迟、定时重复等字段。这里的 `no-loop` 只是防止规则因自己的结果反复触发，**不等于“一生只触发一次”**。[Drools 规则语言参考](https://docs.drools.org/8.39.0.Final/drools-docs/docs-website/drools/language-reference/index.html)
- EventBridge、Knative 都是先按事件来源、类型、主题等元数据过滤，再把匹配事件交给目标。这个做法正好能解决“准确拿 Hook，不扫描全部世界规则”的问题。[Amazon EventBridge 事件模式](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-event-patterns.html)、[Knative Trigger](https://knative.dev/docs/eventing/triggers/)
- Fortnite 的 Tracker 包含追踪指标、目标值、个人/团队范围、重置和持久化，以及是否显示在 HUD、显示什么标题和进度。[Fortnite Tracker 文档](https://dev.epicgames.com/documentation/fortnite/using-tracker-devices-in-fortnite-creative)
- 游戏系统里的“冷却”通常是额外的激活限制，而不是条件内容。Unreal 的 Gameplay Ability 就把能否激活、阻止标签、冷却期分开处理。[Unreal Gameplay Ability System](https://dev.epicgames.com/documentation/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system)
- Ink 有条件选择、内容访问次数、`TURNS_SINCE`，并明确区分默认一次性选择和可重复的 sticky choice。[Ink 官方写作指南](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)
- Harlowe Storylet 有开放条件、紧迫度、互斥度，调试面板会列出当前是否开放及其条件。[Twine Storylet 文档](https://twinery.org/cookbook/storylets/harlowe/harlowe_storylets.html)、[Harlowe 手册](https://twine2.neocities.org/)
- articy:draft 把“判断条件”和“修改变量的指令”明确分开；模拟时还能显示哪个子条件为假。Arcweave 调试器则显示当前节点及变量修改前后的值，并限制调试信息只对编辑者等角色可见。[articy 条件与指令](https://www.articy.com/help/Scripting_Conditions_Instructions.html)、[articy 模拟模式](https://www.articy.com/help/Presentation_Simulation.html)、[Arcweave 调试器](https://docs.arcweave.com/project-tools/play-mode/debugger)

综合判断，真正普遍的最小骨架是：

1. 触发器是谁、是否启用。
2. 监听哪类输入。
3. 满足什么条件。
4. 条件适用于什么故事范围和对象。
5. 匹配后把什么载荷交给谁。
6. 当前匹配结果及证据。

一次性/重复、预热、冷却、可见性都建议有，但地位不同：

- **一次性/重复**：常用，而且应明确建模。
- **冷却**：常用，但主要控制重复激活或提醒频率。
- **谁可见**：应放在投影策略里，不能混进故事条件。
- **预热**：在这些样本里很少是触发器原生字段，更适合做“尚未匹配但距离阈值已近”的独立状态。

## 2. 统一外壳可行，但业务表不能合并

可以把公共层理解成“一张只管判断和提醒的触发器表”。

| 层                                     | 是否统一 | 放什么                                             |
| -------------------------------------- | -------- | -------------------------------------------------- |
| `trigger_specs` 触发器定义             | 统一     | 输入、条件、范围、重复、预热、冷却、输出、文案     |
| 世界规则表                             | 分开     | 规则正文、例外、适用世界范围、版本                 |
| 义务表                                 | 分开     | 义务人、权利人、产生事件、期限、兑现/违约/豁免状态 |
| Hook 表                                | 分开     | 埋设意图、回收条件、保密范围、是否已埋/已回收      |
| 未来计划表                             | 建议分开 | 安排、目标事件/故事时间、选中状态、被替代或取消    |
| `trigger_evaluations` 评估记录         | 统一     | 某次为什么匹配、用了哪些事件和状态                 |
| `active_indicator_projection` 当前投影 | 统一     | 画布和 CLI 共同读取的“现在正在生效”列表            |

公共触发器通过 `payload_ref = {kind, id, version}` 指向业务对象。一个义务、Hook 或世界规则可以拥有多个触发器，例如“提前一天预热”“正式到期”“尝试违规动作时停下”。

这个做法和 CloudEvents 很像：事件使用统一的 `id/source/type/subject/time` 外壳，具体业务内容放在 `data` 中；统一外壳没有把不同业务事件变成同一种东西。[CloudEvents 规范](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)

Hook 和义务必须分表，原因很具体：

- 义务有“产生、开放、到期、兑现、违约、豁免”等状态。
- Hook 有“构思、埋设、现在可用、计划回收、实际回收、放弃”等状态。
- “义务已兑现”和“Hook 已回收”看起来都像完成，实际所需证据、权限和后续影响完全不同。
- 义务通常属于故事事实层；Hook 很可能是作者私密规划。
- Hook 被选入执行包，不能因此变成“已埋”；义务存在一个回收计划，也不能因此变成“已兑现”。

同理，计划和实际事件不能共用一个 `occurred=true/false` 字段。领域事件在通行定义里表示“过去已经发生的事”；计划属于意图或安排。[微软 Domain Events 说明](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation)、[CloudEvents Primer](https://github.com/cloudevents/spec/blob/main/cloudevents/primer.md)

建议明确分三个输入平面：

- `story_actual`：已经确认发生的故事事件和当前故事状态。
- `author_plan`：作者安排、候选事件、已选计划。
- `author_context`：作者当前正在编辑的地点、人物、主题和动作。

从计划进入事实，应另有明确的 `realization_link`，把计划项链接到一个已确认的实际事件。触发器不能自己创建这条链接。

统一外壳能避免：

- 同一个“加冕礼后三日”在不同表里被解释成不同时间。
- 有的模块按事件 ID 匹配，有的靠模糊文本搜索。
- Hook、CLI、画布各自重写一套判断。
- 一次性、重复和冷却语义到处不一样。
- 作者看到亮灯，却查不到为什么亮。
- 每次为了找 Hook 扫描全部世界规则。

它也会带来几类风险：

- 用一个通用 `status` 抹平“到期”“可回收”“规则生效”等不同含义。
- 把计划条件误送进事实触发器。
- 用通用 `action` 偷偷修改事实。
- 作者私密 Hook 通过调试或 CLI 泄漏。
- 用简单的 `repeatable: true/false` 表达不了“每个对象一次”“每次易主一次”。
- 做出一张大量空字段的“大宽表”，数据校验越来越弱。

## 3. 怎样同时让程序能匹配、作者能看懂

其实核心就一件事：**条件树和解释证据必须来自同一份结构，不能一边写机器表达式，一边另写一段可能过期的说明文字。**

推荐把条件存成只读的“条件树”，每个最小条件都有稳定 ID：

```yaml
all:
  - clause_id: event_type
    source: latest_event
    path: type
    op: eq
    value: artifact.possession_transferred
    explain: 刚发生的是宝物易主事件

  - clause_id: artifact
    source: latest_event
    path: subject
    op: eq
    value_ref: artifact.tianheng_seal
    explain: 易主对象是天衡玺

  - clause_id: new_owner_lineage
    source: current_state
    path: person[$event.to].lineage
    op: contains
    value: fallen_royal
    explain: 新主人具有亡国王裔身份
```

这类表达式必须只读、无副作用。CEL 一类嵌入式表达式语言就是这个方向：程序只读取宿主提供的数据，不能在判断过程中修改状态。[CEL 官方说明](https://cel.dev/)

每次评估应产生结构化结果：

```yaml
status: active
reason_kind: all_clauses_matched
as_of_event_id: evt_8402
as_of_story_time: 赤历312年·冬至夜
snapshot_id: state_991
matched_event_ids: [evt_8402]
clause_trace:
  - clause_id: event_type
    expected: artifact.possession_transferred
    actual: artifact.possession_transferred
    result: true
```

作者看到的是证据投影，不是这些字段：

> 现在生效的是「王印认主」；因为刚发生的易主事件把天衡玺交给沈雁，而当前状态记载沈雁具有亡国王裔身份。已放入本次执行包；系统没有自动写入“认主成功”。

建议固定成四段：

1. **现在是什么状态**：生效、到期、相关、预热。
2. **因为哪些证据**：实际事件、当前状态、故事时间或作者计划上下文。
3. **工作流发生什么变化**：亮灯、入包、优先级提高、动作被护栏拦住。
4. **什么没有发生**：未写事实、未标兑现、未标回收、未开卡。

成熟工具也在走“结果＋原因”的方向。LaunchDarkly 的评估结果会返回 `reason`，区分规则匹配、前置条件失败、默认分支和错误；articy 会高亮失败子条件，Arcweave 会显示变量修改前后的值。[LaunchDarkly Evaluation Reasons](https://launchdarkly.com/docs/sdk/concepts/evaluation-reasons)

⚠️ 缺数据不能默认为 `false`。建议评估结果至少有：

- `match`
- `no_match`
- `unknown`
- `error`

尤其是“期限已到但没有兑现事件”这种否定条件，作者文案应写：

> 已发生事件账本中尚无归还记录。

不要擅自写成：

> 他没有归还。

前者是系统掌握的证据，后者已经在断言故事事实。

## 4. 预热、黄灯和停点怎么分工

这三者不应是同一个严重度滑块，而是三个不同工作流动作。

| 层级 | 语义                                           | 界面方式                               | 是否打断       |
| ---- | ---------------------------------------------- | -------------------------------------- | -------------- |
| 预热 | 条件还没满足，但距离明确阈值已近               | “即将相关”区域、淡色标记、执行包预备区 | 不打断         |
| 黄灯 | 条件已经满足，当前写作应该看见它               | 亮灯并进入本次执行包，提高材料优先级   | 不强制停下     |
| 停点 | 作者正在执行一个会违反硬规则或跨越真值层的动作 | 在动作提交前显示原因、证据和处理选项   | 会停下当前动作 |

🔥 世界规则生效时可以一直亮黄灯；只有作者真的尝试“用凡火打开月蚀中的镜门”时，才出现停点。不能因为规则存在就不停弹窗。

预热只适合有明确“距离”的条件：

- 距义务到期还剩一个故事日。
- 三项前置条件已满足两项。
- 计数达到 4/5。
- 当前计划已经包含地点和人物，只差指定主题。

这些条件不应预热：

- 一个普通布尔条件目前为假。
- 模糊语义搜索觉得“也许相关”。
- 数据缺失导致无法判断。
- 作者仅仅浏览过某条规则。

还要区分两件容易混淆的事：

- **预热**：条件仍为假，只是接近。
- **稳定等待**：条件已经为真，但要持续一段时间才通知。Grafana 把后者称为 Pending，用来过滤短暂波动；这不是你们所说的预热。[Grafana 告警状态](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/)

避免垃圾提醒可以定几条硬规则：

- 只在状态发生变化时提示：未接近→预热、预热→生效、证据明显改变。
- 相同 `activation_fingerprint` 不重复弹，只更新现有投影。
- 同一因果根或同一故事线的多个提醒合并显示。
- 预热默认不发弹窗，只进入画布上的“即将相关”区域。
- 允许“延后到某故事事件”“延后到某故事时间”，不用“延后三章”。
- 进入和退出预热使用不同阈值，避免故事时间来回修订时闪烁。
- 页面只显示最相关的少量条目，其余折叠为数量。
- 只有作者现在能采取行动的信息才升级提醒。Google SRE 对告警的经验也很直接：会打断人的提醒必须对应明确行动；相似提醒应分组，否则很快会被忽略。[Google SRE 监控原则](https://sre.google/sre-book/monitoring-distributed-systems/)、[Grafana 通知分组](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/group-alert-notifications/)

冷却也建议拆成两种：

- **语义冷却**：多久以后才允许形成新的激活，例如“同一宝物再次易主后才重新激活”。
- **展示节流**：匹配依然被记录，但同一工作会话里不重复提醒。它不能改变触发器真假。

## 5. 触发器外壳字段建议

⚠️ 下面是调查后的建议稿，不是你们已冻结的字段合同。

| 用途           | 建议字段                                                     | 含义                                                         |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 标识和版本     | `trigger_id`、`schema_version`、`revision`、`enabled`        | 稳定引用、迁移、启停                                         |
| 指向业务载荷   | `payload_ref.kind/id/version`                                | 指向世界规则、义务、Hook 或计划；不复制业务状态              |
| 隔离输入真值层 | `input_plane`                                                | `story_actual`、`author_plan`、`author_context`，禁止隐式跨层 |
| 选择候选输入   | `input_mode`、`selector`                                     | 事件、状态、故事时间、历史序列、作者上下文；先按类型、对象缩小候选 |
| 限定语义范围   | `scope`                                                      | 故事、故事线、地点、人物、宝物、世界区域、有效故事时间窗     |
| 完整判断       | `condition.type/tree`                                        | `event_match`、`state_predicate`、`story_time`、`sequence/count`、`absence_by_deadline`、`context_match` |
| 处理缺数据     | `unknown_policy`                                             | 推荐产生诊断，不把未知当作假或真                             |
| 激活方式       | `activation_mode`                                            | `edge`：新事件/假转真时激活；`level`：条件为真期间持续生效   |
| 一次性和重复   | `repeat_policy`、`activation_key`、`rearm_on`                | 一生一次、每对象一次、每事件一次、条件退出后重新武装         |
| 预热           | `warmup.metric/enter/exit`                                   | 距离必须可计算；进入和退出阈值分开                           |
| 冷却           | `cooldown.basis/value/until_event`                           | 按故事时长、事件数量或指定故事事件；不按章号                 |
| 包内排序       | `attention_tier`、`priority`、`exclusive_group`              | 只影响材料排序和互斥，不影响故事真值                         |
| 输出           | `effects[]`                                                  | 只允许亮灯、入包、提高优先级、动作护栏                       |
| 谁能看         | `audience`、`redaction`                                      | 作者本人、协作者角色、管理员 CLI；理由和证据也要受权限控制   |
| 出现在哪       | `surfaces`                                                   | 画布、执行包、CLI、调试界面                                  |
| 作者文案       | `title`、`active_template`、`warm_template`、各条件 `explain` | 文案使用实际绑定值生成                                       |
| 可检索依赖     | `compiled_dependencies`                                      | 从条件树编译出的事件类型、实体 ID、状态路径；供索引使用      |
| 调试信息       | `debug_tags`、`condition_hash`                               | 查版本和条件是否漂移                                         |

输出建议只开放三种：

```yaml
effects:
  - kind: indicator.raise
  - kind: execution_package.include
    priority_boost: high
  - kind: action.guard
    actions: [draft_fact_commit]
    enforcement: require_override
```

明确禁止这些输出：

```yaml
fact.write
plan.mark_realized
obligation.mark_fulfilled
obligation.mark_breached
hook.mark_seeded
hook.mark_paid_off
card.create
```

“刚发生的事件”建议至少提供：

- `event_id`
- `event_type`
- `subject`
- `source`
- `story_time`
- `data`
- `schema_version`
- `record_class=occurred`

“当前状态”建议至少提供：

- `snapshot_id`
- `as_of_event_id`
- `story_time`
- `changed_paths`
- 有稳定 ID 的人物、物品、地点状态

故事时间可以是虚构历法时间，也可以是：

```yaml
anchor_event_id: evt_coronation_finished
offset: 3_story_days
window: [start, end]
```

完全不需要章号。

运行时评估记录应和作者填写的定义分开，供画布与 CLI 共同读取：

- `evaluation_id`
- `trigger_id/revision`
- `status`
- `reason_kind`
- `as_of_event_id`
- `as_of_story_time`
- `snapshot_id`
- `matched_event_ids`
- `clause_trace`
- `activation_fingerprint`
- `suppressed_by/cooldown_remaining`
- `planned_effects`
- `unknown_fields/errors`

这样管理员 CLI 读到的就是画布所用的同一份评估结果，不会出现 CLI 自己重新解释条件。

## 四个例子

### A. 世界规则：月蚀禁门

```yaml
payload_ref: world_rule/wr_moon_gate
input_plane: story_actual
input_mode: state
selector:
  state_paths: [world.eclipse.phase, scene.objects]
condition:
  all:
    - world.eclipse.phase == total
    - scene.objects contains mirror_gate
activation_mode: level
rearm_on: world.eclipse.phase != total
effects: [indicator.raise, execution_package.include]
```

作者看到：

> 现在生效的是「月蚀禁门」；因为故事时间已经进入月蚀，当前场景包含镜门。已放入本次执行包。

如果需要阻止凡火开门，给同一个世界规则另配一条 `author_context` 动作护栏。只有作者尝试该动作时才停下；规则触发本身不修改门的状态。

### B. 义务到期：加冕礼后三日归剑

```yaml
payload_ref: obligation/obl_return_sword
input_plane: story_actual
input_mode: hybrid
selector:
  event_types: [story_clock.advanced, sword.returned]
condition:
  all:
    - story_time >= coronation_finished + 3_story_days
    - obligation.status == open
    - no_confirmed_event(sword.returned, obligation_id)
activation_mode: level
repeat_policy: once_per_deadline_revision
warmup:
  metric: story_time_to_deadline
  enter: <= 1_story_day
effects: [indicator.raise, execution_package.include]
```

作者看到：

> 「归还青霜剑」已经到期；因为故事时间到了加冕礼后三日，而已发生事件账本中尚无归还记录。已有“宴后归还”的安排，但它仍是计划，尚未兑现。

系统不自动标记违约，也不自动开卡。

### C. 作者 Hook：北港的蓝线结

```yaml
payload_ref: author_hook/hook_blue_knot
input_plane: author_plan
input_mode: context_match
selector:
  payload_kind: author_hook
  entity_refs: [north_harbor, old_sailor]
  context_tags: [missing_sister]
condition:
  all:
    - plan.location == north_harbor
    - plan.participants contains old_sailor
    - plan.topic == missing_sister
activation_mode: edge
repeat_policy: once_per_plan_item_and_hook_revision
effects: [indicator.raise, execution_package.include]
audience: [author, authorized_editor, admin_cli]
```

作者看到：

> 现在相关的是 Hook「蓝线结」；因为你正在安排“北港 × 老船工 × 失踪姐姐”的对话。该 Hook 的材料优先级已提高；这不表示它已经埋入或兑现。

检索时先按 `payload_kind=author_hook`、人物、地点和主题索引拿候选，只评估少量 Hook，不扫描世界规则。

### D. 宝物易主：天衡玺落到王裔手中

```yaml
payload_ref: world_rule/wr_seal_recognition
input_plane: story_actual
input_mode: event
selector:
  event_types: [artifact.possession_transferred]
  subjects: [artifact.tianheng_seal]
condition:
  all:
    - event.to != null
    - state.person[event.to].lineage contains fallen_royal
activation_mode: edge
repeat_policy: once_per_event
activation_key: event.event_id
effects: [indicator.raise, execution_package.include]
```

作者看到：

> 隐藏条件「王印认主」已亮；因为刚发生的易主事件把天衡玺交给沈雁，而当前状态记载沈雁具有亡国王裔身份。已放入本次执行包；系统没有自动写入“认主成功”。

如果“天衡玺交给沈雁”只存在于计划表，这条实际事件触发器不会亮。计划侧可以另行显示：

> 如果按当前计划落笔，将满足「王印认主」的前置条件；目前尚未发生。

🔥 最该尽早冻结的不是所有字段，而是四个边界：`input_plane`、`payload_ref`、只读条件树、输出白名单。它们一旦模糊，后面最容易出现“计划冒充事实”“触发顺手改真值”“Hook 和义务状态混成一团”这三类大债。
