✅ 结论：不要把后台每一站一比一搬成工具。更合适的是：

- 一套能力内核，复用现有管线；
- 三张工具菜单：作者主 Agent、外部 Agent、管理员检修；
- 每轮只给模型与当前意图有关的 5～9 个工具；
- 正史入账不属于任何 Agent 工具，只能由网页/手机上的作者确认动作触发。

合适的工具粒度可以概括成一句话：

> 一个工具只处理一种用户意图、一个权限等级、一类副作用，并给出一张可审计回执。

读取可以适当聚合，写入越靠近权威层越要拆细。你们已经拍板的“探讨 ≠ 查询 ≠ 真改”，应该直接变成工具可见性规则，而不是只写在聊天提示词里。

下面的调查没有使用附件补前提。公开检索截至 2026 年 8 月 14 日。文中的工具名都是命名草案，不是你们的数据合同或字段定义。

## 公开产品怎样处理“管线各站”

公开资料通常看不到写作产品内部真正的 function schema，只能核对它们给用户暴露的阶段和动作。不能把产品按钮反推成后台工具。

| 对照产品/规范       | 公开能确认的做法                                             | 对你们有用的部分                                             |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| MCP                 | 明确分成三种东西：模型自动决定的 Tools、应用决定怎样提供的 Resources、用户主动点选的 Prompts。[MCP 工具与资源说明](https://modelcontextprotocol.io/docs/2026-07-28/learn/server-concepts)、[Resources 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)、[Prompts 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/prompts) | 卡牌、理论、画布选项不必全做成工具。作者点选的卡更像 Prompt；账本上下文更像 Resource；只有模型需要主动查询或发起工作时才是 Tool。 |
| Novelcrafter        | 把 Plan、Write、Chat、Codex、Review 分成不同界面；Chat 内容还要经过 Extract 才进入 Codex、章节或场景节拍。[功能结构](https://www.novelcrafter.com/help/docs)、[Extract 文档](https://www.novelcrafter.com/help/docs/organization/the-extract-feature) | “聊天里说了”与“结构化内容发生变化”是两个动作。这个方向与你们的提案边界一致。 |
| Novelcrafter 上下文 | 作者主动给场景挂接 Codex 内容；官方文档承认挂得太多、条目太长会让模型忽略关键信息，冲突内容会造成矛盾输出。[场景上下文说明](https://www.novelcrafter.com/courses/codex-cookbook/codex-scenes) | 不要让查询工具吐整本账本。按任务编译小而相关的上下文包。     |
| Sudowrite           | Story Bible → Outline → Scenes → Draft 是显式阶段，Scenes 是下游输入。[Story Bible](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/what-is-story-bible/jmWepHcQdJetNrE991fjJC)、[Scenes & Draft](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/scenes--draft/49p5MTVxTKkVFEC5rVUzpY) | 只借鉴“阶段产物可见、下游输入明确”的界面方式。它会生成正文，这一点不适用于你们。 |

## 1. 工具粒度怎么定

【工程建议】作者工具不要跟“后台站点数量”对齐，要跟“作者意图和审核单元”对齐。

| 情况                               | 合适做法                                                   |
| ---------------------------------- | ---------------------------------------------------------- |
| 回答一个问题需要跨多个账本区域读取 | 可以聚成一个任务级只读工具，例如“取得某范围的确认状态快照” |
| 每次都固定连续调用几个内部站点     | 由后端封装，别让模型逐站调度                               |
| 会产生一份可单独审核的修改         | 单独做提案工具                                             |
| 读取与提案具有不同权限或副作用     | 必须拆开                                                   |
| 启动作业后需要等结果               | 拆成预览、启动、查状态、取产物                             |
| 原始交接物、重放、修索引、死信队列 | 留在管理员工具                                             |
| 作者签字写入正史                   | 不做 Agent 工具                                            |

Anthropic 的公开经验是：不要机械包装每个 API；可以把总是连用、风险相同的操作聚合。但它也强调工具必须目的明确、功能少重叠。[Anthropic 工具设计工程文](https://www.anthropic.com/engineering/writing-tools-for-agents) OpenAI 也建议把必定连续调用的函数合并，并把模型不需要决定的参数交给代码处理。[OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling)

这里有一条很重要的限制：

> “可以聚合”只适用于同一权限、同一副作用等级。绝不能把查询、建提案、签字入账塞进一个带 `mode` 参数的万能工具。

每轮工具数量方面，OpenAI 的公开建议是初始可见函数尽量少于 20；使用工具搜索时，每个 namespace 最好少于 10 个。[Function Calling](https://developers.openai.com/api/docs/guides/function-calling)、[Tool Search](https://developers.openai.com/api/docs/guides/tools-tool-search)

【待实测】你们可以先用每轮 5～9 个作为保守起点，而不是把 30～50 个工具全塞进去。这个数不是行业定律，要拿不同厂商模型跑同一批意图题验证。

建议的意图门控：

| 作者表达                     | 当轮可见能力                                      |
| ---------------------------- | ------------------------------------------------- |
| “聊聊如果他背叛会怎样”       | 选中的卡牌/上下文；必要时只读查询；不出现提案工具 |
| “现在谁知道密道？”           | 只读查询                                          |
| “把他知道密道改成第八章以后” | 只读＋提案；只能创建待审提案                      |
| “这里是不是冲突了？”         | 只读＋质检；可给解决提案，不能直接修账            |
| “按这一章开工/编译”          | 只读＋开工作业                                    |
| 作者在确认卡上签字           | 不经过模型工具，直接进入受保护的签字事务          |

## 2. 名称、描述和入参怎样写

推荐使用“命名空间＋明确动词＋对象”：

- namespace：`truth`、`proposal`、`quality`、`work`、`ops`
- 扁平化兼容名：`truth_search_confirmed_facts`
- 不用 `manage`、`process`、`handle`、`smart`、`sync`、`fix` 这类看不出边界的词

动词最好固定含义：

| 动词                   | 固定含义                                |
| ---------------------- | --------------------------------------- |
| `get`                  | 已知稳定引用，精确取得一个对象          |
| `search`               | 不知道引用，按文字或条件找候选          |
| `list`                 | 有边界、有分页的集合                    |
| `check`                | 纯检查，不创建提案，不改状态            |
| `create/update`        | 只操作提案区，名字中必须出现 `proposal` |
| `submit`               | 把提案送审，不代表接受                  |
| `start`                | 启动作业，返回作业回执                  |
| `commit/apply/publish` | 保留词，不出现在 Agent 工具清单         |

工具描述不能只写“查询事实”。公开文档的共识很一致：

- 写清做什么；
- 什么时候用；
- 什么时候不要用，以及应该改用哪个相邻工具；
- 是否产生副作用；
- 从哪一层数据读取；
- 返回什么、会不会截断；
- 参数的格式、范围和含义。

Anthropic 把详细描述称为影响工具表现最重要的因素，并建议复杂工具给输入示例；同时要求把相似工具的边界写清楚。[Claude 工具定义文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)

一个合格描述可以是：

> 只搜索作者已确认的故事事实。当调用者不知道精确引用、需要按人名、事件或自然语言寻找候选时使用。它不会推断新事实、创建修改提案或改变任何账本状态；已知精确引用时应使用 `truth_get_confirmed_fact`。默认返回少量匹配项、显示名称、稳定引用和继续分页所需信息。

入参建议：

- 模型只填写它真正需要判断的内容：作者问题、目标范围、时间点、希望修改的内容、作者选中的卡牌引用。
- 用户身份、作品身份、权限、当前版本、幂等标记、租户信息由宿主注入，不让模型猜。
- 使用保守的 JSON Schema：明确类型、枚举、必填项、数组上限；关闭未知属性。
- 不给一个无边界的 `options` 或 `metadata` 大口袋。
- 不让模型传后台站点名、数据库表名、内部交接物路径。
- 即使模型输出通过 schema，服务端仍要重新验权限、范围和业务规则。

OpenAI 的严格模式要求 schema 约束明确，并建议用枚举和对象结构排除非法状态。[OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling) 为了不绑某家模型，公共合同最好只用各家普遍支持的 JSON Schema 子集，复杂条件留给服务端验证。

## 3. 已公开的失败案例

| 案例                     | 已验证事实                                                   | 对你们的含义                                                 |
| ------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 工具清单变大             | LongFuncEval 把工具目录从约 8K 增到 120K token，不同模型的表现下降约 7.59%～85.58%，还出现位置偏差和格式幻觉。[LongFuncEval 论文](https://arxiv.org/html/2505.10570v1) | “上下文装得下”不等于“模型选得准”。动态裁剪是正确性措施，不只是省 token。 |
| 相似工具混淆             | ACL 2025 的 ToolExpNet 把“语义相似工具选错”和“忽略工具依赖”列为真实 API 数据中的主要失败模式。[ToolExpNet 论文](https://aclanthology.org/2025.findings-acl.811.pdf) | 不同时暴露 `find_fact`、`search_fact`、`lookup_fact` 这种同义工具。 |
| 描述让参数走偏           | Anthropic 公布过一个内部案例：Web Search 工具描述不够好，Claude 会多余地给查询加上年份 `2025`，修改描述后才纠正。[工程复盘](https://www.anthropic.com/engineering/writing-tools-for-agents) | 描述不只是说明书，也在控制参数策略。需要真实作者题库做回归测试。 |
| 长上下文掩盖重点         | Novelcrafter 官方文档承认，挂接太多或太长的 Codex 条目会让 AI 忽略重要信息；相互冲突的上下文会导致矛盾结果。[官方说明](https://www.novelcrafter.com/courses/codex-cookbook/codex-scenes) | 返回整本账本是错方向。工具默认只给当前决策需要的高信号信息。 |
| 读写权限混在一个 Agent   | Invariant Labs 公开演示：一个正常的“查看公开 Issue”请求读到恶意指令后，Agent 又利用同一 GitHub 权限读取私有仓库并把内容写进公开 PR。[GitHub MCP 攻击演示](https://invariantlabs.ai/blog/mcp-github-vulnerability) | 这是公开可复现的研究演示，不是已确认的生产泄露事故。它证明“可信工具＋不可信内容＋过宽权限”也足够出事。 |
| “只读查询”仍可能向外泄露 | OpenAI 官方安全文档专门举例：恶意只读 MCP 可以诱导模型把私密内容塞进下一次搜索参数，从而外传数据。[OpenAI Deep Research 安全说明](https://developers.openai.com/api/docs/guides/deep-research) | `readOnly` 只说明不改本地状态，不代表不向外发送数据。外部搜索和内部真源读取不应在同一高权限阶段并存。 |
| 工具描述本身被投毒       | Invariant Labs 演示过恶意 MCP 把读取密钥的指令藏在工具描述里，用户界面只显示简化说明。[Tool Poisoning 演示](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) | 外部工具描述必须锁版本、审核、完整展示；不能把动态第三方描述直接塞进主 Agent。 |

我没有找到一份公开、可逐项核对的生产事故复盘，能够证明某个名叫 `query_*` 的具体工具暗中修改了业务数据。因此这一点不能包装成“已有事故结论”。能确认的是：

- HTTP 规范把安全请求定义为调用方不要求状态变化；[RFC 9110](https://datatracker.ietf.org/doc/html/rfc9110)
- Temporal、ink、MCP 等系统都明确区分只读与副作用；
- MCP 的 `readOnlyHint`、`destructiveHint` 等只是提示，不是安全保证，服务端仍要硬性限制。[MCP ToolAnnotations](https://modelcontextprotocol.io/specification/draft/schema#toolannotations)

## 4. 管理员与作者工具要不要分开

✅ 要分开。准确说，是同一套能力内核，至少三张菜单、三套凭证，不是复制三份业务逻辑。

| 能力                           | 作者主 Agent      | 外部 Agent                 | 管理员检修                             |
| ------------------------------ | ----------------- | -------------------------- | -------------------------------------- |
| 查询作者已确认内容             | 可以              | 只读经过批准的确认投影     | 仅在授权范围内诊断                     |
| 查询未确认讨论、私密规划       | 按作者权限        | 默认不可以                 | 默认不因“管理员”而自动可读正文内容     |
| 创建修改提案                   | 可以              | 可以创建自己有权提交的提案 | 可查工作流故障，不代替作者表达创作意见 |
| 启动编译、质检、导出审阅包     | 可以              | 按已拍约束不开放           | 可查、重试、排障                       |
| 原始交接物、站点回执、索引状态 | 不开放            | 不开放                     | 可以                                   |
| 修复派生索引、重试失败作业     | 不开放            | 不开放                     | 可以，且不得改变作者事实               |
| 写入正史                       | 不存在这个工具    | 不存在这个工具             | 也不应靠检修工具绕过作者签字           |
| 作者签字                       | 网页/手机确认服务 | 不可以                     | 不可以代签                             |

管理员工具可以叫：

```text
ops_list_station_runs
ops_get_station_receipt
ops_trace_handoff_lineage
ops_compare_handoff_versions
ops_validate_projection
ops_rebuild_derived_index
ops_replay_run_dry
ops_retry_failed_run
ops_quarantine_artifact
ops_get_audit_trace
ops_verify_author_signature
ops_check_tool_manifest
```

这里的核心是：

- 作者工具讲“我要查什么、提议改什么、开始什么工作”；
- 管理员工具讲“哪一站失败、哪张回执异常、能否重放”；
- 外部工具只讲“读已确认投影、交提案”；
- 权限由服务端和凭证决定，不靠模型自觉，也不能只靠 `tools/list` 隐藏。

VS Code 的 Plan/Implementation 分权、Claude Code 默认只读并对编辑和命令单独授权，都是公开的相邻做法。[VS Code Custom Agents](https://code.visualstudio.com/docs/agent-customization/custom-agents)、[Claude Code Security](https://code.claude.com/docs/en/security)

## 5. 返回值：两套投影，但只能有一个语义结果

✅ 模型和作者应该看到不同投影，但不能维护两份独立事实。

建议分成：

1. 模型回执：短、结构化、能继续调用。
2. 作者投影：人话、可视化差异、确认按钮。
3. 长证据：按需取得的资源，不默认塞进模型上下文。

模型回执至少表达这些“语义槽位”；这不是字段命名建议：

| 内容                             | 用途                         |
| -------------------------------- | ---------------------------- |
| 成功、部分成功、被阻止、等待确认 | 模型决定是否继续             |
| 查询或作业范围                   | 避免回答范围漂移             |
| 来源层和版本时点                 | 防止把提案当确认事实         |
| 少量结果、稳定引用、显示名称     | 既能继续调用，也便于解释     |
| 冲突与警告                       | 走质检或提案                 |
| 是否截断、怎样继续取             | 控制上下文                   |
| 对提案区造成的变化               | 明确“只改了提案，没有改正史” |
| 允许的下一步                     | 避免模型猜流程               |

MCP 原生支持 `structuredContent`、输出 schema、文本内容和资源链接；长内容可以返回资源引用。[MCP Tool Results](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) OpenAI 的 MCP Apps 还区分模型可见的结构化内容和仅界面可见的 `_meta`。[OpenAI Apps SDK 工具结果](https://developers.openai.com/apps-sdk/llms-full.txt)

给作者看的“已确认”“待作者确认”“发现三处冲突”这类权威句子，最好由回执确定性渲染，不让模型自由改写状态。模型可以补充解释，但解释必须引用回执，不能改变状态标签。

## 6. 建议的四层工具清单

### A. 只读查询层

这些工具只读取，不建提案、不启动后台修复。外部 Agent 只能看到其中经过“已确认投影”过滤的子集。

```text
truth_search_confirmed_facts
truth_get_confirmed_fact
truth_get_scope_snapshot
truth_get_character_state
truth_get_world_state
truth_get_character_knowledge
truth_get_active_plans
truth_get_open_obligations
truth_get_applicable_rules
truth_trace_evidence
truth_trace_change_history
quality_check_consistency
quality_explain_conflict
```

其中计划、义务、知情等是否属于外部可读的“确认事实”，必须依照你们现有合同决定，不能因为工具存在就自动放出去。

### B. 提案层

这些工具只能改变“待审提案”的状态，不能接受提案，更不能写正史。

```text
proposal_create_change
proposal_get_draft
proposal_update_draft
proposal_attach_evidence
proposal_add_alternative
proposal_check_against_truth
proposal_preview_impact
proposal_submit_for_review
proposal_get_review_status
proposal_list_review_feedback
proposal_resubmit
proposal_withdraw
```

`proposal_update_draft`、`attach_evidence`、`add_alternative` 是否合并，要跑选错率测试。如果三者总在同一编辑动作里出现，可以合成一个严格 schema 的更新工具；不要只是为了“工具少”硬塞在一起。

### C. 开工/编译层

这一层可以写作业记录和派生产物，但不能改正史。作者看到任务级动作，不看到后台站点零件。

```text
work_preview_compile
work_start_compile
work_get_run_status
work_list_outputs
work_fetch_output
work_validate_output
work_explain_blocker
work_retry_failed_run
work_cancel_run
work_compare_runs
work_export_review_packet
work_get_run_log_summary
```

`work_start_compile` 内部可以调多个固定站点。模型只选择工作类型和范围，不负责安排站点顺序。

### D. 禁止注册的工具或能力

下面列的是不要做成 Agent 工具的名字和能力：

```text
story_do_everything
story_manage
story_process_request
truth_query_and_update
truth_search_and_fix
work_compile_and_publish_truth
chat_save_as_truth
quality_auto_resolve_conflict
canon_commit_change
canon_accept_proposal
canon_bulk_replace
proposal_auto_approve
external_write_truth
admin_bypass_author_signature
theory_auto_apply
story_generate_chapter_prose
```

它们分别有四类问题：

- 名字太虚，模型无法判断边界；
- 把读取和副作用藏在一个动作里；
- 绕过作者签字或质检；
- 违背“不自动冒理论、不代写正文”的产品约束。

这些事也不该做成领域工具：

- 画布点选、拖拽、确认和作者签字；
- 卡牌展示与选择；
- 权限判断、租户判断、审计记录；
- 幂等控制和当前版本注入；
- 作者句子的界面渲染；
- 固定的站点间交接；
- 模型供应商选择；
- 自动应用理论或自动修正正史。

## 建议的验收门槛

🔥 真正上线前，不要只测“模型会不会调用”，要测“它什么时候绝对不能调用”。

至少准备这些题型：

- 探讨句不得创建提案；
- 查询句不得触发任何写操作；
- 含糊的“改一下”最多创建草稿，不能提交，更不能入账；
- 冲突句必须走质检；
- 外部 Agent 无法取得未确认内容；
- 任何角色都不存在正史写入工具；
- 相似工具、错别字、人物别名、时间模糊题；
- 返回大量结果时是否自动缩小范围；
- 恶意正文、外部网页或提案内容能否诱导跨权限调用；
- 同一题在多家模型、不同版本上的选工具差异。

核心指标建议记录：

- 正确工具选择率；
- 应该不用工具时的克制率；
- 错权限调用率；
- 查询产生副作用的次数；
- 提案泄漏成正史的次数；
- 参数校验失败率；
- 单次返回 token 和重复调用次数；
- 不同模型间的方差。

其中“外部越权”和“绕过作者签字”不该靠追求 99.9% 模型准确率解决，而应该在接口层做到调用路径不存在或服务端必拒绝。

一句话收束：

> 把作者意图做成工具菜单，把后台站点留在能力内核，把确认权留在界面事务里。读取可以聪明地聚合，提案必须可审核，正史写入永远不让模型拿到手柄。
