下面的调查截至 2026-08-14，只使用题面约束和公开资料，没有把附件内容当成前提。

## ✅ 核心结论

V0 不该做一个“小说健康分”，也不要显示“候选 219 条”这类机器过程数据。完成度、事实正确性、节奏判断的可信程度完全不同，硬揉成一个分数会制造假精确。

建议拆成四种互不混用的反馈：

- 中性进度：作者亲自定义的任务完成了多少。
- ⛔ 红色硬冲突：两条已经确认的事实不能同时成立，能点开回验。
- △ 黄色提醒：节奏、手法或情绪可能不符合当前意图，不代表写错。
- ? 灰色未知：没检查、资料不足、结果过期；绝不表示“没有问题”。

没命中时不亮灯。颜色必须同时配图形和文字，不能只靠颜色区分；这是 [W3C 的明确要求](https://www.w3.org/WAI/WCAG21/Understanding/use-of-color.html)，IBM Carbon 的状态指示规范也要求高关注状态使用图标、形状、颜色和文字标签共同表达。[Carbon 状态指示规范](https://carbondesignsystem.com/patterns/status-indicator-pattern/)

每个灯都必须回答五件事：哪几章、看到了什么、可能造成什么感受、依据在哪、作者下一步能点什么。

节奏总览放在规划画布拉到最远后的章级投影里。时间轴仍是独立预览，不与主画布合并。

## 1. 专业工具怎样让人一眼看懂

| 行业         | 用户实际看到什么                                             | 对本产品的启发                                               |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 视频时间线   | Premiere 把红、黄、绿状态直接画在受影响的时间段上方，用户不必先打开报表。[Adobe 官方说明](https://helpx.adobe.com/premiere/desktop/render-and-export/render-sequences-for-playback/render-a-section-of-a-sequence.html) | 借它的“问题落在具体范围上”，不要借它的颜色含义。你们应把提醒落在第几章或哪条连线上，红黄仍按已拍定义。 |
| DAW 音频软件 | Ableton 先给全局负载反馈，再给每条音轨一个相对影响表；定位到问题音轨后，可进入 Freeze 等处理动作。[Ableton 官方说明](https://help.ableton.com/hc/en-us/articles/12911009486108-Optimizing-CPU-Intensive-Devices) | “整体感觉不对”下面必须能找到主要贡献章，并紧跟一个动作。不要把模型中间统计全摊出来。 |
| IDE 代码诊断 | VS Code 同一诊断会出现在状态栏摘要、正文旁、右侧概览尺和 Problems 面板；点开还有 Quick Fix。[VS Code 官方说明](https://code.visualstudio.com/docs/editing/editingevolved) | 同一条投影可以出现在章卡、最远视图、聊天和详细面板，但语义只能算一次。 |
| IDE 规则配置 | IntelliJ 允许按检查项设置严重级别、作用范围，也可“不高亮但保留修复入口”。[JetBrains 官方说明](https://www.jetbrains.com/help/idea/configuring-inspection-severities.html) | 理论插件要能限定卷、故事线、章节范围和提示强度；作者不想看时可以静音，不必卸载。 |
| 项目管理     | Jira 用一根分段进度条显示未开始、进行中、完成，具体数量放到悬停详情；“卡住”还会参考该项目自身的状态时长分布，而非固定天数。[Jira 官方说明](https://support.atlassian.com/jira-software-cloud/docs/understand-insights-on-the-board-in-a-team-managed-project/) | 主屏显示作者认识的状态比例；阈值尽量参考本书自身习惯或作者设置，不用全平台统一标准。 |
| 项目趋势     | Jira 把累计流图放在独立报告页，用来观察随时间形成的瓶颈，不硬塞回看板。[Jira 累计流图说明](https://support.atlassian.com/jira-software-cloud/docs/what-is-the-cumulative-flow-diagram/) | 这正好支持“章级工作流画布”和“时间轴预览”分开。主画布只放当前投影，趋势另看。 |

行业里并不是完全不显示数字。VS Code 会显示错误数，是因为每个数都对应一个用户能点开的错误。可用一条简单判断：

> 作者认识、能逐项处理的单位，可以显示；模型自己生产的过程单位，不上作者主屏。

所以“6/8 张章任务卡完成”可以显示；“抽取候选 219 条、合并后 73 簇”不可以。

信息展开方式建议照“概览 → 点开详情 → 进入动作”三层做。渐进披露的好处就是把少用、复杂的内容留在次级界面，减少学习成本和误操作。[Nielsen Norman Group](https://www.nngroup.com/articles/progressive-disclosure/)

## 2. 从计算信号变成一句话和一个下一步

其实核心就一条流水线：

**可复核信号 → 意图/体裁/尺度校验 → 模型解释可能影响 → 一句话＋一个动作**

规则负责“发生了什么”，模型负责“这在当前故事里意味着什么”。规则不能越权宣布“节奏写坏了”。

| 信号           | 规则能稳定计算什么                                 | 必须交给模型或作者判断什么                   |
| -------------- | -------------------------------------------------- | -------------------------------------------- |
| 钩子间隔       | 距离上一个已确认钩子多少章；连续多少章没有钩子标记 | 这一处是否真能牵引读者；这里是否在刻意休整   |
| 欠账堆积       | 已确认承诺的开启时间、未兑现时长、净增趋势         | 哪条承诺最重要；延期是在加深期待还是让人遗忘 |
| 连续无兑现     | 连续章段中是否只有新增承诺、没有任何兑现记录       | 小兑现是否已经足够；读者是否真的会觉得疲劳   |
| 连续无推进     | 场景功能、人物目标、关键状态是否连续不变           | 是重复，还是有意制造压抑、停滞、仪式感       |
| 事件/细节密度  | 每章事件数、场景数、篇幅、细节展开层级及相对异常   | 详写是否有价值；略写是否错过了重要转折       |
| 情绪变化       | 情绪标签的跳变、长时间平直、触发事件是否缺失       | 转变是否“挣到了”；突切是否是作者想要的手法   |
| 钩子和兑现质量 | 规则做不了                                         | 相关性、力度、意外但合理、兑现是否与铺垫相称 |
| 理论适配       | 只能检查插件声明的前提是否具备                     | 这部作品是否应该采用该理论、采用到什么程度   |

计算叙事研究确实可以用事件相对描写的比例去估计节奏和悬念，但“事件顺序”和“事件功能”本身仍需解释。[ACL 叙事理论论文](https://aclanthology.org/2021.emnlp-main.26/) 长篇节奏研究也把“重要事件写得太快”和“次要事件写得太细”视为两类不同问题，并且仍用人类判断结果。[ACL 长篇节奏研究](https://aclanthology.org/2023.findings-emnlp.723/)

更关键的是，目前没有公认、可泛化的自动“张力分”；最新研究仍明确指出这一点。[Narrative Forecasting 论文](https://arxiv.org/html/2604.09854v1) 2026 年 NARRABENCH 对 78 个叙事评测的调查也认为，大量叙事理解带有视角和主观性，现有基准只覆盖其分类体系的大约 27%。[NARRABENCH](https://aclanthology.org/2026.eacl-long.176.pdf)

因此，不建议出现“节奏分 63”“爽点健康度 71%”。

推荐的黄色文案格式：

> **范围＋观察到的模式；如果这不是作者刻意安排，可能产生的读者感受。**

配一个主要动作：

| 机器信号     | 作者看到的一句话                                             | 主要动作             |
| ------------ | ------------------------------------------------------------ | -------------------- |
| 钩子间隔过长 | “第 8—11 章没有明确的新牵引点；如果这段不是刻意休整，章末继续读的动力可能偏弱。” | **检查第 11 章结尾** |
| 欠账净增加   | “第 14—16 章持续提出新问题，却没有回收旧承诺；如果不是刻意加压，读者可能觉得只铺不收。” | **处理最早的承诺**   |
| 情绪跳变     | “第 21 章从绝望直接转为轻松，账里没有对应的触发事件，情绪转折可能缺少落点。” | **确认转折触发点**   |
| 硬事实冲突   | “第 12 章人物已经知道凶手姓名，但第 16 章才第一次获得这个信息。” | **对照两处证据**     |
| 覆盖不足     | “第 20—24 章尚未完成节奏检查。”                              | **检查这五章**       |

“查看依据”可以一直存在，但它是详情入口，不占用那个主要动作。

## 3. 理论插件怎样被选用，而不是强套

最稳的产品关系是：

> 节奏诊断只说症状；作者主动点“找一种方法”后，才进入插件选择。

不能做成“检测到三章无兑现 → 自动启用救猫咪 → 建议改大纲”。

建议流程：

1. 黄灯先给无理论诊断，例如“连续加压、暂未兑现”。
2. 作者可以处理、标记“这是刻意的”，也可以点“找一种方法”。
3. 选择器先问三个很短的问题：想产生什么读者感受、问题发生在场景/章节/故事线哪一级、是否接受类型化结构。
4. 只展示最多三张合适的卡，每张同时写“适合什么”和“什么情况下别用”。
5. 作者选择插件、作用范围和层级后，插件才运行。
6. 结果只生成问题、指导和提醒；不写正文，不改大纲。
7. 插件提醒进入要点汇聚屏，按插件和来源分组折叠。作者可忽略、暂停或关闭。

这与 VS Code 的插件模式很接近：插件可只在当前工作区启用或关闭，也可以只在用户真正调用命令、打开视图时激活。[VS Code 插件管理](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace)、[激活事件](https://code.visualstudio.com/api/references/activation-events)

节奏症状与插件类型的关系建议这样控制：

| 当前症状             | 可供作者选择的方法类型                | 不该机械推荐什么         |
| -------------------- | ------------------------------------- | ------------------------ |
| 单个场景没有状态变化 | 场景转折、目标—阻力—结果类插件        | 英雄之旅等全书结构       |
| 承诺越积越多         | 铺垫—兑现、悬念回收、类型奖励节奏插件 | 为了“凑结构”增加新转折   |
| 整卷缺少宏观转向     | 救猫咪、英雄之旅、三幕式等结构插件    | 直接套到每一章           |
| 情绪突然断裂         | 情绪弧、反应场景、场景—余波类插件     | 强行加钩子或打脸         |
| 网文奖励感偏弱       | 爽点、打脸、阶段奖励类插件            | 未确认类型意图就默认启用 |

同一插件的三层标准可以直接告诉用户：

| 层级       | 它回答什么                             | 输出边界                                                     |
| ---------- | -------------------------------------- | ------------------------------------------------------------ |
| 出题层     | “现在最该决定什么？”                   | 1—3 个短问题，不讲长理论                                     |
| 写法指导层 | “这个决定可以怎样写？”                 | 2—4 种做法、适用条件和风险；作为同一次 API 结果里的隐藏附页，展开时不再调用 API |
| 分镜层     | “选定做法后，每个场景或镜头承担什么？” | 按场景/镜头拆意图、转折、情绪和视觉任务；只有作者明确进入分镜层才运行 |

自制插件至少要声明：

- 适用症状和不适用情况
- 支持的尺度：场景、章节、故事线、卷或全书
- 需要读取哪些账
- 三层分别输出什么
- 来源、版本和作者
- 提醒怎样分组
- 允许的动作

V0 建议把理论插件权限锁成“只读账本、输出投影和提醒”。插件最多发黄灯，不能发红灯，也不能提交大纲修改。

Microsoft 的人机协作规范同样强调：AI 能力应容易主动调用，也应容易忽略、纠正；目标不明确时缩小范围，并让用户能看懂系统为何这样判断。[Microsoft Human-AI Guidelines](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/)

## 4. 画布、聊天 Agent、管理员 CLI 怎样读同一投影

你可以把“投影”理解成一张机器可读的小票。小票记事实，三个界面各自决定说多长，但不能各算各的。

```json
{
  "code": "pace.payoff_gap",
  "state": "yellow",
  "scope": { "chapter_from": 14, "chapter_to": 16 },
  "observation": "连续章节新增承诺而未兑现",
  "possible_effect": "可能让人感觉只铺不收",
  "evidence_refs": ["promise:p17", "chapter:14-16"],
  "next_action": "review_oldest_open_promise",
  "source": {
    "kind": "core_rule",
    "id": "payoff-gap",
    "version": "0.3"
  },
  "coverage": "complete",
  "debug_ref": "diag:8f14"
}
```

三个界面这样翻译：

| 界面         | 文案                                                         | 可做什么                                                     |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 作者画布     | `△ 第14—16章：持续加压，暂未兑现`                            | 点章段、看依据、打开“最早承诺”决策面板                       |
| 聊天主 Agent | “我能查看这条黄灯的依据，也能用你已经启用的方法卡分析，但不会改大纲。第14—16章可能只铺不收，你想从最早的承诺看，还是先点一章？” | 先暴露能力，再围绕作者点中的章或灯回答                       |
| 管理员 CLI   | `YELLOW pace.payoff_gap scope=ch14..16 action=review_oldest_open_promise source=core/payoff-gap@0.3` | 默认看同一投影；加 `--debug` 才显示阈值、模型版本、记录 ID 和原始计数 |

三者必须共享这些字段：语义代码、严重度、章节范围、证据引用、来源、主要动作、投影版本。

画布文案可以很短，聊天可以解释，CLI 可以技术化；但聊天 Agent 不能把黄色说成红色，也不能临时换一个下一步。

节奏监控不另建“节奏事实账”。它只保存可丢弃、可重算的投影缓存和最小检查回执，例如输入账版本、规则版本、检查时间。作者标记“这是刻意的”则写入作者决策/静音记录，不写入新的节奏真相账。

## 5. V0 作者可见指示器：建议 10 个

没命中时不亮灯。完成度使用中性进度条，红黄不要拿来表示“还没做完”。

| 名字         | 数据来自哪类账                               | 红                         | 黄                                                 | 灰                                         | 作者能点什么                                 |
| ------------ | -------------------------------------------- | -------------------------- | -------------------------------------------------- | ------------------------------------------ | -------------------------------------------- |
| 本章完成度   | 任务卡、工作流状态、依赖关系                 | 不用                       | 不用                                               | 未建任务或结果过期                         | 展开未完成卡、调整本章任务                   |
| 接收区归位   | 接收区记录、卡片去向                         | 不用                       | 不用                                               | 接收区尚未读取或状态过期                   | 打开第一条待归位内容；不显示机器候选总数     |
| 硬事实冲突   | 事实、人物知识、事件、设定和证据记录         | 两条已确认事实不能同时成立 | 不用                                               | 尚未回验或证据不足                         | 对照两处证据、重新回验、修正其中一条         |
| 节奏走势     | 现有章节、事件、钩子、承诺、情绪账的组合投影 | 不用                       | 当前章段可能不符合作者意图                         | 覆盖不足或尚未检查                         | 在最远规划视图定位章段，打开一句诊断和动作   |
| 章末牵引间隔 | 已确认钩子、章末作用记录                     | 不用                       | 超过作者或已选插件设定的间隔，且上下文确认可能偏弱 | 没有可靠钩子标记或尚未设意图               | 检查具体章末、标记钩子、确认“刻意放慢”       |
| 承诺与兑现   | 铺垫、问题、承诺、兑现记录                   | 不用                       | 欠账持续增加、过久或连续无兑现                     | 承诺记录未确认或覆盖不足                   | 打开最早且重要的承诺，选择兑现、升级或延期   |
| 连续无推进   | 事件、人物目标、场景功能、状态变化           | 不用                       | 连续章段缺少目标或状态变化，模型判断可能形成停滞   | 缺少场景功能或目标信息                     | 查看受影响章段、确认变化点或标记为有意停滞   |
| 情绪连续性   | 人物情绪、触发事件、关系变化                 | 不用                       | 情绪骤变或长时间平直，可能不是作者意图             | 情绪资料不足或模型无法稳定判断             | 对照转变前后片段、确认触发点                 |
| 已选方法提醒 | 插件启用配置和插件输出投影                   | 插件永远不能发红           | 作者主动启用的插件产生提醒                         | 插件缺少所需数据或尚未运行；未启用时不显示 | 进入要点汇聚屏，按来源展开、忽略、暂停或关闭 |
| 检查覆盖     | 各账版本、检查回执、内容更新时间             | 不用                       | 不用                                               | 有章节未检查、数据过期或范围不足           | 查看未覆盖章节并重新检查                     |

待复核线索不放进这张灯表，也不拿黄色冒充。它保留独立账本入口，按“待确认、已确认、已排除”管理，主画布不显示总候选数。

### 明确不要上主屏的内部量

- 抽取候选总数、被过滤数、合并簇数
- 向量检索命中数、相似度、图边权重
- 模型原始置信概率、投票数、重试数
- 规则内部窗口、阈值和中间计数
- Token、API 调用数、成本、延迟
- 模型名称、提示词版本、温度参数
- 账本行号、索引版本、哈希、缓存命中率
- 插件激活日志、校验日志
- “综合健康分”“好节奏概率”这类假精确数字
- 尚未回验的冲突候选
- 待复核线索的总候选数

这些信息可以留给管理员 CLI 的 `--debug` 或插件开发者面板。Google 的监控经验也强调：主提醒应聚焦用户感受到的症状和可执行动作，成因与过程数据放到诊断层；否则很快形成噪声。[Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)、[Google Cloud 告警建议](https://cloud.google.com/blog/products/management-tools/good-relevance-and-outcomes-for-alerting-and-monitoring)

## 可以直接锁进 V0 验收标准的八条

- 红灯只能来自已回验的硬事实冲突。
- 插件、模型体感和理论不允许产生红灯。
- 黄灯必须指向具体章节或章段，并附可查看依据。
- 每条黄灯只能有一个主要下一步，且不能自动改大纲。
- 灰色永远表示未知、未检查或已过期，不能表示“安全”。
- 节奏总览是章级画布投影，不与时间轴预览合并。
- 插件只在作者主动选择后运行，提醒统一进入要点汇聚屏。
- 插件输出问题、指导和分镜任务，不产正文，也不承诺“降 AI 率”。
