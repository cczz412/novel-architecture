# 调查结论

✅ **你给出的候选方向是成立的，而且与成熟系统的稳妥做法一致：**

> **事件／事实保留历史真源；“现在什么样”由统一计算层现算。为了性能可以存快照，但快照只能是带来源位置、规则版本和过期状态的只读缓存，删掉后必须能重建。**

还要补三道边界：

1. **“现在”必须带查询时点**：基于哪条故事线、哪个已确认版本、故事内哪个时刻算出来。否则多线异步、倒叙、插叙时，“当前”没有唯一含义。
2. **stale、未知、硬冲突要分开**：过期可以重算；证据不足只能报未知；两条硬事实互斥才是冲突。
3. **自动修复只允许重建投影**：绝不能自动补“他大概已经离场”“道具应该转手了”这类故事事实。

------

## 1. 当前状态：公开系统普遍不是纯快照，也不是每次从头重放

公开做法大致分三类：

| 系统类型                 | 常见做法                                         | 局限                                       |
| ------------------------ | ------------------------------------------------ | ------------------------------------------ |
| 简单游戏存档             | 直接保存当前变量和对象位置                       | 快，但历史不可追，内容版本变化后容易不兼容 |
| 纯事件重放               | 保存所有事件，查询时从头重算                     | 干净，但事件多了以后代价高                 |
| **事件＋快照＋尾部重放** | 历史事件是真源；从最近快照开始，只重放之后的事件 | 工程上最常见，也最适合长篇                 |

Godot 的官方存档示例就是典型“当前状态快照”：把对象位置、生命值、等级等变量序列化保存。它适合游戏存档，却没有解决“这份状态是由哪些历史变化得到的”。([Godot Engine documentation](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html))

事件溯源系统的公开做法更接近你们的约束。Axon 明确把快照定义为“事件流某个位置上的状态”，加载时从快照开始，再应用之后的事件；快照只是性能优化，不替代事件，坏了或不兼容时应退回完整事件重放。Microsoft 的 CQRS 文档也把事件库视为唯一真源，把物化视图定义为可重建的只读缓存，并建议长事件流定期建立快照。([AxonIQ Docs](https://docs.axoniq.io/axon-framework-reference/5.2/snapshotting/))

MediaWiki 走的是另一种同构形状：每次编辑产生新修订，页面只保存一个指向“当前修订”的指针；给读者看的 HTML 是缓存。页面或依赖模板变化时，缓存会被标为过期，再重新渲染。缓存不是另一份页面真值。([MediaWiki](https://www.mediawiki.org/wiki/Manual%3APage_table))

Temporal 这类持久任务系统也保留事件历史，通过重放恢复工作流状态；定时器同样作为命令和事件进入历史，而不是另开一张互相双写的“倒计时真值表”。([Temporal Docs](https://docs.temporal.io/encyclopedia/architecture/how-temporal-works))

### 对几百章连载的适配建议

**设计推导：**可以存“当前状态快照”，但必须同时满足下面七条，才能保证它不是第二真值：

| 约束                     | 作用                             |
| ------------------------ | -------------------------------- |
| 只读，不提供单独编辑入口 | 防止作者改人物页，却没改事件依据 |
| 标明基于哪个已确认提交点 | 判断源账是否已经往前走           |
| 标明故事内查询时点       | 支持倒叙、多线不同步和历史查询   |
| 标明计算规则版本         | 规则升级后知道哪些结果应重算     |
| 带依赖依据清单或其摘要   | 能解释“为什么算成这样”           |
| 源账变化后立即变 stale   | 不允许旧状态继续装成新状态       |
| 删除快照后可以重建       | 这是“缓存而非真值”的最硬判据     |

长篇不必每次从第一章重放。可以：

- 按人物、物品、地点等对象分流计算；
- 在作者确认、关章或累计一定事件量后生成检查点；
- 查询时读取最近检查点，只重放其后的变化；
- 全局查询走物化索引，不扫描全书；
- 规则升级或怀疑漂移时，再做一次完整重建核验。

Axon 公开支持按事件数量、读取耗时或特定领域事件触发快照；Kurrent 的投影则保存处理检查点，重启后只检查检查点之后的事件。([AxonIQ Docs](https://docs.axoniq.io/axon-framework-reference/5.2/snapshotting/))

🔥 **建议把“快照能否删掉重建”写成验收门。**只要删掉快照后系统无法从事件、关系和知情依据恢复，它就已经偷偷变成第二真源了。

## 2. “谁在场”：位置变化是真依据，场景名单只能是计划或核对材料

公开叙事引擎里，较稳的物理世界表示不是“最近提到过谁”，而是明确的位置和包含关系。

Inform 7 的世界模型要求对象处于某个房间，或者明确处于场外；物品可以被人物携带、放在容器里，而“位置”通过包含链推导。人物移动时，其携带和包含的物品一起移动。([Ganelson](https://ganelson.github.io/inform-website/book/WI_3_25.html))

这比场景上直接维护名单稳，因为同一套机制可以同时回答：

- 人现在在哪；
- 谁和谁处在同一地点；
- 谁手里拿着什么；
- 包里的物品跟着谁移动；
- 人是否已经离开故事现场。

### 三种方案比较

| 方案                                 | 优点                                 | 主要问题                                       | 推荐身份               |
| ------------------------------------ | ------------------------------------ | ---------------------------------------------- | ---------------------- |
| 场对象直接存人物名单                 | 作者一眼能看懂，规划方便             | 实际发生变化后容易忘记同步，形成第二真值       | **计划名单／核对清单** |
| 从人物最近一次被提到的位置推         | 不用额外录入                         | “被提到”不等于移动；漏写离场后会一直残留       | 不宜单独使用           |
| 显式进入、离开、移动、携带变化＋现算 | 可追溯，可解释，能同时算位置与持有物 | 原文没交代移动时会产生未知                     | **实际状态主路线**     |
| POV＋显式变化                        | 能过滤角色看见什么                   | POV 只代表叙事视角，不代表物理上只有这些人在场 | POV 只作输出过滤       |

这里还要把“在场”拆成两个查询，不必另开两张账：

1. **物理同处**：谁被算在这个地点；
2. **本场上台参与**：谁实际参与了当前场景、被看见、说话或行动。

一个人在酒楼后厨，可能物理上和主角处在同一建筑，但不属于当前包厢场景的上台人物。反过来，电话里说话的人参与了这场戏，却不在物理现场。两个结果可以从同一批事件现算，不应硬塞成一个名单。

### 配角没写离场，怎么办

✅ **不应自动补离场，也不应无限默认在场。**

较稳的处理是：

- 如果后文有明确的新位置事件，新事件覆盖旧位置，系统不要求额外补一条离场；
- 如果场景换地点，而人物没有移动依据，则他仍保留“上次确认位置”，但不自动进入新场景；
- 如果下一场仍在同一地点，系统可以算出他仍物理同处，但同时提示“从上一场延续，未发现离场或继续参与的明确依据”；
- 作者确认“他已经离开”后，应形成新的事实或事件，而不是直接改场景名单。

Unreal 的 Gameplay Ability System 有一个很直观的同类故障：能力结束时如果没有显式执行结束动作，系统会一直认为能力仍在运行，甚至永久阻塞后续能力。它说明“只有开始、没有结束”的生命周期对象，确实会长期污染当前状态。([Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine))

⚠️ 我没有找到公开研究统计“网文中配角漏写离场”的发生率。因此，这里能确认的是**工程故障形状真实存在**，不能声称它已被量化证明是网文高频问题。

## 3. stale 怎么亮：必须告诉作者“为什么旧了”，不能只贴一个黄标签

Kubernetes 的公开状态设计提供了很好的最小形状：状态条件会记录自己观察的是哪个对象版本。假设对象当前已经是第 12 版，而状态只观察到第 9 版，那么它明确就是过期状态；条件还带人可读说明、原因以及 True／False／Unknown。([Kubernetes](https://kubernetes.io/docs/reference/kubernetes-api/apiextensions/custom-resource-definition-v1/))

MediaWiki 也不是笼统写“缓存可能有问题”，而是根据页面和依赖资源的更新时间判断缓存是否早于最新变更，从而标为 dirty。([MediaWiki](https://www.mediawiki.org/wiki/Manual%3AParser_cache))

### 作者界面至少应显示什么

只显示：

> 人物页和最新事实对不上

信息不够。作者还得重新翻书。

更有用的最小展示是：

> **人物页过期**：当前显示“林昭在客栈”，它基于第 141 章收工版本；第 143 章确认事件已把林昭移到码头。
> 影响：本章执行包、在场人物计算。
> 待确认提案“林昭当夜返回客栈”未计入实际状态。

也就是至少露出：

- 哪个投影过期；
- 它显示的旧结果；
- 它基于哪一版源账；
- 哪条新事件让它失效；
- 哪些下游视图受影响；
- 是否有未确认提案被排除；
- 可以执行什么动作：重算、看依据、提交修订提案。

### stale 不要包办所有异常

建议至少分成四类：

| 情况           | 含义                             | 推荐处理                 |
| -------------- | -------------------------------- | ------------------------ |
| **过期**       | 源账已经更新，投影尚未重算       | 自动重算投影             |
| **依据不足**   | 没找到足够事件，无法确定         | 报未知，不补故事         |
| **待确认提案** | 有计划或模型建议，但尚未成为事实 | 单独展示，不混入当前状态 |
| **硬冲突**     | 两条已确认硬依据互相排斥         | 红灯，允许挡关章         |

这样才能继续遵守“检查器没检到，只能说覆盖范围内未检出；只有硬冲突才能挡关章”。

### 哪些自动修，哪些只亮灯

| 公开产品／系统 | 自动处理范围                                                 | 对这里的启发                         |
| -------------- | ------------------------------------------------------------ | ------------------------------------ |
| Axon           | 快照不可用时忽略快照，从事件重放                             | **可以自动修缓存**                   |
| MediaWiki      | 页面或依赖变化后让缓存失效并重渲染                           | **可以自动修展示层**                 |
| Terraform      | 用 refresh-only 先展示漂移；旧 refresh 会不经检查直接覆盖状态，因此官方更推荐先看计划再决定 | **有语义选择时不要自动落账**         |
| Argo CD        | 只有声明源明确权威、且用户打开自动同步／自愈时才自动改；自动删除默认还有额外保护 | **自动修复必须有明确权威方向和授权** |
| Ink            | 故事内容升级后尝试兼容旧存档，但明确警告不可能完美，并记录运行时警告 | **版本迁移只能尽力，不能假装无损**   |

([AxonIQ Docs](https://docs.axoniq.io/axon-framework-reference/5.2/snapshotting/))

✅ **在小说系统里，安全的自动修复只有：**

- 删除旧快照；
- 从现行源账重新计算；
- 更新投影检查点；
- 重建索引；
- 让人物页、时间线和执行包重新读取同一结果。

❌ **不应自动做：**

- 猜人物已经离场；
- 猜物品已经转手；
- 在两条硬事实之间替作者选一条；
- 把未确认计划并入已发生状态；
- 因为人物页显示某值，就反过来修改事件账；
- 为了消掉 stale 而伪造补丁事件。

最危险的坑不是“缓存旧了一会儿”，而是**系统为了让界面重新变绿，偷偷补了一条故事事实**。

## 4. 四套投影怎样避免各算各的：统一计算语义，消费者只筛选和展示

Redux 的官方架构建议是：底层状态尽量少，能计算出的值不要再存一遍；通过统一 selector 封装计算，并用 memoization 避免输入未变时重复计算。Microsoft CQRS 则让同一批事件生成不同读模型，但这些读模型都是只读视图，可以从同一个事件源重建。([Redux](https://redux.js.org/usage/deriving-data-selectors))

对你这个场景，更合适的公开形状不是“人物页、检查器、时间线、执行包各自有一套代码”，而是：

```text
同一个查询边界
（项目／分支、已确认提交点、故事内时点、读取范围）
                         ↓
事件＋关系边＋知情硬账＋计划
                         ↓
              同一版本的一致读取
                         ↓
           统一的状态归约与派生计算
              ├─ 当前地点／包含关系
              ├─ 持有物
              ├─ 物理在场／场景参与
              ├─ 故事线相关性
              ├─ 倒计时／冷却
              └─ 依据、覆盖、新鲜度
                         ↓
          一份可复用的派生结果
              ├─ 人物页只负责展示
              ├─ 时间线只负责排序展示
              ├─ 检查器只负责比较和报灯
              └─ 执行包只负责筛选最小充分子集
```

🔥 **“一次计算、多处读取”指的是共享同一套语义和同一输入版本，不是生成一个全书巨型对象塞给所有地方。**

实际可以按人物、场景、故事线和查询范围分别缓存，但缓存键至少要区分：

- 当前项目或分支；
- 已确认源账提交点；
- 故事内查询时点；
- 计算规则版本；
- 查询对象与范围。

所有跨账读取还要锁在同一个提交点。不能人物事件读到第 102 版，知情账只读到第 99 版，然后拼成一个看似完整的答案。投影系统通常通过检查点记录自己处理到哪里；Kurrent 公开说明投影从检查点恢复时，只检查其后的事件，以判断是否追到最新位置。([Kurrent Docs](https://developers.eventstore.com/server/v24.10/features/projections/))

### 四个消费者允许做什么

| 消费者 | 可以做                           | 不可以做                     |
| ------ | -------------------------------- | ---------------------------- |
| 人物页 | 选择人物字段、折叠历史、显示依据 | 自己计算另一套当前位置       |
| 时间线 | 按故事时间／叙述时间排序         | 把排序结果反写成事实         |
| 检查器 | 比较两份统一派生结果、报告异常   | 私自更新人物页缓存消除异常   |
| 执行包 | 从统一结果中裁出当前任务所需部分 | 为了凑上下文自行推断缺失状态 |

## 5. 最小计算图建议

下面是**适配你给定约束的设计推导**，不是外部产品已经验证过的一套小说字段方案。

### 输入

| 输入                 | 进入实际状态计算的条件   | 作用                                   |
| -------------------- | ------------------------ | -------------------------------------- |
| 已确认事件／事实变化 | 已发生、有依据或作者确认 | 位置、转手、受伤、时间经过等变化       |
| 已确认关系边         | 在当前故事时点有效       | 人—人、人—物、人—势力、人—线的连接     |
| 知情硬账             | 有硬状态和原文锚         | 谁知道、谁不知道、谁被误导             |
| 计划                 | 始终保持计划身份         | 只影响未来约束、预演和执行包目标       |
| 查询边界             | 必须明确                 | 算哪个分支、哪个提交点、故事内什么时候 |

计划可以参加“计划中的场景”和“下一步执行包”编译，但**不能进入当前已发生状态归约**。

### 计算与输出

| 输出                 | 怎么算                                           | 遇到缺口怎么办                           | 执行包                           | 真值地位   |
| -------------------- | ------------------------------------------------ | ---------------------------------------- | -------------------------------- | ---------- |
| **当前所在**         | 截至查询时点，归约已确认的位置变化；支持包含关系 | 没有明确位置则未知；两个硬位置并存则冲突 | 涉及人物必带                     | ❌ 派生结果 |
| **持有物**           | 物品转移事件＋人／容器包含链                     | 所有权和物理持有不清时分开回答           | 只带与本场有关或会约束剧情的物品 | ❌ 派生结果 |
| **物理在场人物**     | 当前地点与场景地点相同，且没有后续离开／移走依据 | 漏离场时显示延续依据和不确定性           | 当前场核心内容                   | ❌ 派生结果 |
| **本场参与人物**     | 本场已确认行动、对话、被观察或远程参与事件       | 不能只从同地点推出                       | 当前场核心内容                   | ❌ 派生结果 |
| **线相关人物**       | 线的直接关联＋线上事件参与者＋受限范围的关系连接 | 必须返回“为什么相关”；不能无限沿图扩散   | 只带当前活跃、直接相关部分       | ❌ 派生结果 |
| **倒计时／冷却剩余** | 原始截止点或持续时长减去当前故事时间             | 缺起点、单位或故事时间时返回未知／区间   | 只带即将到期或影响当前决策者     | ❌ 派生结果 |
| **计划后的预计状态** | 从计划单独预演                                   | 永远标计划，不覆盖实际状态               | 可作为目标／禁做约束             | ❌ 计划投影 |

倒计时采用“原始触发或截止依据＋当前故事时间现算”是成熟系统中常见的形状。Unreal 提供的是对当前激活冷却剩余时间的查询，Temporal 则把定时器的开始与完成放在事件历史里。两者都支持“剩余时间是查询结果，而不是另一份独立事实”。([Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/UGameplayAbility))

### “线跟谁有关”要限制扩散

这是最容易把执行包撑爆的输出。

建议只纳入：

1. 明确挂在该线上的人物；
2. 该线已确认事件的参与者；
3. 当前未解决事件直接涉及的人；
4. 当前场所需、且能给出短依据路径的关系对象。

不建议把关系图整个连通分量都算进来。否则主角认识某人、某人属于一个势力、该势力又认识几十个人，算到后面全书所有人物都“跟这条线有关”。

每个被纳入的人都应能回答一句：

> 因为他参与了该线的哪条事件，或通过哪条直接关系影响当前未决问题。

这套限定规则属于**待验证设计推导**，公开系统能支持的是“派生结果应保留依赖和可重建性”，并没有现成的网文故事线相关性标准。

## 执行包和检修口的分工

### 允许进执行包

只放当前任务的最小充分内容：

- 当前场地点；
- 当前参与人物；
- 这些人物的相关持有物；
- 这些人物需要遵守的知情边界；
- 当前线直接相关人物及一行理由；
- 即将到期或会改变当前选择的倒计时；
- 有 stale 时的一行风险提示；
- 计划目标，但明确标为尚未发生。

### 只进检修口

- 完整事件重放轨迹；
- 每个结果的全部支持依据；
- 所有历史位置；
- 全量物品清单；
- 所有线相关候选和关系路径；
- 全部倒计时；
- 缓存检查点、计算规则版本；
- stale 的失效事件；
- 未确认提案；
- 覆盖范围与未读取材料；
- 场景边界缺失的入场／离场线索。

### 禁止物化成真值

下面这些可以缓存、展示、导出，但不得成为独立真值：

- “人物当前在某地”这一汇总结论；
- 场景当前人物名单；
- 当前持有物清单；
- 故事线相关人物集合；
- 倒计时还剩几天；
- 人物页当前摘要；
- 时间线排列结果；
- 检查器结论；
- 执行包；
- 计划预演后的状态；
- 模型推测的离场、转手或知情变化；
- soft guess，包括读者大概猜到什么。

对应的**位置变化事件、物品转移事件、原始期限、确认关系和知情硬状态**可以是真值；它们计算出来的“当前结果”不是。

## 对候选方向的逐项判词

| 候选方向                         | 外部调查判词 | 要补的限定                                       |
| -------------------------------- | ------------ | ------------------------------------------------ |
| 当前状态从事件＋关系边＋知情现算 | ✅ 支持       | 必须明确 as-of 查询边界                          |
| 谁在场现算                       | ✅ 支持       | 区分物理同处与本场参与；场景名单只作计划／核对   |
| 线跟谁有关现算                   | ✅ 支持       | 必须限制扩散，并返回纳入理由                     |
| 对不上亮 stale，不自动改账       | ✅ 强支持     | stale、未知、待确认、硬冲突分开                  |
| 长篇允许快照                     | ✅ 支持       | 只读、带检查点和规则版本、可丢弃重建             |
| 倒计时／冷却挂原始事件上         | ✅ 支持       | 剩余值现算；故事时间不足时返回未知               |
| 四套投影共享一次计算             | ✅ 强支持     | 共享计算语义、源版本和检查点；各端只能筛选和渲染 |

## 证据边界

**公开资料已验证：**

- 事件＋快照＋尾部重放是长事件流的成熟工程形状；
- 快照可以只作性能优化，失败时回到事件重放；
- 投影与渲染缓存应带源版本、依赖和过期机制；
- 显式位置与包含关系能够统一回答人物位置和物品携带；
- 自动修复适合重建缓存，不适合替用户决定有歧义的状态；
- 统一 selector／投影层可以避免多处重复维护派生值。

**本报告的适配推导，仍需你们实测：**

- 场景边界缺少离场时的具体提示方式；
- “物理在场／本场参与”两种查询的前台表达；
- 故事线相关人物的扩散深度；
- 哪些倒计时进入执行包；
- stale 对作者确认负担的影响；
- 快照放在关章、事件数阈值还是读取耗时阈值最合适。
