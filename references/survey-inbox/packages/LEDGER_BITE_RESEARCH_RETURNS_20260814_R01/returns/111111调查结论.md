# 调查结论

✅ **“公共门牌同构”可以成立，而且应当尽早定成所有一等对象的共同纪律。**

但要把边界说清：

> **同构的是身份、类型、版本、来源、生命周期和引用协议；不是把人物、地点、物品、计划事件、事实句塞进同一套内容字段，更不是把计划与事实合账。**

公开产品与标准反复出现两种成熟形态：

- **一个资源登记层，靠类型区分内容**：同一套 `id＋type＋版本＋引用`，类型再决定具体字段。
- **人物、物品等分成不同文档或表，但继承同一个基础外壳**：物理上分开，身份协议、引用方式、版本规则仍一致。

Foundry VTT 就是第二种：Actor 和 Item 是不同文档类型，却都继承统一的 Document 体系，共有 `_id`、`name`、`type`、系统数据和统计元数据。articy:draft 也给不同对象统一的、不可修改的 Object ID，再用对象类型和模板扩展各自字段。([Foundry Virtual Tabletop](https://foundryvtt.com/api/v11/classes/foundry.abstract.Document.html))

🔥 **所以真正必须统一的不是“一张万能表”，而是“一套门牌合同”。**

检索口径：官方产品帮助页、官方 API 文档、W3C／Wikimedia／JSON:API 标准；核对日期为 **2026 年 8 月 14 日**。

## 1. 业界是否真的共用一套门牌外壳

### 长篇创作工具：Novelcrafter

Novelcrafter 把人物、地点、物品等放在同一个 Codex 中，条目按系统规定的类型分类；不同类型会获得不同能力，例如只有 Character 能成为场景 POV。名称、昵称和别名进入统一识别与追踪，相关条目可以互相引用。它还用 Progressions 表达人物年龄、关系、政治局势等随时间变化的内容。([novelcrafter](https://www.novelcrafter.com/help/docs/codex/codex-types))

它给出的一个直接反例是“双重身份人物”：官方推荐优先保留**一个条目**，把其他身份和名字登记成 aliases，而不是每个名字建一个人物。([novelcrafter](https://www.novelcrafter.com/courses/codex-cookbook/dual-nature-characters))

⚠️ Novelcrafter 的公开文档能证明“共同条目外观＋类型＋别名＋引用”，但没有公开其数据库主键、删除墓碑或不可变版本结构，不能把这些内部细节当成已验证事实。

### 世界观 Wiki／TRPG：Kanka

Kanka 有人物、地点、组织、家族、事件、时间线、日历等二十多类条目，但公开口径是“所有内容放在一处并互相连接”；所有实体都可以拥有关系、附加文章、秘密和文件。它的高级引用实际写成 `[entity:123]`，显示文字可以单独改成 `Alex`，说明**目标身份与界面显示名已经分离**。([Kanka](https://kanka.io/))

Kanka 还把创建、修改、删除、恢复放进通用历史日志，删除条目可在一定期限内恢复；事件甚至可以转换成物品，说明类型变化和生命周期不是每类对象各写一套孤立机制。([Kanka](https://docs.kanka.io/en/latest/guides/bulk.html))

### 游戏叙事系统：articy:draft

articy:draft 对流程节点、对话、实体、地点等对象使用统一且不可修改的 Object ID；另有 Technical Name、External ID、Template 和 References。模板是在基础对象参数之上增加项目专用字段，引用槽还能限制允许指向的对象类型或模板。([Articy](https://www.articy.com/help/Flow_Sheet.html))

对象被删除后，引用它的其他对象不会被当成“从未引用过”，而是会被冲突检查找成“指向已删除对象的无效引用”。这对长篇检修非常关键。([Articy](https://www.articy.com/help/ad3/UI_Conflicts.html))

### 游戏实体与 TRPG 运行时：Foundry VTT

Foundry 将 Actor、Item、Journal、Card 等分成不同 Document 类，但所有文档都继承共同基础类，并由 `_id` 引用。Actor 与 Item 公开 Schema 中都出现 `_id`、`_stats`、`name`、`type`、`system`、`flags`、`ownership` 等共通字段。([Foundry Virtual Tabletop](https://foundryvtt.com/api/v11/classes/foundry.abstract.Document.html))

这证明了一件事：

> **分表或分文档类型，不等于必须分成互不兼容的门牌体系。**

### 事实陈述系统：Wikibase／Wikidata

Wikibase 的实体有 `id`、`type`、labels 等共同身份信息；事实不是把所有内容直接写在实体外壳上，而是拆成 Statement。每条 Statement 由主张、限定信息和 references 组成，时间有效期等信息挂在 Statement 的 qualifiers 上。([Wikimedia Open Source](https://doc.wikimedia.org/Wikibase/master/php/rest_data_format_differences.html))

这正好说明：

- 人物、地点、组织等可以是实体；
- “某人于某段时间属于某组织”更适合成为带来源和有效期的陈述或关系；
- **来源与时间不应只挂在人物或组织的总门牌上。**

## 2. 门牌外壳通常有哪些字段

业界没有唯一统一名称。常见叫法包括：

- `resource object`
- `base document`
- `system fields`
- `object identity`
- `content type`
- `document type`
- `template`

JSON:API 对通用资源的最低要求就是 `type＋id`，关系目标也用 `type＋id` 表达；Foundry 称为 Document，Sanity 称为 document system fields，articy 称 Object ID 与 Template。([JSON:API](https://jsonapi.org/format/))

下面是公开体系反复出现的 **8 个字段族**。这些是业界叫法，不是建议直接拿来当你们合同字段名。

| 字段族       | 业界常见叫法                                              | 应承担什么                                   |
| ------------ | --------------------------------------------------------- | -------------------------------------------- |
| 稳定身份     | `id`、`identifier`、`UUID`、`Object ID`                   | 永久认出“还是同一个东西”，不能跟着改名变化   |
| 类型判别     | `type`、`document type`、`content type`、`template`       | 决定允许哪些专用字段、校验和界面能力         |
| 人类可读名称 | `name`、`label`、`title`                                  | 给作者、检修界面和日志看；绝不能拿它当主键   |
| 别名         | `aliases`、`alternate names`、`nicknames`                 | 旧名、化名、简称、其他语言名、历史称呼       |
| 修订身份     | `revision`、`version`、`_rev`、`lastrevid`                | 回答“这次引用的是哪一版”以及并发修改是否冲突 |
| 来源与责任   | `references`、`provenance`、`attribution`、`derived from` | 回答谁声明、从什么材料得到、经什么动作形成   |
| 生命周期     | `archived`、`in_trash`、`deleted`、`tombstone`            | 区分当前有效、归档、软删除、已合并和永久删除 |
| 引用关系     | `relationships`、`references`、`links`                    | 指向其他对象，不复制另一份内容               |

其中，版本字段在 Contentful、Sanity、Wikibase 等系统中都是通用系统元数据；归档／回收状态也出现在 Contentful、Notion、Kanka 等通用对象上，而不是只有某一种内容才有。([Contentful](https://www.contentful.com/developers/docs/references/content-management-api/entries/))

### 对计划事件和事实句的特殊说明

**已验证：**公开创作工具通常不会把事实句和人物卡做成完全相同的内容模板；Wikibase 也把实体与 Statement 分开。([MediaWiki](https://www.mediawiki.org/wiki/Wikibase/DataModel))

**推论：**只要计划事件或事实句会被其他对象引用、会修订、会撤回、会追来源，它们就已经是一等对象，应该获得同构门牌：

- 有稳定 ID；
- 有类型；
- 有当前版本；
- 有来源；
- 有生命周期；
- 能被统一指针指到。

这不意味着计划事件与事实句同表，更不意味着共用发生状态。**它们只共用身份证格式，不共用真值资格。**

## 3. 类型应放一个登记表，还是分表共享外壳

✅ **推荐语义：一个逻辑登记层＋类型专用内容层。**

数据库物理形态可以晚点决定。

你可以直接理解成：

```text
共同登记层
  ├─ 身份
  ├─ 类型
  ├─ 当前显示
  ├─ 当前修订
  ├─ 生命周期
  └─ 通用寻址

类型专用内容
  ├─ 人物专用资料
  ├─ 地点专用资料
  ├─ 势力专用资料
  ├─ 物品专用资料
  ├─ 计划事件专用内容
  └─ 事实句专用内容与证据
```

这类做法在工程里通常叫 **supertype/subtype（父类型／子类型）** 或 **base document＋typed payload（基础文档＋类型载荷）**。

### 两种物理做法都成立

**一种登记表、类型枚举：**

- Sanity 的文档都有不可变 `_id`、`_type`，并有 `_rev`、创建和更新时间；具体文档类型再定义自己的字段。([Sanity.io](https://www.sanity.io/docs/content-lake/schema-and-content-migrations))
- JSON:API 用 `type＋id` 唯一定位资源，属性和关系再按类型展开。([JSON:API](https://jsonapi.org/format/))

**不同表或文档类，但共享外壳：**

- Foundry 的 Actor、Item 分开，却继承共同 Document 外壳。([Foundry Virtual Tabletop](https://foundryvtt.com/api/v11/classes/foundry.abstract.Document.html))
- articy 的流程节点、对话、实体等是不同对象类型，却共用 Object ID、技术名、模板和引用系统。([Articy](https://www.articy.com/help/Flow_Sheet.html))

### 怎样防止人物系统、地点系统后来各长各的

建议把下面六件事收归公共层，而不是让每个类型自己写：

1. **ID 分配与解析**：任何一等对象走同一套永久身份规则。
2. **别名解析**：人物、地点、组织、物品都走同一查询和去重入口。
3. **版本规则**：同一套当前版、历史版、并发冲突和回滚语义。
4. **删除／归档／合并规则**：同一套墓碑、恢复、重定向和断链检测。
5. **引用解析器**：所有指针统一判断当前目标、固定版本、已删除目标和重定向目标。
6. **类型专用校验**：只有内容字段和业务限制下沉到人物、地点等各自模块。

Kanka 把不同实体的关系、历史与恢复做成通用能力；articy 把对象 ID、模板和引用槽做成公共机制；Foundry 把不同文档挂在共同 Document 基类下。这些都支持上述归纳。([Kanka](https://docs.kanka.io/fr/latest/overview.html))

🔥 **一句话裁定：一张表不是必须，一套身份与生命周期协议是必须。**

没有证据支持地点、势力、物品必须各自另造一套版本、别名和删除规则。Foundry 这种“分类型存、共外壳”的公开反例，已经足以排除“内容差异大，所以门牌无法同构”的说法。([Foundry Virtual Tabletop](https://foundryvtt.com/api/v11/classes/foundry.abstract.Document.html))

## 4. 来源身份和版本应该挂在哪里

### 来源不能只挂在总门牌上

Wikibase 把 references 挂在具体 Statement 上，qualifiers 也修饰具体 Statement，而不是笼统挂在整个实体上。一个实体可以同时存在多个来源、多个时间段甚至互相冲突的陈述。([MediaWiki](https://www.mediawiki.org/wiki/Wikibase/DataModel))

W3C PROV 也把“由谁负责”“从什么派生”“是哪一版的修订”表达为实体或修订间的 provenance 关系，包括 `wasAttributedTo`、`wasDerivedFrom`、`wasRevisionOf`。([W3C](https://www.w3.org/TR/prov-o/))

因此更稳的分工是：

| 层               | 放什么                                                |
| ---------------- | ----------------------------------------------------- |
| 门牌层           | 稳定 ID、类型、当前显示名、当前修订指针、当前生命周期 |
| 修订层           | 这一版的实际内容、修改人、修改时间、来源、派生过程    |
| 陈述／关系层     | 这条具体判断的来源、限定、有效时间、置信或争议状态    |
| 门牌上的来源摘要 | 可以有，但只能是方便检索的当前汇总，不能代替逐条来源  |

你们的“作者声明／旧稿反推／模型建议”可以映射到业界的 attribution、derived-from、generation activity 等来源机制。

⚠️ **这是产品适配推论。**本次没有找到公开产品恰好使用这三个中文来源类别；已验证的是“来源应能跟随具体内容、陈述或修订，而不应只在整个实体上留一个单值标签”。

### 版本也要分两层

更稳的是：

- 门牌保存“当前版是谁”；
- 每次修订产生一个不可变的 revision；
- 旧版继续可追溯；
- 普通界面引用可以跟随当前版；
- 证据、发布版本、作者签字结果要能钉住确切 revision。

Contentful 更新条目时要求提交当前版本号，Sanity 为每个文档维护 `_rev`，Wikibase 返回实体修订 ID。它们都没有把“对象 ID”和“内容版本”混成一个值。([Contentful](https://www.contentful.com/developers/docs/references/content-management-api/entries/))

### 改名、换装、设定修订应怎样理解

- **改名**：稳定 ID 不变；当前显示名变化；旧名进入别名或历史名称。
- **换装、受伤、成长**：通常是同一实体的状态／外观修订，不是新实体。
- **势力改名**：先判断是不是同一组织延续；若是，ID 不变，名称带有效期；若是组织解散后另组新组织，才应是两个实体并建立承接关系。
- **设定改判**：同一对象产生新 revision，旧章和旧判断仍能说明自己当时依赖哪一版。
- **身份揭露**：同一个人只是过去有多个称呼，优先一个实体＋多个别名；真的是两个人，才拆成两个 ID。

Novelcrafter 对双重身份人物明确推荐“单一条目＋其他身份作为 aliases”。([novelcrafter](https://www.novelcrafter.com/courses/codex-cookbook/dual-nature-characters))

### 已被公开系统证实的失败面

**名字当身份：**

Unity 官方文档明确说明，修改 GUID 会被视为删除旧资产再加入新资产，原引用因此断裂；使用 GUID 而不是名称引用，则允许改名而不必更新所有依赖。

**路径／文件名当身份：**

Obsidian 必须提供“改名时自动更新内部链接”功能；aliases 则另行处理昵称、缩写和不同语言名称。这说明名称型链接并非不能用，但需要持续做全库重写和别名补偿。([Obsidian](https://obsidian.md/help/links))

**删除后静默消失：**

articy 会专门报告所有仍指向已删除对象的引用；Kanka 则保留操作历史和删除恢复窗口。([Articy](https://www.articy.com/help/ad3/UI_Conflicts.html))

对长篇连载来说，最危险的不是“页面打不开”，而是：

> 引用失败后系统把它解释成“从来没有这个对象”，造成静默漏读。

## 5. “指针槽”最小需要表达什么

单存一个目标 ID，只够做最简单的当前链接。长篇真源系统的安全最小值建议分两档。

### 所有指针都要有

| 能力         | 回答的问题                                         |
| ------------ | -------------------------------------------------- |
| 目标身份     | 指向谁：全局唯一 ID，必要时连同目标类型            |
| 关系角色     | 为什么指：出现于、属于、持有、发生在、依据、替代等 |
| 版本解析方式 | 跟随目标当前版，还是固定到某一版                   |
| 目标版本     | 选择固定模式时，究竟钉住哪一个 revision            |
| 指针状态     | 当前正常、目标归档、目标删除、已重定向、无法解析   |

JSON:API 的关系对象至少用 `type＋id` 指向目标；Kanka 用实体 ID 链接，同时允许显示文字另行指定；articy 的引用槽还可以限制目标对象类型或模板。([JSON:API](https://jsonapi.org/format/))

### 会随故事变化的关系，再加有效时间

适合增加故事内有效区间的包括：

- 人物属于哪个势力；
- 物品当前归谁；
- 人物当前位于哪里；
- 某个称呼在什么阶段使用；
- 某段关系何时成立、破裂、恢复；
- 某外观、伤势、身份或能力状态何时有效。

Wikidata 允许用 start time、end time 和 point in time 修饰陈述，并明确说明它们用于表示某条陈述在什么时期为真。([Wikidata](https://www.wikidata.org/wiki/Help%3ADates))

### 两种时间不能混成一个

这里至少有两条时间轴：

- **故事内有效时间**：世界里什么时候为真。
- **系统修订时间**：作者或系统什么时候登记、修改、撤销。

Wikibase 的时间 qualifiers 表达前一种；W3C PROV 的 generated／invalidated time 更偏对象或版本的产生、失效时间。([Wikidata](https://www.wikidata.org/wiki/Help%3ADates))

说白了就是：

> “角色在故事第十天加入势力”与“作者在 8 月 14 日补登记这条信息”绝不能共用一个时间字段。

### 哪些体系用有效区间，哪些偏当前指针＋历史日志

**明确使用陈述有效区间：**

- Wikibase／Wikidata：Statement qualifiers 可带开始、结束、时点及来源。([Wikidata](https://www.wikidata.org/wiki/Help%3ADates))

**公开文档更偏当前对象＋版本／历史：**

- Kanka：当前实体引用加创建、修改、删除、恢复日志。([Kanka](https://docs.kanka.io/en/latest/features/mentions.html))
- Contentful：当前条目有版本控制，并支持归档／取消归档。([Contentful](https://www.contentful.com/developers/docs/references/content-management-api/entries/))
- Sanity：当前文档有不可变 ID、类型和持续更新的 `_rev`。([Sanity.io](https://www.sanity.io/docs/content-lake/schema-and-content-migrations))
- articy：引用默认指当前对象，删除后进入可检测的无效引用。([Articy](https://www.articy.com/help/ad3/UI_Conflicts.html))

这些公开文档没有展示一套覆盖所有普通引用的通用 `valid-from／valid-to`。因此，不应给每个链接强塞时间区间。

✅ 推荐分工：

- 普通界面跳转、当前人物卡、规划引用：默认跟随当前版。
- 冻结书稿证据、作者签字事实、发布章回执：固定确切版本。
- 归属、持有、位置、名称、状态等会变化的关系：增加故事内有效区间。
- 普通静态引用：不要求填写有效区间，默认开放区间即可。

## 6. 所有一等对象的必备清单

这里要区分 **“必须有值”** 和 **“必须具备统一能力，但允许为空”**。

| 项目                 | 建议纪律                                                     | 严禁只给谁                                    | 缺失后的长篇故障                                             |
| -------------------- | ------------------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------ |
| **稳定 ID**          | 所有一等对象必须有；创建后不因改名、移动、换类型展示而变化；不复用旧 ID | 严禁只有人物有                                | 地点改名后场景失联；物品转手后被重建成新物品；同名人物串账   |
| **显示名／可读标签** | 所有用户可见对象必须能显示人话名称；事实句、计划事件可用句子本身或自动短标题；不能当主键 | 严禁只有实体卡有                              | 检修页全是裸 ID，作者只能复制内容判断是哪条，误签率上升      |
| **别名机制**         | 所有“有名字的对象类型”共用；允许列表为空；别名应能带来源、状态，必要时带有效期 | 严禁只给人物有                                | 地点旧称、势力简称、物品代号无法命中；旧名被误建成第二实体   |
| **类型**             | 所有一等对象必须可判型；类型变化走受控迁移，不从文件夹、表名或前缀临时猜 | 严禁只有共享实体登记有                        | 引用槽无法限制目标；人物被当地点渲染；计划与事实走错确认规则 |
| **来源身份**         | 所有内容修订与陈述必须可回到来源；权威细节挂修订／陈述，门牌只留当前摘要 | 严禁只有事实句有                              | 模型建议被当作者决定；旧稿反推内容覆盖作者新设定；无法解释谁改了什么 |
| **版本／修订**       | 所有可变化对象必须有当前版和历史版；冻结引用可钉住确切版     | 严禁只有书稿或人物有                          | 改设定后无法判断旧章引用的是改前还是改后；检修结果无法复现   |
| **删除／归档**       | 所有对象共用生命周期语义；至少区分归档、软删除、墓碑／重定向、永久删除 | 严禁各类型各写一套                            | 地点删除后相关场景静默消失；事实撤回后派生结论继续存在；恢复规则不一致 |
| **统一指针协议**     | 所有一等对象都必须可被同一种解析器寻址；不要求每个对象都有对外关系 | 严禁人物用 ID、地点用字符串、物品直接复制名称 | 改名要全库搜索替换；一条内容被复制到十处后长期漂移；版本与删除无法统一传播 |

这份清单与 JSON:API 的 `type＋id＋relationships`、Foundry 的 Document 外壳、articy 的 Object ID／Template／Reference、Kanka 的跨实体 ID 引用和通用历史机制方向一致。([JSON:API](https://jsonapi.org/format/))

### 还应补一条横向硬规则：合并／拆分／重定向

这不必另建真值账，但必须属于公共身份服务：

- 两个别名实体确认其实是同一个：合并后旧 ID 不能凭空死亡，应留下重定向或合并墓碑。
- 一个误合实体后来发现其实是两个人：拆分必须保留原操作历史和受影响指针。
- 删除目标仍被引用：显示断链，不得静默清掉。
- 改名：只改显示和别名，不改 ID。

Unity 的 GUID 断链、articy 的无效引用检测、Kanka 的历史／恢复都支持这一风险判断。

## 建议形成的裁定口径

### ✅ 可以现在确定

1. **所有一等对象必须服从同一门牌合同。**
2. **地点／势力／物品进入一种共享实体登记，用类型区分；不另造三套版本、别名和删除体系。**
3. **人物可以继续有专用人物内容页，但门牌外壳、引用解析和生命周期应与共享实体登记同构；物理上是否同表不影响这条。**
4. **计划事件与事实句继续分账、分状态、分确认权，但都获得同构身份外壳。**
5. **名称只负责显示与检索，稳定 ID 才是引用身份。**
6. **来源详情挂修订或具体陈述，门牌只保留当前来源摘要。**
7. **普通指针默认跟随当前版；证据和冻结结果固定版本；故事内有效区间只加给真正会随时间变化的状态与关系。**
8. **删除、归档、合并、拆分、重定向和断链检测必须走公共机制。**

### ⚠️ 不应被这次调查提前拍死

- 最终是一张物理表，还是共同登记表加类型子表；
- 类型枚举的完整清单；
- 哪些关系必须有故事内有效区间；
- 有效区间的精确字段名和空值规则；
- 规则／能力／例外是否拆成独立对象；
- 读者承诺是否单开对象。

### 证据边界

**已验证：**

- 多类对象共享稳定身份、类型、显示、引用和生命周期是成熟重复模式；
- 分表并不妨碍共享外壳；
- 名字或路径充当身份会产生改名传播成本；
- 来源和有效时间适合挂在具体陈述／修订上；
- 当前指针＋历史日志与显式有效区间是两条真实存在的行业路线。

**调查归纳，不是某个产品原样合同：**

- 把作者声明／旧稿反推／模型建议整理成统一来源分类；
- 要求计划事件和事实句也成为可寻址的一等对象；
- 上述八项门牌清单的具体组合；
- “默认当前版、证据固定版、可变关系加有效区间”的分流规则。

本次没有找到一个公开产品把“人物／地点／组织／物品／计划事件／事实句”六类完整公开成同一张 Schema。结论来自创作工具、TRPG、游戏叙事系统、内容平台和知识图谱标准的交叉证据，而不是声称已经存在一款可整套照搬的产品。
