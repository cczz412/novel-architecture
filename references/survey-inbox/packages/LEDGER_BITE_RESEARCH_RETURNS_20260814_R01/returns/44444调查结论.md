# 调查结论

✅ **公开系统没有把“世界规则”统一塞进一种容器。成熟做法通常分成三层：**

1. **给人读的材料**：世界观文章、门派说明、魔法原理、背景设定。
2. **可稳定引用的定义**：某条规则、某个能力、某种状态效果有独立身份，其他对象可以指向它。
3. **可计算的运行记录**：谁获得了能力、用了几次、冷却是否结束、临时效果何时消失。

创作工具和世界观 Wiki 主要停在前两层；游戏与互动叙事引擎大量使用第二、第三层。([novelcrafter](https://www.novelcrafter.com/help/docs/codex/anatomy-codex-entry))

🔥 因而，A／B／C 不是简单的“低配、中配、高配”，而是在承诺三种不同能力：

- **A 承诺能找到材料。**
- **B 承诺能准确指到某一条。**
- **C 承诺能回答此刻是否成立、还能不能用。**

最危险的不是选了哪档，而是**存储只有 A，却让检查器表现得像 C**；反过来，把所有世界观都按 C 拆，也会让作者先填完一套游戏数据库才能写故事。

公开研究把这种中间路线叫“逐步结构化”：允许人话材料和结构化对象并存，只有真正需要检索、引用或推理的部分逐步升级，而不是一次把整个知识域形式化。([ACM Digital Library](https://dl.acm.org/doi/abs/10.1145/306686.306690?utm_source=chatgpt.com))

> 调查口径：只使用公开产品文档、开源项目文档和研究论文；访问日期为 **2026 年 8 月 14 日**。下文的 A／B／C 是我为了对照你给出的三档做的映射，不是这些产品自己的术语。

# 1. 四类系统里，规则和能力通常住哪

## 长篇创作工具：以“文章／条目＋弱结构”为主

| 产品                      | 公开设计                                                     | 对应档位 |
| ------------------------- | ------------------------------------------------------------ | -------- |
| **Novelcrafter Codex**    | 人物、地点、物品等住在独立 Codex 条目中；条目可以互相关联，系统按名称和别名追踪正文、规划和聊天里的提及，并决定何时把内容送入 AI。它能稳定引用对象，但公开文档没有显示一套用于计算冷却、次数和规则例外的运行时规则引擎。 | A＋轻 B  |
| **Campfire Magic Module** | 用专门面板和说明手册组织魔法体系、法术、药剂等，更像结构化设定集；重点仍是作者整理和阅读。 | A＋轻 B  |
| **Plottr**                | 场景卡可以增加自定义属性，但官方支持的属性仍是短文本或段落文本，主要用于记录目标、动机、冲突等，不是可执行条件。 | A        |

Novelcrafter 的“Tracking”明确依赖名称／别名检测；Campfire 用面板和 Guidebook 描述魔法；Plottr 的自定义属性只有文本和段落两种。([novelcrafter](https://www.novelcrafter.com/help/docs/codex/anatomy-codex-entry))

**调查归纳：**长篇创作工具普遍愿意给设定一个门牌，但很少承诺“现在还能使用几次”这类确定性答案。它们主要解决作者找得到、AI 能读到，而不是运行规则。

## TRPG／世界观 Wiki：文章优先，按需增加条目和数值

| ---------------- | ------------------------------------------------------------ | ----------- |
| **World Anvil**  | 核心是文章。不同模板提供角色、组织、语言等提示项，但所有模板都有自由写作区，提示项也是可选的，整篇都写在自由区也可以。 | A＋可选 B   |

World Anvil 和 LegendKeeper 都把自由文本放在中心，只把模板与属性当辅助；Kanka 则在保留 Wiki 条目的同时，对“能力、次数、HP、等级”等少数高频机械量增加了计算能力。([世界锻造](https://www.worldanvil.com/learn/article-guides/articles))

**调查归纳：**TRPG Wiki 最接近“不是整本全拆，而是某些东西升格”。普通历史、文化和传说继续是文章；能力次数、角色数值、日历事件等才进入较硬的结构。

## 游戏 ability／buff 系统：定义和运行实例明确分开

| 系统                               | 公开设计                                                     | 对应档位 |
| ---------------------------------- | ------------------------------------------------------------ | -------- |
| **Unreal Gameplay Ability System** | Ability 定义能做什么、使用成本、可用条件；Gameplay Effect 负责即时、限时或永久修改属性，并支持标签要求、应用条件、叠层、溢出和独立计时。冷却本身通常也是一个正在生效的限时 Effect。 | 完整 C   |
| **Foundry VTT Active Effects**     | 效果定义可以来自角色、状态或物品；真正生效时挂到 Actor 上，带持续时间，到期自动关闭。物品上的效果可以转移到角色。 | C        |
| **Cataclysm: DDA**                 | 法术、附魔和大量机制由带 ID 的 JSON 对象定义；条件对象可以由指定事件触发，检查条件后产生效果，也可以按频率运行或停止。能力还能定义消耗、合法目标、持续时间和充能方式。 | C        |

Unreal 明确区分能力定义、成本／冷却效果和运行中的效果实例；Foundry 区分物品或状态定义与角色身上的 Active Effect；CDDA 则大量采用“有 ID 的定义＋事件／条件＋效果”。([Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine))

**这里有一个很重要的先例：**

> 游戏系统不是不断手改“角色当前状态说明”，而是保留能力定义，再记录获得、使用、施加、移除、到期等运行实例，当前值由这些记录和时间计算出来。

这与“另一张手填当前状态真值表”不是一回事。

## 互动叙事引擎：文本节点之外，必须有变量和条件

| ---------------- | ------------------------------------------------------------ | -------- |
| **ink**          | 故事有命名节点；节点被访问多少次会自动成为计数，可以直接作为条件，例如某线索看过几次后才开放选项。另有变量和逻辑。 | B＋C     |
| **Yarn Spinner** | 节点之外有变量、条件、只运行一次的内容以及运行时计算的 Smart Variables。 | C        |

ink 的节点访问次数就是自动产生的状态；Yarn 把固定变量、运行时计算变量和“一次性”流程分开；articy 则明确拆成“属性／对象”“判断条件”“修改状态的指令”。([GitHub](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md))

**调查归纳：**一旦系统负责决定“这条剧情现在能不能发生”，纯文章就不够了。至少要有可引用对象、状态来源和判断条件。

# 2. 拆太早与拆太晚，各自怎么失败

## 拆太早：作者的工作从写故事变成维护数据库

### 失败一：被迫填大量当下用不到的格子

World Anvil 把模板提示设计成可选；LegendKeeper甚至直接强调不强迫用户填繁琐表单。2025 年一项覆盖 115 个工具、67 篇研究的创作工具调查也发现：作者确实普遍会规划，但固定模板不一定适合每个人，自建表格又很难长期维护；大型写作项目中，工具学习成本本身也会导致弃用。([世界锻造](https://www.worldanvil.com/learn/article-guides/articles))

常见画面是：

- 作者只是想写“此地常年下雪”，却要先决定这是世界物理、地区气候、临时异常还是神力影响。
- 新能力还没写稳定，就被要求填写消耗、目标、持续、冷却、叠层、例外、升级曲线。
- 作者为了过表单，随便填默认值；表面结构完整，内容其实不可信。

### 失败二：结构版本比故事变化更慢

硬结构一旦被正文、章节规划和状态记录引用，改名、拆分和改规则都会牵动下游。ink 官方甚至明确提醒：故事内容发生较大修改后，旧保存状态与新故事之间无法做到完美兼容；不存在的路径只能尝试向上回退并发出运行时警告。([GitHub](https://github.com/inkle/ink/releases))

放到小说里，就是：

- 原来设定“一天三次”，后来改成“每次使用消耗寿命”；
- 规则表已改，前 30 章的使用记录仍按旧次数计算；
- 检查器开始同时面对旧规则、现规则、改史边界和已经发生的例外。

### 失败三：例外语言不断膨胀

Unreal 的成熟能力系统为了接住真实游戏需求，最终要处理持续时间、标签要求、禁止条件、随机应用、叠层、溢出、重置计时和独立计时等大量组合。互动叙事研究也长期把“要管理的状态越来越多”视为作者负担。([Epic Games Developers](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-attributes-and-gameplay-effects?application_version=4.27))

⚠️ **“例外比规则还多”没有可靠公开数据可以量化。**但从这些系统的结构复杂度可以推断：如果小说产品现在就试图正式表达每一种借力、透支、临时豁免、隐藏代价和剧情性破例，很容易长成一套小型编程语言。

### 失败四：形式化本身成为维护瓶颈

知识工程研究把这个问题称作“知识／本体获取瓶颈”：结构更严谨后，开发、验证、连接和维护概念本身就需要大量工作。([Springer](https://link.springer.com/article/10.1007/s10115-003-0136-3))

说白了就是：**C 不只多一张表，它会带来版本、迁移、校验、冲突、缺失值和例外语义的一整串责任。**

------

## 拆太晚：能搜到不等于能判定

### 失败一：关键词没有命中，检查器就当不存在

Novelcrafter 的公开跟踪机制按条目名称和别名检测，并决定是否把内容发送给 AI。这适合找“魔法戒指”相关材料，但如果作者正文写的是“那枚旧银环”，设定条目也没有这个别名，系统就可能不加载对应信息。([novelcrafter](https://www.novelcrafter.com/help/docs/codex/anatomy-codex-entry))

如果规则只藏在长文中，类似问题还包括：

- “每逢月蚀失效”写在第七段，章纲只提“今晚血月”；
- “一天三次”在旧版设定中，后面补充改成“每十二个时辰三次”；
- 一次性破例只记录了事件，检查器不知道它破的是哪条规则。

此时绿灯只说明“这次没检索出来”，不能说明“没有违反”。

### 失败二：找到了定义，也回答不了当前值

知道“每天最多三次”，仍然不能回答“今天还剩几次”。系统还需要知道：

- 故事里的“今天”从哪里开始；
- 已经使用过几次；
- 某次是否失败但仍消耗次数；
- 临时赐予的一次额外使用是否已经消耗；
- 当前是否处在冷却或封印状态。

Kanka、Unreal、Foundry、CDDA 都专门保存 charges、运行中效果、持续时间、冷却标签、充能方式或使用事件，正是因为定义文本本身回答不了这些问题。([Kanka](https://kanka.io/features))

### 失败三：章纲违反规则，却因为没有明确引用而绿灯

这是一个**机制层推断**：

- 如果章纲只写“主角再次发动天眼”；
- 规则文章写“每天只能用三次”；
- 已发生事件记录了前三次使用；
- 三者之间没有稳定指针或可解析关系；

那么检查器只能临时猜测“天眼”对应哪项能力、哪些事件算使用、现在属于哪一天。任何一步没召回，都可能绿灯。

因此，A 可以做“相关材料检索”，但很难对外承诺确定性的“合法／非法”。

# 3. 金手指、门规、世界物理和一次性破例，是否应是同一家

✅ **业界通常会分家，但不一定分成四本账。更常见的是：共享对象身份，按语义类型采用不同检查方式。**

| 内容                       | 它是什么                     | 是否需要回答“现在还算不算数”       | 合适的业界类比                 |
| -------------------------- | ---------------------------- | ---------------------------------- | ------------------------------ |
| 世界背景、历史、文化习俗   | 描述性知识                   | 通常不需要                         | World Anvil／LegendKeeper 文章 |
| 世界物理硬限制             | 对世界可能性的约束           | 一旦参与检查就需要                 | 游戏规则、条件系统             |
| 门派规矩、法律、誓约式禁令 | 规范性规则：可以被违反       | 规则本身要查；人物是否遵守另查事件 | 条文＋违规／豁免事件           |
| 金手指／能力定义           | 能做什么、成本、目标、限制   | 经常需要                           | Unreal Ability、CDDA Spell     |
| 当前剩余次数、冷却、buff   | 运行状态                     | 必须                               | Active Effect、charges、变量   |
| 一次性破例                 | 某次事件对某条规则的局部覆盖 | 必须知道作用范围和是否到期         | 运行中的 Effect、事件触发规则  |
| 纯氛围性魔法描述           | 创作参考                     | 不需要                             | Campfire Guidebook             |

关键区别有三组。

## “不能”与“不许”不是一回事

- “死人绝不可能复活”是世界物理约束。
- “门人不得进入禁地”是规范，人物完全可能违令。
- “主角当前无法进入禁地”可能只是封印、身份或临时状态。

检查器如果把门规当物理规律，会把“违令闯入”误判成不可能；如果把世界物理当普通规矩，又可能把真正的设定冲突放过去。

## 能力定义与能力当前状态不是一回事

Unreal 中，Ability 定义成本和使用条件；冷却由正在生效的 Gameplay Effect 表达。Foundry 中，物品或状态保存效果定义，角色身上保存当前 Active Effect。([Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine))

对应到小说：

- “天眼每天可用三次”是定义；
- “今天已用两次”来自已发生事件；
- “师父临时解封一次”是例外事件；
- “现在剩两次还是一次”是计算结果。

四者不能压成同一句“当前状态”。

## 一次性破例不应自动升级为新世界规则

一次“燃烧寿命强行发动”可以只是：

> 本次事件引用基础限制，并说明为什么这一次被越过、代价是什么、何时结束。

只有当这种破例以后会反复适用，才有理由提名成新的通用条文。否则，每个戏剧性例外都转成全局规则，规则集很快会被具体剧情淹没。

# 4. 只增加一种“可引用单位”，最小要记什么

下面是依据公开系统归纳出的**最小语义要求**，不是你们已经确定的字段合同，也不是建议现在开完整规则表。

## 硬最小：六件事

1. **稳定身份**
   改标题、改措辞后，章纲和事件仍能指向同一条。ID 不能由自然语言标题兼任。
2. **一条可独立理解的人话条文**
   一条只表达一个核心限制或许可。长篇解释仍留在设定集，条文负责成为门牌，不负责复制整篇材料。
3. **适用范围**
   说明它约束谁、什么能力、什么地点、什么势力成员或什么情境。范围应引用共享实体，而不是再复制地点、势力、物品资料。
4. **故事内生效与失效边界**
   可以是某个事件之后、某段故事时间内、直到某事件发生；尚不确定时应明确未知，不能默认永远有效。
5. **来源和版本身份**
   能回到导入设定、作者确认或书稿证据中的具体位置，并知道当前条文对应哪个版本。否则改设定后无法判断旧事件当时服从的是哪一版。
6. **与例外、替代和废止的关系**
   允许指向“本次例外发生在哪个事件”“这条被哪条新规则替代”“本次只是违规而不是规则失效”。

这些要求对应了 articy 对对象 ID、属性、条件和指令的区分，CDDA 对规则 ID、事件触发、条件和效果的区分，以及游戏能力系统对定义和运行实例的区分。([Articy](https://www.articy.com/articy-importer/unity/ad3/html/howto_script.htm))

## 只有需要机器计算时，再附计算信息

并非每条都要有。只对金手指次数、冷却、资源消耗等增加：

- 计算单位是什么；
- 按什么时间窗口重置；
- 哪类事件算一次使用；
- 失败是否消耗；
- 哪些例外会加、减或暂停；
- 当前答案依据了哪些已发生事件。

🔥 **“剩余次数”不宜成为第二个手填真值。**较稳的模式是：

> 基础条文
> ＋已发生的使用／获得／解除事件
> ＋故事内时间
> → 查询时计算当前结果。

如果相关事件或时间不完整，答案应是“无法确定／覆盖不足”，而不是绿灯。

------

## 哪些系统接近“规则 ID＋事件上的例外”

严格说，公开创作工具中，我没有找到把“文学规则条文＋剧情破例事件”完整做成一等对象的成熟产品。最接近的是游戏和互动运行时：

### CDDA：最接近字面结构

`effect_on_condition` 有独立身份，可以：

- 由指定事件触发；
- 检查条件；
- 条件成立后产生效果；
- 条件不成立时执行另一效果；
- 满足停用条件后停止运行。

这几乎就是“规则定义＋触发事件＋局部结果”的公开实现。([DDA Docs](https://docs.cataclysmdda.org/JSON/EFFECT_ON_CONDITION.html))

### Unreal：定义与本次应用分开

Ability 保留定义；使用时提交成本和冷却；冷却是一个有持续时间的 Effect 实例。角色当前能否使用，查询运行中的 Effect 和标签即可，不需要再手写“当前不可用”。([Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine))

### Foundry：来源定义挂出当前效果

物品或状态保存效果定义；装备、诅咒或临时状态把 Active Effect 挂到角色上，到期自动移除。([Foundry Virtual Tabletop](https://foundryvtt.com/article/active-effects/))

### ink／Yarn：状态由经过的故事路径产生

ink 自动把节点访问次数变成计数；Yarn 的 `once` 和 Smart Variables 也让部分状态由故事运行过程推导，而不是作者在另一处重复填写。([GitHub](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md))

⚠️ 这些系统不是“完全没有当前状态”。它们的共同点是：

> **不把当前值复制成另一份人工维护的说明，而是从事件、效果实例、变量和时间得到当前值。**

问“现在还剩几次”，不可能做到零状态；能避免的是**双写状态**。

# 5. A／B／C 各自会在什么书里撑不住

公开产品没有提供“写到第 N 章必须升级”的统计数据。下面的章数是**情景推测，不是实证阈值**。

真正决定压力的不是章数，而是三个量：

- 同一规则被检查得有多频繁；
- 它是否随事件和时间不断变化；
- 检查器误放行一次的代价有多大。

一部 500 章的现实题材小说可能一直不需要 C；一部第 3 章就出现三种资源、共享冷却和临时 buff 的系统文，A 已经可能不够。

| 档位                               | 比较舒服的书                                                 | 撑不住的画面                                                 | 示意章位                                                     |
| ---------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **A 整块设定集**                   | 现实、感情、悬疑、低魔；规则少，主要由作者阅读判断；破例很少重复 | 金手指有每日次数、失败消耗、冷却、临时加次；检查器必须把规则文章、故事时间和多次使用事件临时拼起来 | 低机制书可撑数十至数百章；强机制书可能第 **5～15 章**第一次反复使用能力时就露出问题 |
| **B 可引用条文／例外**             | 长篇连载，有几十条会反复引用的世界规则；多数检查是“这条是否适用于此人／此地／此时”；使用和破例仍能从事件计算 | 一个场景需要同时计算多种资源、共享冷却、叠层 buff、能力授予、封印与解除；稳定 ID 能找到各条，却无法完成组合计算 | 普通长篇可撑 **50～200 章以上**；高机械作品可能二三十章就开始把 B 用成一套隐形 C |
| **C 完整规则／能力／例外真值体系** | 系统流、硬魔法、战斗升级、规则解谜；几乎每章都要判断成本、合法目标、冷却、状态叠加 | 故事规则尚未稳定，作者持续改设定；大量文化、传说和戏剧性破例也被要求填硬结构，维护工作压过创作 | 对强机制作品可能从第 **1 章**就有价值；对普通小说，失败往往发生在前 **1～10 章**——不是算不动，而是作者根本不愿维护 |

这与公开工具呈现出的分层相符：

- 创作／Wiki 工具默认保留自由文本，并让结构可选；
- Kanka 只对能力、charges、属性计算等少数对象加强；
- 游戏引擎只在必须确定运行结果的领域采用完整能力和效果系统；
- 互动叙事研究反复指出，状态组合和可执行分支会迅速增加作者的工程负担。([世界锻造](https://www.worldanvil.com/learn/article-guides/articles))

# A／B／C 的代价对照

| 档位  | 得到什么                                                     | 放弃什么                                                | 最容易冒充的能力                       |
| ----- | ------------------------------------------------------------ | ------------------------------------------------------- | -------------------------------------- |
| **A** | 导入最省事；作者保留完整人话语境；设定改动成本低             | 稳定条文引用、确定性当前状态检查                        | 把“没检索到冲突”说成“确认合法”         |
| **B** | 可以准确说明“本章受哪条规则约束”“本次事件破了哪条”；改名和版本更容易传播 | 复杂状态组合仍算不出来；依赖事件和时间记录完整          | 把“能指到条文”说成“能算出剩余次数”     |
| **C** | 可以确定判断成本、冷却、次数、叠层和组合条件                 | 作者录入负担、Schema 演化、版本迁移、例外建模和测试成本 | 把游戏式确定性强加给尚未稳定的文学设定 |

## 中性判断

- **A 是完整的材料管理方案，不是完整的规则检查方案。**
- **B 是引用与追责方案，不天然等于状态计算方案。**
- **C 是运行规则方案，不只是“多几个字段”。**
- “世界规则全拆”并不是公开创作工具的常态；“必须回答此刻是否可用”的系统，也几乎不会只靠整篇文档。
- 公开系统最常见的折中不是四处再建当前状态表，而是：
  **原材料保留全文 → 需要时给局部定义稳定身份 → 已发生事件／效果实例承担变化 → 当前状态按查询派生。**

这个调查只能说明三档各自承担什么责任、在哪类书中会出问题；不能替你们决定现在进入哪一档。
