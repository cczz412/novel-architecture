# 结论

✅ **候选方向成立，建议升为产品语义方向，但字段先别拍死。**

更准确的口径应是：

> 人—人、人—物、人—势力、人—故事线，共用一套“带类型的关系边外壳”；关系边只保存结构、当前有效状态和事实／计划指针，不复制第二份事实句正文。人物页、势力页、故事线页出现的各种名单，全部是从边和事件现算出来的投影。

公开资料里能看到高度一致的做法：

- Neo4j 的属性图把关系统一表达为“起点—关系类型—终点＋属性”；
- W3C ActivityStreams 用同一个 `Relationship` 对象表达朋友关系和“人属于组织”，同时把加入、离开、关系建立等变化表达为事件；
- Google Zanzibar／OpenFGA 把对象—关系—对象统一成关系元组；
- articy:draft 允许各种叙事对象互相引用，但能限制允许连接的对象类型，并提供自动查询生成的反向列表。([Neo4j Graph Intelligence Platform](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/))

需要补两条护栏：

🔥 **“同一种边”不等于“所有关系都一个意思”。**
应当共用结构外壳，但不同关系类型必须限定：

- 能连接哪两类对象；
- 是有方向还是对称；
- 允许带哪些限定信息；
- 是否允许同时存在多条；
- 变化由什么事件开启、修改或结束。

🔥 **“属于某条线”与“曾在某条线出现”不是一回事。**

- 稳定关联、主导、对抗某条线：可以是人—线边；
- 只在这条线的一场戏露过一次：应从场／事件参与记录推出来，不能自动升级成“线成员”。

## 1｜同一种关系边，最小应表达什么

### 已验证的外部模式

Neo4j 的关系至少有起点、终点、方向、类型，并可附属性；OpenFGA 的最小关系元组是“主体、关系、对象”，还可附条件；articy:draft 则在通用引用之上限制可连接的对象类型或模板。三者共同说明：**共用外壳可行，但必须有类型约束，不能变成任意对象随便连。** ([Neo4j Graph Intelligence Platform](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/))

W3C ActivityStreams 还把“关系本身”做成可以被指向的对象：关系有主体、关系种类、客体，可以记录开始和结束时间；关系的建立、加入、离开则由活动事件表示。([W3C](https://www.w3.org/TR/activitystreams-vocabulary/))

Wikidata 的做法则是：简单关系之外，用限定信息补有效时间、角色、适用范围等，再挂来源；W3C PROV-O 也允许把一条普通关系“升格”为可附加来源、时间和其他说明的中间对象。([Wikidata](https://www.wikidata.org/wiki/Help%3AStatements))

### 对你们最合适的语义槽位

下面说的是**语义上必须回答什么，不是替你们发明字段名**。

| 语义槽位           | 建议地位       | 说明                                                         |
| ------------------ | -------------- | ------------------------------------------------------------ |
| 关系两端是谁       | 必须           | 两端都指稳定对象身份，不能写人物名字文本                     |
| 两端各是什么类型   | 必须           | 人、物、势力、故事线必须可校验                               |
| 是什么关系         | 必须           | 恨、持有、属于、关联、结婚不能混成一个“相关”                 |
| 方向或两端角色     | 必须           | “甲恨乙”有方向；“甲与乙结婚”通常对称；“甲持有剑”有持有人与物品角色 |
| 关系自身的稳定身份 | 对你们建议必须 | 当证据、人物页注解、历史变化都要指向这条边时，需要稳定门牌；纯元组系统未必单设 |
| 故事内有效时间     | 可变关系必须   | 何时成立、何时结束；没结束就是开放区间                       |
| 依据指针           | 对你们必须     | 指向已发生事实、作者确认或计划事件；不能把事实句再抄进关系边 |
| 类型专属限定       | 按关系开放     | 仇恨程度、门派职级、持有方式、在线中承担的角色等             |
| 候选／不确定程度   | 只给推测层     | 已确认关系不需要概率；模型猜测不能冒充当前关系               |
| 系统版本、刷新状态 | 工程需要       | 管投影和缓存，不属于故事世界语义                             |

### “强度”和“公开性”不要做成所有边都必填的通用尺子

OpenMW 的 faction 系统在同一人—势力关系上分别处理成员身份、职级、声望和是否在人物界面显示；加入、离开也有专门操作。它并没有拿一个统一的“关系强度”包办所有含义。([OpenMW 文档](https://openmw.readthedocs.io/en/latest/reference/lua-scripting/openmw_types.html))

因此建议：

- “恨”的程度可以有；
- 门派关系更适合职级、声望、是否被逐出；
- 持有关系更适合持有方式，如保管、借用、偷得；
- 婚姻通常不需要“强度 0.8”；
- 人—线关系更适合主导、对抗、视角承载、稳定关联等角色。

⚠️ **“公开性”也不是一个简单布尔值。**

它至少可能指四件不同的事：

1. 作者界面是否显示；
2. 故事世界里是否公开；
3. 读者是否已经知道；
4. 某个角色是否知道。

OpenMW 的 `Hidden` 只控制 faction 身份是否显示在人物窗口，并不等于完整的“谁知道这件事”。([OpenMW 文档](https://openmw.readthedocs.io/en/latest/manuals/openmw-cs/tables-characters.html))

所以关系边可以有展示范围，但“谁知道／误信什么”仍应走知情结构，不能塞进一个“公开／秘密”开关。

## 2｜“这条线现在有谁”：存成员表、存边，还是两边都有

✅ **逻辑真值只存边；界面两边都可以显示名单，但名单没有写入权。**

工程上可以分三档：

| 做法                             | 是否推荐       | 实际含义                                     |
| -------------------------------- | -------------- | -------------------------------------------- |
| 每次直接查边                     | MVP 推荐       | 人物页、势力页、线页面打开时现算             |
| 边是真源，另存缓存／物化视图     | 数据量大后可用 | 物理上“两边都有”，但缓存只是加速，可随时重建 |
| 人物页和势力／线页面各自编辑名单 | ❌ 禁止         | 两份真值，迟早不一致                         |

W3C ActivityStreams 把“朋友名单”描述成一组 `Relationship` 对象的集合，而不是每个人各抄一份独立朋友数据；articy:draft 的自动引用栏和计算引用栏也会从已有引用反查并自动列出结果。它甚至专门举例：配方记录使用了哪些原料，原料页上的“哪些配方用了我”由查询自动生成，不要求人工反向补一遍。([W3C](https://www.w3.org/TR/activitystreams-vocabulary/))

### “这条线现在有谁”本身还要拆成三个问题

| 用户实际想问什么       | 正确来源                                 |
| ---------------------- | ---------------------------------------- |
| 谁与这条线有稳定关联   | 查询有效的人—线关系边                    |
| 最近／当前场景里有谁   | 查询本场及附近事件的参与记录             |
| 历史上谁曾在这条线出现 | 查询所有属于该线的场／事件，再反查参与者 |

这三种结果可能完全不同。

💡 例子：

- 复仇线长期围绕甲展开，甲有稳定人—线边；
- 乙只负责送一次信，乙在某一场出场；
- 丙是幕后仇人，一直与线稳定相关，但尚未实际出场。

如果都压成一个“成员名单”，会立刻分不清乙和丙。

### 已验证的失败机制

没有找到足够可信、细节完整的公开事故复盘，能逐字证明“某叙事软件里作者改了门派、门派名单没改”。但相关故障机制有明确公开证据：

- IBM 对“更新异常”的定义正是：同一数据存在多个位置，只改了一处、其他位置没改，最终失去一致性；
- OpenFGA 官方文档直接说，把用户目录里的群组关系再同步到另一套关系元组存储很有挑战；如果依赖旧令牌，关系变更后还可能一直保留旧权限直到令牌过期；
- Arcweave 官方也明确说，项目变大后手工在各处更新人物信息很容易出错，所以引用会随对象改名自动更新。([IBM](https://www.ibm.com/think/topics/database-normalization))

### 套到你们产品的具体失败样例

下面是按已验证机制推演出的产品风险，属于**工程推论，不是公开事故原文**：

1. 人物卡把甲从青云门改到魔教，但青云门名单仍有甲，魔教名单没有甲。
2. 线页面删掉乙，但乙仍挂在本线三场戏里；系统一处说“乙不在线”，另一处又说“乙正在本线行动”。
3. 宝物页写“当前持有人甲”，甲的物品栏却没有；乙的物品栏还保留旧记录。
4. 甲人物页写“已离婚”，乙人物页仍写“配偶甲”。
5. 页面缓存没刷新，作者误以为真正的关系边没有更新，又手工改了一遍，产生重复边或错误结束事件。

## 3｜故事线能不能只有一件事，没有固定班底

✅ **结构上完全成立，而且公开叙事工具已经给出同方向证据。**

Plottr 的场景卡位于“章节 × 故事线”的交叉位置，可以先创建一张只有标题的空白场景卡；人物、地点和标签是在侧栏里另外选择是否链接的内容。也就是说，**场景先属于某条线，并不要求先挂人物。** ([Plottr知识库](https://docs.plottr.com/article/57-timeline-scene-cards))

Arcweave 同样把故事流和人物／物品组件分开：board 上的元素和连接负责故事事件与流程，人物、地点、物品是另外的可复用组件。官方还明确说组件保存数据，但不负责驱动叙事流程。([Arcweave 文档](https://docs.arcweave.com/project-items/overview))

公开文档没有直接写一句“零人物故事线合法”，所以这里应标为：

- **已验证**：故事线／故事流和人物链接可以独立建立；人物链接不是创建场景的必填条件。
- **强推论**：允许一条线暂时只有一个事件、物品、地点变化或未决目标，而没有固定人物班底，是符合这些数据模型的。

### 对产品的推荐规则

- 创建故事线不检查“至少一名成员”；
- 零个人—线边是正常状态，不亮错误；
- 人物第一次在该线的某场出现，只增加场／事件参与，不必自动升成稳定人—线关联；
- 只有作者明确认定“这个人物持续属于／主导／对抗这条线”，才形成稳定人—线边；
- 线页面可以显示“稳定关联人物”“当前出场人物”“历史出现人物”三个投影，但不能出现一个可独立编辑的总成员表。

💡 例如，“封印松动线”开出来时，可能只有“地底封印出现裂缝”这一件事。主角五章后才发现它。这条线在前五章没有固定人物，完全合理。

## 4｜关系边与人物页关系列表怎样分工

这里建议严格分三层：

| 层                                   | 回答什么                               | 能不能直接编辑                   |
| ------------------------------------ | -------------------------------------- | -------------------------------- |
| 事实／计划／事件来源                 | 为什么关系成立、何时发生了什么         | 按各自确认规则处理               |
| 当前关系边                           | 现在两对象之间是什么状态，依据指向哪里 | 只能随来源变化或显式关系操作改变 |
| 人物页、物品页、势力页、线页面的列表 | 给人看的整理结果                       | ❌ 不具备独立真值写入权           |

说白了就是：

> 事实或计划负责“发生了什么”；关系边负责“现在是什么状态”；页面列表负责“给作者怎么看”。

关系边依然不是第二套事实句正文。它只保留对象指针、关系类型、有效区间和来源指针。

### 发现不一致时，自动改还是亮 stale

答案是：**看冲突发生在哪一层。**

| 不一致情况                   | 推荐处理                                       |
| ---------------------------- | ---------------------------------------------- |
| 页面列表和关系边不一致       | 自动重算页面列表；不问作者                     |
| 页面用的是缓存，暂时落后     | 自动刷新；确实还没追上时显示“数据更新中／过期” |
| 关系边指向的来源已经失效     | 把关系边标为 stale，停止把它当当前状态使用     |
| 新事实能确定地结束／开启关系 | 自动重建关系边，但不改事实来源                 |
| 来源之间有语义冲突或无法判断 | 亮待复核，由作者裁定                           |
| 计划边和已发生边不同         | 不是错误；分区展示，不能自动互相覆盖           |

AWS 对事件投影的官方说明是：事件产生的派生投影可能因为更新延迟而暂时不是当前状态；PostgreSQL 的物化视图同样需要通过重新执行底层查询来整体刷新。([AWS 文档](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/event-sourcing-pattern.html))

因此最合适的纪律是：

- **投影落后：自动重建。**
- **依据失效：关系边 stale。**
- **事实含义有争议：不自动拍板。**
- **冻结书稿、已确认事实、计划内容：绝不因页面名单不一致而被反向改写。**

## 5｜“只许当边／只许当事件结果／严禁另抄名单”清单

### A. 当前状态只许通过边表达

| 内容                   | 当前状态放哪里       | 变化怎样发生                                           |
| ---------------------- | -------------------- | ------------------------------------------------------ |
| 谁恨谁                 | 有方向的人—人边      | 结仇、加深、和解、放下是事件，开启／修改／结束该边     |
| 谁和谁真实结盟         | 人—人或人—势力关系边 | 结盟、背盟、解除是事件                                 |
| 谁持有宝物             | 人—物边              | 获得、偷走、借出、交还、遗失、转交是事件               |
| 谁在门派               | 人—势力边            | 加入、离开、逐出、晋升、降级是事件                     |
| 谁与某条故事线稳定关联 | 人—线边              | 加入叙事关注、退出、转为对抗方等由计划或已发生事件承托 |
| 谁和谁结婚             | 对称的人—人边        | 结婚事件开启；离婚、婚姻无效等事件结束                 |

这里有几个容易踩坑的细分：

- “持有”和“拥有”不是同一种关系。甲可能替乙保管宝物；
- “恨”通常有方向，不能因为甲恨乙就自动建立乙恨甲；
- 婚姻通常对称，但仍只保留一条可引用的关系，不给双方人物卡各建一条独立配偶记录；
- 人—线边表达稳定叙事关联，不叫队伍成员也可以。

### B. 只许当事件结果或事件参与表达

| 内容                 | 正确身份             | 不应升级成什么                               |
| -------------------- | -------------------- | -------------------------------------------- |
| 谁本场出场           | 人参与场／事件的记录 | 不自动变成长期人—线成员                      |
| 谁加入／离开门派     | 变化事件             | 不只改一个名单格子                           |
| 宝物从甲转到乙       | 转移事件             | 不同时手改甲物品栏、乙物品栏、宝物持有人三处 |
| 谁与谁举行婚礼／离婚 | 关系变化事件         | 不把婚礼事件本身当永久关系                   |
| 谁欺骗了谁           | 已发生事件           | 不直接制造被欺骗者相信的世界事实             |
| 谁在本线某一章露面   | 场／事件参与         | 不因一次露面就形成稳定人—线边                |

W3C ActivityStreams 正好把 `Relationship` 与 `Join`、`Leave`、`Create Relationship` 等活动拆开，支持“事件改变关系，而关系描述当前连接”的两层表达。([W3C](https://www.w3.org/TR/activitystreams-vocabulary/))

### C. “被误导以为结盟”要单独处理

假设：

> 甲被误导，以为乙和丙已经结盟。

这里有三件不同的东西：

1. **欺骗行为发生了**：事件结果；
2. **甲当前相信“乙与丙结盟”**：进入知情／误信结构；
3. **乙与丙在世界里是否真的结盟**：看客观关系边。

❌ 绝不能因为甲相信，就给乙—丙建立一条真实结盟边。
❌ 也不能给甲建一条“与乙、丙结盟”的人际关系边。
✅ 人物页若展示“甲目前误信的关系”，只能从知情／误信结构投影出来。

这也是为什么“所有东西统一成边”必须加一句限定：

> 可以共用边的技术外壳，但世界关系、事件参与、角色知识是三个不同的语义家族，不能互相冒充。

### D. 严禁另抄一份可编辑名单

下面这些列表都可以显示，但只能查询生成：

- 人物页“仇人／盟友／配偶”；
- 人物页“携带物品”；
- 物品页“当前持有人／历任持有人”；
- 人物页“所属势力”；
- 势力页“当前成员／历史成员”；
- 故事线页“稳定关联人物”；
- 故事线页“当前出场人物／历史出现人物”；
- 场页面“本场人物”；
- 人物页“参与过的场／故事线”；
- 人物页“误信中的联盟关系”。

“严禁”禁止的是**第二份可写真值**，不是禁止作者看到这些列表。

## 推荐的候选方向收口

建议把候选方向收成下面六句，字段继续开放：

1. **关系采用同一种带类型的边外壳**，允许连接人—人、人—物、人—势力、人—故事线。
2. **每种关系限定合法端点、方向、对称性和可用限定信息**，不设无语义的万能“相关”边。
3. **关系边是事实／计划的当前状态影子＋指针**，不复制第二份事实句正文；计划关系与已发生关系不混。
4. **故事线允许零稳定人物**；开线不以建立队伍名单为前置条件。
5. **加入、离开、转手、结婚、背盟等是事件；当前成员、持有人、婚姻等由事件和事实投影为边。**
6. **人物页、物品页、势力页、故事线页、场页面的一切关系列表均为只读投影；可以缓存，但不能获得独立写入权。**

再加一条容易被漏掉的解释：

> “谁属于这条线”只指显式、稳定的人—线关联；“谁在这条线出现过”从场／事件参与记录现算，二者不自动互转。

## 已验证与推论边界

### 已验证

- 通用“起点—类型—终点＋属性／条件”的关系模型广泛存在；
- 人—人和人—组织可以共享同一种关系对象；
- 关系变化可与关系当前状态分开；
- 时间、角色、来源等可作为关系限定信息；
- 叙事工具可以自动生成反向关系列表；
- 故事流／故事线可以先于人物链接建立；
- faction 关系可以包含职级、声望和显示隐藏等附加语义；
- 重复保存会产生更新异常；
- 缓存／物化投影可能暂时 stale。([Neo4j Graph Intelligence Platform](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/))

### 对你们产品的推荐推论

- 用一套关系边外壳覆盖四种端点组合；
- 线允许零人物；
- 明确区分稳定人—线关联与一次性出场；
- 页面不一致时按“投影自动重建／来源冲突亮 stale”分流；
- 本场出场只进事件参与；
- 误信结盟只进知情结构，不污染客观结盟边。

### 没有足够证据冒充已验证的部分

- 没找到高质量公开事故复盘，能精确还原某叙事产品发生“改了人物门派但势力名单未更新”的全过程；
- 没有公开实测证明某一种统一边表结构在你们预计数据规模下一定性能最优；
- 没有证据要求所有边都必须带强度、公开性或独立关系编号；
- 读者承诺／类型期待是否单开，不属于本题，也不从这次调查推出任何结论。
