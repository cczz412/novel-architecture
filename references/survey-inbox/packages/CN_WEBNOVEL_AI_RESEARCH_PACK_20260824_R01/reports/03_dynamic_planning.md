# 动态长篇规划：边写边改与日更连载

## 结论先说

长篇网文规划不该被设计成“先把全书想完，再逐章执行”。更贴近真实创作的模型是：

> **远处只定方向，近处才写细；已发布内容默认锁定；未来计划允许分叉、试写、撤回和重排；每次重要改动都做影响分析，但最终由作者决定是否接受连带修改。**

这叫滚动规划。它承认作者会在写作中发现新人物、新冲突和更好的路线，也承认日更压力下不可能把未来几十万字一次想清楚。

## 1. 为什么固定大纲不适合长期连载

### 1.1 写作本身会产生新信息

作者在真正写一场戏时，才可能发现：

- 某个配角比预想更有生命力；
- 原定反派的动机站不住；
- 一句对话自然产生了新的误会；
- 某条感情线推进太早；
- 世界规则与计划高潮冲突；
- 计划里的“爽点”写出来并不爽；
- 读者记住了作者原本没打算重点写的细节。

这些不是规划失败，而是创作过程的正常产物。

### 1.2 连载会把未来计划暴露给现实压力

猫腻谈到曾因竞争和连载节奏提前释放高潮，随后必须面对后续兴奋阈值被抬高的问题。爱潜水的乌贼也指出，日更和即时反馈会帮助调整细节，却可能打乱长期节奏。

所以计划系统不仅要问“这条路线好不好”，还要问：

- 为什么现在改；
- 是临时救急还是长期方向改变；
- 提前兑现后，后面靠什么继续；
- 哪些旧铺垫因此失去作用；
- 哪些人物状态和时间安排要跟着变。

### 1.3 计划不是事实

最危险的错误之一，是把作者想过的路线当成已经发生。

计划可能是：

- 只是灵感；
- 候选 A；
- 作者倾向但未确认；
- 已排进近十章；
- 已在正文公开承诺；
- 已经发布。

这些权重完全不同。系统必须保存计划身份和承诺程度。

## 2. 论文给了哪些直接证据

### DOME：粗长期大纲 + 动态局部细纲

DOME 不预先生成完整详细大纲，而是保留粗略高层方向，在写作过程中依据已生成内容继续细化局部计划。它还用时间知识图谱保存已发生内容，并加时间冲突分析器。

这支持“远粗近细”，但它仍是自动生成实验：故事只有约 7,000 词，使用固定英雄旅程式粗纲，没有验证真实网文作者如何改计划。

### PlotMachines：持续跟踪剧情状态

PlotMachines 不只是把 outline 重复塞给模型，而是维护动态剧情状态，跟踪哪些情节点已经覆盖、当前语义位置在哪里。它说明固定大纲与当前运行状态需要分开。

局限是故事很短、结构固定，不能证明适合百万字连载。

### Re³：计划、当前状态、最近文本共同驱动下一段

Re³ 把全局计划、人物描述、相关旧内容、最近摘要和上一段原文组合起来，再生成、重排和修订。它说明“下一步计划”必须被已发生内容约束。

### DOC：详细大纲提高控制，但可能压缩创造空间

DOC 的详细层级大纲提高了人评中的连贯、相关和有趣程度，作者也觉得更可控。但论文同时提示，过强控制可能产生重复和狭窄路线。

### MutaGReP：可以修改整份计划，而不是只往后加

代码工程研究 MutaGReP 比较了两种计划搜索：一种只能追加步骤，另一种可以修改、删除、重排原步骤。后者在较低预算下明显更好。迁移到小说，这支持“未来计划可以非单调修改”，不能只在旧大纲尾部继续加章。

## 3. 候选规划模型：四个距离带

### 带 A：已发布事实区

- 默认不可被计划改写；
- 小修必须记录版本；
- 大修需要说明读者基准如何处理；
- 所有未来路线必须服从这里的事实和公开承诺。

### 带 B：近程执行区

建议覆盖未来 3—10 章，或作者自己设定的短窗口。

这里可以写得较细：

- 每章主要意图；
- 出场人物；
- 视角、地点、时间；
- 本章变化；
- 要回收或新建的承诺；
- 章末状态；
- 需要提前查的事实。

近程区不是绝对锁死，但改动要明确影响后续章槽。

### 带 C：阶段承诺区

建议覆盖当前卷、地图、案件或关系阶段。

这里保存：

- 阶段目标；
- 关键转折；
- 必须发生或不能发生的事；
- 预计高潮；
- 离场状态；
- 活跃故事线；
- 允许变化的空间。

### 带 D：远期方向区

这里只保留：

- 终局意向；
- 角色可能目的地；
- 核心谜团答案候选；
- 不可违背的长期约束；
- 未来分支；
- 尚未决定的问题。

越远，越不应该假装精确到章。

```mermaid
flowchart LR
    A[已发布事实区\n锁定] --> B[近程执行区\n3-10章较细]
    B --> C[阶段承诺区\n当前卷/地图/案件]
    C --> D[远期方向区\n粗略、多分支]
    D -.作者选择/新发现.-> C
    C -.滚动细化.-> B
    B -.正文发布.-> A
```

## 4. 每个计划对象要有状态

推荐的状态不是“完成/未完成”两档，而是：

| 状态 | 含义 |
|---|---|
| `idea` | 灵感，还没进入正式计划 |
| `candidate` | 候选路线，可与其他路线并存 |
| `preferred` | 当前倾向，但尚未承诺 |
| `scheduled` | 已放入近程章槽 |
| `committed` | 已被多个后续计划依赖，改动代价高 |
| `foreshadowed` | 正文已对读者公开铺垫或承诺 |
| `published` | 已发生事实 |
| `paused` | 暂停，保留恢复入口 |
| `abandoned` | 放弃但不删除 |
| `fulfilled` | 已执行并回收 |
| `blocked` | 被事实、时间或其他计划阻挡 |

产品可以使用更自然的中文名称，后台仍需保留明确身份。

## 5. 锚点与弹性区

### 锚点

作者明确不希望轻易变化的内容：

- 核心结局；
- 主角底线；
- 世界硬规则；
- 已公开的关键身份；
- 当前卷必须完成的任务；
- 已经投入大量铺垫的高潮；
- 重要人物最终命运。

### 弹性区

可以随写作调整：

- 谁来完成某个中间任务；
- 两次关键事件的顺序；
- 一个配角是否扩展；
- 关系推进速度；
- 具体章数；
- 某次冲突发生在哪个场所；
- 用哪一条支线承接过渡。

### 未决区

作者还没想清楚，系统应该保护这种不确定性：

- 反派是否洗白；
- 某个秘密由谁揭开；
- 两条路线最终选哪条；
- 结局是开放还是封闭。

⚠️ 系统不应为了“数据完整”把未决区自动填成确定答案。

## 6. 作者改计划时，系统应该做什么

假设作者把原定第 205 章发生的“北境叛乱”提前到第 188 章。

系统的工作流程应该是：

### 6.1 保存改动意图

- 改动：提前叛乱；
- 原因：都城线过长，作者想切换节奏；
- 当前状态：候选；
- 原方案保留；
- 作者希望保持的锚点：叛乱幕后主使不变。

### 6.2 找直接影响

- 原第 188—204 章的计划；
- 叛乱前必须完成的三次铺垫；
- 北境人物当前状态；
- 从上次出现到现在的故事内时间；
- 已经公开的倒计时；
- 都城线当前悬念被挂起多久。

### 6.3 沿依赖继续传播

像 CodePlan 处理代码改动一样，计划改动可能沿依赖传播：

- 叛乱提前 → 军粮线必须提前；
- 军粮线提前 → 韩夜的假死调查时间不足；
- 调查时间不足 → 需要增加新情报来源，或修改上次事件；
- 切线提前 → 都城证人失踪悬念暂停时间变长；
- 暂停变长 → 可能需要在北境章中保留一个都城回声。

### 6.4 生成“待处理义务”，不是自动改完

系统列出：

- 必须处理；
- 建议处理；
- 可接受风险；
- 无法判断，需要作者拍板。

作者逐项决定，之后才把分支提升为当前计划。

## 7. 计划图与影响图要分开

### 计划图

表达“作者打算怎样走”：

- 事件先后；
- 候选分支；
- 章槽；
- 阶段目标；
- 计划状态。

### 影响图

表达“改变一个点会碰到什么”：

- 因果依赖；
- 人物动机依赖；
- 时间依赖；
- 伏笔/回收依赖；
- 读者承诺依赖；
- 世界规则依赖；
- 出场和位置依赖。

二者不能混成一张图。计划图可以随作者变化，影响图更多来自已发生事实和显式关系。

## 8. 怎样处理读者反馈引起的改动

读者反馈进入计划系统时，建议经过四步：

### 信号归纳

例如：大量读者误以为韩夜真的死了；很多人期待林策亲自查案；某章留存明显下降。

### 回指文本

找出读者形成判断的具体段落，而不是只看评论结论。

### 判断属于哪一类

- 作者故意制造的误判；
- 表达不清；
- 读者形成了意外但有价值的期待；
- 与目标受众不匹配；
- 只是少数偏好；
- 平台数据噪声。

### 作者决定处理方式

- 不改；
- 后文澄清；
- 调整节奏；
- 扩展某条线；
- 建新候选分支；
- 记录为读者认知，不改变计划。

读者反馈不应直接改事实账或正式计划。

## 9. 计划偏移和“回拉”

系统不该把偏离大纲一律视为错误。可以把偏移分成：

- **有益扩展**：新人物或新线增强了核心体验；
- **局部绕行**：暂时延迟主线，但有明确回归点；
- **资源消耗**：花很多章却没有产生后续价值；
- **方向漂移**：作品承诺和主角目标发生无意变化；
- **事实阻塞**：新路线被已发布事实卡住；
- **节奏挤压**：前面拖长，后面回收空间不足。

“回拉”不是强行回旧大纲，可以有三种动作：

1. 回原路线；
2. 把新路线升级为正式路线，再修正长期方向；
3. 为新旧路线设计汇合点。

## 10. 废案为什么必须保留

废案不只是垃圾。它能回答：

- 这个方案为什么被放弃；
- 哪些铺垫已经为它做过；
- 哪些人物动机曾依赖它；
- 以后是否能拆出局部复用；
- 作者是否正在无意中重新走回旧死路。

废案需要：标题、版本、放弃原因、关联对象、可复用部分、禁止复活部分。

## 11. 一个可操作的周循环

### 每章前

- 确认当前章槽；
- 检索必带事实；
- 看近程计划是否仍成立；
- 处理高风险冲突。

### 每章后

- 提取已发生变化；
- 更新最近发生；
- 将本章从计划转成事实；
- 记录新增承诺和未结事项；
- 检查后续三章是否受影响。

### 每 5—10 章

- 重看当前阶段；
- 比较计划与实际偏移；
- 重新排序近程章槽；
- 清理失效候选；
- 选择需要回拉或升级的新线。

### 转卷时

- 确认离场状态；
- 关闭、暂停或转交故事线；
- 生成阶段总结；
- 把远期方向细化为下一阶段；
- 保留上一卷未结事项的明确去向。

## 12. 评测动态规划是否真的有用

建立一套真实连载实验，不只看成品故事质量。

### 任务

- 把一个高潮提前 15 章；
- 删除一个原定重要配角；
- 把两条故事线合并；
- 读者反馈后调整关系推进；
- 停更后重新规划未来十章。

### 指标

- 系统找到的受影响对象召回率；
- 无关影响的误报率；
- 作者确认改动所需时间；
- 改动后一致性错误数量；
- 被作者接受的待处理义务比例；
- 作者撤回或恢复旧版本的成功率；
- 作者是否觉得系统在强迫执行旧计划；
- 计划维护成本是否低于收益。

🔥 最关键的不是“计划预测正确率”，而是**计划改变时，作者是否更容易看见代价并继续写下去**。
