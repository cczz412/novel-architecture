# DR-MEM-04｜规则、能力与例外要不要提前拆条：从“找得到”到“算得出”分清三种承诺

**调查执行日：2026-08-14**  
**研究语言：中文、英文**  
**调查对象：规则引擎、互动叙事、Rules as Code／政策即代码、法律文档结构化、写作与世界观工具、中国网文作者公开实践**  
**说明：能力档 A/B/C 与下文“证据等级 A/B/C/D/U”是两套完全不同的字母。前者说产品承诺，后者说证据强弱。**

## 一页人话结论与调查方法

**一页人话结论**

这轮研究最稳的结论不是“规则应该拆多细”，而是：

> **整块材料、可引用条文、可运行规则，确实对应三种不同的用户承诺。最危险的不是停在 A，而是数据实际上只有 A/B，却让检查器说出 C 档才有资格说的“能不能”“还剩几次”“这个例外是否生效”。**

规则引擎的官方设计非常明确：可执行规则并不是“把一段文字切成几条”就结束，它需要**规则逻辑 + 当前事实/状态 + 冲突或优先级处理 + 对缺失输入的处理**。OPA 把 policy 与 `input`/`data` 分开；Drools 也明确把 rules 与 facts 分开，多个规则同时匹配时还要解决执行冲突。citeturn17view0turn17view2turn17view5turn23search3

对应到小说工作台，可以把三档承诺直接理解成：

| 能力档 | 产品真正能承诺什么 | 不能偷说什么 |
|---|---|---|
| **A 整块材料** | “我找到了与你问题相关的设定材料，你自己看原文。” | 不能因为检索到一句“每日可用三次”，就回答“今天还剩两次”。当前已用次数可能根本没有被维护。 |
| **B 可引用条文** | “这条判断涉及规则 X、例外 Y；我可以指出来源、原文位置和冲突。” | 不能因为条文已经拆开，就假装所有条件、状态、优先级已经有机器语义。Akoma Ntoso 这类标准能把法律片段稳定标识、引用和交叉引用，但它并不因此成为规则执行器。citeturn21search0turn21search1 |
| **C 可运行规则** | “在**这版规则、这个时间点、这些已知状态**下，结果是 X；这是参与计算的规则和输入。” | 状态缺失、范围未覆盖、规则相互冲突或自然语言仍有解释空间时，必须退回 unknown，不能自动补成 yes/no。OPA 本身就存在 `undefined`，也专门提供 `default` 让开发者决定是否把未定义情况压成默认值。citeturn17view3turn17view4 |

研究结果支持把 **B 看作“引用与解释能力”**，而不是“半个 C”。法律结构化标准 Akoma Ntoso 的一个核心工作就是给文档片段稳定标识，从而精确引用、修订和交叉引用；Rules as Code 则进一步要求机器能够对规则进行计算。两者解决的不是同一件事。citeturn21search1turn19view0

**什么时候 C 才明显有额外价值？** 加拿大政府做 Rules as Code 实验时，刻意选择的就是**描述性强、互相关联、范围大、变化相对频繁**的规则，而不是主观、彼此独立、范围窄且静态的规则；互动叙事工具 Ink、Twine/Harlowe 也主要在“变量、玩家状态、条件与重复访问”出现时引入运行逻辑。小说里对应的就是“每日次数、冷却、资源余额、前置条件、作用域、状态变化、明确例外”等机械问题。citeturn19view1turn17view9turn18view8

这并不等于“硬魔法＝必须 C”。有些硬魔法只是作者希望前后不吃设定，B 已经足够；只有当检查器真的要回答“现在能否施放”“还有几次”“满足哪几个条件”，C 才开始承担不同的承诺。反过来，软魔法、社会潜规则、感情禁忌、模糊预言等内容，**模糊本身可能就是文学效果的一部分**。Brandon Sanderson 在自己的创作论里明确把“软—硬魔法”看作连续谱，并反复强调所谓“laws”只是他的创作经验，不是普遍定律；软魔法甚至可以通过让人物和读者都不知道能力边界来制造未知感。citeturn19view7turn19view9

**形式化的收益是真实的，但成本也是真实的。** 加拿大早期实验发现，把自然语言规则写成代码确实能暴露漏洞、遗漏和歧义；同一份报告也把过程形容为漫长、费力且难持续，困难包括解释旧规则、跨专业沟通，以及程序语言无法轻易完整保存自然语言含义。citeturn20view0 Catala 的研究也发现法律形式化可以暴露原实现中的错误，但它存在的理由恰恰是普通编程语言和自然语言之间有很深的语义鸿沟。citeturn19view2

因此，**“提前拆条越多越安全”没有被证据支持。** Sanderson 对“过度世界构建”的反思、中国短篇网文研究、加拿大 Rules as Code 的成本经验都指向同一个边界：结构化越深，只有在后续确实消费这些结构时才值得。citeturn19view9turn16view2turn20view0

中国网文公开样本也没有支持“作者普遍愿意维护规则引擎”。能找到的是另一种更弱但稳定的信号：设定复杂、游戏化、悬疑逻辑重的作品会投入更多世界观、大纲、人物设定和关卡设计；公开 AI 辅助写作工作流里也确实有人使用“状态卡、账本、战力逻辑、伏笔、设定变更记录”等显式维护物。卖报小郎君谈《灵境行者》时说新作的世界观、大纲和人物设定比前作更详细，并采用游戏模式；《十日终焉》作者则把游戏关卡设计直接视为作品写作重点。citeturn16view1turn16view0turn22view0 这些只能证明“显式维护实践存在”，**不能证明作者愿意逐条写可执行规则**，证据等级只能到 C。

目前最大的 **U（未知）** 有三个：没有找到面向中国长篇网文作者、直接比较整块设定/条文/运行规则的受控实验；没有可靠数据告诉我们作者愿意为 C 每章多维护多少分钟；也没有证据能给出“多少条规则、多少次查询以后应从 B 升 C”的通用阈值。这个阈值应该靠本地实验，而不是外部材料猜。

**几种流行说法目前不能下结论：**

“知识图谱做了就能精确查规则”不成立。World Anvil、Campfire、Novelcrafter、Scrivener 等公开文档展示了模板、资料卡、元数据、时间 progression、引用和搜索等能力，这些能提高可找回性和维护性，但**结构化资料并不自动拥有可执行语义**。citeturn18view0turn18view2turn18view3turn18view6

“AI 一致性检查＝规则计算器”也不能下结论。一些写作产品公开页面确实宣传 AI 可检查设定冲突，但这轮没有获得可独立复算的规则语义、覆盖率或缺失状态处理机制；相关能力只能作为 D/U 线索，不可当成已验证 C 档。citeturn22view3turn22view4

**问题范围与调查方法**

本轮检索以 2020—2026 年材料为主；规则引擎、产品能力和软件版本以 **2026-08-14 当日公开一手资料**为准。Sanderson 等较早创作文章因讨论的是稳定的作者方法论而保留，但只作为创作者经验，不拿来证明行业统计规律。OPA 当日公开最新 release 为 v1.19.0，2026-07-30 发布；Yarn Spinner 编译器公开最新为 v3.2.1，2026-05-05 发布；Twine 公开最新 release 为 2.12.0，2026-04-10 发布。citeturn17view1turn17view8turn17view10

检索渠道覆盖 OPA、Drools、Ink、Twine/Harlowe 等官方文档；OASIS、OECD、加拿大政府 Rules as Code；Microsoft Research、ACM/DIS 论文；World Anvil、Campfire、Novelcrafter、Scrivener 官方资料；中国作家网作者访谈与研究文章；少量 GitHub、Notion 模板评论和中文产品文档作为社区/市场样本。营销页只用来证明“厂商这样宣称”，不用于证明能力真的达到 C。citeturn19view0turn19view1turn19view3turn18view0turn18view3turn16view0

样本采用**目的性取样**，不是统计抽样：专门寻找“规则执行很有价值”的材料，也专门寻找“不应形式化”的反例。明显偏差包括：公开资料会高估成功实践；中国作者公开谈“怎么维护设定”的材料远少于谈创作心得的材料；国际写作工具样本偏英语生态；本轮没有登录付费 SaaS 账户逐项实操，因此涉及其 AI 检查精度的说法一律不升级证据等级。

一个很重要的反直觉点是：**B 并不是“临时过渡态”。** OASIS 的 Akoma Ntoso 花了完整标准去解决“文档片段怎样被稳定、长期、无歧义引用”，说明“可引用”本身就是独立工程能力；它与“能执行”不是同一个目标。citeturn21search0turn21search1

同样，**C 也不是更可信的原始真相。** 加拿大 RaC 项目明确提醒：代码化结果仍然是对规则的解释，而不是原规则本身。小说场景更简单，因为作者通常拥有最终决定权，但这个经验仍然支持一条产品边界：C 的结果最好能一路回到作者原设定/已发表事实，而不是让“计算表示”偷偷取代来源。citeturn20view1

## 中国网文用语、题材条件与三档案例

**中国网文常用说法表**

这里有一个很明显的中英文语境差异：工程文档常说 *policy、facts、state、condition、default、conflict resolution*；中国作者公开实践更常说的是“设定、人设、状态卡、账本、战力逻辑、吃书、伏笔”。两套语言不能一一硬翻。

| 中国网文/创作语境说法 | 同义或近义说法 | 谁在用、什么场景 | 对应工程概念 | 差别 |
|---|---|---|---|---|
| **世界观 / 设定** | 设定集、世界设定 | 卖报小郎君公开谈“世界观、大纲、人物设定”；World Anvil/Campfire 中文语境也常被用户理解为此类资料。citeturn16view1turn18view0 | Knowledge base / domain knowledge | 通常是一整块知识，不默认可执行 |
| **人设 / 人物设定** | 人物卡、角色卡 | 傅九直接把人设列为创作前期核心；中文产品使用“角色卡”。citeturn16view4turn22view4 | Entity record / profile | 人设包含审美、性格等软信息，远超结构化字段 |
| **大纲** | 卷纲、细纲 | 中国作者案例普遍使用；公开 AI 工作流还有“卷纲总表”。citeturn16view1turn16view4turn22view0 | Plan / prospective model | 是未来规划，不等于已发生事实 |
| **设定圣经** | Story Bible、设定书 | 中文 GitHub 工作流出现“设定圣经”；Novelcrafter 直接把 Codex 称 Story Bible。citeturn22view0turn18view5 | Canon/knowledge repository | 仍不代表每条内容都有机器语义 |
| **状态卡** | 当前状态、阶段状态 | 公开 AI 长篇工作流把它用于当前境界、敌我关系、资源等。citeturn22view0 | Runtime state / facts | 这是 C 最关键、而普通设定集常缺的一层 |
| **账本** | 资源账、章节结算、进度账 | 同一公开工作流使用“账本维护、资源折算、章节结算”。citeturn22view0 | Ledger / event-derived state | 与“世界规则”不是同一份东西 |

| **OOC** | 人物跑偏、人物失真 | GitHub 公开工作流把 OOC 列入质量审查。citeturn22view0 | Behavioral consistency | 通常无法被简单规则引擎完全判定 |
| **伏笔 / 回收** | 悬念、待回收伏笔 | GitHub 工作流维护 pending hooks；马良文档有悬念卡、埋设和回收位置。citeturn22view0turn22view4 | Lifecycle/state tracking | 更像状态机/任务生命周期，不一定是“世界规则” |
| **游戏关卡 / 规则关卡** | 副本、博弈游戏 | 《十日终焉》作者公开讨论十二类游戏、难度层级和具体关卡。citeturn16view0 | Stateful rule system | 当胜负依赖明确条件时很接近 C；但叙事中的“假规则”仍是反例 |

题材差异比“长篇/短篇”更能决定是否值得走向 C，但篇幅会放大维护问题。中国网文公开案例显示，游戏模式、悬疑逻辑和复杂关卡会推动作者做更细的设定准备；现实言情作者的公开方法则更偏人物、人设、主题和情节线；工业现实题材大量依赖真实行业资料。citeturn16view1turn16view0turn16view4turn16view3 这说明“规则复杂度”不能只看作品字数。

**规则案例与三档处理对照**

下面的 16 个案例是**研究者构造的覆盖样本**，用来测试表示层边界，不是对真实作者作品的统计抽样。  
“准确性”一栏写的是**在信息完整时这档理论上有资格回答到什么程度**，不是伪造出来的产品实测准确率。真正的百分比应由下一节的小实验测。

| 案例 | 典型查询 | 能力档 A：整块材料 | 能力档 B：可引用条文 | 能力档 C：运行规则 | 维护动作 / 例外 | 错误自信最大来源 |
|---|---|---|---|---|---|---|
| **系统文：每日抽奖 3 次** | “今天还剩几次？” | 能找到“每日三次”；**算不出剩余** | 能引用次数条文；若另有“奖励次数”可同时指出 | 有今日已用次数、重置时间后可算 | 每日重置；活动赠送；VIP/剧情特批 | 把“每日三次”误当“当前还有三次” |
| **技能冷却** | “现在能不能再用？” | 能找冷却设定 | 能指出“冷却 10 分钟”等条文 | 有上次使用时间和当前时间后可算 | 时间推进；时间停止；减 CD 效果 | 当前时间/上次使用没维护却回答 yes/no |
| **硬魔法：法力消耗** | “还能放两次火球吗？” | 能找消耗和总法力描述 | 能引火球消耗、恢复规则 | 有当前法力值后可计算 | 临时 buff、区域修正、透支规则 | 使用“最大法力”代替“当前法力” |
| **修仙突破条件** | “现在能突破吗？” | 能找突破章节/设定 | 能列出“境界、丹药、心境”等条件 | **只应计算明确机械部分**；“心境圆满”若无操作定义应 unknown | 秘法越级、剧情突破、主观条件 | 为了得到布尔结果，把文学判断偷偷量化 |
| **副本每周 2 次** | “这周还能进吗？” | 找到次数上限 | 可引用上限和重置条款 | 周期、角色记录完整时可算 | 跨周；特殊票券；队长权限 | 周界线、服务器时间或赠票没纳入 |
| **道具三次充能** | “护符还剩几次？” | 找到“最多三次” | 引用充能/消耗条文 | 消耗事件完整时可算 | 修复、重新充能、一次双耗 | 最大容量与剩余量混淆 |
| **门派禁令＋掌门特批** | “弟子能否进入禁地？” | 能找到门规和某段特批 | B 很有价值：同时援引总规则和例外 | 只有特批对象、有效期、地点范围都明确时才可判定 | 特批撤销；代理掌门；仅限某层 | 只检索到总规则，漏掉例外 |
| **能力血脉前置** | “没有王族血脉能学吗？” | 找能力说明 | 可引用资格条款及已知例外 | 身份/血脉事实和例外完整时可算 | 伪装身份、移植、后天觉醒 | 把“没人做到过”误算成“规则禁止” |
| **规则怪谈：午夜不能照镜子，某房间除外** | “现在照镜子会死吗？” | 可找所有相关规则文本 | B 往往比直接 C 更安全：能指出相互矛盾规则和来源 | 只有作品已经确认“哪些规则是真规则”时才适合求值；否则 unknown | 假规则、诱导规则、规则来源不可信 | **把角色看到的规则纸当作者世界真理** |
| **悬疑：谁在何时知道某秘密** | “第 8 章此人能知道凶手身份吗？” | 搜到涉及秘密的章节 | 能引用获知/泄露证据 | 若维护知识状态和信息传播事件，可计算可知性的一部分 | 偷听、推理、假情报、遗忘 | “正文没写知道”不等于“不知道” |
| **软魔法：森林会拒绝‘心不纯’的人** | “这个角色一定进不去吗？” | 找原设定，通常已经够用 | 可指出用词模糊、过去案例 | **不宜强行 C**，除非作者后来主动定义“心不纯”的可判条件 | 神意、象征、例外、未知机制 | 把模糊文学命题伪装成精确逻辑；软魔法本就可能保留未知。citeturn19view7 |
| **言情：家族不允许与竞争对手联姻** | “两人是不是绝对不能在一起？” | 找家族态度 | B 可区分“制度”“长辈意见”“过去惯例” | 多数情况下 C 收益低；若是明确继承资格条款另说 | 长辈改口、私奔、利益交换 | 把社会压力当硬禁止 |
| **现实职业：救援队操作规范** | “角色这样做是否违反流程？” | 找资料/SOP | B 通常很有价值，可引用程序来源和适用条件 | 只有稳定、确定的流程分支才值得 C；外部规范还需版本 | 紧急豁免、现场判断、机构差异 | 把外部真实世界规则写成永恒不变；现实题材作者确实会依赖资料研究。citeturn16view3turn16view4 |
| **历史：某朝礼制/官制** | “这个身份能不能进殿？” | 找史料和设定 | B 强：必须保留时代、来源和作者架空修订 | 若作品主动建立机械宫廷规则，可局部 C；历史事实本身不宜轻率计算 | 朝代/时期变化、特殊恩典、小说架空 | 把不同年代资料混成一个规则 |
| **宫斗/社会礼法** | “她越级称呼是否一定犯禁？” | 找礼仪材料 | B 可列正式制度、惯例、人物关系 | 多数为 B；明确品级权限可局部 C | 皇帝默许、私下场合、礼制与实务不同 | 把“通常如此”变成“绝无例外” |
| **科幻飞船资源与权限** | “氧气够不够 6 人撑 4 小时？” | 找舱容和耗氧描述 | B 能引用参数来源 | 参数、损耗和当前库存完整时可直接计算 | 漏气、备用罐、不同人员耗氧 | 用设计容量代替当前可用量 |

这张表里最重要的不是“哪一行归 C”，而是出现了大量**混合规则**。比如“突破需要筑基圆满 + 一枚丹药 + 心境成熟”：境界和丹药可以算，心境成熟未必应该算。工程上完全可以存在“这一条规则只覆盖机械部分，其余返回 unknown”，而不是逼作者把整条文学规则都形式化。规则系统本来就需要处理未定义输入和未覆盖情形。citeturn17view3turn17view4

这也解释了为什么**规则怪谈是一个非常好的反例题材**。《十日终焉》这类作品公开创作经验显示游戏规则/关卡本身可以成为叙事焦点。citeturn16view0 但“规则很重要”不等于“所有被角色读到的规则都是真理”。只要叙事允许假规则、误导、认知限制，系统就必须区分“文本里出现的规则”和“作者已确认的运行规律”；否则 C 会比 A/B 更容易产生高置信度错误。这一点是本研究从互动叙事与规则执行架构做出的产品推断，证据级 **B/C**。citeturn17view2turn19view7

## 分歧、负结果与反例

**分歧与负结果**

**反例一：规则越硬，不代表越应该提前把所有东西写成运行规则。** Sanderson 自己就反复提醒，他的“魔法法则”只是经验指南，而且世界构建过多会挤占人物、情节和正文创作时间；他更强调少量能力被深入推演，而不是不断添加能力。citeturn19view9 这直接反驳“只要是硬魔法，越早全量 C 化越安全”这种推论。

**反例二：可执行表示会暴露歧义，但不能神奇消除解释责任。** 加拿大 RaC 早期实验一边发现代码化能暴露漏洞，一边发现把既有规则完整转为代码非常困难，有时程序员只能在“少编码一部分意义”和“投入大量额外工作”之间选择。citeturn20view0 Catala 的存在也正是因为普通编程语言很难贴合法律结构。citeturn19view2 对小说来说，作者不需要法律级严谨，但自然语言→机器逻辑的语义损失不会因为领域变成文学就消失。

**反例三：C 的输出不应该反过来覆盖来源。** 加拿大项目明确把编码视为规则的可信解释，而非与官方规则同等地位的权威文本。citeturn20view1 对创作产品的类比是：如果作者改了原设定，而运行规则没同步，应该说“运行表示可能过期”，而不是让旧计算结果把新作者决定判成错误。

**反例四：更友好的形式化界面能降低成本，但目前没有证据证明能把成本降到普通网文作者可以忽略。** DIS 2026 的 CatalaBlocks 比较法律专业人员使用文本式 Catala 与块式表示，块式用户完成更快、代码更准确、主观难度更低、信心更高。citeturn19view3 这是很有用的正面证据，但样本是法律专业人员，任务也是法规编码，所以它只能支持“交互形式会改变形式化成本”，不能支持“作者愿意维护 C”。

**反例五：中国社区里“越结构化越好”也有明显的学习门槛信号。** Notion 中文小说模板评论里既有人称其简单好用、方便梳理，也有人明确认为对创作新手“显得很专业”。citeturn22view2 这不是代表性调查，所以只能算 C/D，但至少说明“结构化维护成本为零”没有事实基础。

**负结果：没有找到真正的写作版规则引擎标杆。** World Anvil 会把魔法整体规则、具体 spell、condition 等分到不同模板；Campfire 有 Magic Module；Novelcrafter 有 Codex、Lore、Progressions；Scrivener 能用 metadata 搜索和过滤。citeturn18view0turn18view2turn18view4turn18view6 这些都能证明“作者工具在结构化资料”，但本轮没有找到一款主流小说工具，其公开一手文档同时给出类似 OPA/Drools 那样清楚的**规则语义、当前事实输入、异常/undefined、冲突优先级和可复算执行轨迹**。所以不能把它们当 C 的已验证行业参照。

Novelcrafter 的当前页面还提供了一个有意思的反方向提醒：其 Codex 可以维护 progressions，以时间点覆盖旧 lore；同时官方页面建议给 AI 的信息应只保留请求真正需要的内容，以免信息过多造成混淆。citeturn18view5 这支持“长期知识底座可以很丰富，但每次检查不应无差别加载所有东西”，却仍不能证明它拥有确定性规则执行。

**负结果：中国作者侧缺维护成本数据。** 卖报小郎君、《十日终焉》作者、傅九、晨飒的公开文章能证明不同题材确实采用不同程度的设定准备和专业资料研究。citeturn16view1turn16view0turn16view4turn16view3 但这些材料没有记录“维护一条设定花几分钟”“修改一次例外需要触碰几处”“多少条规则后作者放弃维护”。所以这一块不能给 B，更不能给 A，仍是 **U**。

**负结果：没有证据支持把文学模糊性视为待清洗的数据质量问题。** Sanderson 的软魔法讨论反而给出了明确反例：人物与读者不知道魔法全部能力边界可以是设计目标。citeturn19view7 因而检查器发现“无法严格判断”时，有时正确结果就是“当前设定故意没有给出确定答案”，而不是催作者补字段。

**例外爆炸也不能简单理解成“规则条数很多”。** 真正麻烦的是多个规则同时适用以后，谁覆盖谁。Drools 的官方规则引擎专门存在 agenda、salience 等机制来处理同时匹配和执行顺序。citeturn23search3 因此，“总规则 + 例外 + 例外的例外”一旦被承诺为 C，就必须面对优先级和作用域；只把文本拆成更多行并不会解决问题。

OPA 的最小复现思路非常适合验证这道题里的“unknown 不等于 false”。官方说明 Rego 是对结构化数据求值的声明式策略语言，并明确存在 undefined。citeturn17view0turn17view3 可以准备这样一条极简规则：

```rego
package novel

can_use if {
    input.used_today < data.max_per_day
    input.cooldown_done == true
}
```

对应数据：

```json
{
  "max_per_day": 3
}
```

完整输入：

```json
{
  "used_today": 2,
  "cooldown_done": true
}
```

理论上，这时规则有足够信息判定 `can_use`。把 `cooldown_done` 删除以后，规则不再满足完整求值条件；OPA 的语言语义允许出现 undefined，而不是天然把所有缺项解释为“世界规则禁止”。citeturn17view3turn17view4

这段实验真正想验证的不是 Rego 语法，而是产品承诺：

> **“我没有足够数据算”必须与“规则算出来不能”分开。**

这可能是 C 档检查器最重要的诚实边界。

**建议的本地 A/B/C 小实验**

外部资料无法替你们决定阈值，所以最有价值的下一步不是继续搜“别人怎么拆字段”，而是做一轮小型受控测试。实验不需要写作模型，也不需要生成正文。

建议从上面 16 个案例中选 **12 个**，保证硬规则、混合规则、故意模糊规则各占一部分。为每个案例准备同一份“作者真相包”，再生成三种表示：

**A 组**只有整块设定材料；**B 组**把相同内容变成可独立引用的小条文，但不加入运行语义；**C 组**只把其中真正机械的部分实现成可求值规则，并提供独立状态。

每位被试处理同样的问题，但采用交叉顺序，避免“先做过一遍所以后面更熟”。不需要很大样本；**12～18 名与你们首发画像接近的作者**已经足够用来发现明显的维护摩擦和误信模式，这个数量是产品探索实验建议，不是统计功效结论。

查询不要只问简单题，而要故意加入四类陷阱：

| 测试注入 | 示例 | 真正想测什么 |
|---|---|---|
| **状态缺失** | 有“每日三次”，不给“今天用了几次” | 系统会不会把 unknown 硬答成数字 |
| **后加例外** | 原本禁入，后来给角色一次性特批 | A/B/C 哪个最容易漏维护 |
| **版本漂移** | 第 12 章作者把 10 分钟 CD 改成 5 分钟 | 旧条文/旧运行规则会不会继续生效 |
| **故意模糊** | “只有心境成熟者才能突破” | 系统是否承认这不是当前可计算命题 |

记录五个指标就够：

| 指标 | 怎么算 | 为什么重要 |
|---|---|---|
| **查询正确率** | 与作者预先确认的 gold answer 比较：正确 / 错误 / 正确返回 unknown | 直接回答 A/B/C 是否真的提高核对能力 |
| **错误自信率** | 在信息不足题里，仍给确定 yes/no/数字的比例 | 这是本题最关键的风险指标 |
| **维护时间** | 作者完成一次规则修改到系统重新正确回答所需时间 | 判断 C 的收益是否被维护成本吃掉 |
| **维护触点数** | 一次规则变化要改多少处 | 观察版本漂移和重复维护 |
| **例外漏失率** | 增加例外后，旧结论仍被错误沿用的比例 | 直接测“例外爆炸”风险 |

这里最好把 **unknown 作为一种正确答案**。例如“规则写了每天三次，但系统不知道今天用过几次”，gold answer 就应该是“无法计算剩余次数；缺今日使用状态”，而不是 0、1、2 或 3。OPA 对 undefined 的明确语义为这种设计提供了很好的工程参照。citeturn17view3turn17view4

还应单独记录作者对答案的信任程度。因为 C 最大的风险可能不是“平均准确率比 B 低”，而是**错的时候更像真的**。可以在每题后只问一句：“你有多大把握会按这个结果继续写？”再比较错误回答时的信任分数。这样能测出“错误自信”而不仅是模型准确率。

有一个很值得预注册、但现在**不能当结论**的假设：

> A 可能维护最快，但回答复杂规则时只能帮忙找材料；B 可能在大量文学规则里得到最好的“证据能力/维护成本”比；C 可能在次数、冷却、资源、明确前置等机械题上大幅占优，但一旦状态过期或覆盖不完整，也最容易出现“伪精确”。

加拿大 RaC 的“可自动化但维护艰难”、CatalaBlocks 的“形式化界面能降低难度”、OPA 的 undefined 语义共同让这个假设值得测，但它仍需要你们自己的作者实验才能升级证据。citeturn20view0turn19view3turn17view3

## 产品候选启示与旧报告关系

**对产品的候选启示**

这轮证据可以支持的方向，核心有七件事。

**一是把“查询问题的性质”放在“规则有没有拆条”前面。**  
“这本书原来怎么写的？”、“哪条设定支持这个判断？”、“今天还剩几次？”其实是三种不同任务。OPA/Drools 的运行架构以及 Akoma Ntoso 的引用架构都说明，检索、引用、求值之间存在真实技术边界。citeturn17view2turn17view5turn21search1 因而“是否值得 C”更适合看**是否反复出现状态化、机械化问题**，而不是看设定字数多不多。

**二是 B 可以有独立长期价值，不必把它当成 C 的半成品。**  
作者即使永远不需要算次数，也可能需要回答“这条门规在哪写的”“后来哪章加了例外”“哪个版本覆盖哪个版本”。稳定的条文引用本身就能服务核对、版本修订和解释；法律文档标准专门为这种精确引用设计了稳定标识机制。citeturn21search1

**三是 C 只对“有运行状态的问题”说计算话。**  
如果规则写“每天三次”，但没有“今天用了几次”，C 的诚实输出应当是“规则上限已知、当前使用状态未知，所以剩余次数不可计算”，而不是回退到语言模型猜测。OPA 明确保留 undefined，就是很好的工程类比。citeturn17view3turn17view4

**四是 C 的解释最好还能回到 B/A。**  
“不能使用”如果只给一个红叉，会掩盖规则版本和语义错误。更可信的承诺是：“在规则版本 X、当前状态 Y 下，被规则 Z 阻止；Z 来自这段作者设定。”加拿大 RaC 明确把代码看作原始规则的解释而非取代物，这为这种可追源设计提供了强外部依据。citeturn20view1

**五是允许局部 C，不要逼整块世界观进入 C。**  
“突破需要筑基圆满、丹药一枚、心境成熟”可以让前两个条件进入计算，把“心境成熟”保留为作者判断。这样既保留文学模糊性，也避免为了机器完整而发明作者没有说过的定义。Sanderson 对软魔法和不完全可知性的论述，以及 Rules as Code 对自然语言歧义的实际困难，都支持这种边界。citeturn19view7turn20view0

**六是例外应该被视为 C 成本信号，而不是“拆条越多越好”的理由。**  
当“通常不行”“掌门可特批”“只限一层”“战争期间例外”“主角血脉另算”开始叠加时，机器执行需要的不只是更多条目，而是明确哪个规则在什么范围覆盖哪个规则。Drools 的冲突解析机制说明，这类问题是真实的规则引擎工作，不是普通知识库检索。citeturn23search3

**七是作者维护动作应该尽量由真实写作事件触发，而不是让作者先建一个完美规则数据库。**  
中国公开 AI 长篇工作流已经出现“当前状态卡、章节结算、设定变更记录”等做法，而且会把状态卡过期视为需要修正的问题。citeturn22view0 这是单案例，不能直接照搬，但它提示了一个值得本地验证的方向：作者可能更愿意在“发生使用、恢复、特批、改设定”时确认变化，而不是开书时预先穷举全部未来例外。证据级 **D，候选实验价值高**。

对应三档，检查器能诚实说的话可以先控制在这个层面，不涉及字段设计：

| 能力档 | 可以承诺 | 遇到覆盖不足时应说 | 不应该说 |
|---|---|---|---|
| **A** | “找到了相关原设定/章节。” | “没有在当前纳入材料里找到足够依据。” | “所以一定允许/禁止”“剩余 N 次” |
| **B** | “这些条文支持/冲突；这里有原文依据。” | “条文存在歧义 / 可能有未纳入例外 / 两条来源冲突。” | “因为条文都拆好了，所以结果一定可计算” |
| **C** | “按当前规则版本和当前状态，结果为 X，并能给出参与求值的规则。” | “缺状态”“规则未覆盖此情形”“存在未解决冲突”“运行表示可能过期”“该条件仍需作者判断” | 在上述任何一种情况下偷偷退化成确定 yes/no |

这套语言是候选承诺边界，不是最终 UI 文案。

**不能由本研究证明的东西**

外部研究不能证明 B 应成为你们产品默认档，也不能证明 C 应只开放给某个题材；不能给出“规则超过 20 条就运行化”这种阈值；不能证明自动从自然语言抽出的 C 规则可以无人复核；也不能证明作者愿意接受某种维护流程。尤其是自动形式化，法律研究里即使有专门语言和专业人员，也仍然需要处理歧义、例外和解释问题。citeturn19view2turn20view0

同样，本研究不支持“软规则不用拆”。软规则可能非常值得 B：比如门派伦理、恋爱禁忌、历史礼仪，作者照样需要精确找回和引用，只是不适合让机器替作者做确定性判决。

## 更新触发器与完整来源

**更新触发器**

按本题指定触发器，以下事件一出现就值得重查：

**产品准备真正上线规则检查器时。** 这时外部概念研究的收益已经下降，应优先用你们自己的真实规则查询做 A/B/C 对照实验，重点统计 wrong-but-confident，而不是只看召回率。

**首批用户开始频繁问“为什么算错了”时。** 尤其是错误集中在“当前次数不对、漏了特批、旧规则仍在生效、规则怪谈假规则被当真”时，应重新审视运行状态、版本和作用域覆盖，而不是单纯换模型。

**首批用户大量拒绝维护规则时。** 这会直接改变 C 的经济性。加拿大 Rules as Code 已经给出“形式化成本可能难持续”的外部警报。citeturn20view0

**出现新的写作工具公开提供真正可复算的规则引擎时。** 判定标准不是厂商说“AI 会查设定”，而是能否公开说明：规则输入、当前状态、缺失输入、例外/冲突、版本和求值解释。当前被抽样的主流写作工具公开文档主要还停留在资料组织、story bible、metadata、progressions 等层面。citeturn18view0turn18view3turn18view6

**OPA、Drools、Yarn/Twine 等基础技术出现影响语义或作者工具设计的新版本时。** 当前核查基线分别包括 OPA v1.19.0、Yarn Spinner compiler v3.2.1、Twine 2.12.0；这些版本信息很容易过期，应重新核。citeturn17view1turn17view8turn17view10

**Rules as Code 出现新的实地长期维护研究时。** 目前加拿大材料很有价值，但它自己已经记录了早期编码工作的可持续性困难；更长周期的维护数据会直接影响我们对“形式化成本”的判断。citeturn20view0

**中国网文侧出现大样本作者维护研究时。** 当前中国证据主要是作者个案、社区工作流和模板反馈，最多支撑 C；任何覆盖题材、作者资历和连载长度的正式调查，都可能显著更新本报告。citeturn16view0turn16view1turn22view0turn22view2
