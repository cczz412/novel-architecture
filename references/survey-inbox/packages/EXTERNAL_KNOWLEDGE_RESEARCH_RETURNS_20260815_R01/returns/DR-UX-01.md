# DR-UX-01｜普通中文作者看得懂聊天、画布、卡片、账本和确认吗：从“搜做法”转向测理解

**调查执行日：2026-08-14**  
**适用对象：中文长篇网文作者，重点是已经写过黄金三章、正在第 3～20 章继续推进的作者**  
**结论性质：公开证据研究＋可复现理解测试方案；本轮没有招募真实作者，也没有执行真实原型测试，因此凡涉及“目标作者到底会不会误解”的结论，不能伪装成实测结果。**

## 一页结论与调查方法

**一页人话结论**

先把最重要的一句话放前面：

> **现在有足够证据支持“别把后台概念直接端给作者”，但没有足够证据证明某一套具体词和界面已经被中国作者看懂。真正需要验证的，不是作者喜不喜欢聊天、画布或卡片，而是他在操作前能不能准确回答：什么会被改、改到哪里、什么没改、依据了哪些章节、出了错怎么回来。**

### 已经比较有把握的部分

**作者自己的语言体系，明显是围绕故事和写作对象长出来的，不是围绕软件对象长出来的。** 在番茄的创作指导、阅文作者资料、作家访谈和中文创作者视频里，稳定出现的是“大纲、细纲、章节、人物／人设、设定、世界观、故事线、主线、支线、伏笔、素材、码字”等词。比如齐佩甲直接说自己会在每章前写章节“细纲”；“跳舞”则明确说自己从不写大纲，并把大纲看成有利有弊的“双刃剑”；Bilibili 创作者也大量用“大纲、人设、人物关系图、故事线、关键事件、素材库”等词组织写作经验。citeturn18view2turn18view1turn23view0turn23view1turn23view2

所以，**“大纲”可以继续作为作者界面的主词；但不能因为内部把它当规划账，就认为作者也会把它理解成有严格状态、权限和真值语义的数据库。** 更强的反例恰恰来自资深作者：“跳舞”长期不写大纲，而是边写边想；这说明“规划账”可以服务写作，却不能反过来要求作者按照数据库思维写小说。citeturn18view1

**“卡片”不能当成已经验证的作者词。** 当前公开中文样本确实出现“人物卡片”，也出现“知识库、素材库”，说明部分工具型作者能接受这些组织方式；但证据支持的是**“人物卡片”这个带语义的复合词**，不是裸的“卡片”。“卡片”究竟是人物资料、AI 建议、剧情事件、一个 UI 容器还是已经写入系统的正式对象，公开资料没有回答。citeturn23view3

**“画布、账本、关章、覆盖范围”目前都不应该被当成中国网文作者已经掌握的自然术语。** 本轮针对“关章”“覆盖范围＋网文写作”“画布＋网文作者”等进行了定向检索，没有找到稳定的作者实践语料能证明这些词具有目标产品想赋予它们的含义；“覆盖范围”的检索结果更多是一般中文意义下的“传播覆盖范围”，不是写作检查范围。这个结论不是“作者一定看不懂”，而是**目前证据等级只能到 U：没有资格假设他看得懂。** citeturn16search1turn16search7

**“收工”尤其容易产生状态错觉。** 2026 年对全职网文作者林海听涛的采访里，“什么时候收工”对应的是“写完这一天的五六千字”——它是非常自然的日常结束用语，但没有“锁章、提交、发布、冻结事实、把聊天写入账”的含义。把“收工”拿来当系统状态动作很亲切，却同时可能让人猜：是不是自动保存了？是不是今天结束了？是不是这一章不能再改了？这些问题必须测。citeturn18view3

**聊天入口最大的危险，不是聊天本身，而是“聊天到底只是说，还是会动东西”。** IUI 2025 的 Agent 用户研究发现，参与者对 Agent 内部如何行动的心智模型经常不完整，用户会依赖可见的行动描述和来源来判断系统到底做了什么；Notion 2026 当前规则也明确区分只读取数据的 read tools 与会 create/update/delete/send 的 write tools，并默认让写操作在执行前确认。换句话说，成熟 Agent 产品自己也没有把“聊一句”和“改数据”当成一个无需解释的动作。citeturn19view3turn20view2

对你们来说，这意味着一个很具体的候选原则：**聊天可以是万能入口，但“建议”和“改变长期对象”最好不是同一个不可见动作。** 用户至少要看得见“准备改什么→改到哪里→确认后发生什么→完成后哪里变了”。这得到 Agent 研究和当前产品规则的跨来源支持，但**中国网文作者是否会因为双入口而产生“偷偷改账”错觉，目前仍是 U，必须通过本地理解测试回答。** citeturn19view3turn20view2turn21view2

**“多弹确认框”也不是答案。** CHI 2026 一项包含 8 人形成性研究和 48 人被试内实验的研究，比较了多步骤 Agent 任务中的确认时机；81% 的参与者偏好中间关键点确认而不是只在结尾确认，该实验中任务完成时间下降 13.54%。另一方面，通用可用性原则也提醒，确认框过多会让人形成一路点击同意的习惯。方向更像是**在有后果的状态转折点确认，而不是每一步都问“确认吗？”**。citeturn21view0turn22view3

**目前没有证据支持给“小白作者”和“高级作者”做两套权限语义完全不同的主界面。** 可用性原则允许给熟练用户提供加速器、快捷操作和更高信息密度，同时保留同一套核心对象与动作；2026 年 Computer Use Agent 研究也发现用户控制、解释和信息需求会随情境分化。更稳的待测假设因此是：**同一套事实和权限语义，不同信息密度、展开层级和停点**，而不是两种世界。citeturn22view3turn21view2

**章工作流的连线图，也没有证据支持放在作者主视野里。** 中国作者确实会画“人物关系图”，也会用“故事线＋关键事件”梳理剧情，这证明图形化关系本身并非作者不能理解；但这和“把后台执行流程画成节点连线，并拿它当主导航”是两回事。现有证据最多支持“关系图在特定故事任务中有用”，不能支持“工作流图适合成为小白作者的主界面”。citeturn23view0turn23view1

### 仍然不知道的部分

本轮**没有证据可以回答百分比意义上的以下问题**：

“有多少 3～20 章作者看到‘事实’就知道它只代表已经发生／已经写明的内容？”——U。

“有多少作者看到聊天里的建议，会以为它已经进入大纲？”——U。

“卡片、画布、账本、计划、确认、收工、关章、覆盖范围，哪一种具体文案错误率最低？”——U。

“新手和高级作者分别需要多少信息密度？”——U。

“故事概览、战报背景、章工作流和正文区放在哪个相对位置最好？”——U。

这些都属于**原型任务数据**，不能靠继续搜竞品文章补齐。可用性测试的标准做法也是让真实或接近真实的用户完成具体任务，观察其行为，而不是用“你喜欢哪种界面”代替完成证据。citeturn19view0turn19view1

### 几种现在不能下的流行结论

“5 个用户说看懂了，所以 80% 作者都能看懂”不成立。5 人左右的研究适合找问题，不适合估计总体成功率；NN/g 明确区分了定性找问题和定量估计，后者通常需要显著更大的样本。citeturn19view2

“作者会用人物卡片，所以可以把一切都叫卡片”没有证据。公开样本只证明某些作者会说“人物卡片”。citeturn23view3

“现在 AI 产品都在走聊天＋画布，所以这是成熟答案”也不成立。截至 2026-08-14，Anthropic 仍把 Artifacts 作为与主对话分开的独立窗口，用于后续修改和复用；OpenAI 的当前发布说明却记录了 GPT-5.5 Instant/Thinking 已取消 Canvas，把写作和编码重新收进聊天里的 writing/code blocks，只有付费用户还能在 legacy models 中有限期继续用 Canvas。主流产品并没有收敛到唯一答案。citeturn22view0turn22view1

“所有作者都需要大纲”更直接被中国作者实践反驳。齐佩甲按章节细纲推进，而“跳舞”几乎走相反路线；两者都是成功的长期网文作者。citeturn18view2turn18view1

**问题范围与调查方法**

本轮以**中文简体语料为产品理解主证据，英文 HCI／官方 Agent 文档为交互机制证据**。中文作者实践的核心时间范围取 2020～2026，同时保留较早但仍能揭示失败模式的工具社区案例；当前产品能力一律按 2026-08-14 重新核查，不拿历史功能介绍冒充今天现状。

取样渠道分为五类：番茄／阅文等作者平台官方材料；中国作家网、作协网站、媒体直接作者访谈；Bilibili 中文写作创作者资料；晋江论坛、知乎等失败反馈；IUI/CHI 等可核方法的 HCI 研究与 Notion、Anthropic、OpenAI、Linear 当前官方文档。可用性研究方法参考 NN/g 与 GOV.UK。citeturn18view2turn18view1turn23view2turn19view0turn19view1

纳入材料必须至少满足一个条件：出现作者实际使用的词；展示真实写作组织方式；描述具体失败／困惑；给出当前产品动作与权限规则；或者提供可核查的人机实验。只宣传“AI 写作神器”“全流程效率提升”但没有任务证据的资料，不用于提升关键结论等级。

本轮中文本地语料故意占较高权重，但存在明显偏差：机构采访容易集中于已经成功的作者；Bilibili 创作者本身比普通作者更愿意研究工具；“签约作者／全职作者”等视频账号身份有一部分只有作者自述，不能自动视为独立认证；论坛和知乎会过采样遇到问题的人。Bilibili 的播放量、关注数等均**没有**被用作证据升级依据。citeturn23view1turn23view2turn23view3

还有一个关键限制：公开网页能抓到部分 Bilibili 标题、简介、合集和视频时长，但本轮没有可靠取得逐字字幕及对应画面时间戳。因此我没有伪称“观看后做了视频行为编码”。这些材料只编码公开页面可复核的标题、简介和作者自述；正式用于原型刺激材料前，还需人工复看原视频。

| **确认** | 确定、提交、采纳、保存 | 通用 UI 语言，不是网文术语 | 可能只是 acknowledgement，也可能触发 commit/write | ⚠️ 权限错觉高风险候选 |

| **关章** | 未找到稳定同义行业词 | 定向检索没有找到目标用法 | 更像产品自造状态词 | **U／不适用：当前不能当行业惯例** |

这里有个非常重要的区别：**“作者听过这个词”≠“作者准确理解这个对象的权限”。** “计划”谁都认识，但如果产品内部存在“AI 临时候选、作者已经决定、正式大纲”三种状态，仅靠一个“计划”标签仍可能造成严重混淆。

**分歧与负结果**

### 大纲不是统一工作法

齐佩甲的实践非常结构化：每章前写细纲，再按细纲推进；“跳舞”的实践则是动态滚动式，甚至公开表示自己从来不写大纲，但脑中会一直提前想后续情节。两人共同证明的不是“大纲好不好”，而是**网文作者对计划外化程度差异极大**。citeturn18view2turn18view1

因此，产品若把“建立完整大纲”变成使用系统之前必须完成的前置任务，会直接与一部分成熟作者的工作法冲突。这条不能证明“不要大纲”，只能反驳“所有人都应该先填完规划表”。

### 图并不是坏东西，但“故事关系图”不等于“系统流程图”

全职小说作者自述账号“墨久歌星辰”专门制作过以《琅琊榜》为例的人物关系图内容；另一创作者会把小说拆成“故事线＋关键事件”。这说明故事关系本身可以被作者图形化。citeturn23view0turn23view1

反过来，当前没有中国作者证据表明他们希望看到“Agent 调用→状态读取→检查节点→commit→回写”的工作流连线。**把叙事关系图的可理解性外推成后台流程图的可理解性，是一个危险类比。**

一个比较稳的原型假设是：关系图只在作者主动处理“这个人跟谁有什么关系”“这条故事线走到哪”时出现；后台 Agent 连线则不要拿作者来帮机器监工。这个仍需实测，等级 D/U。

### “聊天＋独立画布”甚至在主流 AI 产品里都没有收敛

Anthropic 截至 2026-08-14 仍明确让 Claude 把需要后续修改、迭代、复用的大块内容放进主对话之外的独立 Artifact 窗口，并支持多档账户。citeturn22view0

但 OpenAI 在 2026 年 5 月的当前发布记录里明确写明：GPT-5.5 Instant 和 GPT-5.5 Thinking 不再提供 Canvas，写作和编码功能改为直接出现在聊天响应中的 writing/code blocks，Canvas 只通过 legacy models 为付费用户暂时保留。citeturn22view1

这给本题一个很有价值的负结果：**连头部通用 AI 产品都不能证明“独立画布一定优于聊天内对象”，所以中国作者产品更不该靠竞品投票选答案。真正稳定的需求是“对象可定位、可复用、可区分状态”，至于它物理上是不是叫画布，需要测。**

### 多入口不是问题，入口之后失去追踪才是问题

Linear 的 Asks 是一个成熟项目管理反例：请求可以继续从用户熟悉的 Slack、邮件、Web 表单进入，但每个 Ask 会转成 Linear 中可追踪、分派和回复的 issue，而且对话与 issue 可以继续关联。Linear 官方明确把它描述为解决原本散落在 chat、email 和 ad-hoc forms 中的请求。citeturn22view2

这不能直接证明网文作者需要 issue 化，但它反驳一种常见想法：“为了可追踪，必须禁止聊天入口”。**熟悉入口和正式状态可以分离；麻烦的是系统偷偷从一个变成另一个。**

### “所有动作都确认”同样可能失败

CHI 2026 的 Agent 研究显示，结尾才确认容易让早期错误一路传播；每一步确认又会带来繁琐开销，因此研究者测试的是中间关键点确认。citeturn21view0

NN/g 的错误预防原则也提醒：确认对不可逆操作有用，但过度使用会让用户习惯无脑通过。citeturn22view3

Notion 当前做法提供了一个很具体但不能照搬的参考：read tools 不改变外部数据，适合自动执行；create/update/delete/send 等 write tools 默认需要确认，并明确展示将执行什么动作。citeturn20view2

所以“确认”应该被研究为**动作风险设计**，而不是一个万能按钮文案。

### 创作工具加功能，可能把核心写作体验弄丢

较老的中文社区案例里，知乎有墨者用户在 3.0 加入社区能力后抱怨产品不如原来纯粹；晋江论坛的迁移讨论则出现找不到迁移入口、PC/移动端衔接困惑、基础写作体验不满意并转向其他工具的用户。它们不是代表性样本，而且已经较旧，只能证明**这种失败模式真实存在过**，等级 C/D。citeturn6search1turn6search8

当前墨咕官网又主打云端同步、界面布局自定义等能力，说明产品后来也在继续调整，因此不能把 2019～2021 的抱怨描述成 2026 当前状态。citeturn6search0

但历史案例对本题依然有价值：**创作工具最容易犯的错之一，就是把“新增能力”当“作者更容易写”。对正在码字的人来说，多一个社区、仪表盘、关系图、Agent 运行区，都可能是额外的迷路机会。**

### 真正应该做的本地理解测试

因为本轮没有真实作者参与，以下是**研究计划，不是研究结果**。

建议分两阶段。

**形成性理解测试**：18 人，三组各 6 人。这个规模用于发现误解类型，不用于说“60% 作者会怎样”。NN/g 对定性研究的建议也是小样本迭代找问题，而不是用小样本估总体率。citeturn19view0turn19view2

三组建议这样招：

| 组 | 招募条件 | 为什么要有 |
|---|---|---|
| 小白推进组 | 已真实写到 3～20 章；尚无稳定长篇完本经验；平时不依赖复杂知识管理工具 | 最接近首发主体 |
| 稳定作者组 | 有较稳定连载经验，至少完成过一部长篇或长期连载；可以使用大纲，也可以不用 | 防止产品只适合教程型新人 |
| 重度工具组 | 有真实网文推进经验，同时经常使用表格、Obsidian、Notion、Scrivener、知识库或 AI 辅助工具中的一种以上 | 检查高级信息需求，但不能让这组代替普通作者 |

应主动控制题材和平台偏差：男频／女频都要有，番茄／阅文／晋江等不要只招一个站；不能只招签约成功作者；不能从 AI 写作社群单一招募，否则“画布、知识库、Agent”等词的理解会被严重高估。

若产品真的需要一个“术语理解率”数字，再单独做**第二阶段定量验证**，至少让每个关键分层获得足够样本并报告置信区间，而不是把 18 人形成性测试换算成全体作者比例。citeturn19view2

### 七个关键任务

这些任务故意不问“你喜不喜欢”，而是测**预测、执行、状态判断和恢复**。GOV.UK 的可用性指导同样要求任务目标真实、不要在题干里泄露答案，并观察用户到底能不能完成。citeturn19view1

| 任务 | 给参与者的场景 | 客观成功判据 | 重点观察 | 任务后的理解题 |
|---|---|---|---|---|
| **继续写** | “这是你昨天写到一半的书。今天接着写。”不要提示入口 | 能在不经过机器状态教学的情况下找到上次正文位置，并识别当前是草稿还是已发表内容 | 是否先被故事概览、战报、流程图、聊天吸走；返回正文用了几步 | “你现在看到的是哪一章？哪些已经发出去了？哪些还能随便改？” |
| **只问一次，不改东西** | “你觉得第 7 章人物动机有点怪，让助手帮你看看。” | 完成查询后能准确说出：聊天给了建议，但哪个长期对象尚未改变 | 是否默认聊天说了就等于大纲已改；是否去其他区域寻找“修改痕迹” | “刚刚系统改了你的书里什么？大纲变了吗？事实变了吗？” |
| **把一条建议正式留下** | 从上一任务中挑一条真正准备采用的建议 | 用户能在行动前预测写入目标，执行后找到变化位置，并知道如何撤销／修订 | “确认”是否让人盲点；用户是否知道它进入大纲、计划还是事实 | “现在和上一分钟相比，哪样东西真的变了？你以后在哪儿能找到它？” |
| **事实还是未来计划** | 给出：“第 5 章已经写明张三左腿受伤”；“你打算第 9 章让他痊愈”；“AI 建议第 7 章先安排复诊” | 能分清已写内容、作者计划、AI 候选，且不会把后三者自动改写成第一类 | 哪些标签导致三种状态被混在一起 | “哪一句现在已经算书里的事实？哪一句只是你准备这么写？AI 那句现在算不算你的决定？” |
| **决定检查范围** | “帮我查张三受伤以后有没有前后矛盾。”让原型给出不同 scope 表达 | 用户能在执行前准确复述系统会查看哪些章节、正文／草稿／大纲中的哪些内容 | “覆盖范围”是否被跳过；用户是否以为系统看了全书 | “这次到底查了第几章到第几章？大纲算进去了吗？没查的地方有哪些？” |
| **今天到这里** | “今天写到这里，你准备离开。”展示“收工／关章／保存／确认”等概念变体，但底层能力保持一致 | 离开前能说清是否已保存、是否锁定、是否发布、是否只是结束本次工作 | 哪个词引发“锁章”“发布”“自动确认事实”等错误推断 | “点这个以后，明天还能改吗？读者能看到吗？AI 会不会把今天的东西当最终事实？” |
| **出问题后找回来** | 在故事中制造一个人物状态矛盾，提供写作区、故事概览、检查结果、背景战报和一份可选关系/流程图 | 能从发现问题→找到证据→理解来源→处理→回到原正文，不发生导航迷失 | 回退次数、错进工作流图次数、是否忘记原来在写哪一段 | “这条警告为什么出现？依据哪一章？改完后你下一步准备去哪？” |

### 必须统一记录的观察指标

每个任务至少记五件事：

**预测正确性**：动作前问“你觉得点下去会发生什么？”

**状态识别**：动作后问“现在到底哪里变了？”

**来源识别**：能不能说出系统用了正文、大纲还是 AI 建议。

**恢复能力**：一旦走错，是否能自己回到写作位置。

**严重错误**：是否出现“以为没写入实际上写入”“以为已经写入实际上只是聊天”“把未来计划当已发生事实”“误以为已发布／已锁章”等。

满意度可以收，但不能替代这些行为指标。可用性研究本来就把 task success、行为观察与“感觉如何”区分开来。citeturn19view0

### 术语理解题不能直接问“懂不懂”

不要问：

> “你理解‘覆盖范围’吗？”

这非常容易得到礼貌性的“懂”。

应该给东西让作者解释，例如：

> “这个地方写‘覆盖范围：正文 1～8 章＋当前大纲’。你觉得它刚才看了什么？没看什么？”

对“确认”：

> “你还没点。你觉得点‘确认’之后，最有可能发生什么？只是关掉提示、保存、修改大纲、发布章节，还是别的？”

对“卡片”：

> “你觉得这里这张东西是什么？关掉以后还在吗？换个聊天还能找到吗？”

对“收工”：

> “点了以后明天还能改吗？这章会发布吗？系统会不会把今天的内容视为已经定稿？”

对“事实”：

> “作者脑子里已经确定‘皇帝其实没死’，但正文还没揭示。在你看来这算这里说的‘事实’吗？”

**🔥 最关键的一道题其实不是术语题，而是状态题：**

> **“现在系统里有哪些东西，是因为你刚才那个动作才真的变了？”**

如果用户回答不了，名称再亲切也没有解决权限错觉。

## 产品候选启示与旧调查关系

**对产品的候选启示**

以下只写**研究支持的候选方向**，不冻结字段、不画最终 UI。

### 候选方向：作者看到故事词，系统内部再承担工程复杂度

外部证据足以支持作者层优先用“大纲、正文／书稿、章节、人设／人物、设定、故事线、伏笔、素材”等词，而让 canonical state、provenance、scope、agent run 等概念继续留在内部。citeturn18view2turn18view1turn23view0turn23view1

这不代表内部模型要变简单。恰好相反，后台完全可以严格区分：

已发表书稿、当前草稿、作者确认的设定、未来大纲、私人想法、AI 临时候选、查询结果。

只是**不要要求作者先学会这七种数据类型的工程名字才能写小说。**

还需本地实验验证的是：在这些差异必须暴露时，哪一种人话组合最清楚。例如“正文已经写明”“你后面的打算”“AI 这次建议”“只在本次聊天里”等，比抽象状态词更清楚还是更啰嗦，目前未知。

### 候选方向：聊天默认让人感觉是“问”，改长期对象要制造清楚的状态转折

Agent 研究和当前产品设计共同支持“读”和“写”应该让用户可区分。IBM 的研究说明用户需要可见行动信息建立心智模型；Notion 当前甚至在工具层直接区分 read/write，并默认要求用户批准写操作。citeturn19view3turn20view2

因此值得进入原型 A/B 的不是“要不要聊天”，而是：

**A 型：**聊天给建议 → 出现“放进大纲／记为设定／暂时不要”这样的明确落点。

**B 型：**聊天可以直接执行，但执行前显示具体变化，例如“准备把这句话加入第 8 章计划”。

**C 型反例：**用户说一句“好”，系统静默更新长期对象。

C 型尤其应该用任务实测，因为它最有可能制造“好=我只是同意你的观点，还是好=你获得了写权限？”的歧义。现在不能声称中国作者一定会错，但这是高价值风险。

### 候选方向：别把“确认”当按钮设计问题，要把它当权限语义问题

“确认”最危险的不是这个汉字不好，而是它经常隐藏宾语。

“确认”什么？

确认我看到了？  
确认这是正确的？  
确认采用建议？  
确认写入大纲？  
确认覆盖已有内容？  
确认发布？

CHI 2026 的结果与 Notion 当前规则都更支持**围绕真正状态变化设置停点**，而不是统一让所有动作经过一个“确认”。citeturn21view0turn20view2

值得测试的是带后果的动作文案，例如“加入大纲”“记下这条设定”“只保留在聊天里”，而不是现在就宣布其中某一个必然是最终词。

### 候选方向：同一权限语义，不同信息密度，比两套产品更值得先试

现有研究没有足够理由把“小白版”和“专家版”做成两套不同状态模型。通用界面原则允许高级用户拥有快捷入口、定制和加速器，而不会让底层动作含义改变。citeturn22view3

可以把实验变量放在：

小白默认只看当前书稿＋就近提示；  
稳定作者主动展开故事概览；  
重度作者再展开关系、来源、检查历史和更完整状态。

**权限不随“高级模式”偷偷变化。**

如果高级模式一打开，聊天从“只建议”变成“自动改大纲”，用户就需要重新学习另一个世界。这恰好是应重点避免并测试的权限错觉。

### 候选方向：写作区应是“回得去的主场”，而不是所有对象平级

这里必须克制：公开证据**不能证明某一种最终布局最好**。

但可以提出一个强测试假设：

> 作者完成任何核对、聊天、关系查看或检查之后，都应该很容易回答“我刚刚写到哪了”，并快速回到正文。

这比测试“左边栏还是右边栏”“画布在中间还是正文在中间”更有决策价值。

候选布局可以同时测三型：

**写作主场型**：正文持续占主位置，故事概览和检查按需出现。

**双栏型**：正文与故事对象长期并列。

**后台主场型反例**：打开项目先看到故事图、战报或工作流，再进入章节。

观察哪种在七个任务中造成更少的失向、错误返回和状态误判。不能仅问“哪一个看起来高级”。

### 候选方向：故事概览可以可见，Agent 工作流不必可见

中文作者已有“人物关系图、故事线、关键事件”等外化实践。citeturn23view0turn23view1

所以“可视化”不是敌人。真正该分开的是：

**作者故事关系**：谁认识谁、这条线走到哪、这个伏笔还没回收。

**机器执行关系**：Agent 调了哪个工具、哪个节点重试、哪个 workflow edge 触发。

前者属于作品理解，后者更多属于系统调试。

除非本地实验显示作者真的需要第二类来恢复失败，否则不要因为后台是 graph，就让作者也住在 graph 里。

### 候选方向：范围不要只给一个抽象字段，要让作者能复述

“覆盖范围”目前没有本地自然用法证据。比把它当固定术语更重要的是让作者看得见：

> “这次只查第 1～8 章已发表正文。”

或者：

> “查第 1～8 章正文，也参考你目前的大纲。”

产品真正的成功标准不是作者能背出“覆盖范围”四个字，而是他能准确回答**“AI 刚刚看了什么、没看什么”**。

### 不能证明的东西

本研究**不能**证明“画布应该删除”。

也不能证明“卡片不能用”。

不能证明“聊天绝不允许写状态”。

不能证明“收工一定不能作为按钮”。

不能证明“高级作者永远不需要工作流图”。

甚至不能证明“大纲是全部作者最喜欢的首页入口”。

当前能证明的是：这些选择的正确性**没有来自目标作者的任务证据**；下一步应该测它们造成的权限、状态和导航理解，而不是继续堆竞品截图。

## 更新触发器与完整来源

**更新触发器**

出现以下情况时应重查，而不是让这份报告长期冻结：

**产品原型真正可操作。** 这是最高优先级触发器。届时公开研究的重要性会下降，七个任务的真实行为数据应成为主证据。尤其是一旦出现“用户说聊天只是建议，但实际上已经写入大纲”或反过来的严重错误，这类本地证据应直接压过竞品类比。

**真实作者频繁误解权限或状态。** 特别关注四类日志／访谈信号：“我以为已经保存了”“我以为 AI 只是说说”“它什么时候改了我的大纲”“为什么它把我没写的东西当事实”。出现重复模式后，应重查整个动作词体系，而不是只换一个按钮文案。

**主要聊天／画布竞品发生交互改变。** 2026 年本身已经出现 Anthropic 继续强化 Artifact、OpenAI 在 GPT-5.5 上撤掉 Canvas 的分化，因此这部分证据非常容易过期。citeturn22view0turn22view1

**Notion、Claude、ChatGPT 等 Agent 产品改变 read/write、自动执行、确认或 activity log 规则。** 这些资料只是“当前实践”，不是稳定的人类规律；版本变化应触发重查。Notion 当前 write tools 默认确认的规则尤其属于高时效证据。citeturn20view2

**出现新的中国网文写作工具或作者平台实践。** 如果番茄、阅文等主流作者工作台开始稳定使用“事实、卡片、画布、章状态”等词，需要重新判断这些词是否已经形成行业习惯，而不是继续沿用本轮 U 级结论。

**出现中国作者专门的同行评审 UX／HCI 研究。** 当前 Agent 控制研究主要不是中文网文作者，任何针对连续创作、作者状态管理或中文创作工具心智模型的实验都应优先纳入。

**本地实验显示新手与高手存在稳定、重复的断层。** 只有这时才有足够理由重新讨论是否需要两套界面，而不是现在先按“新手/高手”人为拆产品。

**这轮研究能给出的最硬结论，不是一套最终术语，而是一条验收线：**

> **任何“聊天、画布、卡片、事实、计划、确认、收工、关章、覆盖范围”的设计，只有当普通作者在没被教学答案提示的情况下，能正确预测动作后果、辨认什么真正发生了变化、说出变化落在哪里、知道系统依据了什么、并在出错后自己回到正文，才能算“作者看懂了”。**

在完成这轮真实理解测试之前，**“大纲、人设、故事线”等作者自然词可以获得较高外部证据支持；“画布、账本、关章、覆盖范围”只能作为待测候选；“聊天会不会偷偷改账”“事实／计划是否分得清”“新手和高手是否真的需要两套界面”都应继续保持 U，而不是被竞品做法提前写成产品真相。**
