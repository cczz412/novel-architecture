## 结论

截至 2026 年 8 月 13 日，公开生态里没有一套成熟方案能同时满足：

- 角色可参数化复用；
- 表情、动作可换；
- 中式古风与都市场景覆盖；
- 风格统一；
- 允许嵌入商业 SaaS 并让用户批量生成或导出。

推荐架构是：

> 故事事实 → `visual_scene_spec` → 确定性 SVG 渲染 → 可选 AI 美化候选 → 作者确认后冻结

MVP 默认走 SVG，模型调用费接近零；AI 只做离线扩充素材、背景/道具和少量重点帧。不要让每章默认走完整文生图，也不要让 AI 图片反向修改人物与剧情事实。

| unDraw / Storyset / Blush                         | 固定插画和营销配图丰富                                       | 不宜作为自动生成器的内嵌素材底库。[unDraw](https://undraw.co/license)明确限制 integration、素材包再分发及 ML 使用；[Storyset](https://storyset.com/terms)限制把素材放入数据库、素材集合和自动化第三方服务 |

古风资源方面，本次检索只找到零散包，例如 [Ancient Chinese Character Pack](https://opengameart.org/content/ancient-chinese-character-pack-1) 和少量中国建筑 SVG，没有找到统一画风、部件可换、动作可换的完整系统。

因此，中式古风/都市部件库是主要空白，也会成为产品真正能积累的视觉资产。比较稳的组合是：

- DiceBear 式确定性内核；
- Open Peeps/Humaaans CC0 只用于快速验证；
- 自绘或买断的中式人物与场景包；
- Kenney/IconPark 补通用道具；
- 所有素材进入白名单 `asset_manifest`。

素材台账至少保存：`asset_id`、原始网址、作者、许可证及快照、下载日期、文件校验值、修改记录、归因文字、是否允许原始 SVG 导出。

## 2. 参数化人物怎么设计

游戏捏脸和 VRoid/VRM 最值得借鉴的是“分层参数”，不是直接采用其 3D 技术或素材。[VRoid](https://vroid.pixiv.help/hc/en-us/articles/360012681033-About-Editors-Design-and-Texture-Tabs-Properties-Panel)把脸、头发、身体、服饰分区；[VRM](https://vrm.dev/en/vrm/how_to_make_vrm/setup_vrm/)进一步把身份、表情、眨眼、视线和物理动作分开。

建议的数据结构：

| 层       | 参数示例                                                     | 变更规则                                              |
| -------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| 身份锚点 | `character_id`、体型族、脸型、肤色、发型、主服装轮廓、疤痕/发簪/眼镜等标志物 | 跨章锁定；剧情发生明确变化时生成新的 `visual_version` |
| 部件槽位 | 前后发、脸、眼、眉、口、上衣、下装、长袍、鞋、手持物         | 离散选择，避免自由路径形变                            |
| 材质颜色 | 肤色、发色、衣服主辅色                                       | CSS variables 控制，不复制 SVG 路径                   |
| 表情     | 平静、喜、怒、悲、惧、惊、怀疑                               | 映射为眉、眼、口的组合，不改角色本体                  |
| 动作     | 站、坐、走、跑、谈话、拥抱、战斗、倒地                       | `pose_id` 与角色身份分离                              |
| 镜头场景 | 朝向、远中近景、位置、比例、遮挡、天气、时间、场景模板       | 每章场景参数                                          |
| 兼容关系 | 锚点、关节坐标、z-order、遮挡区、禁配规则                    | 防止斗笠穿过头发、长袖与手势断裂等问题                |

连续滑杆只保留头身比、整体缩放、颜色、轻微偏移。脸宽、鼻形、衣袖长度等若做连续 SVG 路径插值，会迅速放大美术和兼容测试量。

### 表情与动作的成本排序

- MVP：`<symbol>/<use>` 复用部件，固定 `<g>` 插槽和锚点；眼、眉、口直接替换。SVG 的复用机制见 [MDN ``](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/use)。
- 动作：先做 8～16 个高频预制姿势。肩、肘、长袖、长发采用重叠遮挡或整段姿势部件，不急着做蒙皮。
- 微动画：CSS/SMIL 只做眨眼、呼吸、轻微摇摆、镜头推拉、雨雪烟雾。[`animateTransform`](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/animateTransform)足以覆盖这些需求。
- 产品化：若出现互动预览、动作状态机和连续肢体变形，再接 Rive。它支持骨骼、IK、状态机和数据绑定，官方 runtime 为 [MIT、可商用](https://rive.app/docs/runtimes/getting-started)，但 `.riv` 编辑与导出能力有席位费用。
- Lottie 适合固定循环动画和转场，不适合大量运行时换发型、服装和姿势。
- Spine 动画能力强，但工具和 runtime 许可证更重，不适合这个 MVP。

### “每张价格”不等于“每张可验收图片价格”

实际预算公式应写成：

```
有效单价 = API 单价 × 平均可计费尝试次数 + 参考图输入/训练/部署成本
```

若规划时假设平均 2～3 次生成才能验收：

- 0.20 元模型：约 0.40～0.60 元/可验收张；
- 0.22 元模型：约 0.44～0.66 元/可验收张。

这里的 2～3 次是预算情景，不是厂商公布的行业平均值。

按每章 3 帧、每月 10 万章计算：

- 全量使用 0.20 元模型，一次成功：约 6 万元/月；
- 平均两次生成：约 12 万元/月；
- 只美化 10% 帧、平均两次：约 1.2 万元/月；
- SVG 默认渲染：模型费为 0，但仍有 CDN、存储和导出计算成本。

### 人物一致性可行度

控制强度大致是：

1. 固定提示词＋seed：弱。阿里官方也说明，同 seed 只能相对稳定，不能保证完全一致。
2. 固定“角色视觉卡”＋每次重传参考图：中等。
3. 多参考图＋沿上一张继续编辑，或同一请求生成连续组图：中强。
4. 专属角色 LoRA/SFT：较强，但增加训练、部署、版本治理和审查成本。
5. SVG 人物保持不变，只让 AI 生成背景/光影/道具：确定性最高。

所以，“同一角色跨几百章不走样”目前不能靠纯 prompt 或固定 seed 解决。对故事概览，最稳的方法仍是人物 SVG 锁定，AI 不碰脸和标志物。

## 4. SVG＋AI 局部素材的混合路线

没有找到公开可核验的“小说产品已经成熟使用参数化 SVG 人物＋AI 槽位生成”的直接先例。相邻产品已经证明这种交互成立：

- [Adobe Illustrator Generative Shape Fill](https://helpx.adobe.com/illustrator/desktop/use-generative-ai/generate-shape-fills.html)：在既有矢量轮廓内生成内容，可控制轮廓贴合强度、风格参考和颜色。
- [Canva Magic Edit](https://www.canva.com/features/generative-fill/)：选中局部区域增补或替换，不重绘整张。
- [Bannerbear](https://www.bannerbear.com/blog/how-to-add-accurate-text-to-ai-images-using-bannerbear/)：AI 生成图片层，文字、布局和模板层保持确定性。

适合你的三种混合方式：

1. **离线扩库**：AI 生成新服装、道具或背景候选 → 人工清理/矢量化 → 对齐锚点、调色板、遮挡规则 → 入库长期复用。运行时仍是零模型费。
2. **背景生成**：SVG 人物置于 AI 背景之上，再统一描边、颗粒和色板。人物一致性不受生成模型影响。
3. **重点帧美化**：先渲染确定性 SVG 草图，用户主动点击“美化本章”后调用涂鸦作画或参考生图。输出保存为候选，不覆盖 SVG 真源。

不建议在线按槽位自动生成一个发型或衣袖后立刻投入使用。未经清理的部件通常无法满足锚点、遮挡、左右朝向、长袖和多姿势兼容要求。

## 5. 分阶段推荐与量级

| 阶段             | 推荐路线                                                     | 量级估算                                                     |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| MVP：零边际成本  | 自建 DiceBear 式渲染器；浏览器端 JSON→SVG；人物用离散槽位；预制姿势；场景模板＋道具＋天气遮罩；支持 SVG/PNG 导出 | 首发都市＋简化古风合计：8～16 个姿势、6～8 种表情、20～30 个发型/头饰、12～20 套服装轮廓、30～50 个道具、15～25 个场景模板。1 名前端/图形工程师＋1 名矢量插画师，约 5～8 周。这是项目估算 |
| 产品化：追求好看 | 扩展自有题材包；建立视觉编辑器和兼容测试；高频互动动作转 Rive；AI 离线扩充素材＋10%～20%重点帧美化 | 2 名工程师＋2 名视觉/动效设计，约 3～5 个月形成三类题材包、资产治理、候选审批和 AI 队列。若每 1 万帧只美化 10%，按 0.20 元、两次尝试，约 ¥400；全量 AI 则约 ¥4,000～¥6,600 |

MVP 的技术重点不是把组合数做得很大，而是保证：

- 同一 `character_id + visual_version` 永远渲染出同一视觉身份；
- 表情、动作和临时状态不污染身份参数；
- 每个部件有锚点、遮挡和兼容规则；
- 一个画面只表达一个主要剧情节拍；
- 无法表达时降级为剪影＋道具＋字幕，不让 AI 猜人物事实；
- AI 结果属于“候选视觉资产”，作者确认后才能冻结。

还有一条安全边界：若允许用户上传 SVG，不要未经处理直接内联。应使用白名单清洗，移除脚本、事件属性、`foreignObject`、外部资源引用并限制路径复杂度；可参考 [DOMPurify](https://github.com/cure53/DOMPurify) 与 [OWASP 文件上传指南](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

一句话决策：**MVP 做“确定性 SVG 故事投影器”；产品化再把 AI 放到离线扩库、背景和重点帧美化层。真正会形成差异的，是中式题材部件库、角色视觉版本和部件兼容契约，而不是单次生成模型。**
