## Q01｜为什么规则写得更清楚，4B 反而抽得更差？

```text
请做一次深度技术调查，解释“小型指令模型在结构化事实抽取中，增加看似正确的原子规则后，为什么可能出现过度抽取、误报暴涨和语义准确率下降”。

我们的本地实测对象是未微调的 4B 指令模型，同一模型、同一24题、同一正文、同一输出格式、同一解码，只改变系统提示词中的附加规则：

- 极简规则基线：TP 93、FP 154、FN 187，F1=0.352941
- 加一条“每个 fact 只写一个核心断言，不同主体/动作/状态分开写”：TP 55、FP 269、FN 225，F1=0.182119
- 再加一条“计划、承诺、推测、误信、否认必须保留状态”：TP 59、FP 256、FN 221，F1=0.198319

两条新规则都让输出变多、变碎，但真正命中反而减少。

请重点调查：
1. 这是否符合小模型的 instruction overload、constraint interference、salience bias、over-decomposition、prompt-induced verbosity 等已知现象。
2. 为什么“语义上正确的规则”不等于“对小模型有效的规则”。
3. 规则长度、规则位置、正向命令/禁止命令、字段说明和任务目标之间如何互相干扰。
4. 哪些论文或大厂实践支持“极简合同 + 示例”可能优于继续堆规则。
5. 对我们这个结果，下一步最合理的是删规则、改规则、加示例，还是进入微调；请给证据支持的优先级。
6. 请明确区分：论文直接证据、相近任务证据、你根据我们数据作出的推断。

优先找论文、技术报告、官方工程文档和可复现实验，不要只给提示词经验帖。请给原始链接、实验模型大小、任务类型和适用边界。
```

## Q02｜固定“双成员对比例”到底应该怎么设计？

```text
请调查：在4B左右的小型指令模型做中文结构化事实抽取时，一组固定的 contrastive few-shot pair 应该怎样设计，才能教会状态边界，而不是诱发抄词、固定事实数量或新的过度抽取。

我们准备比较：
- EX0：完全无示例
- EX1：所有题前固定加入同一组两个都正确的最小对比例
- 只新增EX1的24次推理，其他变量全部不变

对比例计划：
- A例：计划/承诺尚未执行；人物误以为“没有某物”，客观上实际存在
- B例：同样结构改成已经执行；人物检查后正确否定“没有某物”，客观上也确实不存在
- A/B人物、物件、编号结构、事实数量相同
- 两个答案都正确，不使用“错误答案作为反例”
- 每例5条事实，并故意保留一个不应抽取的气氛句
- 示例人物和词面与24道考试题完全隔离

请调查：
1. 两个正确示例组成的 minimal contrastive pair，是否比“一个普通正例”更适合教计划/已发生、误信/客观事实、说话人来源等边界。
2. A/B顺序是否会产生 recency 或 label-position bias；是否应固定顺序、轮换顺序，还是本轮只固定一种。
3. 示例事实数固定为5，会不会把模型输出数量拉向5；怎样检测 density anchoring。
4. 示例比真实题短很多，会不会带来长度或粒度偏差。
5. 如何做 anti-copy、实体隔离、谓词隔离和近重复检查。
6. 应该把示例放在 system 后、实际 user 前，还是放进 system；对 ChatML/Qwen 类模型有何证据。
7. 给一个最小、可预注册的实验合同和淘汰门，不要建议继续扩成很多示例臂。

请优先引用 few-shot prompting、contrastive demonstrations、in-context learning、example ordering、copying bias、label bias 方面的论文和官方技术资料。明确哪些结论在4B小模型上有直接证据，哪些只是大模型结果。
```

## Q03｜小说事实抽取到底应该怎么切块？

```text
请深度调查“长篇小说事实抽取的责任块切分”，重点不是上下文窗口能放多长，而是怎样避免把一个完整事实、指代链或连续两句话机械切断。

我们的本地结果：
- 保留自然完整责任段，长度约620–923个Unicode字符，中位数约760：8题F1约0.3494
- 固定约300字非重叠块：同8题F1约0.1386，117条预测只有14个TP
- 约60字机械块还没调用模型就退出：24题中约54.3%的Gold跨块，Stage1八题约57.6%的Gold跨块
- 所以“块越短模型越准”在端到端系统里并不成立；短块会先把事实结构切坏

请调查：
1. 文学叙事/小说信息抽取中，句子、自然段、对话轮、事件单元、EDU/discourse unit、语义段，哪种更适合作为责任块边界。
2. 怎样把“咚”“嗯”“……”等极短段落与相邻段合并，而不破坏对话归属。
3. 怎样识别两句共同构成一个事实：前句给主体，后句给动作；前句提出误信，后句纠正；前句条件，后句结果。
4. 动态块算法应该先按自然边界切，再用什么规则合并到大约600–900字。
5. 是否应允许少量重叠；若允许，跨块重复事实怎样聚合和去重。
6. 对远距离姓名/代词问题，应该扩大只读上下文、另做coreference后处理，还是把它混进责任块。
7. 请给一个可实现的Python切块流程、必要特征、失败回退和评估指标，但不要设计庞大的新系统。

优先找长文信息抽取、事件抽取、discourse segmentation、semantic chunking、coreference-aware chunking、RAG chunking评测的论文和大厂工程资料。请把“检索切块”和“事实抽取责任块”区分开。
```

## Q04｜24道题选 Prompt 赢家，可信度够不够？

```text
请调查：我们用同一组24道小说事实抽取题做成对比较，应该怎样判断Prompt方案真的更好，而不是小样本波动。

当前做法：
- 每个方案答同一24题
- Gold固定
- 剩余预测做匿名语义裁决
- 主要指标是micro Precision/Recall/F1
- 格式、非法证据、重复、触顶另设硬门
- 目前暂用“F1至少比基线高0.02且Recall不退”作为替换条件
- 多个家族依次只选一个赢家，不做全因子3×3×3

请调查：
1. 24个case的paired comparison应使用 paired bootstrap、randomization test、per-case bootstrap，还是别的方法。
2. micro-F1差0.02在280条Gold、约200–300条预测的规模下，通常是否足以说明提升。
3. 应怎样报告置信区间、胜率、case-level差异和错误家族，避免只看一个F1。
4. 多轮连续挑赢家会产生多重比较或winner’s curse吗；最小修正是什么。
5. 什么时候24题适合“淘汰明显差方案”，什么时候不足以“选冠军”。
6. 如果只想做Demo、控制成本，建议怎样设置最小门和停止规则。
7. 请给能直接执行的统计方案，最好附Python伪代码或公开实现。

请优先引用信息抽取、分类、生成式结构化预测评测、paired bootstrap/randomization及小样本模型比较方面的原始论文或权威文档。不要只说“多收集数据”。
```

## Q05｜选好输入结构后，怎样把它迁移到 LoRA 教材而不再训崩？

```text
请调查：当未微调4B模型已经选出相对较好的输入结构后，怎样设计LoRA/SFT教材，让模型同时学会格式和事实抽取，而不出现“全空、疯狂重复、过度抽取”三种塌陷。

我们的现场背景：
- 当前相对最优输入是：完整自然责任段约620–923字 + 左右各最多180字只读背景 + JSON事实列表 + evidence_ids + 极简规则
- 旧训练集主要由较长、事实较多的样本构成，模型出现过重复和过度抽取
- 补空/稀疏样本后，不同batch配对与loss归一化又会导致全空或局部塌陷
- token-weighted gradient accumulation、sample-mean loss、不同样本排序都试出过失败面
- 现有TRAIN96大约一半长段、一半短段，但当前结构赢家主要落在620–923字区间
- 我们不想继续盲目加教材或扫超参数

请调查：
1. 训练输入长度、责任段长度、事实密度是否应与推理默认结构对齐；允许多大比例的短样本。
2. 空答案、1–2条、3–6条、10条以上样本该怎样配比，才能教“该多则多、该少则少”。
3. batch_size=2、梯度累积时，长短答案如何采样/配对，怎样避免某类样本权重异常。
4. token-level mean、sample-level mean、按有效输出token加权，各自会怎样影响空答案和长答案。
5. 小数据LoRA更适合一轮完整遍历、按optimizer update计剂量，还是多轮低学习率。
6. 是否应把格式学习和语义抽取分阶段，还是保持同一答案同时学习。
7. 给一个“只允许一两次训练”的最小方案和硬停诊断，不要给大规模网格搜索。
8. 哪些教材和格式合同未来迁移到商用Mini模型仍有价值，哪些4B配方结论不能直接外推。

请找SFT样本加权、sequence-length bias、gradient accumulation、loss reduction、curriculum、catastrophic forgetting、小模型结构化生成方面的论文和官方实现。请把直接证据与推断分开。
```
