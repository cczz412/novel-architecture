## ✅ 独立审查结论

这张合同可以继续保留现有 36～60 次主网格，不必加模型、加 seed 或加题，但派生执行票还缺几把“归因锁”。

最重要的判词有五条：

* 首块格式失败后停跑可以保留；它会造成结果相关的不对称缺失，但只要失败臂不从总表消失，就不会被包装成优胜者。
* 所有模型和 A／B／C 必须用同一个固定首块。不要轮换首块，轮换只用于后三块的调用顺序。
* B 对 A、C 对 B 只能解释为“冻结 Prompt 整包的增量效果”，不能进一步声称是纯语义规则效果，因为长度和位置也同时变了。
* 4 个 DEV 块只够做描述与方向筛选，不够支撑显著性、跨模型规律或生产赢家。
* 36／48／60 必须是所有生成请求尝试的共同硬顶，包括运输失败和人工重试。

以下修改只应写进尚未冻结的 A／B／C 派生执行票，不碰天然基线、已有人工裁决和当前受控波次。

## 1. 首块停审：可以保留，但失败臂不能消失

它确实会产生“不对称缺失”：

* A 失败，A 的后三块不再运行；
* B、C 如果通过，仍有完整四块；
* 因而只比较“跑完四块的臂”，得到的是“通过首块格式门之后的条件成绩”，不是所有 A／B／C 的公平总体成绩。

结果相关的停测不能当普通随机缺失处理；统计设计的一般原则也是必须预先说明停测后缺失数据代表什么，而不是分析时直接删掉。[[FDA ICH E9(R1) 指南](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/e9r1-statistical-principles-clinical-trials-addendum-estimands-and-sensitivity-analysis-clinical)](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/e9r1-statistical-principles-clinical-trials-addendum-estimands-and-sensitivity-analysis-clinical)

失败臂应保留四行计划记录：

| 层级  | 应记录内容                                                       |
| --- | ----------------------------------------------------------- |
| 首块  | `attempted=1`、`FORMAT_GATE_FAIL`                            |
| 后三块 | `attempted=0`、`NOT_RUN_BY_FORMAT_GATE`                      |
| 整个臂 | `arm_status=GATE_FAIL`、`full_dev4_semantic=N/A`             |
| 完成账 | `observed_format_fail=1`、`policy_skip=3`、`usable_cells=0/4` |

关键处理：

* 不要把整臂语义 F1 填成 0：后三块语义没有观察到，填 0 会把格式失败误写成语义全错。
* 也不能把它从榜单删除：应放在“格式门淘汰”区，排序位置低于任何完整臂。
* 如果首块无效 JSON 里仍有可机械解析的事实，可以给 `FIRST_BLOCK_DIAGNOSTIC_ONLY`，但不能恢复参赛资格。
* Prompt 总结必须同时显示：`首块通过模型数/M`、`完整模型臂数/M`、完整臂的条件语义成绩。
* A／B／C 的汇总语义比较，只能使用三臂都完整的共同模型集合；其余差异只报格式结果。

首块建议固定为所有模型、所有 Prompt 共用的同一个块，而且要在看到 A／B／C 输出前，用块 ID 或冻结 SHA 的机械规则选定。不要因为某块历史上容易、难，或已经先完成人工裁决而临时选择。

确定性轮换首块会把“块难度”和“谁能活下来”混在一起。后三块的顺序可以轮换，首块不要轮换。

严格格式门本身也要补成明确布尔规则：解析、Schema、最终正文、截断分别怎样判；不能夹带语义质量、事实数量或 F1 条件。

## 2. Prompt 长度：硬门与记录项要分开

即使所有机械问题都排除，现有三臂仍不能把“语义内容”和“多出来的 Token”完全拆开。没有长度匹配的空白对照臂，就只能这样表述：

* B－A：固定例子整包的观察效果；
* C－B：新增三层尺子整包的观察效果；
* 不能写成“例子语义净效应”或“三层尺子纯净效应”。

长上下文中，信息位置变化本身就可能改变模型表现；能容纳不等于位置和长度没有影响。[[Liu 等人的长上下文实验](https://aclanthology.org/2024.tacl-1.9/)](https://aclanthology.org/2024.tacl-1.9/)

运行前必须设成硬门：

| 硬门       | 合格条件                                                        |
| -------- | ----------------------------------------------------------- |
| 实际序列化内容  | 冻结真实 `system/messages/schema/parameters`，不是只冻结 Markdown 源文件 |
| Token 预检 | 每个模型分别计算 A／B／C × 4 块输入 Token                                |
| 上下文容量    | 输入、系统包装、思考预算、固定输出上限均能放入模型实际窗口                               |
| 输出预算     | 同一模型的 A／B／C 使用相同输出上限和思考设置                                   |
| 自动处理     | 禁止静默截断、自动压缩、自动缩短历史或动态降低输出预算                                 |
| 参数       | 温度、采样、结构化输出、停止符和思考档共同冻结                                     |
| 失败处理     | 任一组合预检放不下，不允许临时缩 C、抬上限或删例子                                  |

各模型必须单独算 Token；同一文字换模型或版本，Token 数并不固定。官方文档也明确要求按实际模型重新计数。[[Token 计数说明](https://platform.claude.com/docs/en/build-with-claude/token-counting)](https://platform.claude.com/docs/en/build-with-claude/token-counting)、[[上下文窗口说明](https://platform.claude.com/docs/en/build-with-claude/context-windows)](https://platform.claude.com/docs/en/build-with-claude/context-windows)

运行中只记录、不因此改 Prompt：

* Prompt 字节数、规则／例子／正文各自 Token；
* 普通输入、缓存写入、缓存命中 Token；
* 实际输出和思考 Token；
* `finish_reason`、截断、空正文；
* 首 Token 时延、总时延、时间戳；
* 请求 ID、实际模型 ID、Endpoint、套餐线路；
* 计费前后余额或官方账单字段。

缓存配置能固定时统一关闭；不能关闭时，记录命中／未命中，并把延迟和成本分开报告。共享前缀和短期缓存可能使后运行的臂更便宜、更快，[[官方缓存说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)明确展示了这种前缀与时间窗口关系。缓存状态不应被拿来解释语义胜负，但会影响速度和成本比较。

## 3. B／C 例子逐字相同：必要，但还不够

B 和 C 共用逐字相同、顺序相同的例子，只能排除“换了一套例子”，还没有排除这些同时变化：

* 三层尺子插入后，例子、Schema、目标正文的绝对位置变化；
* 规则、例子、尺子、Schema 的段落顺序变化；
* C 多了一句过渡语、总结语或“请严格遵守”；
* Schema 在 C 中被重复提醒；
* B／C 使用了不同 chat role，例如一个放 system、一个放 user；
* 分隔符、标题、换行和 JSON 转义不同；
* 例子答案已经隐含了必抽／可选／禁抽和颗粒度；
* 例子固定事实数量、输出密度或拆分方式，给模型形成了数量暗示；
* 平台对 system／developer／user 消息的包装不同。

建议对“真正发给 API 的序列化请求”做机械差分：

* `B-A` 只能多出一个固定例子区块；
* `C-B` 只能多出一个固定尺子区块；
* 其余共同字节、角色、顺序、参数必须一致；
* C 专属的过渡语、优先级说明都必须包含在该尺子区块内，不能散落在别处。

C 的专属区块可放在共享例子之后、共同的最终 Schema／作答提醒之前。这样 B／C 的例子仍处于相同前缀位置，只移动后面的共同作答部分；位置影响仍然存在，但范围更窄。

例子答案若已经完整演示三层判断，并不是合同失效，只是 C－B 的含义应写成：

> 在已经看过隐含尺子的相同例子后，再把尺子显式说出来的增量。

不能写成“第一次引入三层尺子”。

例子顺序和位置不是小事。已有实验发现，相同 few-shot 样本只改顺序就可能明显改变结果，而且某个模型的好顺序不一定迁移到另一个模型。[[Lu 等人，ACL 2022](https://aclanthology.org/2022.acl-long.556/)](https://aclanthology.org/2022.acl-long.556/)

## 4. 模型×Prompt 交互应怎样报告

每个模型单独报告以下内容：

* A／B／C 首块门结果；
* 每块 `B-A`、`C-B`、`C-A` 差值；
* 四块汇总差值；
* 必抽 F1 之外的禁抽、证据、状态、说话人、颗粒度变化；
* 四块中改善／不变／退化分别有几块；
* 删除任意一个块后，方向是否翻转。

跨模型只做描述：

* 多少个模型方向为正／零／负；
* 模型间增量的中位数和范围；
* 哪些模型出现明显相反反应；
* 是否存在“C 只对某一个模型有效”的情况。

允许的表述：

> 在这 4 个 DEV 块和这组已选候选中，3/4 个模型的 C－B 为正。

不允许改写成：

> 三层尺子对模型普遍有效。

即使所有模型同方向，也只能写“当前候选集合内方向一致”。这些模型不是从全部模型中随机抽取的样本。

## 5. 不加 seed 时的机械调用顺序

建议串行执行，A／B／C 在同一个“模型＋块”内相邻运行，同时平衡谁先、谁后。实验设计里常用“分块处理可控干扰、平衡无法消除的顺序影响”；时间正是这里的干扰项。[[NIST 随机分块设计说明](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)

固定六个 Prompt 次序：

```text
ABC, BCA, CAB, CBA, ACB, BAC
```

机械生成规则：

```text
models = 按 SHA256(run_id + stable_model_arm_id) 排序
G      = 预先冻结的共同首块
R      = 其余三个块按 SHA256(run_id + block_id) 排序
orders = [ABC, BCA, CAB, CBA, ACB, BAC]
```

门检波次：

```text
第 i 个模型在共同首块 G 上，按 orders[i] 运行 A/B/C。
```

因此候选为 3、4、5 个时，门检顺序分别取前 3、4、5 个次序；每个 Prompt 出现在前、中、后的位置次数最多只差 1。

后三块：

```text
for r = 0..2:
    模型列表左移 r 位
    原始序号为 i 的模型运行 R[(i+r) mod 3]
    Prompt 顺序使用 orders[(M + r*M + i) mod 6]
    首块失败的 Prompt 保留槽位，但标记 SKIP_GATE，不重新压缩次序
```

这样做能保证：

* 每个模型都跑完其余三个块；
* 不会出现“先把所有 A 跑完，再跑 B、C”；
* 不会把某个平台或某个 Prompt 永远放在实验尾部；
* Prompt 先后顺序和可能的缓存优势得到轮换；
* 发生首块淘汰后，原计划槽位仍可回读。

运输重试放在当前波次末尾，按原失败槽位排序，不立即插队，也不重新排列后续主请求。

模型 ID尽量使用固定版本，不使用会自动热切换的 `latest` 类别名。官方版本说明明确写明某些 `latest` 别名会在新版本发布时自动切换。[[Gemini 模型版本规则](https://ai.google.dev/gemini-api/docs/models)](https://ai.google.dev/gemini-api/docs/models)

## 6. 4 个块能做什么统计

块才是接近独立的比较单位；块内事实、同一人物、同一事件链不能当成几十个独立实验。若四块还来自同一叙事卷，实际独立信息甚至低于 4。

可放心描述：

* 每块 TP／FP／FN 和 P／R／F1；
* 四块 micro 指标；
* 四块 macro 均值、最小值、最大值；
* A→B、B→C 的逐块差值；
* 改善／持平／退化块数；
* leave-one-block-out：每次删掉一块，方向是否翻转；
* 格式、运输、截断的确切次数和分母；
* 每个模型自己的 Prompt 反应。

只能写探索性结论：

* 某 Prompt 在当前 DEV 上更值得进入未见确认；
* 某模型似乎更吃例子或更吃显式尺子；
* 某类错误可能改善，但证据尚少；
* 当前哪一个 Prompt 是模型级方向候选。

必须留给未见确认集：

* 跨章节、跨小说的稳定提升；
* Prompt 的一般规律；
* 生产赢家或产品线达标；
* 显著提升、可靠置信区间；
* 三层尺子的纯语义因果效果；
* 平台版本变化后的稳定性。

不建议做：

* 把每条 Gold 或预测当独立样本的 bootstrap、卡方、Fisher 或 McNemar；
* 四个块上的普通 t 检验、ANOVA、混合效应模型；
* 只有四个簇的常规聚类稳健标准误；
* 报很多小数位的 wild-cluster bootstrap p 值；
* 从“某模型显著、另一模型不显著”推出模型交互。

少量簇会让标准误偏小、p 值过于乐观；相关方法在簇数很少时也有明显离散性问题。[[Cameron 与 Miller 的聚类推断综述](https://www.liuyanecon.com/wp-content/uploads/CameronMiller-2015.pdf)](https://www.liuyanecon.com/wp-content/uploads/CameronMiller-2015.pdf)

更直白地说：四个块做最简单的双侧配对符号检验，即使四块全同方向，最小 p 值也是 `2/16=0.125`。所以这轮不应设置“p<0.05 才算赢”。

## 7. 各类错误必须分账

不改冻结 F1 公式，只增加清晰账层：

| 账层    | 互斥主结果／字段                                                                        | 是否进入必抽 F1  |
| ----- | ------------------------------------------------------------------------------- | ---------- |
| 请求尝试账 | 运输失败、HTTP 状态、重试、时延、Token、套餐、缓存                                                  | 否          |
| 逻辑单元账 | 未运行、格式、解析、Schema、空正文、截断                                                         | 否，单独展示     |
| 语义主账  | `MATCH_REQUIRED`、`MATCH_OPTIONAL_NEUTRAL`、`MATCH_FORBIDDEN`、`UNSUPPORTED_OTHER` | 依冻结公式      |
| 错误标签账 | 状态、说话人、证据、颗粒度                                                                   | 不单独重复加进 FP |

具体规则：

* OPTIONAL_NEUTRAL 单列；命中不算必抽 TP，也不算 FP，漏掉也不算 FN。
* 明确禁抽单列为高风险错误，不埋进普通 FP。
* 普通误抽排除 optional 和 forbidden 后再统计。
* 状态、说话人、证据、颗粒度是可重叠诊断标签，不能彼此相加当总错误数。
* 格式和运输失败永远不塞进语义 F1，但必须和 F1 同屏显示。

同一语义预测可以复用裁决键，但复用范围要收紧：

* 语义键必须包含主体、动作、否定、状态／时态、说话人或归因；
* “计划去”和“已经去”不能共用键；
* 相同事实文本用了不同 `evidence_ids` 时，可以复用语义裁决，但证据合法性必须按每次输出单独判；
* 格式、运输、截断、缓存和顺序只能挂在各自 occurrence／attempt 上，不能随语义键复用。

## 9. 运输重试与硬顶：必须采用同一个真实请求上限

建议明确写成：

> `real_generation_attempt_cap = 12 × candidate_model_count`。任何调用生成 Endpoint 的尝试，从客户端开始发送时即计 1，包括连接失败、超时、HTTP 失败、流中断和授权运输重试。

因此：

* 3 个模型：所有实际生成尝试合计不超过 36；
* 4 个模型：不超过 48；
* 5 个模型：不超过 60；
* 重试不增加逻辑单元，但增加一次 `attempt_count`；
* 重试使用同一 `cell_id`、新的 `attempt_id`，并写 `retry_of_attempt_id`；
* 新请求 ID不能重新获得“一次重试资格”；
* 原始失败不可覆盖；重试成功只让逻辑单元获得可用正文，运输失败率仍按尝试账统计。

为了不让重试挤掉原本能运行的正常单元，可以加一条容量规则：

> 重试只能使用已经被永久停审臂释放的额度。执行重试前，要为所有仍有资格的主网格单元保留一次首发额度；若是首块运输重试，还要为其成功后会重新开放的后三块保留额度。余额不足时记 `RETRY_ELIGIBLE_NOT_RUN_CAP`。

这意味着：如果所有臂都通过首块、完整主网格正好占满 36／48／60，那么运输失败虽然“有资格重试”，但没有额外额度保证它一定执行。两条冻结规则同时成立时，这是不可避免的结果。

不把重试计入硬顶会出现三类问题：

* 即使严格做到每单元只重试一次，真实生成请求仍可能从 60 增长到 120；
* 如果重试生成新 ID，或 SDK、代理层又自动重试，次数可能继续放大；
* 失败较多的臂获得更多请求机会、更长运行时间和不同套餐状态，归因不再对称。

这不是假设风险。官方 OpenAI Python SDK 默认会对若干错误自动重试 2 次；AWS SDK 的默认 `max_attempts=3` 也包含首发加两次重试。[[OpenAI 官方 SDK](https://github.com/openai/openai-python)](https://github.com/openai/openai-python)、[[AWS 官方重试说明](https://docs.aws.amazon.com/sdkref/latest/guide/feature-retry-behavior.html)](https://docs.aws.amazon.com/sdkref/latest/guide/feature-retry-behavior.html)

所以执行票必须关闭所有底层自动重试，由实验脚本统一记账。否则表面的一次调用，底层可能早已是三次。
