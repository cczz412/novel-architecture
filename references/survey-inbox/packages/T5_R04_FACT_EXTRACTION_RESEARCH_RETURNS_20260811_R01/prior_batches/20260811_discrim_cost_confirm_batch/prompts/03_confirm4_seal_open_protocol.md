背景（真实项目）：我们把 4 章从未发给任何模型的原创章节封为「确认卷」（CONFIRM4），正文至今没有打开，也没进过任何 API 请求；另有 4 章「判别卷」用于日常筛选迭代。担心的问题：整个开发流程会反复迭代 Prompt 和评分规则，如果确认卷用得不小心，它很快就会被「间接污染」——不是模型见过原文，而是我们照着确认卷的失败案例改 Prompt，让它失去「未见」的意义。

请给出一套确认卷封存/开封协议的最佳实践：

1. 机器学习里 holdout / test set 纪律的标准做法怎么映射到「LLM 提示工程迭代」场景：确认卷最多能用几次、每次使用之间允许改什么；
2. 「开封门」应该设哪些硬条件（例如：候选已冻结、评分器已冻结、预注册了预期结果和过门线，才许开封一次）；
3. 用过一次之后的确认卷算不算烧掉？部分烧掉（只看汇总分不看逐条错误）能不能延长寿命？有没有「分层开封」（先开一章、留三章）的先例；
4. 怎么留下可审计的证据链证明「确认卷在开封前确实无人看过正文」（哈希封存、访问日志、双人见证之类的轻量做法）；
5. 如果确认结果和判别卷结论冲突，标准处理是什么（哪个算数、要不要第三卷仲裁）。

期望产出：一份带编号的封存/开封协议（我们会直接抄进执行合同），每条说明依据；以及最常见的三种「确认集悄悄失效」事故模式和检查办法。
