## Prompt 1｜小样本判别测试怎么设计（发：聊天+极高+深度研究）

```text
背景（真实项目，中文网文事实抽取评测）：我们要从约 13~20 个商用 API 模型条件里筛出 3~5 个候选。已有两块旧材料的完整人工裁决（每块 225/337 个预测键全审），但按确定性区间支配判定，20 个模型组里 18 个仍分不开。我们准备了 4 章从未发给任何模型的新鲜章节做「判别卷」，任务形态是：给定章节正文+只读背景，模型按固定输出合同抽取事实句，与人工金标逐条比对，可算 Precision/Recall/F1、格式通过率、假事实率。预算级别：总调用数希望控制在一两百次以内。

请深度调查并回答：在「候选多、题目少、预算有限」的约束下，怎样设计一次小样本模型判别测试才能可靠分开头部模型？具体想要：

1. 学界/工业界在小样本模型排名上的成熟做法：配对比较（Bradley-Terry/Elo）、序贯淘汰、自适应选题（类似 IRT 的高判别力题目优先）各自适用条件；
2. 每个模型至少需要多少独立评测单元，排名才不至于被单章特性主导；bootstrap/置换检验给小样本排名置信区间的标准做法；
3. 题目难度不均衡的坑怎么防（比如某章天然事实密度高，会系统性抬高 Recall）；
4. 「先用少量题淘汰明显差的，再对头部加题加密」的两阶段设计有没有先例和标准停止规则；
5. 明确指出哪些结论只适用于人类偏好评测（如 Chatbot Arena 类），不能直接搬到我们这种「有金标的确定性打分」场景。

期望产出：一套能直接落到我们场景的设计规则（题目数、分配方式、置信判定、停止规则），每条附出处；以及「什么证据出现时应该放弃小样本判别、改为扩大题量」的红线。不要替我们选具体模型。
```

## Prompt 2｜API 评测的费用/Token/时延记账标准（发：聊天+极高+网页搜索）

```text
背景（真实项目）：我们对多家中国商用 LLM API（火山方舟 Agent Plan 套餐、硅基流动按量计费等）做同题对照评测。上一轮的教训是：语义质量分都齐了，但每次调用的费用、Token、时延账没记全，导致最后无法做「质量×成本」的候选筛选——这个缺口再多审语义也补不上。下一轮开跑前要先把记账合同定死。

请调查并回答：

1. 公开基准（如 HELM、Artificial Analysis、各类 LLM leaderboard 的成本维度）对「每次调用记什么」的标准字段：输入/输出/思考(reasoning) Token 分账、缓存命中折扣、重试与失败调用怎么计入、限流等待算不算时延；
2. 跨平台价格归一化的通行做法：按百万 Token 单价换算的坑（阶梯价、思考 Token 单独计价、缓存价），「每任务成本 cost-per-task」和「达标质量下最低成本 cost@quality」哪个更适合选型；
3. 套餐制（额度包月）和按量计费混在同一张对照表里怎么处理才公平——套餐边际成本近零，但不能因此在表里记零成本；
4. 思考型模型（reasoning model）时延和 Token 的特殊坑：思考 Token 是否计费各家口径、同模型不同思考档要不要拆成不同条件；
5. 失败/空输出调用在成本账里的标准处理（记成本不记质量分？单列失败率？）。

期望产出：一张「每次调用最小必记字段清单」+ 归一化公式 + 失败处理规则，每条注明出处或行业惯例；能直接抄进我们的执行票。不需要评价任何具体模型好坏。
```

## Prompt 3｜未见确认卷的封存与开封协议（发：聊天+极高，可不联网）

```text
背景（真实项目）：我们把 4 章从未发给任何模型的原创章节封为「确认卷」（CONFIRM4），正文至今没有打开，也没进过任何 API 请求；另有 4 章「判别卷」用于日常筛选迭代。担心的问题：整个开发流程会反复迭代 Prompt 和评分规则，如果确认卷用得不小心，它很快就会被「间接污染」——不是模型见过原文，而是我们照着确认卷的失败案例改 Prompt，让它失去「未见」的意义。

请给出一套确认卷封存/开封协议的最佳实践：

1. 机器学习里 holdout / test set 纪律的标准做法怎么映射到「LLM 提示工程迭代」场景：确认卷最多能用几次、每次使用之间允许改什么；
2. 「开封门」应该设哪些硬条件（例如：候选已冻结、评分器已冻结、预注册了预期结果和过门线，才许开封一次）；
3. 用过一次之后的确认卷算不算烧掉？部分烧掉（只看汇总分不看逐条错误）能不能延长寿命？有没有「分层开封」（先开一章、留三章）的先例；
4. 怎么留下可审计的证据链证明「确认卷在开封前确实无人看过正文」（哈希封存、访问日志、双人见证之类的轻量做法）；
5. 如果确认结果和判别卷结论冲突，标准处理是什么（哪个算数、要不要第三卷仲裁）。

期望产出：一份带编号的封存/开封协议（我们会直接抄进执行合同），每条说明依据；以及最常见的三种「确认集悄悄失效」事故模式和检查办法。
```
