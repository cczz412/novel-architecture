# 调查任务：怎样证明独立验真器真的修好了事实抽取，而不是与提议模型一起犯错

触发原因：准备自建新的评测与流程；已有开发卷被反复使用，若不先查先例，容易把验证器的自信和开发集调参误当成产品改善。

## 本地背景

当前四块来自原创新小说，Gold把候选分成必抽、可抽可不抽、明确不该抽三类。97次API调用产生1,132个去重预测，尚待正式人工语义复核；当前四块已经参与多轮模型和Prompt比较，只能当开发集。下一步若引入补漏器和验真器，需要预先定义验证器校准、相关错误控制、灰区处理和未见题确认，避免“两个模型都同意”却都错。

## 新增的数据回流与持续确认问题

新总账含 Ling 的一次短预算格式失败和四次成功调用，共 97 次；匿名队列增至 1,132 条。请把 HTTP 成功但最终结构化正文未完成，明确列为验证器和管线的机械失败面。

验真器、人工裁决和用户投诉未来还会成为训练数据来源。请设计一条可审计的数据回流链：保存哪一版原始答案、谁给出修正、怎样构造成 chosen/rejected 偏好对、哪些失败只适合 SFT、哪些适合 DPO、怎样防止验证器和教师模型共同犯错后被再次训练放大。请预注册持续监控：未见小说确认卷、按失败类型分层、模型更新漂移、用户线上分布漂移和强 API 对照；没有未见题复现时，不得把训练集改善称为产品改善。

## 请你深度调查

请设计一套适用于“候选事实生成＋逐条证据验真＋程序合并”的评测办法，专门回答：验真器是否真的提升整条管线，而不是只与提议模型共享偏差。

请比较同模型自检、同家族不同模型、不同厂商模型、判别式小模型和人工抽检；说明验真器该用哪些标签，如何校准置信度与拒答，如何测 `SUPPORTED / CONTRADICTED / NOT_STATED / AMBIGUOUS`，怎样处理必抽/可选/不该抽三类事实，以及如何把验证器自身的误杀和漏放传导到最终P/R/F1。还请给出开发集、校准集、未见确认集的正确分工，以及成对bootstrap/随机化检验或置信区间应如何用于最终决策。

## 期望产出

- 论文、官方技术报告或可靠工业实践，重点看验证器校准、相关错误、选择性预测、级联分类和LLM-as-judge风险
- 一张最小数据切分与盲审流程，不要求一开始就造大规模新Gold
- 验真器单体指标和端到端管线指标，含误杀、漏放、拒答、灰区和每章最差表现
- 一个预注册模板：何时过DEV晋级门，何时只能保留，何时必须在未见题确认
- 适用条件、失败条件和出处链接

## 采用／否决判据

- 只有当验真器在独立校准集上可测、端到端P/R改善、每章不塌陷且未见题方向一致时，才允许称为管线改善
- 若同模型/同家族相关错误明显，必须给出盲输入、换家族或人工抽检的硬条件
- 当前四块只能用于DEV筛选，不能单独证明生产更优
- 若研究只报告judge与人工的一致率、却不报告它对最终抽取P/R的影响，不足以采用
