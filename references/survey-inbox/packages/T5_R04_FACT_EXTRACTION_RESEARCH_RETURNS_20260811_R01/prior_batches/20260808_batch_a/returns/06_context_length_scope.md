# 研究综述：更多上下文并非总是更好  
研究发现**上下文长度对LLM性能影响不均匀**。技术报告指出，随着输入长度增长，模型表现往往变得不稳定甚至下降。特别地，“**中间丢失**”现象普遍存在：当关键信息出现在提示文本的开头或结尾时，模型准确率最高；而信息埋在中间时，性能显著下降。背后原因是注意力稀释：前几个标记默认吸收了大量注意力分数，后续标记分到的注意力就少了。添加无关文段会夺取有用信号，导致准确率下降。例如，一项研究发现，当无关但相关的信息出现在提示中时，模型准确率会**大幅下滑**；即使检索到100%相关信息，仅增加提示长度（用空白或掩码填充）也会导致13.9%–85%的性能下降。  
另一方面，在特定领域任务中，**适当的上下文信息也有提升作用**。有研究表明，对特定任务提供更长的指令和背景知识，通常能提高模型指标；但即便如此，LLM的表现仍大多远低于人类水平。这意味着简单堆砌信息并不能彻底解决问题，重点在于*提供有效信息*。实践经验也建议：提示结构要层次清晰，如将人格设定/任务目的置于前面，正文内容放中间，用明显分隔符隔开，上下文要求和格式放在最后。并保持长度适中（如几百词内），避免过度膨胀。此外，如果多次调用固定开头的系统提示或规则，这部分可以利用**KV缓存**复用前缀计算结果，大幅降低推理开销。总体而言，**更多上下文信息不一定更好**，无关或冗余内容往往会稀释关键信号。  

# 实验设计与评估指标  
针对文中提到的假设，建议设计以下对照实验：  
- **分层Token预算对照（CTX-0/S/M/L）**：逐层增加上下文信息，如按提示所述：  
  - CTX-0：只给出小说正文和最小格式约定。  
  - CTX-S：在CTX-0基础上添加简短规则说明和元数据。  
  - CTX-M：再加入已确认的人物背景等信息。  
  - CTX-L：进一步加入上一轮状态和示例。  
  每层记录新增的信息类型（规则、背景、例子等），不要仅关注总Token数。比较各层在语义事实抽取上的**精度/召回/F1**、人物说话人识别等指标，并评估输出的依赖背景错误率。  
- **提示内容位置实验**：尝试不同元素顺序：  
  1. 规则→背景→正文  
  2. 背景→规则→正文  
  3. 规则→背景→正文→简短检查表（让模型回答后再核对）。  
  比较三种顺序下输出质量，看是否前置或后置说明对遵守规则和信息提取有影响。  
- **等Token干扰项对照**：在每个对照组中，插入等长度但无关的文本（如随机文章段落）作为干扰，以衡量性能下降是否纯粹由提示变长引起，还是特定内容造成。如果纯长度问题，添加任何无关文本都会同样降低表现；如果内容冲突问题，则特定干扰影响更大。  
- **预注册评估指标**：  
  - 语义事实抽取的**精/召/F1**（基于人工标注的正确事实判断）；  
  - **精度/召回变化**（与最短提示相比，各层提示后指标是提升还是下降）；  
  - **说话人识别正确率**；  
  - **依赖背景错误率**（提取事实时是否误用或错误关联背景信息）；  
  - 输入Token数、推理时延和每条预测成本（如以模型调用费用衡量）。  
  通过自动化流水线记录上述指标，确保可复现评估流程。  

# 最小充分上下文探索方法  
- **边际价值评估**：衡量每条额外上下文项对结果的贡献。可采用*留一法*：依次去掉规则、示例、背景等某部分，观察性能变化；或更系统的Shapley值方法（尽管计算昂贵）。另外，可尝试分析Attention或梯度权重，判断哪些段落对输出影响最大。目标是找到“**增量信息不再显著提升核心指标**”时的上下文量。  
- **上下文检索策略**：对于背景知识的检索，可基于实体、事件或时间线关键词匹配，也可用向量相似度检索（RAG常用方法）。文献中常见做法是将文档切块（chunk），对每个块计算嵌入向量，根据问题检索相关块。适用于我们的小说场景，可先检索出与当前段落最相关的情节背景，再作为提示输入。  
- **Context Pruning**：结合简化技术，如摘要或知识提取，将长背景信息压缩为简要要点。也可使用**LLM摘要**：先让模型总结已有状态，再用摘要作为输入，而不是原文冗长信息。  
- **Prompt 设计注意**：尽量将关键信息靠近预测指令位置（首尾），以利用“首因效应”和“近因效应”；规则说明一般放在开头，输出格式限制可放在结尾提醒。必要时在正文前后重复关键规则，提高遵守率。  

# 对本地Dense Qwen代理模型的建议  
✅ **结论：** 对小规模Qwen-3.4B代理模型，应尽量提供*最少且必要*的上下文信息，避免冗余。根据“Context Rot”等研究，小模型在长提示中更易被无关信息干扰。在本地可做分层实验（如上所述），找出在保证事实精度的前提下最短提示长度。一般来说，先提供任务目标和必要规则，再给正文，后台人员和示例信息只在明显帮助时才加，否则反而可能降低精度。  
⚠️ **风险/坑：** 小模型容易“丢失中间信息”，增加多余文本会显著拉低性能。实验中若发现精度随Token增加反而下降，应检视是否被干扰信息占用注意力；如果是，应考虑丢弃相应内容。

# 对未来Sparse Ling Tiny的复验建议  
✅ **结论：** Ling 3.0 Tiny作为稀疏架构验算模型，关注于复核已筛选出的结论，可使用**更聚焦的上下文**。因为它只重新验证2–3个关键结论，提示中无需重复全部历史，只需给出那些结论相关的关键句子和少量必要背景。实验时也可采用同样的分层策略，预计Ling对少量关键信息敏感度更高。  
🔥 **最重要：** 测试时保持“最小上下文”原则：先用最简单的提示（仅提供必要句子和简短指令），再逐步添加更多背景，看其表现变化。Ling Tiny往往对提示内容的顺序和含义非常敏感；确保关键信息位置不被遮掩（根据“中间丢失”规律）。可以考虑在正文后追加简短的**核对清单**（short checklist），促使模型验证每条输出是否符合规则。  
💡 **示例：** 如果有核心事实A、B、C，可先让Ling只看到对应提取的句子和规则，输出验证结果；再在下一轮添加其他角色背景或历史信息，比对结果是否改变。这样可以验证每种信息添加的边际效果。  
👉 **下一步动作：** 在Ling Tiny上复现Qwen的实验设计；特别关注指令遵守率。当Ling正式可用时，执行相同的**分层对照**和**位置对照**实验，检查其对长提示的敏感度。  

# 对Doubao Mini/Lite生产迁移建议  
✅ **结论：** 在生产环境使用Doubao Mini/Lite时，因成本和延迟敏感，应尽量**精简提示并使用缓存/检索**技术。静态提示（如产品规则、格式说明）可利用KV缓存复用，避免重复计算；动态部分则通过检索选出最相关的上下文片段。我们建议构建自适应提示管线：首先对当前段落检索出相关的背景或历史状态（通过关键词匹配或嵌入搜索），然后仅将这些信息与必要指令传入模型。  
⚠️ **不建议：** 盲目增加所有可能的上下文。更多信息虽能提高召回，但研究表明这往往严重降低精度。生产中应设定“停损线”：如果新增信息未带来显著提升，就不再继续添加。  
👉 **下一步动作：** 实施与Qwen相同的**等Token干扰对照**，量化提示长度与质量的折中。并监控每次调用的**消耗Token数与对应收益**（如每增加100个Token后精度提升多少），为成本敏感的部署提供参考。探索**Prompt Caching**：对重复出现的标准前缀进行KV缓存，以降低Mini/Lite的推理开销。
