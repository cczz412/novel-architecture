## 1. 先给结论：小说事实抽取不能只看一个 F1

行业中最常见的基本分数仍是精确率、召回率和 F1：

\[
P=\frac{TP}{TP+FP},\quad R=\frac{TP}{TP+FN},\quad F1=\frac{2PR}{P+R}
\]

大白话说，**精确率**回答“抽出来的东西有多少是真的”；**召回率**回答“该抽的关键事实漏了多少”；**F1**把两者折中。对抽取任务，这是必要的底座，但远远不够。因为一份输出可能“事实大致对”但 JSON 坏了，也可能 JSON 完美却编了故事，或者事实句对但证据编号越过责任区。把这些全压成一个“准确率”，会看不出到底哪里坏了。

公开工程实践已经常把结构验证和字段正确性分开。例如 LangChain 的公开抽取基准把 `json_schema` 是否通过，与枚举分类、字段相似度、整体 JSON 差异分别度量；其数据集也采用“候选生成后人工审核”的路线。[8] 开放信息抽取研究 BenchIE 则指出，单纯 token 重合会把“字词重了但事实错了”误判为好结果，主张按“事实是否等价”而非只按字面重合评分。[3]

> **关键判断**：公开界并没有统一把它们固定命名为“格式门”和“事实门”。但“Schema／结构合规”和“字段或事实的语义正确”分开测，已经是结构化抽取的常见做法。[3] [8] 对本产品而言，`格式门` 与 `事实门` 这两个名字可以保留，因为它们正好把工程失败与叙事事实失败说清楚。

| 评测层 | 它在问什么 | 推荐指标或判定 | 为什么不能与别层混成一分 |
|---|---|---|---|
| 运行层 | 模型有没有正常产出？是否触顶、复读、空输出？ | 完成率、触顶率、复读率、空输出率 | 这反映调用稳定性，不等于会不会抽事实。 |
| **格式门** | 输出是否可解析、满足 Schema、字段类型／枚举／编号是否合法？ | JSON 可解析率、Schema 通过率、非法 ID 率 | 合法 JSON 可以是胡说；不合法 JSON 即使内容似乎对，也不能安全入库。 |
| 逐字与定位门 | evidence 的文本、起止位置、来源版本是否可机械复验？ | 原文切片回验率、位置精确匹配率、SHA 一致率 | 这证明“引用到哪里”，不证明“这段话真的支持这条主张”。 |
| **事实门** | 抽出的剧情原子是否真发生、是否应登记、是否多抽或漏抽？ | 事实级 P／R／F1、TP／FP／FN 原始计数 | 这是抽取质量的核心；只测格式会漏掉它。 |
| 证据承托门 | 这条事实是否真的被所报 evidence 支撑，而不是搭错证据？ | evidence 有效率、语义承托率、无支撑事实率；必要时人工复核 | “编号存在”不等于“编号支撑这句话”。 |
| 端到端门 | 一条结果能否以完整、合法、可回验形式安全交给下游？ | 端到端合格率；同时保留上述分项 | 这是上线安全视图，不应替代诊断视图。 |

### 1.1 F1 到底按什么对象算

如果“事实”是产品的稳定剧情原子，那么 TP、FP、FN 应按**事实身份**算，而不是按输出行数或 token 数算。一个 Gold 事实被模型用两个近似句重复写出，只能给一次 TP，第二条应记重复或 FP，不能靠重复把召回刷高。BenchIE 的事实簇（fact synset）正是类似思路：不同表面写法只要表示同一个事实，就归入同一簇；TP 按被覆盖的不同事实簇计，重复输出同一事实不重复获分。[3]

对本产品，建议固定两张分数表：一张是**严格表述分**，要求输出命中指定的剧情原子身份与关键槽位；另一张是**语义等价分**，允许在不改事件主体、关键变化、时间态和因果强度的前提下有同义改写。两张都要留，不能只留宽松分。严格表能防止“看起来差不多”的偷换，语义等价表能避免把纯措辞差异当模型错误。

### 1.2 事实门要不要人工复核

要。至少在小规模 DEV／blind 或争议样本上，要有独立人工语义复核。理由不是“机器评分没用”，而是小说事实经常涉及指代、隐含状态、时间先后、误导叙述与多个合理改写。BenchIE 为降低单一字面 Gold 的误伤，采用两位专家独立标注、补看系统输出、再合并分歧，并报告事实层的标注一致性。[3] NovelQA 也给每道小说问题配人工 golden answer 和文本 evidence。[2]

这里的人工不是让人“凭感觉给模型打总分”，而是处理自动规则难以安全决定的边界例：这是不是已发生态；是否是后续不能安全遗忘的关键变化；证据是否足以托住该主张；两个不同写法是否是同一剧情原子。人工规则、样例、仲裁顺序与一致性都应在评分前冻结。

## 2. 常见评测指标：建议怎么落到咱们的抽取合同上

### 2.1 基础事实分：同时报 P、R、F1 与原始计数

事实级精确率、召回率和 F1 是主表，且建议以 micro 方式汇总所有事实，再以“章／样本”为单位补一个 macro-F1。micro 更能反映总体事实量，macro 能防止少数事实很多的章节淹没小章节。无论哪一种，都必须把 TP、FP、FN 原始计数一并列出，避免分数变化没有解释空间。

| 指标 | 大白话解释 | 对剧情原子应怎样定义 | 典型误读 |
|---|---|---|---|
| Precision | 报出来的有多干净 | 模型报的已发生态剧情原子中，被 Gold 或人工确认的占比 | 高 P 不代表好：可能只报两条最容易的，漏了很多。 |
| Recall | 关键变化有没有漏 | Gold 中应登记的剧情原子，被模型覆盖的占比 | 高 R 不代表好：可能把背景设定、计划或猜测全塞进来。 |
| F1 | 干净与不漏的折中 | 基于同一匹配规则下的 P、R 调和平均 | 不能比较不同 Gold 版本、不同输入范围或不同门槛下的 F1。 |
| 重复率 | 有没有反复登记同一事 | 等价剧情原子重复出现的输出占比 | 不能把重复当多条 TP。 |
| 无支撑率 | 有多少事实没有真正证据 | 语义复核认定“evidence 不足以支持主张”的事实占比 | 不能用“证据 ID 格式合法”替代它。 |
| 端到端合格率 | 下游能否安全消费 | 同时过格式、定位、事实、证据承托的样本／事实比例 | 适合作为门槛，不适合作为唯一诊断分。 |

### 2.2 格式门与事实门应怎样接起来

建议把评测输出拆成两个视图，而不是二选一。

**视图 A：条件事实分。**只在 JSON／Schema 合法的输出中计算事实 P／R／F1。它回答“结构能用时，模型的语义抽取有多好”，便于诊断语义能力。

**视图 B：端到端事实分。**任何格式失败均不进入安全通过；必要时整样本记端到端失败。它回答“真实流水线上能安全交付多少”。这两张表如果差很大，问题主要在格式合同；如果两张都低，问题才更可能在语义抽取。公开抽取基准已经把结构验证和字段指标分开测，[8] 而背景板中的 evaluator R02 也已把机械正确和语义正确分开。这一做法与外部实践方向一致，但具体门槛仍须后续冻结。

### 2.3 证据要单独测，不能附带一笔带过

NovelQA 的每个问题除了金标答案外还带 evidence，且将多跳、单跳、细节问题分开；这说明在小说长文本里，“答对”与“能说明依据在哪里”应当同时存在。[2] 对咱们来说，证据的要求更严格：不仅要有文本片段，还要能回到冻结书稿的来源版本、位置与 SHA。因此建议把证据分为三道：

| 证据子门 | 机械还是语义 | 建议判定 | 出错时说明什么 |
|---|---|---|---|
| evidence ID／责任区合法 | 机械 | 引用 ID 存在、属于目标责任区、无越界 | 模型或编排把背景当作可写证据，或编号合同出错。 |
| 原文／位置／SHA 回验 | 机械 | 按 0 起算、左闭右开切片，逐字等于声明文本且来源版本一致 | 引用无法稳定回原文；不能进入长期底账。 |
| 主张是否被证据托住 | 语义 | 人工或经校准的复核规则确认“该片段足以支持该剧情原子” | 证据虽真但搭错了，或主张超出了原文。 |

## 3. 金标怎么建；怎样防泄露

### 3.1 金标不是“让人把整章摘要一遍”

本产品的目标不是全书百科，也不是摘要。因此 Gold 的单位应当是“**目标责任区内、已发生且有证据、后续不能安全遗忘的关键变化**”。先建“该不该常驻登记”的事实清单，再建每条事实的证据与位置。若先让标注者随意写摘要，再从摘要里反推事实，容易混进气氛描写、未来计划、设定解释或作者意图。

可参考 NovelQA 的做法：它把题目分成多跳、单跳、细节，并为每题配金标答案和 evidence；它还明确让人工标注者构造问题、答案和证据。[2] 可参考 BenchIE 的做法：同一事实允许不同可接受表面写法，并由独立标注和分歧合并来减少 Gold 不完整造成的误判。[3] 但两者都不能原样照搬：产品 Gold 还要记录“已发生态”、目标责任区、稳定事实身份，以及冻结书稿版本下的位置与 SHA。

### 3.2 建议的 Gold 构建流水线

| 阶段 | 做什么 | 产物 | 需要冻结的东西 |
|---|---|---|---|
| 1. 先写边界 | 明确样本、目标责任区、何种变化才算常驻事实，以及不能算什么 | 标注指南与样本清单 | 事实定义、排除规则、上下文可见范围。 |
| 2. 双人独立初标 | 各自列剧情原子、证据片段、是否需要前情才能判断 | 两份候选 Gold | 标注者不能互看答案。 |
| 3. 对账与仲裁 | 合并同一事实的不同写法；标记争议；必要时新增可接受改写 | Gold v1、争议表、事实等价表 | 仲裁角色与判据必须事前写明。 |
| 4. 机械固化 | 分配事实 ID；写入来源版本、SHA、位置、逐字切片；跑回验 | 可机读 Canonical Gold | 任一位置歧义不由程序猜，隔离或人工裁定。 |
| 5. 评分校准 | 用小 DEV 跑评分员一致性检查，修评分说明而不追改 blind | 评分手册、错误分类表 | 评分规则、阈值、评测代码版本。 |
| 6. 盲测封存 | 分配 DEV／blind；隐藏 blind Gold；锁版本并留审计记录 | blind 包与 manifest | blind 不参与提示词磨合、格式样例或人工规则迭代。 |

### 3.3 防泄露：要防三种，不只防“训练集喂进去”

第一种是**同书、同作者、同来源交叉**。DocRED 在关系抽取中发现，训练与开发／测试若出现重叠关系事实，模型分数会偏高，因此另报 Ign F1：把训练中已出现的事实忽略掉，再看未见事实表现。[4] 产品不必复制 Ign F1 这一名称，但应采用同样的保守原则：正式 blind 至少做到**作者级、书级、来源级**都不与训练和 DEV 交叉，并单独报告该严格 blind 的结果。这与背景板要求的作者、书、来源零交叉方向一致。

第二种是**开发泄露**。DEV 样本若反复用于 prompt、Schema、few-shot、错误规则、人工评分口径的修改，它就不能再被称为 blind。应在版本清单里记录每个样本是否碰过“模型训练、提示词样例、格式调试、评分调参、人工审阅”，并在发生接触后降级为 DEV 或诊断集。

第三种是**基座模型预训练污染**。对公开小说或闭源模型，这件事通常无法被完全证明为零。Deng 等人提出检索预训练语料重叠和 Testset Slot Guessing 两类污染探查方法；后者通过遮住不太可能的词或错误选项，测试模型是否异常地复现测试内容。[7] 因此应如实写“已做了哪些切分与污染检查”，而不要写“保证模型从没见过”。此外，可另建**不用于正式产线结论的原创／获授权 canary 样本**，对角色名、物件或因果作受控变体，以诊断是否只是背诵；但 canary 不能替代真实、封存的 blind。

> **防泄露的最低口径**：不公开 blind Gold；不让 blind 进入训练、提示词样例、格式修复或评分规则迭代；按作者／书／来源切分；每次跑分都绑定数据、评分器、提示词和模型版本；并承认闭源预训练污染只能“降低与探查”，不能凭空“证明不存在”。NovelQA 也采用测试 golden answers 不公开的做法以降低过拟合。[2]

## 4. 上下文范围：只看目标段、看前后文、还是看整章

公开研究的答案不是“窗口越大越好”。LongBench 发现，检索／压缩可以帮助较弱长上下文模型，但并不等于获得稳定的长上下文理解。[5] “Lost in the Middle”则显示，只改变关键信息在长输入里的位置，就可能显著影响效果；信息在开头或结尾时常更好，在中间时经常下降。[6] NovelQA 在超长小说问答中也报告，多跳、细节和极长输入仍是难点，并观察到远处 evidence 的性能下降。[2]

这对咱们最直接的意思是：**“Wide Read / Narrow Write”值得测，但不能凭常识定为默认。**它要和局部读在同一批冻结样本、同一模型、同一输出合同、同一评测器下比较；宽读的背景只能帮助判断，不能替目标责任区的书稿 evidence。

### 4.1 建议的三种输入臂

| 输入臂 | 模型可读内容 | 可写内容与 evidence 规则 | 主要检验什么 | 主要风险 |
|---|---|---|---|---|
| **T：只看目标段** | 目标责任区的书稿 | 只写该区事实；evidence 只能来自该区 | 纯局部抽取底线；噪声最少 | 漏掉指代、状态前提、跨段因果。 |
| **T±：目标段＋固定邻近文** | 目标段及事先冻结的前后相邻窗口；若场景在创作中，不能偷看未来未确认文本 | 仍只能写目标区事实、引目标区 evidence | 相邻上下文是否补足指代／承接 | 变量太多；窗口大小若不固定，不能公平比较。 |
| **C：宽读整章／只读前情** | 完整已冻结章节，或明确版本的前情上下文 | 仍只写目标责任区；背景不能作 evidence | 宽读是否真实改善跨段状态与因果 | 注意力稀释、位置偏差、把背景事实抄成新事实。 |

上表是**建议的对照设计**，不是已运行实验，更不是将 P4 宣布为优胜。尤其整章臂必须遵守时间可见性：若任务是在章节尚未写完时做增量抽取，就不能把将来未确认段落塞进输入，让模型借“后文解释前文”。

### 4.2 怎样公平比较三种范围

同一条样本的目标责任区与 Gold 要保持不变；同一模型、解码参数、输出 Schema、评分器版本也要固定。每个样本同时标上四个分析标签：**事实类型**（局部／需前情／跨段因果）、**Gold evidence 相对位置**（前／中／后）、**上下文长度桶**与**是否存在可误抄背景事实**。最终至少按这些标签拆表，而不是只公布总 F1。

建议预先写下主判定：端到端合格率、事实级 F1、证据承托率哪个优先；再写下平局／反向时怎么处理。比如，宽读若让 Recall 上升但多报背景事实、Precision 与证据承托率下降，就不能只拿“召回更高”宣布胜利。P3 中“规则写法伤召回”和“确认前态泄漏”的现象，也说明输入改变可能带来不同类型失败，必须分层看，不能单看一个分数。

## 5. 可直接吸收的 7 条启发

| 编号 | 建议 | 为什么值得吸收 | 与背景板的关系 |
|---|---|---|---|
| 1 | **保留六层记分卡，不压成单总分。** | 公开抽取实践已显示，结构合规、字段正确与事实等价不是一回事。[3] [8] | 与 R06 已有的输出、Schema、逐字、语义、evidence、承托分层完全同向。 |
| 2 | **同时报“条件事实分”和“端到端分”。** | 前者查语义能力，后者查能否安全交付；两者差距就是格式／编排债。 | 不让一次 invalid JSON 遮住语义诊断，也不让语义高分掩盖线上不可用。 |
| 3 | **Gold 以稳定剧情原子为中心，给争议事实留等价写法表。** | BenchIE 说明，单一字面 Gold 会误伤合理改写；重复同一事实也不该重复给分。[3] | 适合 `fact_sentences` 诊断与长期底账，不要求模型逐字模仿 Gold。 |
| 4 | **把 evidence 作为独立质量维度，做“合法—定位—承托”三连门。** | NovelQA 把答案和 evidence 同时标注；长叙事里的正确答案需要可定位依据。[2] | 直接服务 C2_UNIT 的 evidence ID、位置和 SHA 合同。 |
| 5 | **DEV／blind 坚持作者、书、来源三级不交叉，并记录开发接触。** | DocRED 的 Ign F1 说明已见事实会抬高分数；模型能力与记住重复事实要分开看。[4] | 与 Production Canonical 的作者／书／来源切分门一致。 |
| 6 | **对上下文做预注册、同源对照，并按 evidence 位置拆报。** | 长上下文模型对关键信息位置不稳，窗口大不等于能用好。[5] [6] | 为 P4 提供“以后值得测什么”的指标，不把 P4 预检提前写成结论。 |
| 7 | **把“材料不足＋回取轨迹”做成可评分的正确回退。** | 小说事实抽取最大的风险不只是漏，更是补故事。应建设必要证据被遮蔽／不在可见范围的反例，测模型是否拒绝登记而非臆造。 | 与背景板“答不出要回材料不足＋回取轨迹，不能补故事”直接相符。 |

上述第 7 条是产品化推论，公开论文并未以同一文案提出；它是将证据型问答、污染控制和背景板的“不能补故事”原则合并后的建议。建议先在 DEV 中校准“什么时候应当 abstain／回取”，再将规则冻结到 blind。

## 6. 对咱们不适用的 3 条常见做法

| 不建议采用的做法 | 为什么不适用 | 应以什么替代 |
|---|---|---|
| **1. 用 ROUGE／BLEU 之类摘要或自由生成重合分，作为事实抽取主结论。** | NarrativeQA 可以用 BLEU、METEOR、ROUGE-L 评生成式问答，[9] 但小说剧情原子是否已发生、是否该常驻登记、是否有合法 evidence，不由句面重合决定。 | 以事实身份 P／R／F1、证据承托与端到端合格率为主；文本生成分只做旁观指标。 |
| **2. 只让一个 LLM 裁判打“总体好不好”。** | 它不能替代逐字位置、SHA、责任区等确定性验证；而且裁判本身也可能受提示词和训练污染影响。 | 程序负责格式／位置／SHA，独立人工复核处理语义争议；LLM 若参与，只能是辅助线索，不能自签绿票。 |
| **3. “整本／整章一次吞掉”的窗口竞赛，直接当产品主评测。** | 公开研究已显示长输入位置敏感、窗口大不等于稳定理解。[5] [6] 这也偏离“关键变化常驻、其余按需回冻结书稿”的产品目标。 | 用 T、T±、C 的责任区对照；宽读可做候选输入臂，但只在目标区窄写、窄证据。 |

---

## 7. 一份最小但完整的评测结果票应写什么

为了让之后的 Mini 路线评测能够复盘，但又不把本报告变成执行票，建议未来每一次受控评测至少出一页结果票，固定包含下表字段。这里不涉及 Lite，也不包含任何训练或调用授权。

| 区块 | 必填内容 |
|---|---|
| 目标与边界 | 评什么输入臂／输出合同；是不是只读诊断；明确不外推的范围。 |
| 数据身份 | Gold／书稿／评分器的版本身份、样本数、分层构成、DEV 或 blind 身份；权利与来源状态由正式合同另列。 |
| 污染边界 | 作者／书／来源切分；是否接触过 prompt、样例、评分调参；blind Gold 是否封存；做过哪些污染自检。 |
| 运行合同 | 模型精确版本、提示词、解码、最大输出、停止条件、重试策略、Schema 版本。 |
| 主结果 | 运行层、格式门、事实门、evidence 三门、端到端门的分项指标；TP／FP／FN；不只一个总数。 |
| 分层结果 | 目标段／邻近／宽读；evidence 前中后位置；局部／跨段／多跳事实；异常样本。 |
| 复核 | 独立人工语义复核人数、规则、分歧数、一致性与仲裁记录。 |
| 失败面 | 格式坏、复读、漏抽、多报、把计划当事实、背景泄漏、证据错配、材料不足却编故事等。 |
| 结论等级 | 只能写该实验实际证明的窄结论；未完成 blind、未完成权利／数据／人审门时不得称生产结论。 |

---

## 8. 结语

对小说或长文本事实抽取，最稳妥的评测不是问“模型读得够不够长”，而是同时问四件事：**它是否抽对了关键已发生事实；是否漏了该记的变化；是否把每条事实牢牢钉在目标责任区的冻结书稿证据上；以及输出是否以确定、可解析、可复验的形式交付。**

外部研究支持把事实等价、Gold 完整性、证据、长上下文位置效应和污染边界一起纳入评测；R06 则已经给出了更贴近本产品的责任区、evidence、位置与 SHA 合同。下一步不该从调研报告直接跳到训练或云调用，而应在正式授权后，将这些原则落成一份同源、预注册、可审计的评测合同，并先用受控 DEV 验证，再讨论 blind 与晋级。
