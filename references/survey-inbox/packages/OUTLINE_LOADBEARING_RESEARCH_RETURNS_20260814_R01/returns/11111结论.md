## 结论

✅ 大纲记“安排”，实体家记“定义”，F／PE 记“变化”，其他页面只展示指针或计算结果。

你可以直接理解成：

| 要回答的问题                         | 唯一住处                                 |
| ------------------------------------ | ---------------------------------------- |
| 这是谁／这是什么／规则是什么？       | 人物、地点、势力、物品、能力自己的实体家 |
| 谁准备在什么时候做什么？             | 规划账 PE                                |
| 原文里谁已经做了什么？               | 事实账 F                                 |
| 截止某一章，他在哪、归谁、什么状态？ | 从 F 或 PE 算出来的只读影子              |

🔥 所以，场篮里的“人物显示名、地点字符串”不该继续当结构化数据保存。界面仍然显示名字，但底下应当指向同一个实体。自由文字里可以写人名地名，只是不能拿那段文字充当人物、地点的户口。

一句话判定：

> 去掉“第几章／什么时候”仍然成立的，住实体家；必须带时间点才成立的，住事件账；只是在别处需要看见它的，只放指针。

以下调查只用了公开资料和你这条消息里的约束，没有拿附件内容替结论背书。

## 1. 公开产品怎么分“情节安排”和“实体户口”

### 已验证的公开做法

| 类别               | 情节一侧放什么                             | 实体一侧放什么                       | 怎么连接                                       |
| ------------------ | ------------------------------------------ | ------------------------------------ | ---------------------------------------------- |
| 长篇创作工具       | 章、场、情节点、场景摘要、节拍、故事线     | 人物、地点、物品、世界设定、魔法规则 | 场景关联实体，不复制实体说明                   |
| 时间线／世界观工具 | 事件、日期、持续时间、参与角色             | 人物、地点、组织、物品               | 独立的“事件—实体关系”                          |
| TRPG／世界 wiki    | 任务、历史事件、会话记录、情节树           | 人物、地点、组织、物品、规则文章     | 任务收集实体引用；实体页反向显示被哪些任务引用 |
| 叙事／Quest 引擎   | 流程节点、分支、条件、指令、对话、任务步骤 | 角色、地点、物品、技能、技术、法术   | 节点挂实体引用；运行状态另放变量               |

具体产品证据：

- **Plottr** 的时间线装章节、故事线和场景卡；场景卡可以关联人物、地点和标签。它甚至建议把普通物品当标签追踪，说明这是较轻量的“出现追踪”，并不是完整的物品户口。[Plottr 场景卡文档](https://docs.plottr.com/article/57-timeline-scene-cards)
- **Novelcrafter** 把人物、地点、物品、设定放进 Codex；官方明确称地点应由 Codex 管理，场景只关联地点条目。场景摘要里仍要写“这场发生什么”，因为“关联地点”只表示取用该地点资料，不等于场景安排。[地点追踪说明](https://www.novelcrafter.com/courses/novelcrafter-cookbook/tracking-locations)
  它的动态变化叫 Progressions：变化挂在具体场景上，并关联某个实体。官方还明确说，这类变化不能替代情节点，情节点仍放场景指令。[Progressions 文档](https://www.novelcrafter.com/help/docs/codex/progressions-additions)
- **Campfire** 把人物、地点、物品、魔法等做成独立元素，再关联到时间线事件；Magic 模块专门装魔法来源、代价和限制，Systems 模块装政府、团体等复杂制度。[元素关联时间线](https://campfirewriting.com/learn/update1)、[Magic 模块](https://campfirewriting.com/learn/magic-tutorial)、[Systems 模块](https://campfirewriting.com/learn/systems-tutorial)
- **World Anvil** 的 Plot 模板用于小说、章节、场景和跑团情节规划；人物、组织、物品、自然法则等各有文章模板。物品文章甚至有“所在地”和“持有者”关联位。[Plot 模板](https://www.worldanvil.com/learn/article-templates/plot)、[物品模板](https://www.worldanvil.com/learn/article-templates/item)、[文章模板分类](https://www.worldanvil.com/learn/article-guides/article-templates)
- **Kanka** 的 Quest 不是人物资料仓库，而是把人物、地点、事件、物品、日志等聚到一个任务下面，每项仍然是引用。人物的当前位置只填在人物一侧，地点页会自动出现这个人物；组织成员则是人物与组织之间的成员关系。[Quest 文档](https://docs.kanka.io/en/latest/entries/quests.html)、[人物文档](https://docs.kanka.io/en/latest/entries/characters.html)、[组织文档](https://docs.kanka.io/en/latest/entries/organisations.html)
- **Aeon Timeline** 明确把事件和实体分开：事件是发生在特定时间、地点的事情；人物、地点、项目等是实体；两者之间另有多对多关系，并能标明“参与者、见证者”等角色。[Aeon 核心概念](https://help.timeline.app/article/154-key-concepts)
- **articy:draft** 把章节、情节点、场景摘要放在 Flow；角色、物品、技能、技术属于 Entity。流程节点可以挂参与角色引用，角色说话人从现有实体里选。实体有不可变的对象 ID，实体页会自动反查自己在什么流程、地点和对话中被引用。[实体文档](https://www.articy.com/en/adx_basics_entities/)、[流程节点文档](https://www.articy.com/en/adx_basics_flow2/)
- **Arcweave** 的 Board 装场景、对话、选择和逻辑；Component 装人物、地点、物品、法术等可复用对象；流程元素只挂 Component 引用。游戏需要记住“拿到钥匙没有”时，放进变量，而不是复制到每个节点。[组件文档](https://docs.arcweave.com/project-items/components)、[变量文档](https://docs.arcweave.com/project-items/variables/overview)、[Board 文档](https://docs.arcweave.com/project-items/boards)

### 从这些产品归纳出的硬边界

这部分是设计判断，不是某一家产品公布的数据库合同。

| 住处               | 应该放                                                       | 绝不应该放                                                   |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 大纲／规划账       | 本章目标、场安排、因果、冲突、转折、场内意图、计划变化       | 完整人物小传、地点说明、门派制度、物品规则、手填的“当前事实” |
| 实体家             | 身份、别名、静态外貌、地点结构、组织制度、物品固有能力、能力规则 | 第几章出现、这场要做什么、事件顺序、复制来的事实句、手填的动态现状 |
| F／PE              | 谁在何时做了什么、地点或归属变化、受伤、结盟、背叛、获得能力 | 整份人物设定、整套门派规矩、重复的物品说明                   |
| 实体影子／反向列表 | 当前状态、成员列表、被哪些场引用、物品此刻在哪               | 独立可编辑的第二份真值                                       |

## 2. “当前在哪、现在归谁、此刻什么状态”到底住哪

公开产品主要有三种做法，没有统一答案。

### 做法 A：当前快照住实体家

Kanka 把人物当前位置填在人物页，再在地点页自动反查；World Anvil 把物品所在地和持有者放在物品文章中。

这对普通 wiki 很方便，但有一个前提：产品把“当前快照”当主要真值。如果历史事件和当前快照都让人手填，就会出现：

- 历史里写宝物已经被夺走，物品页仍显示旧主人；
- 人物事件里已经叛门，组织成员名单仍有他；
- 地点被摧毁了，地点页仍保持完好状态。

这类产品通常不会自动保证事件历史与快照完全一致。

### 做法 B：变化住时间点，实体页显示变化结果

Novelcrafter 的变化记录挂到具体场景，并关联实体；实体页能看到变化发生在哪个场景。它还区分“增加一条新状态”和“替换旧状态”。

这更适合长篇，因为“断臂”“失去宝物”“改换阵营”都必须回答：从哪一场开始成立？

### 做法 C：实体放定义，运行状态放变量

articy:draft 和 Arcweave 都把“流程”和“运行状态”分开：流程中的指令修改变量，后续条件读取同一个变量。不会在五个后续节点各写一遍“已经拿到钥匙”。[articy 状态变量说明](https://www.articy.com/help/ad3/Scripting_in_articy.html)

### 对你们更合适的答案

✅ 两边都可以“看见”，但只能有一边“可写”。

你们已经拍定 F 是已发生真值、PE 是计划，因此不该再选“实体页手填当前快照”这条路：

- 已发生状态，只能从截至某点的 F 得出；
- 计划状态，只能从截至某点的 PE 得出；
- 两种状态不能揉成一个没有标签的“当前”；
- 人物、地点、组织、物品、能力页面只展示计算后的影子，并能跳回来源；
- 算不出来就显示未知，不能邀请作者补填一个没有来源的现状。

这和通用的“事件溯源”做法一致：事件记录是权威来源，当前状态是事件计算出的只读视图；视图随时可以重算，不是第二份真值。[微软 Event Sourcing 说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)、[CQRS 与只读视图](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)

## 3. 公开产品怎样用指针避免双写

常见手段有四个：

- **稳定身份，不拿名字当身份。**
  Kanka 的高级提及内部保存实体类型和数字 ID，显示文字可以另设。人物改名，引用仍指向同一个人。[Kanka Mentions](https://docs.kanka.io/en/latest/features/mentions.html)
- **反向列表由系统查出来。**
  articy 的实体页自动列出它在流程、地点、对话中的引用；Kanka 的 Related Elements 自动列出其他条目对当前实体的引用。[articy 实体引用](https://www.articy.com/en/adx_basics_entities/)、[Kanka Connections](https://docs.kanka.io/en/latest/features/connections.html)
- **名字是渲染结果，不是重复保存的身份。**
  Arcweave 的 `@提及` 会随实体改名自动更新；官方同时警告，手打的普通文字不会更新。[Arcweave Mentions](https://docs.arcweave.com/tutorials/basic/pt-6)
- **允许保留“当时怎么称呼”，但仍指向同一实体。**
  比如场纲里需要写“白衣人”，不能因为人物后来揭晓为“沈策”就把悬念抹掉。可以保留场景里的显示称呼，但身份仍指向沈策。这份称呼是叙述表现，不是第二个人物户口。

### 已验证的失败案例

| 失败长什么样                       | 公开案例                                                     | 教训                             |
| ---------------------------------- | ------------------------------------------------------------ | -------------------------------- |
| 改了实体名，旧地方仍是旧名         | Arcweave 明确说：只有提及会自动更新，手打文字不会            | 结构化人物、地点不能存裸字符串   |
| 同一场在两边各建一次，出现两个场   | Aeon 与 Scrivener 同步时，如果两个同义对象没有先配对，会被当成两个新对象，双方各复制一份 | “看起来一样”不等于“同一个 ID”    |
| 两边同时改同一字段，系统不知道信谁 | Aeon 同步会阻塞，要求人工选择保留时间线版本还是 Scrivener 版本 | 双向可写必然需要冲突协议         |
| 一个角色的多个副本状态分叉         | Foundry 的已放置 Token 可以成为独立副本；未关联时，每个 Token 的资源和状态各走各的 | 只有确实表示不同实例时才允许复制 |

来源分别见 [Aeon 同步与冲突说明](https://www.aeontimeline.com/guides/sync-with-scrivener) 和 [Foundry Token 文档](https://foundryvtt.com/article/tokens/)。

## 4. 关系和组织成员怎么放

✅ 推荐“中间只存一条关系，两端页面都读它”。

这里的“中间关系”可以理解成一张连接卡：它连接 A 和 B，人物页、势力页只是从两个方向展示同一张卡。

公开产品也是这个方向：

- World Anvil 的人物关系录一次，会显示在两个人物文章里；组织关系还能自动生成外交关系图。[World Anvil 关系说明](https://www.worldanvil.com/learn/article-guides/article-templates)
- Kanka 支持镜像关系，另一端自动出现；组织成员关系还能表达当前成员、前成员、上级和角色。[Kanka Connections](https://docs.kanka.io/en/latest/features/connections.html)、[Kanka 组织](https://docs.kanka.io/en/latest/entries/organisations.html)
- Aeon 把关系看成连接两个对象的独立记录，允许同一对人物同时存在多种关系，也支持反向关系。[Aeon 关系说明](https://www.aeontimeline.com/features/relationship-assignment-matrix)

放到你们的体系里：

- “A 恨 B”是有方向的，B 页反向显示“A 恨他”，不能再手填一遍；
- “甲派与乙派结盟”通常两端都显示，但仍是一条关系；
- “人物加入门派”只能产生一条成员关系，人物页显示所属，门派页显示成员；
- 加入、退出、叛变、由敌转友这些变化，实际来源仍是 F，未来安排仍是 PE；
- 中间关系索引如果可以绕过 F／PE自由改，就会变成第三本真值，因此它应当是投影或带来源的结构化索引；
- 不随剧情变化的结构关系，如亲生父子、地点隶属，可以作为实体关系资料；会变化的恨意、同盟、成员资格不能当静态户口。

## 5. “只住大纲／只住实体家／只许指针”清单

| 内容         | 归类             | 具体处理                                                     |
| ------------ | ---------------- | ------------------------------------------------------------ |
| 本章目标     | **只住大纲**     | 这是作者想让本章完成什么，不属于任何人物或地点               |
| 场安排       | **只住大纲**     | 场顺序、冲突、转折、信息揭露、退出点都在这里                 |
| 谁出场       | **只许指针**     | 场关联人物实体；人物页的“出现在哪些场”反向计算               |
| 地点         | **实体家＋指针** | 地点长什么样、结构和常规条件住地点家；这场发生在哪只挂指针   |
| 门派规矩     | **只住实体家**   | 入门条件、等级、禁令、制度、资源等住门派／势力家；某章改规矩是 PE 或 F |
| 宝物下落     | **只许指针**     | “被谁拿走、现在在哪”由 PE／F 变化推出；物品页只显示来源明确的当前影子 |
| 金手指限制   | **只住实体家**   | 固有代价、触发条件、上限、恢复规律住能力／规则家；暂时失效、突破限制是事件 |
| 人物外貌     | **只住实体家**   | 基础外貌住人物家；伤疤、易容、衰老、断臂等变化住 PE／F       |
| 人物此刻动机 | **看时间轴**     | 计划场里的动机住 PE；已写出的此刻动机住 F；人物页只能显示带来源的影子 |

还有两个容易混淆的例子：

- “青云门禁止私传功法”是实体规则；“掌门本章决定废除此规”是事件安排。
- “噬魂剑能吞噬神识”是物品能力；“第八十章被赵云夺走”是事件；“现在归赵云”是事件计算结果。

## 6. 最适合你们的落地方式

建议把现有场篮稍微收紧：

- 人物、地点、势力、物品、能力，只要需要跨场复用、改名安全或独立核对，就给它自己的实体家。
- 场篮仍然可以写自然语言，但“参与人物、主地点、涉及物品／势力／能力”应使用实体引用。
- 实体页分清“作者可编辑的静态资料”和“系统算出的事实态／计划态”；动态部分不能直接手改。
- 每个动态影子都能跳回对应 F 或 PE。事实态与计划态分开显示，绝不合成一个含混的“当前”。
- 人物关系、组织成员、物品归属统一走关系索引；两端页面都是同一关系的不同视角。
- 核对功能重点查：未解析的裸名字、断掉的指针、同一时点身处两个地点、宝物同时有两个主人、计划违反能力限制、PE 与已经落成的 F 不一致。
- 插件或理论卡只能提出建议；作者确认后才产生 PE，不直接改大纲或实体状态。

🔥 说白了就是：门派、势力、宝物、金手指规则都应该各自有家；大纲只写它们在这一章要参与什么。两边看似都有，是因为大纲在“引用户口”，不是又抄了一份户口。
