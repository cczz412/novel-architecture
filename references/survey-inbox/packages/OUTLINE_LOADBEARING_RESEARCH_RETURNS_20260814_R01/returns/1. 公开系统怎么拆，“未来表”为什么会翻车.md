✅ 结论：不要造一张“未来表”，再靠一个 `status` 字段区分灵感、命运、伏笔、计划和触发器。

更稳的做法是：

- 身份不同的东西，拆成不同对象。
- 每个对象内部再用“状态机”——也就是规定它能怎样一步步变化。
- 对象之间用有明确含义的指针连接。
- 计划和已发生事实必须走两条写入通道。

公开资料通常不会公开产品底层的 SQL 表，所以这里的“分表”指逻辑对象和权限边界，不冒充知道厂商内部数据库。

## 1. 公开系统怎么拆，“未来表”为什么会翻车

| 公开模型               | 它怎么拆                                                     | 对小说系统的启示                                             |
| ---------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Plottr                 | Notes 用来脑暴和放“可能采用的想法”；Timeline 的 Scene Card 已落在章节和情节线上，Outline 再从 Timeline 生成。[Plottr 文档](https://docs.plottr.com/article/8-plottr-overview) | 灵感区与已排期计划区分开。                                   |
| Jira Product Discovery | 未确定的 idea 留在发现区；承诺后才连接 Jira 的交付票。官方甚至说，交付 backlog 理想上只放已经承诺的任务。[Atlassian 文档](https://www.atlassian.com/software/jira/product-discovery/guides/delivery/overview) | “可能想写”不能占用“确定要写”的队列。                         |
| Kubernetes             | `spec` 表示想要的目标状态，`status` 表示系统实际观察到的当前状态，由不同主体写入。[Kubernetes 文档](https://kubernetes.io/docs/concepts/overview/working-with-objects/) | 人物命运对应目标；人物当前状态对应已观察事实，不能互相覆盖。 |
| iCalendar              | 日历事件 `VEVENT`、待办 `VTODO`、记录 `VJOURNAL`、提醒 `VALARM` 是不同组件；提醒可以只做 `DISPLAY`，显示文字而不改任务身份。[RFC 5545](https://datatracker.ietf.org/doc/html/rfc5545) | 触发器应是提醒附件，不是剧情事件本身。                       |
| 计算叙事               | 规划系统把初始世界状态、目标状态、达成目标的行动序列分开；叙事研究还区分“故事里发生什么”和“什么时候告诉读者”。[IPOCL 叙事规划论文](https://jair.org/index.php/jair/article/view/10669)、[故事／话语／叙述三层模型](https://cdn.aaai.org/ojs/12839/12839-52-16355-1-2-20201228.pdf) | 当前事实、结局目标、计划事件、伏笔的读者呈现层，天然不是同一种东西。 |
| Novelcrafter           | 人物变化按场景生效，较早场景看不到后来的变化；AI 上下文还能设为永不包含、检测后包含或手动加入。[进展记录](https://www.novelcrafter.com/help/docs/codex/progressions-additions)、[上下文控制](https://www.novelcrafter.com/help/docs/codex/codex-tracking) | 当前状态必须有“截至哪一场”；剧透资料不能默认进入写作上下文。 |

一张表最容易在四处翻车：

- **身份混乱**：同一场“老人交出伞”既可能是第 30 章计划事件，又可能兑现两个伏笔，还可能推动人物命运。它们可以同时成立，不是互斥状态，单个 `status` 表达不了。
- **执行污染**：查询“所有未完成未来项”时，灵感、闲置种子、伏笔债和真正的本章任务一起进包。
- **事实污染**：把计划标成 `done` 后直接当事实；但正文可能改写、删掉或根本没写成。
- **权限和剧透失守**：作者私有灵感、检查器可读的伏笔答案、本章 AI 可读的表层提示，无法共用一套可见性。

公开资料里没有找到小说产品完整披露“一张未来 SQL 表事故”的复盘，不能编一个出来。但能看到三个很典型的产品补救：

- GitHub 后来把开放讨论和想法拆到 Discussions，官方明确说这能减轻 Issues 和 PR 中“活动工作”的管理负担。[GitHub 说明](https://github.blog/open-source/maintainers/create-a-home-for-your-community-with-github-discussions/)
- Jira 把不确定的 idea 与已承诺的交付工作拆开。
- Kubernetes Gateway API 公开承认，Conditions 随产品自然增长后，出现命名、正负含义和行为不一致，后来不得不做带破坏性的统一整理。[Gateway API GEP-1364](https://gateway-api.sigs.k8s.io/geps/gep-1364/)

小说工具也能看到同类症状：Sudowrite 承认人物说明和后续场景信息冲突时，AI 会混乱；其建议是把说明改到当前时间点。[Sudowrite 文档](https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/tips--tricks/eBjBne7foMi8uYFxWEPCai) 这能暂时缓解生成问题，却说明“当前人物”和“最终命运”不能只占同一个说明栏。

## 2. 人物命运和当前状态怎样共存

🔥 最稳的规则是：

- **当前状态**回答：“截至第几章，正文已经证明了什么？”
- **人物命运**回答：“作者现在希望人物最终变成什么？”
- **人物计划**回答：“准备安排哪些事件把前者推向后者？”

当前状态必须带两个信息：

- 这是截至哪一场的状态，例如 `as_of_scene`。
- 这些结论来自哪些正文事实，例如 `source_fact_refs`。

这样回头编辑第 10 章时，系统不会把第 30 章才断臂、结婚或死亡的状态塞回来。Novelcrafter 的场景进展机制正是“从某场起生效，之前场景不可见”。

命运则单独存版本。比如：

- 命运第 3 版：陆沉最终牺牲。
- 命运第 4 版：陆沉幸存，但失去身份。

第 4 版激活后，第 3 版保留为“已替代”，不能原地改掉历史。

命运改变时，这些直接引用必须亮灯：

1. `兑现、铺垫、依赖`旧命运的伏笔，尤其已经亮给读者的。
2. `推动、阻止、完成`旧命运的计划事件和剧情种子。
3. 条件表达式或事件蓝图里引用旧命运的条件剧情。
4. 其他人物命运、人物弧节点、书核结局锚对它的引用。
5. 已生成但仍锁定旧版本的章纲和执行包。
6. 按旧命运算出的偏离检查结果。
7. 已排期的结局场、告别场、死亡场等强依赖章节。

⚠️ 亮灯不等于自动修改。IBM DOORS 的做法很合适：被依赖对象改变后，把关联标成“可疑”，交给人检查，不擅自重写下游对象。[IBM DOORS Next](https://www.ibm.com/docs/en/engineering-lifecycle-management-suite/doors-next/7.2.0?topic=overview-doors-next)

此前已经写成的当前事实通常不亮红灯，更不能跟着改。只有新命运与事实直接冲突时才报警，例如正文已经确认人物死亡，命运却改成“最终活着回家”。

为了知道引用是不是按旧版本算的，可让引用记录一个 `based_on_revision`。它和当前激活版本不一致时显示黄色警告。Kubernetes 的 `observedGeneration` 也是用类似办法判断“这份状态是否仍对应最新目标”。

## 3. “故事是否朝结局走”应该放哪里

答案是三层各管一件事，但只能有一个方向真源：

| 层         | 职责                                                         |
| ---------- | ------------------------------------------------------------ |
| 书核       | 保存当前有效的结局锚指针，允许为空。                         |
| 结局锚版本 | 保存目标结局、不可破坏条件、允许变化的部分、责任人和修改理由。 |
| 检查结果   | 按某个结局锚版本和某个正文截点计算，随时可以重算。           |
| 修改记录   | 记录谁提议、谁批准、为何改结局；它是审计记录，不是另一份结局真源。 |

书核只需要一个可空指针，例如 `active_ending_anchor_ref`。为空时，检查器应该返回“未设结局”，不能硬算成“严重偏离”。

偏离检查不适合只给一个 73 分。至少应拆成：

- **还能不能到达**：当前事实和剩余计划是否已让结局不可能发生。
- **有没有因果支撑**：关键转折是否有前置事件。
- **人物动机是否撑得住**：能到达不代表角色会合理地这么做。IPOCL 研究正是因为普通规划能达到目标，却可能让人物行动毫无可信动机。
- **伏笔是否兼容**：现有读者债是否仍能兑现。
- **剩余篇幅是否够用**：还有没有场次完成必要变化。

对外展示可以收成“正常 / 有风险 / 已阻断 / 无法判断”，下面列具体原因。长篇生成研究也分别衡量情节连贯、对大纲的服从程度和趣味性，而不是拿一个总分代替全部判断。[DOC 论文](https://aclanthology.org/2023.acl-long.190.pdf)

谁能改结局：

- 单人项目：主作者。
- 团队项目：明确授予的“结局所有者”。
- 编辑、检查器和 AI：只能提交修改建议。
- 修改获批后创建新版本，旧版本转为已替代，再给依赖引用亮灯。

NASA 对已确认目标的变更也是“先看影响，再由有权者批准”，并强调双向追踪。[NASA 系统工程手册](https://www.nasa.gov/reference/6-0-crosscutting-technical-management/) 小说系统不用搬来重审批，但“提议”和“生效”必须分开。

## 4. 什么能进本章执行包

| 内容                       | 默认是否进入 | 正确进入方式                                                 |
| -------------------------- | ------------ | ------------------------------------------------------------ |
| 未安放灵感                 | ❌            | 只在作者的灵感箱和专门的灵感整理模式中出现。                 |
| 尚未排期剧情种子           | ❌            | 留在规划检查区；排进具体场拍后，新建计划事件。               |
| 条件剧情蓝图               | ❌            | 条件命中只给规划者亮灯；作者明确选中并排期后，新建计划事件。 |
| 已排到本章的计划事件       | ✅            | 按具体场、拍和版本进入。                                     |
| 开放伏笔                   | 有条件       | 本章要铺、推进或兑现时，只给执行者当前允许呈现的表层指令。   |
| 人物当前状态               | ✅            | 只取本章开始前已经成立的状态。                               |
| 完整人物命运、结局答案     | 默认 ❌       | 必要时只给防跑偏约束，例如“本章不可死亡”“不要揭露身份”。     |
| 灵感、伏笔、命运的完整答案 | 检查器可读   | 不等于本章写作 AI 可读。                                     |

伏笔最好拆成两块：

- **表层呈现**：本章允许读者看到什么。
- **隐藏兑现意图**：这条线最终解决什么、不能提前说什么。

本章执行包只拿表层投影；伏笔检查器和获授权规划者才能看完整答案。World Anvil 的 Secrets 也允许按书、读者群和协作者分配剧透权限。[World Anvil 文档](https://www.worldanvil.com/learn/beginner-tutorials/get-started-secrets)

这么隔离不是多余防范。Novelcrafter 明说，未来剧透进入 Codex 后会过早影响生成；场景挂太多资料也会让 AI 忽略重点或产生冲突。[剧透与上下文说明](https://www.novelcrafter.com/help/docs/codex/guidelines-for-descriptions)、[场景上下文说明](https://www.novelcrafter.com/courses/codex-cookbook/codex-scenes)

种子不烂在抽屉里的办法，不是强塞进本章，而是给规划区提供：

- 已放置但长期未排期的种子列表。
- 与结局或人物命运有关、却没有任何承接事件的目标。
- 到了复看日期的种子提醒。
- 条件已经满足、等待作者处理的提示灯。

这些都只是规划提醒，不创建卡片，不关章，也不把条件剧情写成已经发生。

## 5. 最小对象清单

角色简称：主＝主作者或结局所有者；规＝获授权规划编辑；章＝本章作者或写作 AI；检＝检查器。普通问答默认只读已写事实。

| 对象                         | 身份判据：删掉欠不欠账                                       | 谁读 / 谁写                                              | 章纲怎样引用                                             |
| ---------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- | -------------------------------------------------------- |
| `Inspiration` 灵感           | 尚未安放的愿望。删掉不欠账。                                 | 主、规在灵感模式读写；章、检、普通问答默认不可读。       | 禁止直接引用。安放时新建目标对象，原灵感归档；不退回。   |
| `EndingAnchor` 结局锚        | 全书当前目标，允许没有。删除不直接欠读者，但会失去方向依据。 | 主、规、检读；只有结局所有者激活新版本。                 | `serves_anchor`，通常只给章一个防泄底投影。              |
| `CharacterFate` 人物命运     | 人物被选定的最终目标，不是当前事实。删除通常不欠读者，但会让依赖计划失据。 | 主、规、检读；主或获授权者写。                           | `advances_fate`、`blocks_fate`；章默认只读约束投影。     |
| `PlotSeed` 剧情种子          | 已安放但没有具体场拍。删掉本身不欠读者。                     | 主、规、检读；主、规写。                                 | 不直接进章纲；排期后由计划事件保存 `derived_from_seed`。 |
| `ForeshadowDebt` 伏笔债      | 已经或已承诺向读者露出，并要求日后回应。删掉会欠账。         | 主、规、检看完整内容；章只看本章表层；主、规写。         | `plants_debt`、`advances_debt`、`pays_debt`。            |
| `PlannedEvent` 计划事件      | 已占据明确场和拍。删掉欠排期一致性账，但不等于删掉事实。     | 主、规、检及对应章读；主、规排期。                       | `execute_event`，必须指到具体场拍。                      |
| `ConditionalDesign` 条件剧情 | 有条件和事件蓝图，但没有获得场拍。删掉本身不欠读者；若它承担某伏笔兑现，伏笔债仍在。 | 主、规、检读；主、规写。                                 | 不能直接成为章任务。                                     |
| `TriggerSignal` 触发提示     | 只表示“条件未满足／满足／无法判断”。不是剧情卡。             | 主、规读；条件检查器写观察结果，作者可已读、延后或忽略。 | 不进入执行列表，只保存 `watches_condition`。             |
| `StoryFact` 与当前状态投影   | 正文已经写成并核验的事实；删除属于改设定或改历史。           | 所有创作角色按时间截点读；核验流程写，作者批准纠正。     | `requires_fact`，并带“截至哪一场”。                      |

计划写成事实时也不要修改同一行。正确过程是：

1. 正文真的出现该事件。
2. 核验正文。
3. 新建不可随意改写的 `StoryFact`。
4. 用 `realized_by` 把计划事件连到事实。

微软对领域事件的定义也是“已经发生的过去事实”，并建议使用过去式且保持不可变。[Microsoft Domain Events 文档](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation)

章纲指针不要复制整份对象。它要说明“指向谁、按哪个版本、为什么取、允许看到多少”。例如：

```json
{
  "kind": "foreshadowing_debt",
  "id": "FD-017",
  "revision": 4,
  "purpose": "plant",
  "projection": "surface_only",
  "required": true
}
```

这里的 `projection` 是“允许取出的视图”。`surface_only` 表示只拿本章可写给读者看的部分，不把最终答案塞进执行包。对象升级到第 5 版后，这个仍指第 4 版的章纲就亮灯，等作者确认后再刷新。

🔥 如果只守六条硬规则，结构就不会串：

- 当前状态只能由已核验事实产生。
- 灵感和未排期种子不能进入本章执行包。
- 条件命中只能写提示，不能写计划表或事实表。
- 已开放伏笔不能硬删除，只能兑现、重写来源后撤销，或明确留债。
- 计划事件必须有场拍位置，但完成计划不自动等于事实成立。
- 结局或人物命运换版本后，所有旧版本引用只亮灯，不自动改写。
