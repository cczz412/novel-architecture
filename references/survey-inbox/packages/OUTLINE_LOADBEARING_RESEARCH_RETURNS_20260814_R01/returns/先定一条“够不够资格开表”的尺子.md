✅ 结论：不用给这些对象各发一张“户口本”。在现有大纲、事实、人物、伏笔之外，真正值得新增的故事真值只有三组：

1. 人物知情硬账
2. 事件—时间—约束账
3. 规则—能力—例外账

其余大多是字段、投影，或者检查器临时算出的提示。秘密、关系网、倒计时、读者知情都很重要，但“重要”不等于“必须自己存一份真相”。

这份判断只参考公开论文、叙事规划研究和作者工具公开文档，没有把内部文件当依据，调查截止 2026-08-14。

## 先定一条“够不够资格开表”的尺子

一个对象同时满足下面两条以上，才考虑开一等账：

- 它有自己的稳定身份，会被很多人物、章节、事件引用。
- 它会独立变化，有“建立—生效—失效—撤销”之类的过程。
- 作者需要单独确认、修改、追溯，检查器重跑不能覆盖它。
- 如果只塞在某个人物或章节里，会产生两份互相打架的答案。

反过来：

- 只是某条真值换个角度看：做投影。
- 能从时间、规则、事件确定算出：检查器现算。
- 只是作者的犹豫、废案、工作提醒：留在作者层，别进故事真值。

人物信念、客观世界和读者收到的信息确实应当分开。叙事规划研究会分别表示“客观世界”和“人物可能错误的私人世界”；另一类研究又把故事行动与叙述者改变读者认知的“话语行动”分成两套计划。[人物信念与客观世界](https://cdn.aaai.org/ojs/12411/12411-52-15939-1-2-20201228.pdf)、[故事计划与话语计划](https://aclanthology.org/W16-6602.pdf)、[读者认知随叙述推进而变化](https://aclanthology.org/2021.nuse-1.10.pdf)。

## 1. 候选逐项处置

### 知情、义务、时间、因果、代价

| 对象                           | 处置与唯一住处                                               | 一句话理由                                                   | 没有这家会坏成什么                                           |
| ------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 人物知情                       | **必须一等表**。一行表达“人物—命题—知情状态—有效锚点—获知/误导来源”。软猜测只进检查结果。 | 同一事实会被多人在不同时间知道、忘记或误解，不能挂在事实或人物的一格文本里。 | 女主第40章才得知幕后人，第31章却已经直呼其真名并据此设局。   |
| 读者知情                       | **默认做独立投影，不和人物知情共表**。源头是章节/场景上的已确认“披露、暗示、误导、纠正”记录。 | 读者按叙述顺序接收信息，不按故事时间接收；读者推断还带不确定性。 | 系统把“角色不知道”误当成“读者也不知道”，安排第二次揭晓，读者只觉得作者失忆。 |
| 义务／承诺／誓言               | **v1 做人物或关系下的结构化子记录＋未结投影，不开独表**。至少保留欠谁、答应什么、条件、期限、状态、锚点。 | 它有债务人、受益人和履行过程，但题面已拍 v1 不开表；绝不能借伏笔表代住。 | 主角立誓救回师父，五十章后转身闭关，系统既不提醒违誓，也不知道谁有资格追责。 |
| 秘密                           | **做投影**：真实内容住事实；谁不知道/被误导住人物知情；读者何时看到住披露记录；若兼具铺垫再指向伏笔。 | “秘密”不是一种事实，而是一条事实对不同对象的可见差。         | 秘密表写“无人知晓”，可三名守卫都亲眼见过，系统仍把揭晓写给他们。 |
| 时间线／故事时钟／倒计时／冷却 | **必须一等账**，合并为事件、时间区间和约束边。倒计时与冷却是截至某锚点的投影。 | 时间既有绝对日期，也有“三天后、早于、重叠、持续多久”；不能硬塞成章节编号。 | 72 小时倒计时过了两天还剩 72 小时；人物下午出发，却在上午已经抵达。 |
| 因果前置                       | **作者明确指定的前置条件住事件约束字段；检查器推出来的因果只做提示。** | “A 是 B 的必要条件”属于事件关系，不值得另开因果真值表。      | 没拿钥匙就开了门；更糟的是检查器猜了一个原因，之后被系统当成正史。 |
| 代价／不可逆损失               | **住事件效果和带有效期的状态事实；另做损失清单投影。**       | 代价是某次行动造成的状态变化，不是脱离事件独立存在的东西。   | 主角献祭左眼换来力量，十章后又自然地“双眼微眯”。             |

关于承诺，公开的多智能体研究把它表示为有债务人、受益人、条件、结果和状态变化的对象，并区分履行、取消、释放、违反等状态。这说明它确实比伏笔更像社会义务；只是 v1 完全可以先用结构化子记录承接。[承诺的条件与生命周期](https://www.csc2.ncsu.edu/faculty/mpsingh/papers/mas/Commitments-for-MAS.pdf)。

⚠️ “不知道”不能理解成“知情表里没有这一行”。世上有无限多件事角色不知道。只记录作者明确关心、文本明确测试过或会影响行动的硬性无知。

时间账还要分清三条时间轴：

- 故事时间：事情在世界里何时发生。
- 叙述顺序：读者第几章才看到。
- 发布时间：章节何时上线。

Aeon Timeline 也明确把故事中的时间顺序与叙述顺序分开，并用依赖、约束维持事件先后。[叙述顺序与时间顺序](https://www.aeontimeline.com/getting-started/planning-fiction-from-scratch)、[事件依赖与时间约束](https://www.aeontimeline.com/guides/manage-dependencies-and-event-order)。只有“三天后”时就存相对关系，不要伪造一个精确日期。

### 规则、实体、关系、声口

| 对象                 | 处置与唯一住处                                               | 一句话理由                                               | 没有这家会坏成什么                                           |
| -------------------- | ------------------------------------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------ |
| 能力／金手指规则     | **必须进规则一等账，但不单开能力表。** 一条规则表达触发、效果、限制、代价、冷却、适用范围和例外指针。 | 能力规则跨很多场景复用，又直接决定行动是否合法。         | 瞬移明明不能穿过封锁阵，剧情需要时却随手穿过去。             |
| 世界规则与例外       | **与能力共用规则账**。例外必须指回原规则，并写清范围、成立条件、有效期和证据锚点。 | 例外不是改写原规则，否则无法判断别处是否仍受原规则约束。 | 前文说吸血鬼见日光必死，反派中午出门后系统悄悄把规则改成“多数怕光”。 |
| 地点、势力、物品户口 | **是一等对象，但不要三张平级账**。共用实体主键和类型；具体属性、归属、所在地住事实与关系。 | 三者都需要稳定 ID、别名和跨章引用，身份机制相同。        | “白塔”一会儿被当地点、一会儿被当组织；同一把剑因两个名字被复制成两把。 |
| 关系网               | **关系事实住事实账；网只是按某锚点画出的投影。** 关系应允许方向、有效期和变化事件。 | 图会过期，事实边才是唯一答案；A 信任 B 不代表 B 信任 A。 | 背叛已经发生，旧关系图仍显示“盟友”，执行包把旧图当真。       |
| 声口／说话方式／称呼 | **人物放通用声口字段；针对某人的称呼放关系边或小型子记录；检查器负责比对。** | 一个人的语言习惯和“他面对谁时怎么说”是两层东西。         | 将军私下叫妻子“小满”，在朝堂上也当众这么叫，身份和场合全穿帮。 |

这里有个很实用的三分法：

- “瞬移术冷却三天”是规则。
- “陆遥会瞬移术”是人物事实。
- “陆遥昨夜用过瞬移”是事件。

剩余冷却时间由规则和事件现算，不另存一份“还剩两天”的真值。

声口也不该只做一段人物小传。对话研究发现，“说话者画像”和“说话者—听话者组合”都影响语言；称呼还会随双方关系与正式程度变化。[说话者与说话对象的双层模型](https://aclanthology.org/P16-1094.pdf)、[称呼与关系正式程度](https://aclanthology.org/N15-1185.pdf)。

### 作者意图、场景标签、废案、连续性

| 对象                           | 处置与唯一住处                                               | 一句话理由                                                   | 没有这家会坏成什么                                           |
| ------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 主题／命题                     | **项目级作者字段**，可给卷、人物弧和场景挂指针；不是故事真值。 | “这本书在讨论什么”是作者解释框架，可以调整，也可能故意保持多义。 | 检查器把一场不服务主题的日常戏判成“事实错误”。               |
| 类型公约                       | **项目契约字段**，写主类型、辅类型、必须满足和明确不要求的公约。 | 它负责约束生成与检查口径，不描述故事世界发生了什么。         | 升级流被套进纯悬疑检查，每个能力突破都被批评成“提前揭底”。   |
| 废弃选项／没走的分支           | **明确不要进故事真值和默认执行包**；留版本快照或作者决策档案，标记已废弃。 | 废案的价值是解释“为何没选”，不是与正史共同竞争。             | 模型突然把废弃的双胞胎弟弟写进正文，因为检索时看到他和正史人物同权。 |
| 作者注释                       | **明确不要进故事真值**；放通用作者注释层，可指向章节、人物、规则或事实。 | “这里以后改”“故意不解释”是给系统的命令，不是故事内容。       | “这里以后补动机”被抽取成角色真实动机，甚至写进人物卡。       |
| 场景功能标签                   | **章纲/场景字段＋投影**，不单开账。                          | 铺垫、兑现、转场、日常描述的是这场戏承担的工作，离开场景便失去意义。 | 独立标签表写“兑现”，章纲早改成转场，两处互相争夺解释权。     |
| 反派实际计划 vs 主角以为的计划 | **拆开合并**：反派真实目标和计划住人物计划记录；主角的误判住知情账；界面并排展示。 | 这是“真实意图”和“他人信念”的对照，不是一种新对象。           | 主角每次都按反派真实计划应对，所谓误判只剩作者口头说明。     |
| 连续性琐事                     | **默认检查器现算场景快照**；只有跨场景、参与因果、反复出现或作者钉住的细节才晋升事实。 | 天气、衣服、左右手、杯子位置数量巨大，大部分只在相邻场景有用。 | 完全不查会让湿衣服瞬间变干；全进真值又会产生几万条袜子、杯子和手势记录，挤爆执行包。 |

推荐的“连续性晋升条件”很简单：

- 只出现一次、没影响剧情：留检查缓存。
- 跨场景仍须保持，或影响动作能否发生：提议晋升状态事实。
- 作者确认后才写真值。

影视行业的场记会记录服装、动作和道具来查连续性，但这些首先是拍摄记录，不等于每件东西都要升级成世界核心设定。[ScreenSkills 对场记记录范围的说明](https://www.screenskills.com/job-profiles/browse/film-and-tv-drama/technical/script-supervisor-film-and-tv-drama/)。

## 2. 还漏了的 7 个常见对象

| 漏项                                   | 处置                                                         | 没家时的坏法                                                 |
| -------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 人物当前目标、动机、计划、放弃原因     | v1 做人物或人物弧下的结构化子记录；复杂到同时跑多套跨章计划时再升“行动议程账”。目标、计划、承诺仍要分类型。 | 人物明明急着救妹妹，下一章无解释地跑去参加三个月大比。       |
| 动态状态与资源                         | 变化住事件效果和带有效期的事实；当前血量、伤势、境界、钱、库存、声望做投影。不要每种资源一张表。 | 最后一枚复活丹已经吃掉，二十章后又从口袋里掏出一枚。         |
| 场景 POV／叙述者／焦点人物             | 放场景字段，至少区分叙述模式、焦点人物、允许进入谁的内心；串视角由检查器报。 | 限知视角里突然读出门外杀手的内心计划。                       |
| 实体别名、曾用名、身份、头衔有效期     | 放共享实体注册处；“白鸦就是太子”是否被某人知道，另走知情账。 | 系统把“白鸦”“三殿下”“李昭”建成三个人，统计出三份出场记录。   |
| 作者待定问题／TODO／备选答案           | 放作者任务与决策层，状态可为待定、已决、搁置、废弃；明确禁止当故事事实检索。 | “父亲也许是反派”只是备选，却被下一次续写直接坐实。           |
| 已发布正史、草稿、修订、追溯改设定边界 | 默认做章节版本与发布字段；多平台、已发布后改文时再升操作账。 | 作者改了本地第12章，系统却拿尚未发布的新稿去检查读者已经看到的第80章。 |
| 路线、距离、交通方式与旅行耗时         | 距离和连接住地点关系，速度与限制住规则，某次出行住事件；可行性由检查器现算。 | 两地以前骑马三天，剧情着急时普通人两小时走完。               |

POV 是很容易漏掉的硬字段。计算叙事研究指出，系统必须知道当前心理视角，才能区分人物信念和故事事实；Scrivener 的官方文档也把 POV、地点、日期、修订状态视为适合放在场景元数据里的内容。[叙事视角追踪](https://aclanthology.org/J94-2004.pdf)、[Scrivener 自定义元数据](https://www.literatureandlatte.com/blog/how-to-add-custom-metadata-to-the-scrivener-inspector)。

发布状态也不是纸面问题。连载平台允许章节处于草稿、预约发布、已发布和已编辑状态，已发布改文会立刻改变读者所见版本。[Royal Road 章节、草稿与预约发布说明](https://www.royalroad.com/support/knowledgebase/83)。

## 3. 哪些最容易和章纲抢内容

🔥 总测试句只有一句：

> 去掉“第几章／这场戏”后，这句话还必须长期成立吗？

- 去掉后就没意义：住章纲。
- 去掉后仍要回答“截至某锚点是否成立”：住专用家。
- 两边都需要：真值只存专用家，章纲只写“本章造成什么变化”并放指针。

| 对象           | 住章纲的测试句                 | 住专用家的测试句                                           |
| -------------- | ------------------------------ | ---------------------------------------------------------- |
| 知情           | “本章让女主偷听到王爷未死。”   | “从此锚点起，女主知道王爷未死。”                           |
| 读者披露       | “章尾给读者看见棺内是空的。”   | “截至第32章，读者已收到哪些确认、误导和暗示？”后者是投影。 |
| 时间           | “第72章安排众人在午夜会合。”   | “会合必须晚于祭坛开启、早于日出。”                         |
| 承诺           | “本章男主答应三日内归还剑。”   | “他欠谁什么、何时到期、现在是否履行？”                     |
| 因果           | “本章安排主角拿到钥匙。”       | “开门必须先持有钥匙或触发规则例外。”                       |
| 规则／能力     | “本章第一次展示瞬移。”         | “瞬移不能穿阵，使用后冷却三天。”                           |
| 关系           | “本章两人公开决裂。”           | “决裂后双方关系、称呼和信任状态是什么？”                   |
| 代价／状态     | “本章主角断臂换胜利。”         | “此后他缺失左臂，直到某个明确恢复事件。”                   |
| 真实计划与误判 | “本章反派故意放出假路线。”     | “反派真实目标是什么；主角当前信的是哪条路线？”             |
| 场景功能       | “这场戏负责兑现旧伏笔并转场。” | 没有专用家；它只属于场景。                                 |

章纲说“这一章要发生什么”；专用账说“发生以后，世界变成了什么”。

## 4. 只能再开 3 个一等账时

假定现有事实与人物已经能提供稳定 ID、锚点和带时间的事实，我会选：

### ① 人物知情硬账

它直接解决误知、泄密、角色越权知道、错误计划依据等高频问题，而且题面方向已经拍定。

最小语义即可，不锁字段命名：

- 谁
- 对哪条命题
- 已知／明确未知／被误导
- 被误导成什么
- 从何时到何时
- 获知或受骗锚点
- 作者是否确认

### ② 事件—时间—约束账

它同时托住：

- 世界内时间
- 相对先后和重叠
- 倒计时
- 冷却
- 硬性因果前置
- 事件效果
- 当前状态投影

长篇一致性研究发现，事实和时间是长文本最常见的错误区；FACTTRACK 也采用“原子事实＋有效时间区间”检查大纲矛盾。[时间感知事实追踪](https://aclanthology.org/2025.naacl-long.144.pdf)、[2026 长篇一致性错误分类](https://aclanthology.org/2026.findings-acl.410.pdf)。

### ③ 规则—能力—例外账

它把世界法则、社会规则、技能触发、限制、代价和例外放进一处。能力归属仍是人物事实，实际使用仍是事件。

2026 年的长篇一致性分类专门列出了世界规则、社会规范、能力波动、遗忘能力、地理矛盾、名称混淆、数量错误、视角与声口漂移。这也说明“规则账＋其他投影”比给每种错误各开一张表稳得多。[ConStory-Bench 分类](https://aclanthology.org/2026.findings-acl.410.pdf)。

为什么不是三个强力候选：

- **不是读者知情表**：读者状态可以从已确认披露记录按叙述顺序投影；悬疑或不可靠叙述占核心时，再把“话语披露”升表。
- **不是承诺／人物议程表**：它确实有升表资格，但 v1 已拍不开；先用带稳定子 ID 的结构化记录能安全过渡。
- **不是连续性／当前状态表**：它们应从事件、事实、规则生成。再存一份会出现两个“当前答案”。

还有一个替换条件：

> 如果现有事实层不能给地点、势力、物品稳定 ID，也不能表达带有效期的关系，那么第三席应先换成共享实体注册表；规则暂时作为结构化事实保存。

## 5. 主 Agent／检修 CLI 的 20 问路由

| 作者会怎么问                                     | 先查哪里                           | 返回哪一层                       |
| ------------------------------------------------ | ---------------------------------- | -------------------------------- |
| 1. “阿璃这会儿到底知不知道师父没死？”            | 人物知情账＋指定故事锚点           | 硬真值＋获知证据                 |
| 2. “他到底被反派骗成什么了？”                    | 人物知情账的误导内容与来源         | 硬真值                           |
| 3. “读者到这章已经知道多少了？”                  | 场景披露记录按叙述顺序汇总         | 读者知情投影；隐含推断另标软判断 |
| 4. “这个秘密现在还有谁不知道？”                  | 事实＋人物知情＋读者披露           | 秘密投影                         |
| 5. “谁还欠着谁一个承诺没还？”                    | 人物/关系下的承诺子记录            | 未结义务投影                     |
| 6. “血月倒计时和这招冷却还剩多久？”              | 时间账＋规则账＋最近触发事件       | 计时投影                         |
| 7. “这两件事时间上是不是撞车了？”                | 事件时间、区间和约束边             | 检查结果；不得回写真值           |
| 8. “没拿钥匙，他凭什么开门？”                    | 事件前置＋当时状态＋规则例外       | 因果检查提示                     |
| 9. “这一战到底付出了什么代价？”                  | 事件效果与前后状态                 | 代价/损失投影                    |
| 10. “他现在到底还能不能用这招？”                 | 能力归属事实＋规则＋当前状态＋冷却 | 可用性现算结果                   |
| 11. “这次破例有正式依据，还是我写崩了？”         | 原规则＋例外指针＋适用范围         | 规则真值＋冲突检查               |
| 12. “白鸦和三殿下是不是同一个人？现在在哪？”     | 实体别名＋身份事实＋位置状态       | 实体解析＋当前位置投影           |
| 13. “这俩现在算盟友、仇人还是表面合作？”         | 带有效期的关系事实＋双方知情       | 关系投影                         |
| 14. “他为什么突然改口叫她师娘？”                 | 称呼规则＋关系变化＋知情变化       | 证据解释；异常只进检查结果       |
| 15. “这段是谁的视角，话听着像不像他？”           | 场景 POV＋人物声口＋对话对象规则   | POV/声口检查结果                 |
| 16. “这段还像我们定的悬疑升级味儿吗？”           | 项目类型契约＋主题字段             | 软评估，不是故事真值             |
| 17. “我当时为什么没走双胞胎那条线？”             | 作者决策档案、废案快照和注释       | 作者层                           |
| 18. “这章到底是在铺垫、兑现，还是纯转场？”       | 场景功能字段＋伏笔指针             | 章纲元数据                       |
| 19. “反派真想干嘛，主角又以为他想干嘛？”         | 反派目标/计划记录＋主角知情账      | 对照投影                         |
| 20. “这章发出去以后，草稿和线上版到底谁算正史？” | 章节版本、发布状态、修订链         | 发布/正史投影                    |

CLI 的检索顺序建议固定为：

```
作者问题 → 确定故事锚点与叙述锚点 → 查唯一真值住处 → 生成所需投影 → 必要时跑检查器
```

执行包只带：

- 命中的真值行；
- 直接相关的一跳规则或关系；
- 当前锚点附近的证据；
- 已拍作者约束。

不带整本关系网、所有规则、全部连续性快照。触发条件满足时默认只亮灯；作者确认前，不自动建卡、不自动改状态、更不把“疑似违例”写成真值。

## 调查来源怎么支撑这些判断

- [人物私人信念与客观世界分开](https://cdn.aaai.org/ojs/12411/12411-52-15939-1-2-20201228.pdf)：支持“反派真实计划”和“主角以为的计划”分住。
- [读者模型与信息传递](https://aclanthology.org/2021.nuse-1.10.pdf)：支持读者知情随叙述推进、允许不确定，不照搬人物知情。
- [故事计划与话语计划分开](https://aclanthology.org/W16-6602.pdf)：支持客观发生与读者披露是两套顺序。
- [CPOCL 的前置、效果、时间顺序与因果边](https://cdn.aaai.org/ojs/12428/12428-52-15956-1-2-20201228.pdf)：支持因果前置住事件约束，而不是另造因果真值表。
- [W3C 时间本体](https://www.w3.org/TR/owl-time/)：支持时点、区间、持续时间和相对关系共用时间骨架。
- [RDF 关系模型](https://www.w3.org/TR/rdf11-concepts/)与[SKOS 别名模型](https://www.w3.org/TR/skos-reference/)：支持地点、势力、物品共用实体身份和关系边，不必按类型拆表。
- [PostgreSQL 生成列说明](https://www.postgresql.org/docs/current/ddl-generated-columns.html)：支持“能稳定重算的当前值和汇总应视作投影，不允许人工改成第二份答案”。
- [Scrivener 元数据与快照](https://www.literatureandlatte.com/blog/how-to-add-custom-metadata-to-the-scrivener-inspector)、[版本快照](https://www.literatureandlatte.com/blog/use-snapshots-in-scrivener-to-save-versions-of-your-projects)：支持 POV、地点、状态做场景字段，废案和旧稿留版本历史。
- [Campfire 的模块清单](https://www.campfirewriting.com/pricing)：说明作者确实会管理时间线、能力、地点、物品、关系等对象；但这是界面分区证据，不代表底层需要同样数量的真值表。

一句话收口：

> 真值表负责“作者确认后，长期必须成立的东西”；投影负责“从哪个角度看”；检查器负责“现在看起来哪里可能有问题”；章纲负责“这章打算让什么发生”。
