# ChatGPT Pro 窗口 5：当前合成内容体验审查

请使用你当前可用的最高推理强度，完整阅读共用 ZIP，重点逐份打开 `03_upstream_evidence/.../content_cases/` 中的合成输入、当前实际输出和案例说明。

你是作者产品的内容体验审查员。不要再审架构。你的任务是回答：

> 作者今天看到这些真实由现行函数生成的页面、卡片、报告和文本包时，能不能看懂、能不能做决定、会不会被误导、会不会看到不该看的未来内容、机器有没有把不确定性伪装成事实？

## 审查对象

按包内实际案例覆盖：

- M1 上传与分流摘要；
- M2 责任段与 halo 人读地图；
- M3／M4 候选和事实对象的作者可理解性边界；
- M5 待审页与作者明确动作；
- M6 证据查询、防剧透上下文和空结果；
- M7 体检 finding、覆盖范围、CURRENT／STALE；
- 作者工作稿、检测输入包和检测结果；
- M8 规划选择卡；
- M9 概览；
- M10 场景卡／文本包；
- M11 上下文装入、遗漏、回取和未决说明。

没有实际案例的模块不要靠想象打分；写“本包没有当前输出样例”。

## 每个案例都要检查

1. 作者进来时想解决什么问题；
2. 输出第一眼能否说清“这是什么、基于哪一版、现在能做什么”；
3. 核心结论、逐字证据、来源版本和排除项是否容易找到；
4. 机器术语、状态码、SHA、字段名是否抢走注意力；
5. `候选 / 已确认 / 已驳回 / 当前 / 过期 / 未决 / 未检查` 有没有被混淆；
6. 空结果是不是诚实写成“当前证据门下没找到”，而不是“故事中不存在”；
7. 推荐是否被误写成作者已经选择；
8. provider 给出的判断是否被界面包装成绝对真理；
9. 防剧透输出是否可能泄露 future chapter 的事实、quote、上下文或暗示；
10. 作者下一步动作是否明确，是否必须理解内部实现才能继续；
11. 哪些问题只要改人读输出就能解决，哪些其实是上游语义或 owner 缺口，不能靠改文案掩盖；
12. 同一术语在不同模块是否前后不一致。

## 评分方法

每个有实际输出的案例分别给 0～4 分：

- 忠实度：有没有超出机器结果和来源证据；
- 清晰度：普通作者能否一次看懂；
- 可操作性：作者知道下一步能做什么；
- 证据可见性：重要判断能否快速回到原文；
- 不确定性表达：候选、未决、过期、覆盖不足是否诚实；
- 内容安全：防剧透、跨版本、跨状态是否有危险表达；
- 修改成本：作者需要多少脑力才能纠正系统。

红线错误不要被平均分冲淡，单独列：

- 把候选写成事实；
- 把推荐写成作者决定；
- 把 completed 写成全绿；
- 把 stale 写成 current；
- 把未来内容泄给截至章查询；
- 把“没找到”写成“不存在”；
- 丢失逐字证据却继续给强结论；
- 修改、补写或替作者决定正文。

冻结 provider 的语义正确性不能评分。你只能评分系统如何呈现给定结果，并把需真实语义验证的部分单独挂起。

## 交付

请返回 ZIP，根目录只放：

`CURRENT_SYNTHETIC_CONTENT_EXPERIENCE_REVIEW.md`

Markdown 结构：

1. 一页结论：当前最清楚的 3 个输出、最容易误导的 3 个输出；
2. 本轮能证明和不能证明什么；
3. 逐案例评分表；
4. 逐案例内容审查：优点、困惑、红线、作者下一步、问题归属；
5. 跨模块术语一致性表；
6. 防剧透、不确定性和证据展示专项结论；
7. 只改人读层就能提升的候选清单，最多 10 项；
8. 不能靠文案解决、必须退回上游的内容缺口；
9. 下一版样例应怎样重跑，才能看出体验真的变好；
10. 仍需真实小说或真实作者才能回答的问题。

每个判断引用包内案例相对路径。不要给工程精确写集，不要重新安排七窗口，不要把内容建议自动升级成施工票。
