# ChatGPT Pro 窗口 4：M7～M11 读侧、规划、导出与打包

请使用你当前可用的最高推理强度，完整阅读共用 ZIP 后再作答。

只读审查 M7～M11 以及它们从 AuthorWorkspace 取料、保存和判断过期的接缝，给本地七窗口设计下一批真正增加模块可用性的任务。

范围：

- M7：一致性体检、作者可读报告、保存和过期判断；
- M8：C7 章计划、作者选择目标、模糊意图放置建议、章槽快照；
- M9：事实概览投影、单章／全书视图、保存和过期判断；
- M10：章槽到场景切片、场景卡、Markdown／JSON／确定性文本 ZIP；
- M11：上下文材料筛选、预算、漏装回取说明、未决停止；
- AuthorWorkspace：这些模块怎样从绑定作者的 current 项目安全取料。

这不是全产品规划，不审 M1～M6，也不设计统一工作流平台。

## 必须守住的事实边界

1. M1～M11 是能力图，不是强制串行流水线。
2. 很多结果只是可运行原型或机械校验通过，不等于模块完成、模型能力或产品上线。
3. `C5_OVERVIEW_CARD_PROTOTYPE`、`C8_SCENE_CARD_PROTOTYPE` 仍是原型，不能写成正式 C5／C8。
4. 当前没有正式 C9 合同。`packer.py`／`packer_tool.py` 是 M11／C9 原型，不得替项目冻结正式 C9。
5. M11 只对调用方显式给出的材料做确定性筛选。actuality、HARD／SHOULD／MAY、排序、回取和 token 估算当前不由 M11 自己推断。
6. M8 能生成、校验、排版 C7，也能把作者点的局部卡与 A／B／C／discard 绑定到完整 C7 快照；这不等于正式 `C7_SELECTION_ACTION`。
7. 正式选择仍需要完整长期 `option_record`、current 规划对象、expected revision、合法 `plan_mutations` 和 stop point。不能用空串或默认值伪造 `why_fit / changes / risks / digest_refs`。
8. 模糊意图路由只是零写入建议，不能假装人物走向、关系走向或灵感的 owner 已存在，也不能把建议当作者决定。
9. AuthorWorkspace 是作者隔离和白名单边界。业务模块不得重新接收任意路径、`project_dir`、作者 ID 或项目 ID。
10. 云端迁移只替换 StorageBackend，M7～M11 业务核心不应跟着改写。
11. 设计稿说明想做什么；合同说明冻结了什么；当前代码和测试说明现在真能做什么。冲突时分层报告。
12. 不得因为测试很多就建议再造总控账、复审层或 SHA 治理。

## 必须回答

### A. 逐模块判断当前是否可用

对 M7～M11 分别列：

- 当前真实输入；
- 核心函数实际行为；
- 输出身份；
- 是否能保存、重启读回；
- 怎样判断来源变化和旧结果过期；
- 哪些失败会在写入前停止；
- 作者今天能直接得到什么；
- 哪些只是机械运输，不能外推成语义能力。

每个判断引用具体代码、函数或测试，不要只引用总控简报。

### B. 哪些已经够了，应停止加壳

指出：

- 已足够支撑下一模块，不需继续堆测试或回执的部分；
- 重复、过度防御或偏治理的工作；
- 继续做也不会增加作者可用能力的方向。

### C. M8 选择与模糊意图路由

把两条线分开审：

1. C7 局部选择目标怎样走到正式规划写入；
2. 作者一句模糊未来想法怎样得到放置建议，并在作者确认后进入正确 owner。

说明：已有字段唯一提供什么；缺哪些稳定来源或 owner；哪些能先做纯对象／只读工具；哪些必须等产品语义；discard 是否仍需要完整长期规划卡来源；为什么路由建议不能直接写成决定。

### D. M9 投影边界

检查事实概览是否：

- 只讲已发生事实，不把未来规划写成已发生；
- 保留散条与证据覆盖；
- 能从章级扩展到全书视图；
- 正确标记来源变化后的旧卡；
- 没有为了“新鲜”复制第二份真值。

判断当前“facts 或 chapter index 一变化就让旧卡过期”的保守策略是否够用。只有存在明确、局部、无需新语义的收益时，才建议更细依赖。

### E. M10 最缺哪类取料接缝

审查：

`CHAPTER_SLOT_SNAPSHOT → M10 scene slice → C8 prototype → JSON / Markdown / deterministic ZIP`

区分：

- 可直接从 AuthorWorkspace current 计划读取的内容；
- 仍由调用方提供的人物／地点 anchors、scene bindings、event bindings、export context；
- 哪些补料有唯一现成 owner；
- 哪些不能靠猜测或复制进新通用表；
- 下一步怎样让作者拿到真正可使用的文本场景包，同时不建设图片／视频生产线。

### F. M11／C9 开放缝

给出“当前原型到真实取料”的责任图：

- 谁产生候选材料；
- 谁判断 current／future／unresolved；
- 谁给 HARD／SHOULD／MAY；
- 谁做任务相关性和排序；
- 谁估 token；
- 谁生成可回取入口；
- M11 只负责哪些机械动作；
- 哪些变化会让包过期。

owner 不唯一就标 `OPEN` 并给最小验证办法。不要新建正式 C9，不要用万能 coordinator 代替 owner。

### G. AuthorWorkspace 取料

为 M7～M11 分别说明：

- 读取哪些白名单逻辑键；
- 哪些来源必须一起冻结水位；
- 结果是否需要保存；
- 保存在哪个模块自己的键；
- 怎样防止跨作者／跨项目读取；
- 上云只替换 StorageBackend 时哪些接口保持不变。

不要建议模块扫目录，也不要让一个通用工具拥有所有业务写权。

## 交付

请返回 ZIP，根目录只放：

`M7_M11_PRO_REVIEW.md`

Markdown 必须包含：

1. 一页结论：最接近可用的是哪些、真实卡点、下一批该做什么；
2. 逐模块证据表：已验证能力、证据、仍缺核心预期 ID、不可外推边界、身份结论；
3. M7～M11 与 AuthorWorkspace 的真实职责和数据流图，代码实线、设计虚线、缺 owner 标 `OPEN`；
4. M8 选择动作逐字段差距表：已有唯一来源／材料不足／需要新 owner／需要 CZ 决定；
5. M11 材料责任表：来源、actuality、义务层级、排序、预算估算、回取、新鲜度；
6. 4～7 张下一批施工票；
7. 保留／停止清单；
8. 最多 5 个真正改变产品语义或 owner 的 CZ 问题。

施工票按 `SAFE_NOW / CALIBRATE_FIRST / CZ_DECISION / DEFER` 分类。每张写清：作者多得到什么、原子预期 ID、输入／行为／输出、建议精确写集、最小测试、并行条件、停止条件、为什么比继续补治理更有价值。

不写代码补丁，不修改附件。候选接口必须标“候选设计”。不建议 Git、生产、训练、Gold、真实 API、上传或部署。不把设计箭头写成 runtime，不用统一编排器作为默认答案。任何建议如果不能增加模块独立运行、取料、输出、保存、失败关闭或真实交接能力，就删除。
