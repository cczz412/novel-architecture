# ChatGPT Pro 窗口 3：M1～M6 独立可用性与交接

请使用你当前可用的最高推理强度，完整阅读共用 ZIP 后再作答。

这次只审 M1～M6：

- M1：上传、识别、分流、材料进入系统；
- M2：章节切成责任段；
- M3：从责任段得到事实候选；
- M4：候选进入事实快照；
- M5：作者查看证据并明确确认、驳回或改写；
- M6：从当前已确认事实中查询并展示证据，包含截至某章的防剧透读取。

主任务不是写新架构，而是判断每个模块是否真能作为独立小工具使用，并给出下一批最小施工票。

## 核心判定句

逐模块判断是否满足：

> 给它明确输入，它能独立运行并交出明确输出；输出可保存、重启读回并安全交给下一模块；失败不留半套结果；不同作者不串数据；旧版本不冒充当前版本。

请区分：

1. 当前代码和测试已经证明；
2. 只有机械运输成立，真实语义能力未证明；
3. 有局部切片但普通作者还不能用；
4. 当前明确断点；
5. 可暂缓的未来增强。

## 不要直接接受的假设

- M1 有纯对象入口和 AuthorWorkspace 持久化，但“原始上传 → 合法 C1 v1 current 章节”是否连上要看代码。
- M2 的 C1 v1 → C2 v1 机械切段可能成立，但真实稀疏章、超长段、碎尾和多章批次是否够用要核实。
- M3 大量证明来自冻结离线 response，只能自动证明运输与校验，不能自动证明抽取质量。
- M4 产生 `EXTRACTED` 候选不等于事实成立；去重、冲突分组和高密度候选可能仍开放。
- M5 必须保留作者决定权，不能默认确认；需要检查分页、续审、批量动作、竞态和原子性。
- M6 应只读 current revision 上已确认且证据有效的事实；关键词测试不能冒充自然语言理解或语义回答。

若代码证明不同，以代码和直接测试为准。

## 逐模块审查维度

- 核心对象入口是否只接明确对象，不依赖任意磁盘路径；
- 本地文件工具的输入、输出、错误是否清楚；
- 同路径、软链接、路径逃逸、损坏文件是否安全；
- 同一输入重复运行是否确定；
- 文件写入失败是否保留旧输出；
- AuthorWorkspace 是否真正绑定作者和项目；
- 是否能持久化、重启读回、判断过期；
- 读取期间上游变化时是否返回混合快照；
- 多章或多动作中一项失败是否留下半套；
- 章节版本、原文位置、SHA 和证据是否完整传给下一模块；
- 人读出口是否只展示机器结果，没有偷偷补结论；
- 是否仍要求普通调用方手拼大量内部字段。

## 必须覆盖的真实异常输入

### M1

- TXT、MD、DOCX、ZIP 混合上传；
- 编码异常、空文件、垃圾成员、重复名、嵌套 ZIP、超大成员；
- 一个文件里 1／3／10／20 章；
- 缺章、重复章、乱序；
- 文件名章号与正文标题冲突；
- 简介、标签、设定、章节、大纲混在一起；
- 只有三章裸正文，没有书名、类型、主角；
- Excel／CSV 是支持、明确拒绝，还是无证据。

### M2

- 极短章、极长单段、碎尾；
- 信息极密或极稀；
- 一件事跨切段边界；
- 多章批次里一章版本错误；
- 前后文窗口是否被误算成该段负责正文。

### M3

- provider 少响应、多响应、旧 revision、未知 item key；
- 坏 JSON、缺字段、多字段、截断；
- 一个责任段零候选；
- 一章突然两三百条候选或只有十几句可抽；
- quote 是否逐字属于自己的责任段；
- 当前只证明 transport，还是已证明真实抽取质量。

### M4

- 多章编号、revision、anchor、quote SHA 是否保真；
- 第二章失败是否留下第一章；
- 旧 confirmed 是否被新批次破坏；
- 重复、相似、冲突候选如何处理；
- 两三百条候选是否照单全收；
- 改稿后旧事实 current／needs_recheck／evidence_gone 是否真能工作。

### M5

- 作者按章分页审 250 条；
- 翻页期间 facts version 变化；
- 只确认两条，其余不得默认处理；
- confirm／reject／edit 的证据绑定；
- 批次第二条失败时第一条是否落盘；
- operation 重放、重复 fact_ref、stale SHA；
- 作者改口是否可追溯；
- 是否有危险的全书一键确认。

### M6

- 只查 current revision 上 confirmed 且证据有效的事实；
- 无命中时不得编答案；
- 展示 quote、anchor、revision 和排除计数；
- 截至 c05 时 c06 的事实、证据、正文完全不可见；
- 不连续章节号仍按 chapter_index 顺序防剧透；
- 上下文仍绑定同一 revision；
- 大白话、别名、关系查询是真理解还是字面匹配；
- 作者 A 是否可能读到作者 B 或另一项目。

请再补充你从代码里发现的高风险真实场景。

## 交付

请返回 ZIP，根目录只放：

`M1_M6_USABILITY_REVIEW.md`

Markdown 至少包含：

1. 一页结论：哪些可试用、哪些只是机械切片、哪条交接真实成立、普通作者最早卡在哪、最该做的三件事；
2. M1～M6 能力表：真实输入／输出、对象入口、文件入口、AuthorWorkspace、持久化、重启、失败保旧、可交给谁、不可外推边界，结论用 `可试用 / 机械可用 / 只有切片 / 存在安全断点`；
3. 当前真实交接图：`上传材料 → C1 current → M2/C2 → M3/C3 → M4/C4 EXTRACTED → M5 作者动作 → C4 CONFIRMED → M6 查询与证据`，每条边标已证明／只有文件运输／调用方手拼／缺 owner／缺持久化／缺语义／断裂；
4. M1～M6 原子需求差距：核心已满足／部分满足／未满足／附加可暂缓；
5. 每模块 5～10 个真实异常场景，写用户输入、预期行为、当前可能行为、怎样判定进步、所需最小材料；
6. 8～12 张最小候选施工票，按优先顺序；
7. 明确列出现在不要做的高级但浪费额度的事。

每张施工票必须包含：所属模块、用户问题、输入输出、缺口依据、建议最小写集、一个正常例、一个失败例、完成后多出的真实能力、停下来问 CZ 的条件、依赖关系。必须单模块、窄写集、能独立验收，不能是大重构、统一平台或全链打通。

每个重要判断引用包内代码、函数或直接测试。没有依据写“材料不足”。不修改代码，不提供补丁，不新增 M12／M13，不替 CZ 决定正式语义或作者真值，不宣称生产、训练、Gold 或模型质量合格。
