## 产品立场：导写＋核对，不代写（R06 新增，账序 21:35 条⑤）
这个产品是跟成熟作者一起思考的**编辑助手**：帮作者导写（选线、章纲、约束、材料包）和核对（回收、对账、风险提示），**不替作者写书稿**。
- 系统尽量不生成书稿；“一键成文”只是后续可选模块，不进当前主线；
- 系统所有逻辑参考永远是剧情原子账＋剧情图／章纲，不是书稿字面；
- 作者的书稿是创作结果，系统负责把它回收核对进账（见 03 页回收核对工序）。
## 一句话
这是一个以**章纲与规划剧情图**为作者工作面、以**冻结书稿和确认后的故事状态**为历史依据、能准备下一步创作、追溯证据并安全修改长篇故事的系统。
## 它主要解决什么
作者真正难的不是“让 AI 多抽几条事实”，而是写到几十章、几百章后还能做到：
- 看得清当前故事走到哪里，接下来几章准备往哪转；
- 人物状态、知情、承诺、规则、因果和故事线不崩；
- 缺前情时回冻结书稿取证，不靠模型凭记忆补故事；
- 改一处时只复核真正受影响的部分；
- 剧情图、书稿、分镜和互动分支共享故事底座，但互不冒充真值。
## 默认服务谁
当前已拍口径不是优先服务“十万字以上才遇到长程问题”的作者。主体用户是已经写完黄金三章、正在 3～20 章之间继续推进、开始遇到结构和接续困难的网文作者。
入口是黄金三章工作台，作者可以边写边把故事状态和章纲逐步建起来。已有长篇作品仍可导入，但“先把全书深抽完才能开始工作”不是默认路线。

## 两条主流程
### 导入已有作品
```plain text
冻结书稿
→ 建来源坐标与检索入口
→ 作者提问，系统按需回原文取证
→ 独立判断回答能不能用
→ 将持续影响后文的关键变化提名入账
→ 作者或正式闸确认
→ 更新状态、知情和长线账
→ 生成可编辑的反向剧情图
```
AI 从已有书稿还原出的结构不能叫“作者大纲”。它是**反向剧情图**（成文历史的整理视图），叙事作用推断还要带置信度。
### 从章纲继续创作
```plain text
开章第一问：由规划槽位映射默认给出当前故事线；作者改线或出现规划偏差时询问（切线仍是重动作并出切线包）
→ 接收盒子约束：全书宏观大纲→卷纲→章盒子＋作者本章临时约束
→ 编辑本章计划和场景安排（章纲）
→ 处理大卡与必要小卡（创作卡／修复卡）
→ 章纲关闭（编译吃约束，冲突亮灯）
→ 编译执行包
→ 作者写书稿（系统导写；一键成文＝后续可选模块）
→ 回收核对（写了／没写／写错三态）
→ 作者确认差异（批量默认＋重签清单单独勾选）
→ 将确认稿冻结为带版本、来源编号和 SHA 的书稿证据
→ 登记真正写成的剧情原子和状态变化
→ 关章＝清账不清零（未完事项显式转下章挂账）
```
章节工作室在章纲阶段不产正式稿。系统默认不代写书稿：作者自己写，或在章纲关闭后选用后续可选的生成模块；若某一场需要重做，只重做受影响场，并带上全章章纲、上一场结尾、本场义务包和风格锚。

## R07 产品验证与边界增补

以下五段均为语义方向，不冻结字段、界面或施工合同。状态统一为：`APPROVED_DIRECTION`（依据账序 2026-08-12 21:18 条）。每段保留独立原子 ID，可单独修订或摘除。

### N01｜对外类别工作名

「叙事状态引擎」只作为对外类别工作名，用来帮助外部用户理解“系统持续维护故事状态”这一类产品，不替换正式北极星，也不宣称这是独占品类。正式采用前另做命名查重、商标风险和用户理解测试；没有结果前，不把它写成正式产品名。

### N02｜确认差异，不让作者填 Wiki

“确认差异，不填 Wiki”拆成两条流程：已有长篇导入时，作者先提出真实问题，系统按问题回原文取证，只请作者确认当前答案和需要长期保留的变化；新章回收时，系统汇总本章实际变化，普通项批量确认，高影响项进重签清单单独确认。维护负担、第一次可信结果所需时间和首次确认负担进入双计分卡。

### N03｜一个首发用户和一个设计伙伴轨道

首发主线只服务已经写了 3～20 章、近期准备继续写、正被结构回查和一致性问题拖累的作者。另找 1～2 家短剧或漫剧团队作设计伙伴，只验证同一故事底座能否输出视频生产投影；伙伴不获得与作者主线相同的施工优先级。“一句话生成整本”不作早期承诺。

### N04｜一个内核与垂直扩展边界

多个垂直场景共用一套故事真源内核，但可以各自增加扩展字段。停止条件不是“出现新字段”，而是某个场景要求自动或绕过确认直写真源。投影侧允许编辑，但只能走“投影编辑 → 修改提案 → 影响预览 → 作者批准”；批准前对真源没有效力。

### N19-A｜首版产品证明合同与首次价值路径

首版只证明一条最短可信链：真实项目提出当前问题 → 系统回原文取证 → 作者确认答案 → 故事状态被安全更新 → 作者下一次继续使用。章节工作室其余环节不进这次首版验收。入选作者还要有可导入书稿、近期确实准备继续写、存在具体回查或接续问题，并愿意在一周内再次使用。第一次使用只做“上传材料＋回答一个真实问题”，不先填 Wiki；同时记录第一次可信结果所需时间和首次确认负担。
## 产品长期纪律
- 系统定位是导写＋核对的编辑助手，不代写；一键成文只是后续可选模块；
- 已发生事实和未来计划分账；
- 查询回答默认是临时结果，不自动永久入账；
- AI 只能提议高影响变化，作者确认后才进入正史；
- 事实证据、计划、投影和推断不能互相冒充；
- 有两端可回验依据的已确认硬事实冲突亮红灯，节奏和手法建议亮黄灯，尚查不实的隐含／多跳矛盾只进“待复核线索”队列；系统只能说“当前覆盖范围内未检出”，不能宣称查尽；
- 冲突也可以转成剧情机会，不等于系统只负责把冲突消掉；
- 章纲阶段逐卡撤销，修稿阶段必须能回滚；
- 第一版不做高成本视觉生成，先把章纲、证据、下一章生产和文本分镜跑顺；
- 产品流程不绑定某一家模型。
## 上下文与记忆的长期方向
故事记忆不是“把所有书稿分片塞进向量库”。当前已拍方向是围绕剧情原子做伸缩压缩：越远越压缩，关键因果保留头尾，不可逆变化长期保留；切换故事线时，优先接回同一故事线上一次出现的状态。压缩视图本身就是多粒度派生摘要载体，胶囊和章节摘要只是它的形态，不是另建一套摘要真值。
原文仍然保留在冻结书稿中。远期常驻压缩只负责导航，按需回捞冻结原文是刚需。摘要和状态只负责帮助定位、准备和判断，不能取代证据；“不走书稿分片向量检索主路线”约束的是真值表示，不禁止检索通道使用 BM25 或向量扩召回。
## 成功的最小读数
- 作者的关键问题能被回答，回答能回到原文；
- 下一场或下一章的执行包够用，不必重读整本书；
- 计划、历史、查询和投影不混账；
- 一处改动只重做清楚标出的受影响范围；
- 作者能看见风险和已通过部分，不被系统反复唠叨；
- 模型换掉以后，业务数据、证据和创作流程仍能继续工作。
