# 同步与变更协议

状态：**项目级共同背景的现行更新纪律；不替代裁定、执行和写入授权**

## 这套协议防什么

最容易翻车的不是某一页写错，而是 Notion、ChatGPT、本地和新窗口各自记一套“当前理解”。共同背景板要像编译产物：能追到上游、能看见版本、能重建，也能在冲突时停下来。

它不取代账序真源。账序保存“CZ 当时拍了什么”，背景板保存“把当前有效裁定和现场证据合在一起后，大家现在怎样理解系统”。R05 直接派生自 immutable R04，只吸收 2026-08-09 已拍的五项变更；未通过短审的 CONSUME／EDGE 草稿不进入本版。

## 一个版本必须带什么

- 唯一版本号和状态；
- 证据截止时间；
- 仓库提交和工作树说明；
- Notion 账序、蓝图和决定页的真实 URL；
- Reality Packet 或等价本地快照的 SHA；
- 当前冲突和未决问题；
- 八份核心文档；
- 每个成员的 SHA 和整包 SHA；
- 构建与验收票。

## 什么时候需要出新版本

出现下面任一情况，不在旧版上静默改字，而是建新版本：

- CZ 改了产品骨架或关键术语；
- Notion 账序新增会改变背景板的拍板；
- 正式合同、默认链、Production Canonical 或生产模型角色改变；
- 重大实验推翻当前共同理解；
- 权利、blind、预算或执行授权状态改变；
- 发现旧版引用了错误页面、错误 SHA 或错误权力层；
- 当前冲突得到正式销账。

拼写、断链和不改变意思的排版修复可以发补丁版，但仍要留变更记录和新 SHA。

## 更新流程

```text
提出变更
→ 列出变更影响的核心文档和旧句
→ 收齐与本次变更有关的真源和结果票
→ 对比裁定、正式合同、执行现场和研究建议
→ 把冲突单独登记
→ CZ 拍需要拍的骨架与权力问题
→ 新建背景板版本
→ 做语义审查和机械验收
→ 生成新的完整文件夹和 SHA
→ Notion、ChatGPT、Codex 和新窗口改读新文件夹
```

每次更新只收与变更范围有关的材料。改产品骨架时查拍板和正式设计；改当前状态时查本地指针、合同和结果票；只有改研究判断时才需要外部研究。缺了真正相关的来源，可以做草稿，但要把缺口写明，不能宣布已经对齐。

## 变更分级

| 级别 | 例子 | 谁能批准 |
|---|---|---|
| 文字修复 | 错字、坏链接、不改变意思的排版 | 维护者；留补丁票 |
| 现场刷新 | 当前数字、实验状态、SHA、模型精确版本 | 有本地票即可刷新；不能凭刷新票把候选晋升为正式口径 |
| 角色或合同变化 | Mini／Lite 分工、Production Canonical 门、evaluator 阈值 | CZ／正式合同 owner |
| 产品骨架变化 | 真值层、默认工作面、生成时序、作者确认边界 | CZ 拍板 |
| 权利和费用 | 来源可否训练、预算、云任务数量 | CZ／权利与费用 owner，按正式票执行 |

## 冲突处理

每条冲突至少记录：

- 主题；
- 来源 A 和原话；
- 来源 B 和原话；
- 两边的日期、范围和权力；
- 当前执行采用的最窄安全边界；
- 谁能销账；
- 下一份需要的证据。

“更新文件看起来更合理”不是销账理由。不同范围的两个结果也不要误报成冲突，例如 M1 的 C2 输出表示和 P3 的 C2 输入提示就是不同变量。

## 各方怎样使用

### Notion

账序和裁定库继续保存拍板证据。共同背景板可以做 Notion 镜像，但镜像必须带版本、SHA、来源和过期状态，不能反过来覆盖账序。

Notion 不是当前技术现场的自动仪表盘，普通页面可能落后于本地很久。账序仍是活的裁定通道，也保存可回读的拍板证据；R05 以证据截止时的本地正式合同、结果票和现场为当前技术现实。两者有真正的权力冲突时交 CZ，并把新拍板回到账序留证；不拿旧普通页面压掉新实证。

本协议不重写历史 Notion 迁移纪律，也不规定各窗口必须怎样调研 Notion。它只要求：Notion 里若放共同背景板，就展示同一版 R05、同一核心 SHA 和明确的“共同说明，不是拍板页”身份。要查最新裁定或写入 Notion，仍按对应任务自己的现役规则和授权处理。

### 本地仓库

整个 R05 目录就是交付单元，入口固定为目录内的 `00_READ_ME_FIRST.md`。R01、R02、R03、R04 保留为历史，不原位改写。复制或发送本目录不会修改 `CURRENT_STATE.json`、默认链、冻结合同、数据或模型资产。

仓库当前只启用最小接入：`AGENTS.md` 要求 Agent 开工先读本目录入口，再按任务读取相关页。它不创建新的运行状态指针。R05 验收后只把这一个背景板入口从 R04 切到 R05；外层稳定入口和机器 `CURRENT` 指针仍未启用。

### ChatGPT 和外部模型

每次发送固定版本的整包，不从聊天记忆补缺。外部建议只进候选池，不能直接改现役。回包要保留原文、来源、时间和 SHA。

Repo Bridge 只负责把仓库快照、业务包和同一份回包绑定起来，是运输层和只读视图。当前仍是协议冻结观察候选，观察期未通过；它不能判断事实真值、替 CZ 拍板、授权施工、运行审查结论或修改业务真源。

外部窗口声称某份旧背景文件存在时，必须先找到实物、精确路径和 SHA，再判断它是旧副本、镜像还是竞争入口。找不到实物时只登记“未证实线索”，不凭文件名创建替身。确认旧文件存在后，下一版才给它 `LEGACY`／`SUPERSEDED` 身份并指向新的完整文件夹。

### 新窗口和新 Agent

收到整个 R05 文件夹后，先读 `00_READ_ME_FIRST.md`，再读任务相关核心页。简单机械活不必通读八份，但不能绕过相关页的权力边界。

涉及当前数字和执行权限时，必须回原始票；涉及 CZ 拍板时，必须回账序或裁定库。交接或验收材料应登记所读背景板版本和核心 SHA，避免新窗口靠聊天记忆猜。

## 机械验收

每版至少检查：

- 八份核心 Markdown 全部存在；
- 每份 Markdown 末尾有来源标注；
- 本地相对链接不缺失；
- JSON 可解析；
- 每个成员 SHA 可重算；
- 整包 SHA 可重算；
- 没修改 Reality Packet、现役指针、冻结合同、数据或模型；
- Notion 写入、训练、模型 API、费用、Git commit／push 均有明确计数；
- 文档里没有把“候选”“实验”“讨论”偷换成生产默认。

## 当前 R05 的身份

R05 是 immutable R04 的派生新版本；R01、R02、R03、R04 都保留原字节，不原位回写。它只吸收 CZ 2026-08-09 拍定的五项差量，不刷新同日实验流水。

根 `AGENTS.md` 的最小入口只把复杂任务带到 R05，再按任务路由到真源；它没有创建第二套 CURRENT。


CZ 已接受八份文件结构，并要求把 R05 作为各方共读的本地材料文件夹，也让仓库 Agent 自动找到它。它只统一“大家怎样理解项目”，不把下面这些开放问题自动销账：

1. A v2.7 的 74 组逐来源权利票和当前训练执行锁；
2. Reality Packet Notion 页面 ID 与当前账序祖先链的身份差异；
3. Production Canonical、真实 blind 和训练执行权仍未建立；
4. Mini／Lite 的精确模型、账号能力、预算和执行合同仍未冻结。

这些问题变动时发下一版，不在 R05 原位改字。CURRENT 职责冲突已由 W06-D2 正式销账，Mini／Lite 的角色顺位已由本版销 P0-05。R05 的“当前”不等于其他 P0/P1 已经解决。
