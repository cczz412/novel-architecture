# 跨章上下文：实体账本、前文参考与未来污染防护

## 1. 直接回答

### 只做第3章，会不会参考第1～2章？

推荐做法是：**参考，但只参考程序生成的前文状态账本；不把第1～2章全文重复塞入请求。**

### 只做第4章，会不会参考第1～3章？

同样参考 prior-only 状态账本。第4章的证据短引仍必须全部来自第4章。

### 能不能把第1～50章一次性都给模型？

技术上有些模型可能装得下，方法上不推荐。当前章抽取需要聚焦、清晰的来源边界；全书输入会造成注意力稀释、未来泄漏、成本上升和错误归章。

### API 会自动记住前一次调用吗？

普通无状态 API 调用只看本次发送的消息。即使应用层维护了对话，也不能把“可能仍在窗口里的历史”当成可靠数据库。应由本地程序显式保存和发送经过压缩、版本化的状态账本。

---

## 2. prior state 的职责

prior state 只解决四件事：

1. **别名消歧**：同一人物在前文已经出现过哪些称呼；
2. **代词消歧**：当前段落的“他／她／队长／哥哥”可能指谁；
3. **首次出场判断**：实体是否已在前文出现；
4. **关系／状态基线**：当前章的关系或状态是不是新变化。

它不负责：

- 提供本章证据；
- 替当前章补充未重述的事实；
- 告诉模型后文会发生什么；
- 提供未来别名、未来身份、未来关系、未来出现次数；
- 直接生成正式证据条目。

## 3. 推荐账本结构

```json
{
  "schema_version": "novel-prior-state-v2",
  "through_chapter": 2,
  "source_evidence_set_sha256": "…",
  "entities": [
    {
      "entity_id": "P0001",
      "entity_type": "person",
      "canonical_name": "周明瑞／克莱恩·莫雷蒂",
      "names_confirmed_through_chapter": ["周明瑞", "克莱恩·莫雷蒂", "克莱恩"],
      "do_not_use_yet": ["愚者"],
      "confirmed_state": [
        {
          "statement": "周明瑞在陌生世界醒来，并处于克莱恩·莫雷蒂的身体与生活环境中。",
          "evidence_ids": ["E-01-09", "E-01-11"]
        }
      ],
      "relationships": [
        {
          "other_entity_id": "P0002",
          "relation": "兄妹",
          "status": "confirmed",
          "evidence_ids": ["E-01-16"]
        }
      ],
      "first_seen_chapter": 1,
      "last_seen_chapter": 2
    }
  ],
  "places": [],
  "organizations": [],
  "objects": [],
  "open_threads": [
    {
      "thread_id": "T0001",
      "statement": "克莱恩头部枪伤与存活原因尚未得到解释。",
      "evidence_ids": ["E-01-25", "E-02-12"],
      "status": "open"
    }
  ]
}
```

关键点：

- `through_chapter` 必须小于当前章；
- 每个状态带证据 ID；
- `do_not_use_yet` 可由全局知识库生成，但更安全的做法是根本不把未来名字送入模型；
- 账本只保留对消歧有用的压缩状态；
- 不保存“第1～20章出现597次”这类统计噪声。

## 4. 第3章 prior state 示例

处理第3章时，只需要类似下面的精简信息：

```json
{
  "through_chapter": 2,
  "people": [
    {
      "id": "P001",
      "known_names": ["周明瑞", "克莱恩·莫雷蒂", "克莱恩"],
      "context": "当前叙事主体；周明瑞拥有克莱恩的身体与残缺记忆。",
      "first_seen": 1
    },
    {
      "id": "P002",
      "known_names": ["梅丽莎"],
      "context": "克莱恩的妹妹；前文被提及，尚未在场景中完整出场。",
      "first_seen": 1
    },
    {
      "id": "P003",
      "known_names": ["班森"],
      "context": "克莱恩和梅丽莎的哥哥，家庭主要收入来源。",
      "first_seen": 1
    }
  ],
  "objects": [
    {
      "id": "O001",
      "known_names": ["左轮手枪"],
      "context": "原主死亡现场出现的手枪，来源未明。"
    }
  ],
  "open_threads": [
    "枪的来源、原主是自杀还是他杀、笔记句子含义仍未解决",
    "周明瑞计划尝试与穿越前有关的转运仪式"
  ]
}
```

注意：

- 不能出现“愚者”；
- 不能出现第3章以后才知道的值夜者、塔罗会等信息；
- “计划尝试转运仪式”只能帮助理解开头的“确定了计划”，不能直接作为第3章短引证据。若第3章未明确重述计划内容，证据句应保守表达。

## 5. 第4章 prior state 示例

处理第4章时，账本可以在第3章验收后增加：

```json
{
  "through_chapter": 3,
  "people": [
    {
      "id": "P002",
      "known_names": ["梅丽莎"],
      "new_confirmed_state": [
        "十五岁",
        "廷根技术学校蒸汽与机械系学生",
        "喜欢齿轮、发条和轴承，立志成为蒸汽机械师"
      ]
    }
  ],
  "world_facts": [
    "北大陆历法有十二个月、一周七天",
    "北大陆存在七位正统神灵"
  ],
  "pending_actions": [
    "周明瑞需要购买面包、羔羊肉和豌豆",
    "周明瑞仍想尝试转运仪式"
  ]
}
```

第4章模型可借此识别“买菜”和“转运仪式材料”的连续性，但第4章正式证据只能引用第4章正文。

## 6. 账本更新流程

第N章正式证据通过验收后：

1. 从证据中筛选人物、别名、身份、关系、地点、组织、物品和开放线索；
2. 与第N-1章账本比较；
3. 产生 `state_delta`；
4. 程序应用增量，形成 `through_chapter=N` 的新账本；
5. 保存前后账本 SHA；
6. 第N+1章只接收新账本。

可由模型生成建议增量，但程序必须校验每项 `evidence_ids` 存在且章号不超过N。

## 7. State Updater Prompt

### System Prompt

```text
你是“小说前文状态账本更新器”。输入只有 PRIOR_STATE 和本章已验收证据 ACCEPTED_EVIDENCE。

你只输出由证据直接支持的状态增量：
- 新实体；
- 新别名；
- 身份／职业／年龄／能力／资源变化；
- 新地点、组织和物品；
- 关系建立、变化或终止；
- 开放线索建立、更新或关闭。

每个增量必须引用本章 accepted evidence ID。不得利用原文之外信息，不得预测后文，不得把人物猜测升级为事实。人物说法只能记录为“某人曾这样说／认为”。

只输出 JSON。
```

### 输出示例

```json
{
  "schema_version": "novel-state-delta-v2",
  "chapter": 3,
  "new_entities": [],
  "entity_updates": [
    {
      "entity_id": "P002",
      "add_attributes": [
        {
          "statement": "梅丽莎十五岁，是廷根技术学校蒸汽与机械系学生。",
          "assertion_mode": "narrator_fact",
          "evidence_ids": ["E-03-08"]
        }
      ]
    }
  ],
  "relationship_updates": [],
  "new_open_threads": [],
  "resolved_threads": []
}
```

## 8. 首次出场如何判定

“首次出场”不能只靠当前章模型猜。程序规则：

```text
如果实体 canonical_id 不在 prior state：
    当前章第一次出现位置 = 首次出现候选
否则：
    不是首次出现
```

还要区分：

- **首次被提及**；
- **首次在场景中出现**；
- **首次公开姓名**；
- **首次确认身份**。

例如某角色第1章被提及，第3章才正式进场；这可以生成不同事实，但不能都叫“首次出场”而不说明口径。

推荐内部字段：

```json
{
  "mention_status": "first_mention | first_scene_appearance | first_named | existing"
}
```

最终 Markdown 可根据用户规则选取需要的口径。

## 9. 关系变化如何判定

当前章抽取器记录本章明示事实，例如：

- A称B为哥哥；
- A接受B的邀请；
- A与B达成交易；
- A开始怀疑B；
- A拒绝B。

State updater 与 prior state 比较：

- prior 无关系 → `established`；
- prior 有相同关系 → `continued`；
- prior 关系内容改变 → `changed`；
- 原文明确终止 → `ended`；
- 只有人物猜测 → 记录为态度，不改客观关系。

## 10. 防止未来泄漏的硬规则

每次请求发送前，本地程序检查：

```python
assert prior_state["through_chapter"] == current_chapter - 1
assert max(all_referenced_evidence_chapters) < current_chapter
```

还应维护 `alias_first_confirmed_chapter`：

```python
for alias in injected_aliases:
    assert alias.first_confirmed_chapter < current_chapter
```

任何包含以下字段的注入都应拒绝：

- `future_appearance_range`；
- `total_occurrence_count`；
- `later_identity`；
- `eventual_relationship`；
- 后文章节号；
- 从全书索引反推的当前章未知身份。

## 11. 状态账本长度控制

当人物越来越多时，不要把所有实体全部注入每章。先做检索：

1. 收集当前章文本中出现的姓名、称谓和高频代词；
2. 从账本选取相关人物、关系、地点和开放线索；
3. 加入少量全局核心实体；
4. 总长度设上限；
5. 未检索到的实体不注入，但仍可由当前章重新抽取。

可以使用字符串匹配、别名字典和轻量检索，不必先调用模型。

## 12. 不要依赖单一长对话

长对话看似“有记忆”，但存在：

- 早期消息被截断或压缩；
- 隐式上下文无法版本化；
- 某次错误会持续污染后续；
- 无法精确重放；
- 很难证明第N章只使用了第N章以前的信息。

显式 prior state 可哈希、可审计、可回滚，是本地批处理更可靠的做法。
