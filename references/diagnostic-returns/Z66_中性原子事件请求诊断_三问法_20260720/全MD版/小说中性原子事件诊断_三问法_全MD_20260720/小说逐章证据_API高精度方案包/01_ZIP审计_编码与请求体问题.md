# 当前 ZIP 审计：编码、请求体与抽取误差来源

## 1. 审计范围与证据边界

归档 `全量打印(1).zip` 共含 30 个 ZIP 条目：

- 15 个有效文件；
- 15 个 `__MACOSX/._*` AppleDouble 元数据文件；
- 有效文件中包含 8 份“完整请求体”、索引、结构差异摘记和若干回执；
- 归档主要保存的是**历史请求体与诊断回执**，不是完整模型响应集合，因此无法从本包逐项复原第4章等所有实际输出错误；
- `z60_base_ch0003_完整请求体.md` 内嵌了第3章已落盘的10条中性事件池，因此可以直接审计这部分结果。

## 2. 乱码实际上有两类

### 2.1 ZIP 中文文件名编码错误：已确认

ZIP 条目的通用位标志为 `0x8`，没有设置 UTF-8 文件名标志 `0x800`。文件名实际字节是 UTF-8，但部分库会按 CP437 解码，于是：

```text
z60_entity_ch0003_σ«îµò┤Φ»╖µ▒éΣ╜ô.md
```

实际应为：

```text
z60_entity_ch0003_完整请求体.md
```

这解释了为什么命令行 `unzip` 可能显示正常，而 Python `zipfile`、部分 Windows 工具或其他服务会显示乱码。临时修复可采用：

```python
fixed = broken_name.encode("cp437").decode("utf-8")
```

但根本修复应在**创建 ZIP 时**使用真实 Unicode 路径，让写入库设置 UTF-8 标志，并在交付前机械验收。

### 2.2 文件正文编码：未发现损坏

15个有效文件均能用严格 UTF-8 解码：

- `U+FFFD` 替换字符数量：0；
- NUL 与异常控制字符数量：0；
- 因此正文里看到的“乱”主要不是字节损坏，而是排版和输入切片造成的语义碎裂。

## 3. 打印／渲染异常：超长单行

五份默认请求体把整个锚点 JSON 数组压成一行。最长单行如下：

| 文件 | 最长单行字符数 |
|---|---:|
| `default_ch0003_完整请求体.md` | 14,865 |
| `default_ch0004_完整请求体.md` | 18,144 |
| `default_ch0005_完整请求体.md` | 15,852 |
| `default_ch0013_完整请求体.md` | 14,880 |
| `default_ch0019_完整请求体.md` | 16,697 |

常见后果：

- Markdown 预览器卡顿或水平滚动；
- 打印转 PDF 时超出页面、缩成极小字号或截断；
- 某些编辑器自动折行后，JSON 可读性接近于零；
- 出错位置无法按行定位。

改法：请求日志使用漂亮格式化 JSON；正式证据 Markdown 一条证据一行；原始结构化数据另存 JSON／JSONL。若交付被限定为 Markdown，也应把 JSON 代码块按对象逐行格式化，避免任何超过几百字符的行。

## 4. 当前默认请求到底给了模型什么

五个默认靶章的结构一致：

- 模型：`deepseek-v4-flash`；
- `temperature=0.2`；
- `max_tokens=16000`；
- `n=1`；
- `reasoning_effort=medium`；
- `response_format={"type":"json_object"}`；
- system 只有33个字符：

> 你只做证据约束的中性事件摘取，不做类型判断。只输出合法 JSON。

模型没有看到完整连续正文，而是看到“冻结证据目录”：每个 `anchor_id` 对应约22～31个字符，连续片段通常只重叠4个字符。

## 5. 短片供料的量化问题

| 章 | 完整章字符 | 锚点数 | 平均短引 | 序列化目录字符 | 目录／正文 | 在清晰边界开头 | 在标点边界结尾 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 3 | 3,366 | 175 | 23.5 | 12,078 | 3.59倍 | 0.0% | 3.4% |
| 4 | 4,182 | 215 | 23.8 | 14,918 | 3.57倍 | 0.9% | 2.8% |
| 5 | 3,666 | 184 | 24.4 | 12,917 | 3.52倍 | 3.3% | 7.1% |
| 13 | 3,369 | 172 | 23.8 | 12,113 | 3.60倍 | 2.3% | 6.4% |
| 19 | 3,736 | 197 | 23.1 | 13,699 | 3.67倍 | 3.0% | 5.1% |

这是一种“花了约3.6倍字符，却丢掉了句法结构”的供料方式：

- 几乎所有短引都从句中开始、在句中结束；
- 模型必须从多个 ID 中重新拼接人物、动作、否定和结果；
- JSON 键名、章号和重复文本占用大量上下文；
- 断开的短引更容易把“人物猜测”改写成“客观事实”。

发送3,000～5,000字的完整章节，通常比发送12,000～15,000字的碎片目录更聚焦、更便宜，也更容易核验。

## 6. 任务合同与目标直接冲突

当前 Prompt 中有两句是系统性漏项的核心：

> 找出以后可能被继续读取的原子事件。

> 普通动作、气氛描写、无后续读取价值的场景复述不凑数。

问题在于：

1. 模型被禁止使用后文，却被要求判断“以后会不会被读取”；这是无法可靠完成的预测任务。
2. 用户真正需要的是“事件动作、人物首次出场与身份、地点、组织、体系、关系变化都算证据，宁多勿漏”；当前合同主动把大量可核验事实排除。
3. 不做类型判断意味着没有人物／地点／规则等覆盖清单，模型会天然偏向显眼剧情动作。
4. 不同题材小说的“后续价值”差异极大，Prompt 会在悬疑、恋爱、历史、群像、系统文中表现不稳定。

正确顺序应是：**先按明确类别高召回抽事实，再由后续组件判断用途**。

## 7. 第3章事件池暴露出的精度与召回问题

当前已落盘事件池只有10条。它保留了“确定计划、审视记忆、面试、藏枪、伤口愈合、怀表、购物、上学、转运仪式”等少量动作，却漏掉了大量明确事实，例如：

- 克莱恩记忆和知识均有残缺；手枪来源、自杀或他杀、笔记文字含义等仍未明确；
- 梅丽莎的教育背景、年龄、专业、理想与学费；
- 班森供职公司受南大陆局势影响、裁员超过三分之一，班森为保住工作承担加班与出差；
- 克莱恩因家庭背景在古弗萨克语等方面落后，靠熬夜早起才以中等成绩毕业；
- 父亲遗留怀表、梅丽莎表现出的机械天赋；
- 公共马车费率、步行到学校约五十分钟、梅丽莎为省钱步行；
- 北大陆历法与七位正统神灵；
- 周明瑞明确想回家。

这些都属于目标要求中的人物、身份、地点、社会规则、数字、组织／神祇、动机或未决问题，不应被“无后续价值”过滤。

### 7.1 一条明显过度概括

事件池写道：

> 梅丽莎修好怀表并还给周明瑞。

本章现场直接显示的是：周明瑞没有正确操作怀表；梅丽莎拔起按钮转动，使秒针走动，并根据钟声校准时间后归还。此前叙述只说梅丽莎最近“宣称将它修好了”。更稳妥的原子事实应拆为：

- 梅丽莎拔起怀表按钮转动，使停住的秒针重新走动；
- 梅丽莎根据教堂六下钟声调整怀表时间，并把怀表还给周明瑞。

“修好”把历史说法、当前操作和结果合并，精度下降。

### 7.2 一条证据锚不完整

事件池写道：

> 梅丽莎打开大门，离开家去上学。

所引锚点只覆盖“准备出门”和“打开门后又停下说话”，没有引用后文真正的“关门离开”。这说明“短引 ID 合法”并不等于“短引完整支持事实”。必须进行**精确短引子串＋语义支持**双重校验。

### 7.3 低信息事件挤占高价值事实

“周明瑞确定了计划”没有写明计划是什么，信息密度很低；“答应购物要求”被保留，但人物身份、教育制度和七神体系被遗漏。问题不在单条真假，而在抽取优先级与目标不一致。

## 8. 实体表注入存在未来泄漏

第59／60道实体表把以下信息作为 system 消息注入第3章：

- `克莱恩.莫雷蒂＝克莱恩＝周明瑞＝愚者`；
- 实体在“第1～20章”的出现范围与次数；
- `转运仪式`在第7、13～14、16、19章的未来出现范围；
- “愚者”这一别名在第3章尚未建立；
- “克莱恩自杀”被直接命名为事例，但第3章文本仍以“暂时算自杀吧”保留不确定性。

这与“只看当前章、不得使用本章之后知识”冲突，而且因其位于 system 层，污染风险更高。

实体表的正确形态应是：

- 只包含**当前章之前**已经确认的信息；
- 不包含未来出现章、未来次数、未来别名；
- 每项带来源证据与首次确认章；
- 明确声明“只用于消歧，不可作为本章证据”。

## 9. 无关元数据被送入模型

请求体的用户消息末尾包含：

```text
来源：Codex
```

这不是小说正文，也不是抽取规则，却位于模型可见消息中。它不一定单独造成严重错误，但说明日志／工件层与模型输入层没有完全隔离。任何“来源、回执、调试注释、导出说明”都应留在程序日志，不应进入内容 Prompt。

## 10. 下游无法补回上游漏项

第60道“大纲／逻辑句”只接收已经落盘的10条中性事件。只要第一步漏掉人物身份、地点或规则，第二步无论多聪明都不能补写，因为它被明确禁止补正文事实。

因此：

- **第一步必须高召回**；
- 第二步应先做“对照全文补漏”，再做编排；
- 大纲和逻辑句不能兼任证据恢复器。

## 11. 参数不是首要矛盾

`temperature=0.2`、JSON 模式和较大的输出上限并不能修复上述结构问题：

- 降温只能减少随机性，不能补回被 Prompt 排除的类别；
- 合法 JSON 只保证语法，不保证事实支持；
- 换更强模型会改善一些拼接，但仍会被错误合同稳定地引向漏项。

根因优先级建议按以下顺序处理：

1. 任务合同与覆盖目标；
2. 完整正文供料与行号；
3. 独立审校／补漏；
4. prior-only 跨章状态；
5. 确定性渲染与编码；
6. 最后才是模型与采样参数。
