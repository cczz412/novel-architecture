# 本地实施步骤

## 改请求生成器

你可以直接理解成：同一章给模型两份视图。

- **连续正文**：让模型读懂剧情。
- **锚目录**：让模型返回下游能校验的 anchor_id。

不要再让175个短锚承担“正文阅读器”的职责。

## 保持参数做单变量试验

先沿用现役模型与参数，只替换 system/user。`02_修正版请求体_第3章可直接发送.json` 已按这个原则生成，便于直接对照旧请求。

## 调用后先跑机械校验

这是检查输出文件能否进入后续链的命令：

```bash
python tools/validate_event_output.py   --output 04_第3章完整抽取结果.json   --anchors appendix/第3章冻结证据目录.json   --chapter 3
```

脚本会检查：

- JSON 外壳和字段；
- event_id 是否连续；
- anchor_id 是否存在、重复；
- event 是否有明显代词开头、空泛短语或过短句子。

它不能判断剧情语义是否完全正确，所以仍要用金标或语义复核。

## 接口支持严格 Schema 时

把主请求的 `response_format` 替换为 `02B_接口支持时可替换的严格response_format.json` 中的值。上线前要先确认你们供应商确实支持 `json_schema` 和 `strict`；不支持时继续用 `json_object`，在本地校验。

## 生产建议

```text
生成请求
→ 一次模型调用
→ 本地机械校验
→ 语义抽检／评分
→ 通过入库
→ 失败项定点修复或人工处理
```

机械错误可以用程序修：编号重排、去重、删除无效字段。语义错误不要用字符串替换硬修，应进入定点修复调用或人工复核。

## 先跑哪批章

用你们已有的第3、4、5、13、19章五靶章做第一轮，因为归档里已经有旧请求。新旧请求保持相同参数，对比同一金标。确认收益后再扩到20章，不要直接全量上线。

## 结果怎样才算真的进步

- 不只看 JSON 能不能解析。
- 不只看事件条数是否接近14。
- 要看每条是否能独立读懂、锚是否覆盖全句、有没有把猜测写成事实、有没有漏掉重要状态变化。
- 同义正确句应通过语义评分，不要只按字符串相等判死刑。
