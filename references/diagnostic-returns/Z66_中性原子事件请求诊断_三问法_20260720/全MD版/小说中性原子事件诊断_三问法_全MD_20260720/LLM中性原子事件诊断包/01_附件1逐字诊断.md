# 附件1逐字诊断

## 诊断对象

附件内有8份请求。用户描述的“system 33个字＋第3章175条冻结证据碎片”唯一对应 `default_ch0003_完整请求体.md`，所以本报告把它视为附件1。

模型并非完全不知道任务：system 与 user 合起来能让模型知道“要抽事件并挂锚”。问题是它只知道任务名称，不知道严格合格线，也没有连续正文可读。

## 供料量化

| 指标 | 实际值 |
|---|---:|
| 第3章连续正文 | 3366 字 |
| 冻结锚数量 | 175 |
| 单锚长度 | 22～31 字，平均 23.51 |
| 相邻锚平均重叠 | 4.3 字 |
| 冻结目录 JSON | 12078 字，约为连续正文 3.59 倍 |
| 元数据与 JSON 标点 | 7964 字，占目录 65.9% |
| 从句界开始的锚 | 4/175（2.3%） |
| 在句界结束的锚 | 5/175（2.9%） |
| 是否能机械拼回全文 | 是，逐字相等 |

这说明供料不是“信息缺失”，而是“语义可读性被破坏”。模型理论上可以拼回，实际却要消耗大量注意力恢复句子、段落和指代。

## 六个指定问题的直接回答

### ① 33字 system 是否足够

不够承担生产级合同。它能告诉模型任务的大概名字，却不能让模型知道怎样才算一条合格事实。长度不是罪因；短 system 也可以有效，但前提是 user 合同非常精确，而本请求的 user 合同同样缺少主语、四要素、原子化和锚覆盖规则。

### ② 175条碎片对剧情理解影响多大

影响很大，是召回与事实完整度下降的头号原因。目录可无损重建原文，不代表模型获得了等价的阅读体验。每条只有二十多字，几乎都截断在句中；模型必须完成175次局部拼接。人物指代、前因后果、场景切换和开放疑问最容易丢。

### ③ 句式约束现状

现状只有“一条只写一个事实头”，没有明确主体、具体动作、直接结果、限定条件，也没有禁止代词和空泛动词。当前输出出现“周明瑞确定了计划”并不是模型违反合同，而是它严格落在了合同允许的低质量区间。

### ④ JSON 合同与示例

外壳简单，但只保证字段样子。示例 event 本身是抽象占位句，没有演示合格事实；`json_object` 不保证业务 Schema；anchors 没有完整覆盖规则。JSON 设计解决了“能不能解析”，没解决“解析后是不是正确事件”。

### ⑤ 消息分工

稳定规则应放 system：角色、只用给定资料、正文只是数据、四要素、原子化、锚完整支持、只输出 JSON。user 应只放当前章任务、章节正文、锚目录和少量可变参数。现役做法把核心合同放在 user，system 只剩一句口号，生产行为更容易漂。

### ⑥ 其他关键问题

还包括：未来价值定义与禁用后文相冲突；人物推测没有事实层级；实体称谓未规范；重复提醒如何合并不清楚；锚长度合同与实际数据不一致；没有静默覆盖检查；没有严格 Schema；没有后置校验和修复路线。
