# 修正版请求体：每处改动与理由

主文件 `02_修正版请求体_第3章可直接发送.json` 保留了现役的模型、温度、最大输出、样本数、思考档和 `json_object` 返回方式，只改写 system 与 user。

| 编号 | 改动 | 为什么改 | 预期效果 |
|---:|---|---|---|
| 1 | system 从33字扩为稳定合同 | 把角色、资料边界、四要素、原子化、事实层级、锚覆盖和输出限制放到最高优先级。 | 模型不再只知道任务名，而是知道哪些规则不能让步。 |
| 2 | 声明正文只是数据 | 防止小说对白、作者附言或嵌套文本被误当作指令。 | 降低提示注入与作者附言污染。 |
| 3 | 同时提供连续正文 | 让模型按正常阅读顺序理解人物、场景、指代和因果。 | 这是召回和语义正确性收益最大的改动。 |
| 4 | 保留原冻结证据目录 | 下游仍可机械校验 anchor_id，现有锚合同不丢。 | 理解视图与证据视图分工明确。 |
| 5 | 改掉“预测以后价值” | 改用可观察的准入标准：状态变化、明确安排、信息发现、关系／目标／持续处境。 | 减少模型猜未来造成的随机性。 |
| 6 | 定义 event 四要素 | 每条必须有明确主体、具体动作、直接结果／对象、原文限定。 | 直接解决模糊句、缺主语和信息不全。 |
| 7 | 禁止代词主体与空泛动词 | 列出“他／她／对方／这件事”“确定计划／处理／发生变化”等禁区。 | 让事件脱离上下文仍可读。 |
| 8 | 保留不确定性 | 人物猜测必须写成“某人认为／怀疑／可能”。 | 避免把角色判断污染为客观事实。 |
| 9 | 给出拆分与合并规则 | 触发与直接结果可同句；独立动作拆开；重复提醒合并；同一请求中的物品可同条。 | 原子粒度更稳定。 |
| 10 | 强化锚完整支持 | 多个短锚要共同覆盖姓名、动作、结果、限定；锚截断时继续补相邻锚。 | 解决“ID合法但证据不完整”。 |
| 11 | 要求锚排序、去重、最小化 | 方便下游机械检查和人工回读。 | 减少无关锚与重复锚。 |
| 12 | 加入正反例 | 直接用现役最典型错误展示为什么不合格。 | 模型更容易对齐质量标准。 |
| 13 | 加入静默全章检查 | 要求模型在最终输出前逐段检查漏项和锚覆盖，但不输出推理过程。 | 提高召回，不污染 JSON。 |
| 14 | 定义空结果 | 没有事件时输出 events: []。 | 避免模型编造占位事件。 |
| 15 | 删除文件名与来源噪声 | 章节标题可留在正文，额外文件名和“来源：Codex”不参与任务。 | 减少无关 token。 |
| 16 | 保留现役模型与采样参数 | 本次只改消息合同和供料，便于做单变量 A/B。 | 可以把收益归因到 Prompt 与输入结构，而不是参数变化。 |
| 17 | 另给严格 JSON Schema 片段 | 主请求保持现役 json_object 兼容；接口支持时可换成约束解码。 | 可机械保证字段、类型和 anchor_id 枚举，但不能保证语义。 |

## 对 JSON 输出合同的判断

- `event_id/event/anchors` 三个字段保留，满足下游接口。
- 主请求继续使用 `response_format: {"type":"json_object"}`，避免供应商兼容风险。
- `02B_接口支持时可替换的严格response_format.json` 给出可选的严格 Schema。它能限制字段和 anchor_id，却不能证明 event 的语义真的被锚支持。
- 语义正确性仍由强合同、连续正文、锚规则、回归金标和后置校验共同承担。
