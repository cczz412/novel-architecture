# 实施顺序：从最小改造到高精度

## 0. 先冻结现役版本

在改 Prompt 前保存：

- 当前 runner；
- 当前 system／user Prompt；
- 当前 Schema；
- 模型与参数；
- 第3、4、5、13、19章现有请求和响应；
- 人工认可的金标；
- 所有 SHA。

不要边改代码边覆盖旧产物，否则无法判断哪项变化真正有效。

## 1. 第一优先：修复编码和交付格式

### 必做

- ZIP 解压时跳过 `__MACOSX`、`._*`、`.DS_Store`；
- 严格 UTF-8，必要时 GB18030 回退，不用 `errors=ignore`；
- 修复历史 ZIP 中文名或重新打包；
- 新 ZIP 验证中文名 `flag_bits & 0x800`；
- Markdown 不嵌入一整行大型 JSON；
- 正式证据一条一行；
- ZIP CRC 测试。

### 这一阶段能解决

- 中文文件名乱码；
- 多余隐藏文件；
- 打印／PDF 横向溢出；
- 日志难读。

### 不能解决

- 抽取漏项；
- 事实过度概括；
- 未来知识污染。

## 2. 第二优先：取消固定字符短引目录

把输入从：

```text
175～215个、平均约23字、句中截断的 anchor
```

改为：

```text
完整当前章＋稳定段落／句子行号
```

输出短引由模型选择，程序验证为当前章子串。

这是事实准确率提升最大、改动收益最高的一步。

## 3. 第三优先：改写第一步任务合同

删除：

```text
以后可能被继续读取
普通动作、无后续价值不凑数
不做类型判断
```

替换为：

```text
按16类逐段检查，宁多勿漏；
类别只用于内部覆盖，最终 Markdown 可隐藏；
人物说法、猜测、计划保留模态；
每条只写一个原子事实。
```

先在第3、4、5、13、19章回归，不立刻扩全书。

## 4. 第四优先：加入机械校验

在任何第二次模型调用前实现：

- JSON Schema；
- 章号；
- temp_id；
- line_id；
- quote 连续子串；
- 输出截断；
- 非法字符；
- 当前章未出现的未来别名；
- 最终编号由程序生成。

机械校验稳定后，才值得增加语义审校。

## 5. 第五优先：加入独立 Gap Finder

最小高收益多调用方案：

```text
综合抽取一次
  +
全文补漏一次
  +
只修问题的选择性调用
```

先不急着双抽取器。通过回归集判断：

- 人物／地点／规则类别是否仍频繁漏；
- 如果漏项仍明显，再拆 Extractor-A／B。

## 6. 第六优先：建立 prior-only 状态账本

删除第59／60道全1～20章实体表。建立：

```text
through_chapter = current_chapter - 1
```

只注入：

- 已确认别名；
- 相关人物／地点／组织；
- 既有关系；
- 开放线索；
- 首次出现基线。

每项带前文章节证据 ID；禁止未来范围、次数和别名。

## 7. 第七优先：双抽取器

当单抽取＋Gap Finder 已稳定，再比较：

- 综合单抽取；
- A动作关系＋B实体设定双抽取。

用金标看类别召回和整体准确率，不以输出条数定胜负。

## 8. 第八优先：增强审校模型

若预算允许：

- 首轮用快速模型；
- Verifier／Gap Finder 用更强或不同模型；
- Repairer 可用首轮模型；
- 高风险条目进入人工队列。

不要先换模型、后改 Prompt；那样难以判断收益来自哪里。

## 9. 推荐上线闸门

### 阶段 A：五章试点

章节：3、4、5、13、19。

必须达到：

```text
JSON／引用机械通过率 = 100%
未来泄漏 = 0
明显过度推断 = 0
主要类别召回明显高于现役
```

### 阶段 B：20章扩展

检查：

- 人物别名累积；
- 状态账本长度；
- 关系变化；
- 超长章节分块；
- 总成本和重试率；
- 不同叙事节奏。

### 阶段 C：跨题材回归

至少覆盖悬疑、恋爱、玄幻／系统、历史／权谋、群像。

### 阶段 D：全书

只有 Prompt、Schema、状态账本和验收门槛冻结后再跑全书。

## 10. 最低可用配置

预算紧张时：

```text
每章1次综合抽取
＋本地机械校验
＋仅低密度／类别空缺章调用Gap Finder
＋仅问题条目调用Repairer
```

必须保留：

- 完整当前章；
- prior-only 状态；
- 原文短引校验；
- 模态规则；
- 最终编号由程序生成。

不能为了省调用恢复到字符滑窗。

## 11. 推荐高精度配置

```text
每章：
1. Extractor-A
2. Extractor-B
3. Verifier
4. Gap Finder
5. Repairer（仅有问题时）
6. State updater（可由模型＋程序，或程序规则完成）
```

其中 A／B 可并行，Repairer 只处理小片段；不是每章都需要第五次事实调用。

## 12. 一次作业的状态机

```text
PENDING
  → PREPROCESSED
  → EXTRACTED_A
  → EXTRACTED_B
  → MECHANICALLY_VALID
  → VERIFIED
  → REPAIRED
  → GAP_CHECKED
  → ACCEPTED
  → RENDERED
  → STATE_UPDATED
```

任一步失败就停在该章，不应继续用坏结果更新状态账本。

## 13. 上线前最后检查

```text
[ ] 当前章全文而非字符滑窗
[ ] prior state 只到上一章
[ ] 动态状态不放 system
[ ] 不含来源／回执元数据
[ ] 覆盖16类
[ ] 保留说法／猜测／计划模态
[ ] quote 为当前章连续子串
[ ] 独立补漏
[ ] 最终ID程序生成
[ ] 一条证据一行
[ ] UTF-8 ZIP标志正确
[ ] 旧版本可重放
[ ] 回归集通过
```

## 14. 结果预期

采用上述顺序后，通常会先看到三类改善：

1. **乱码与打印**：中文文件名、隐藏文件、超长行问题立即消失；
2. **召回**：人物身份、地点、规则、数字和关系不再被第一步主动过滤；
3. **准确**：猜测写实、短引不完整、复合事实等问题被独立审校拦截。

真正决定能否接近人工效果的，不是把更多正文“注入一次 API”，而是让程序把阅读任务拆成可核验的多个环节，并把每一步的证据边界锁死。
