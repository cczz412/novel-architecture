# 一次 API 调用能否保证达到高质量

## 结论

✅ 一次调用可以做到“高首轮通过率”。

❌ 一次生成无法保证“100% 语义正确、100% 不漏、100% 与人工金标逐字一致”。温度设为0也不等于绝对确定，更不等于语义正确。

可保证与不可保证要分开看：

| 项目 | 一次调用能否保证 | 做法 |
|---|---|---|
| JSON 可解析 | 接口支持严格约束解码时可以接近机械保证 | JSON Schema／constrained decoding |
| 字段齐全、类型正确 | 可以机械保证 | strict schema，禁止额外字段 |
| anchor_id 存在 | 可以机械保证 | 把合法 ID 做成 enum，或本地校验 |
| event_id 连续 | 可以在调用后确定性校验 | 本地脚本 |
| 每条有明确姓名主体 | 可以高概率做到，也可用规则拦截 | Prompt 禁止代词主体＋本地词法检查 |
| 锚真的支持整条事实 | 不能仅靠一次生成保证 | 需要语义校验、二次修复或人工抽检 |
| 全章事件一个不漏 | 不能保证 | 金标回归、覆盖检查、必要时修复调用 |
| 与人工金标逐字相同 | 不应作为绝对目标 | 采用语义匹配与结构评分 |

## 想让“一次 LLM 调用”尽量接近高质量，系统要这样搭

```text
原始章节
  ↓
确定性预处理：保留连续正文；生成稳定 anchor_id；校验锚可拼回正文
  ↓
一次 LLM 调用：强 system 合同＋连续正文＋锚目录＋静默全章检查
  ↓
确定性验收：Schema、ID、顺序、重复、主体、禁用词、锚存在性
  ↓
通过 → 入库
失败 → 不入库；机械问题本地修，语义问题进入修复调用或人工队列
```

🔥 这里的关键不是把“一次 HTTP 请求”神化成“一遍就必然正确”，而是让一次请求只承担它擅长的语义抽取，把结构与机械错误交给程序。

## 一次调用内部也要分两遍工作

可以在 Prompt 里要求模型静默完成下列步骤，但只输出最终 JSON：

1. 按段扫描，建立候选事实清单。
2. 对候选做拆分、去重、四要素改写和锚覆盖检查。
3. 只输出验收后的事件。

这不会增加 API 次数，也不要求模型展示思维过程，却比直接边读边吐事件稳定。

## 真正的生产高可靠方案

建议把“一次调用”定义为首选路径，而不是硬性红线：

- 首轮结果通过全部机械检查且抽样语义检查稳定时，直接入库。
- 只有失败项触发第二次“定点修复”，不要整章重抽。
- 高风险章节或新 Prompt 版本进入人工抽检。
- 每次改 Prompt 都跑固定金标集，达标后再上线。

## 为什么此前 ChatGPT 的抽取效果不能等同于一次浅调用

此前工作拿到了连续正文，先做逐章证据账，再做分类整理，并有跨文件校验和编号检查。外观看起来是一轮交付，内部工作却是多阶段读取、拆分、回看和验收。想复现那种质量，应该复现“完整供料＋明确合同＋多步校验”的工作方式，而不是只复制一句 Prompt。

## 什么时候可以坚持绝不二次调用

业务允许“失败就拒收、不自动修复”时可以：首轮调用后运行本地校验，合格才入库，不合格进入人工队列。这样能保证坏数据不进入系统，但不能保证每一章都一次产出可用结果。

若业务要求每章必须自动产出，同时还要求高召回和高事实正确率，就应允许修复调用。两者同时要求而又禁止任何重试，工程上没有可靠保证。
