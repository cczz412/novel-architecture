# 事实句与大纲谁是主中心：最终裁决
## 结论
✅ **作者工作的唯一主界面应当是“大纲中枢”；系统判断历史真假的唯一权威应当是“事实底账”。**
生成下一章时，模型的主任务来自大纲，但它必须同时受相关事实、状态、规则和未决线约束。不要让模型只看大纲，也不要让模型面对几百条事实自己临场组装剧情。
这套分工最适合你现在的目标：
- 导入已有小说，拆得准，建立用户信任；
- 从第 15 章开始由作者编辑大纲，再生成第 15、16、17 章；
- 几百章后仍能查回前文，不把角色传闻当成真相；
- 同一份大纲可以投影成正文、分镜、剧情卡和互动选择；
- 作者改节奏、收线、加阻碍、调爽点时，不需要直接改底层事实库。
---
## 1. 为什么不能只选事实句
事实原子擅长回答：
- 谁做了什么；
- 状态从什么变成什么；
- 某人知道／相信／计划什么；
- 哪段原文承托这条主张；
- 哪个事项仍未解决。
它不擅长单独回答：
- 这章为什么现在写；
- 哪件事先让读者看见，哪件事后揭露；
- 这章需要压抑还是释放；
- 哪条线两章内必须收；
- 主角、配角、反派各自怎样行动才不降智；
- 哪个事件适合做一张剧情卡，哪个只是一条状态补充。
说白了就是：**事实原子是零件，不是施工图。**
若把事实列表直接交给生成模型，模型还要临场完成聚合、排序、视角选择、节奏设计、信息隐藏和场景化。任务越多，越容易顾此失彼。
---
## 2. 为什么也不能只选大纲
大纲可以写得很合理，但它仍可能：
- 把角色“听说过”写成“已经证实”；
- 忘记某个伤势、资源数量、地点或关系状态；
- 让反派知道他不该知道的信息；
- 把旧章节里的存疑判断升级成既成事实；
- 为了当前爽点，悄悄改掉几十章前的规则。
大纲是可编辑计划，不是历史证据库。它可以压缩、重排、组合和隐藏信息，恰恰因为它会变，所以不能承担真值源职责。
Microsoft 的 Event Sourcing／Materialized View 设计可用来类比：底层事件记录保存可追溯变化，面向查询和界面的视图可以反复重建。这里不是要求照搬微服务，而是借它的分工：**事实底账保历史，大纲和卡片做可重建视图。** [Event Sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)｜[Materialized View](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)

### 关键原则
- 大纲里不复制整份事实，只存 ID 引用和本章计划。
- 事实底账不塞“这一章要更爽”“三章内收尾”这类作者要求。
- 卡片不反过来改大纲；卡片发现问题时，修改大纲或事实，再重建卡片。
- 生成模型不直接扫全库，由程序编译执行包。
---
## 4. 两种工作流必须分开
你的系统实际上有两条方向相反的链。若不分开，“计划”会被误当成“事实”。
### A. 导入已有正文
```plain text
冻结正文
→ 证据限定式事实抽取
→ 事实硬闸
→ 状态／因果／未决／规则建账
→ 投影为章节大纲
→ 大纲合理性检查
```
这里的核心标准是：**抽到的历史必须能回到原文。**
### B. 没有正文，作者从大纲继续写
```plain text
作者编辑本章大纲
→ 产生 plan_event
→ 编译章节执行包
→ 生成正文
→ 计划—成文实现对账
→ 把真正写进正文的内容登记为 fact
→ 更新状态与长线账
```
🔥 大纲里预定的事件必须用 `plan_event_id`，不能提前发 `fact_id`。
建议的实现状态：
- `planned`：大纲已安排，正文未生成；
- `realized_exact`：正文按计划写成；
- `realized_variant`：核心结果相同，过程或细节变化；
- `omitted`：计划中有，正文没写；
- `contradicted`：正文写成了相反结果；
- `new_unplanned`：正文自行增加了新的可持续事实；
- `deferred`：作者明确移到后章。
### 为什么仍要做成文对账
即使正文由自己的大纲生成，模型也可能：
- 漏掉计划动作；
- 自行补出伤势、道具、知情、承诺；
- 把“试图做”写成“已经做成”；
- 为了语言顺滑改掉因果；
- 在对白中制造新的规则或关系承诺。
不需要把正文从零全抽一遍，但必须围绕 `plan_event` 做差异扫描。这样成本比重抽低，又不会让大纲和正文逐章漂开。
---
## 5. 质量门应该卡在哪里
### 事实门：判断“对不对”
每条事实至少过这些硬项：
1. 事实头完整；
2. 原子边界正确；
3. 否定、情态、时态、强度没变；
4. 发言／相信／计划没有升级成已发生；
5. 主体、客体、归因与作用域正确；
6. 最小证据组完整，允许非连续锚；
7. 跨块重复与别名已归并；
8. 存疑和推断没有混进既成事实。
这与工作基准 v0.2 的 H01–H12、FCR／QCR_full／ASR_full／UCR 是同一路线，应保留。
### 大纲门：判断“好不好用”
大纲还要单独检查：
- 本章入口状态是否接得上；
- 每个关键动作是否有角色目标、已知信息和可用手段；
- 因果链有没有只写结果不写近因；
- 读者知道什么、角色知道什么、世界真相是什么，是否分账；
- 揭露顺序是否制造悬念，而不是制造理解障碍；
- 当前故事线是否推进、合流、暂停或收束；
- 体验合同是否满足：压制长度、释放点、高光、禁写项；
- 本章出口状态是否能供下一章读取；
- 分镜和互动投影是否有足够清晰的动作与状态变化。
### 两道门不能互相抵扣
- 事实全对，但只是流水账：事实门过，大纲门不过。
- 大纲很精彩，但依赖错误历史：大纲门看似过，事实门不过，仍不能生成。
---
## 6. “抽够大纲所需事实就行”为什么仍不够
这句话只有在“所需事实”有一个独立清单时才成立。否则会出现循环：
```plain text
模型没抽到某事实
→ 大纲里看不到它
→ 系统认为大纲不需要
→ 漏项永远不暴露
```
推荐把完成标准改成三层：
### 来源覆盖
每个原文单元都要有处置：
- `SCORE`：包含可持续事件／状态／知情／规则等，需要抽；
- `CONTEXT_ONLY`：只用于理解相邻事实；
- `STYLE_ONLY`：纯氛围、修辞、重复情绪；
- `REVIEW`：有歧义，必须挂票；
- `EXCLUDE`：明确不进入计分，但原文仍保留。
### 事实覆盖
所有 `SCORE` 单元要么关联至少一个合格事实，要么有“无独立事实”的程序／裁判理由。
### 大纲覆盖
所有对后续有用的状态变化、因果端点、未决事项、触发器、读者承诺、规则应用，都要进入对应账或被显式排除。
这比“抽 50 条”更稳定，也能解释为什么某章只有 22 条、某章有 67 条。
---
## 7. 条数怎样控制
✅ **不要要求模型生成固定数量。**
现稿的 25～40 条可以保留为普通章校准带，但只做异常提示：
- 低于带宽：检查漏项，不强行补；
- 高于带宽：检查过拆、重复、把修辞当事实，不强行截；
- 通过覆盖检查后，条数是多少就接受多少。
真正要稳定的是两种粒度：
- **底层事实粒度**：一个独立账本写入＋一个主情节功能；
- **作者显示粒度**：多个事实组合成 1 个 beat／剧情卡。
例如 58 条事实可以组合成 11 个 beat。作者不需要在 UI 里逐条看 58 句，但系统仍保留底账。
---
## 8. 顺序必须拆成两条
你的判断完全正确：信息先给什么、后给什么，会直接影响悬念和爽点。但这不该只靠“事实句在数组里的位置”。
### `story_order`：故事世界里实际发生的顺序
用来保证：
- 时间连续；
- 状态变化前后正确；
- 因果端点不倒置；
- 插叙不会改写历史。
### `discourse_order`：读者／观众看到的顺序
用来控制：
- 先果后因；
- 隐藏身份；
- 反派视角插入；
- 伏笔、误导、反转；
- 情绪压制与释放。
### 生成时读哪条
- 正文与分镜按 `discourse_order` 生成；
- 一致性与因果审计按 `story_order` 检查；
- 两者用同一批 fact／plan_event ID 连接。
这与叙事研究里 fabula（故事世界发生了什么）和 discourse（如何讲述）的区分一致。长篇小说更不能把两者压成一个线性列表。
---

### 回取优先级

## 10. 冲突与改史规则
### 已发生历史
事实底账优先。作者要改，必须显式选择：
- 改判：原来抽错；
- 设定修订：作者主动改史；
- 后文证伪：旧条标废，新条追加；
- 角色被骗：世界事实不变，只改 belief／known_by。
### 尚未发生计划
大纲可自由编辑。plan_event 不是历史，不需要伪装成事实。
### 已生成但未核准正文
处于候选状态。实现对账完成后才写入事实底账。
---
## 11. 最终推荐句
可以把系统原则写成这一句：
> **事实底账保存“不可随意改写的过去”，大纲中枢编辑“尚可调整的未来”；生成器只读由两者编译出的章节执行包。**
这比“事实句和大纲选一个”更准确，也能同时服务续写、正文体检、AI 动漫分镜和互动叙事。
