# 通用大纲中枢与剧情卡结构
## 结论
✅ 大纲不应是一张“什么字段都塞进去”的大表。推荐做成：
```plain text
一份事实真值库
+ 一份世界／人物状态层
+ 四份长线逻辑账
+ 一份作者体验合同
+ 一份按呈现顺序排列的章节计划
+ 多种可重建投影
```
作者看到的仍是一个大纲工作台；程序内部把不同职责分层，避免事实、计划、推断、展示件互相污染。
---
## 1. 建议拆成四个核心合同
现稿的 `chapter-fact-graph-outline-v1` 把 fact graph 和 outline 写进同一个名字，历史导入时勉强能用，但未来先写大纲时会遇到根问题：**尚未发生的 beat 没有合法 fact_id。**
建议拆为：
### `chapter_fact_graph_v2`
保存已经发生并通过证据门的事实、状态变化和关系。它是只读真值层；更正走追加或版本票据。
### `chapter_plan_v2`
保存作者正在安排的本章计划、beat、体验合同、视角和揭露顺序。里面使用 `plan_event_id`；已发生历史只用 `fact_ref` 引用。
### `chapter_execution_packet_v1`
每次生成前按需编译的小包。它不是数据库，不长期手改。
### `projection_card_v1`
从计划和事实投影出的剧情卡、分镜卡、互动节点。可随 UI、动漫或游戏需求重建。

## 2. 六层结构
### L0｜证据层：原文坐标与来源
回答“这条结论从哪里来”。
核心字段：
- `source_id`
- `chapter_id`
- `source_hash`
- `span_id`
- `line_start`／`line_end`
- `char_start`／`char_end`
- `text_digest`
- `full_text_location`
原文全文不必进入所有消费包，但内部必须能通过 ID 反查。
### L1｜事实层：已经发生的最小可核主张
核心字段：
```yaml
fact_id: F-0012
chapter_id: C0015
subject_ref: CHAR-007
predicate: 获得
object_ref: ITEM-019
result: 持有青铜令牌
polarity: positive
actuality: occurred
assertion_owner: narrator
literalness: literal
qualifiers:
time: 当夜
location_ref: LOC-003
quantity:1
support_span_ids:[S-182, S-187]
state_writes:
-slot: resource
before: 无青铜令牌
after: 持有1枚青铜令牌
storyline_ids:[LINE-02]
```
人类界面可以把它渲染为一句自然语言，但数据库不要只存一句自由文本。
### L2｜状态与知情层
回答“此刻世界和人物处于什么状态”。
建议保留 v0.2 的状态槽：
- knowledge
- belief
- goal
- plan
- physical
- emotion_attention
- role_relation
- resource
- location
- constraint
- habit_skill
每次写入都带：
```plain text
before → delta → after
```
并分清三种视角：
- `world_truth`：世界里实际为真；
- `known_by`／`believed_by`：角色知道或相信；
- `reader_visibility`：读者当前知道多少。
这三个不能合成一个“知情字段”。角色被骗、读者先知、反派隐瞒都依赖分账。
### L3｜长线逻辑层：沿用并接入 R10 四账
R10 v0.3 的 A/B/C/D 四账是正确方向，应保留分立：
<table header-row="true">
<tr>
<td>账</td>
<td>含义</td>
<td>为什么不能并入普通未决事项</td>
</tr>
<tr>
<td>A 跨章因果链</td>
<td>已发生状态变化及直接因、后续用途</td>
<td>它描述已发生的因果骨架</td>
</tr>
<tr>
<td>B 故事内触发器</td>
<td>条件满足时待触发的事件监听器</td>
<td>触发前尚未发生</td>
</tr>
<tr>
<td>C 读者承诺／未兑现</td>
<td>作品向读者形成的期待债</td>
<td>事件发生完，读者债仍可能未还</td>
</tr>
<tr>
<td>D 世界规则条件逻辑</td>
<td>可重复使用的规则、条件与代价</td>
<td>不是一次性事件</td>
</tr>
</table>
v0.2 的 `issue` 仍有价值，但要和 C 分开：
- `issue`：故事内问题／任务／承诺／风险；角色或世界维度。
- `reader_promise`：读者期待是否被回应；叙事体验维度。
### L4｜作者体验合同
回答“这几章必须让读者得到什么体验，以及什么不能丢”。
沿用 R10 v0.3 的六件骨架：
- 硬约束；
- 软偏好；
- 控制项；
- 空值合法；
- 详情 ID 引用；
- `contract_version + read_set_revision` 版本封套。
推荐增加这些可执行槽：
```yaml
must_preserve:
- 不揭露幕后人真实身份
- 主角伤势不能突然痊愈
must_avoid:
- 反派无证据猜中主角计划
- 用巧合解决当前困境
reveal_policy:
reveal_now:[令牌能开启外门]
conceal:[令牌真正来源]
misdirection_allowed:true
pressure_release:
recent_pressure_level: high
this_chapter_target: partial_release
payoff_id: PAYOFF-04
arc_deadlines:
-line_id: LINE-03
action: converge
within_chapters:2
-promise_id: RP-08
action: partial_payoff
within_chapters:3
```
### L5｜章节计划与呈现层
这是作者主要编辑区。核心单位不是事实句，而是 **beat**：一次有明确功能的剧情推进、状态变化、信息揭露或选择点。
一条 beat 可以引用多个事实／计划事件；一个事实也可被不同视角或卡片重复投影。

## 4. beat 最小必填字段
为了兼容小说、分镜和互动，不建议每个 beat 都强制几十个字段。可以分为必填与按需字段。
### 必填
- `beat_id`
- `discourse_order`
- `story_order` 或相对时间关系
- `scene_id`
- `viewpoint_ref`
- `function`
- `preconditions`
- `plan_events`
- `intended_outcome`
- `state_targets`
- `fact_refs／rule_refs／issue_refs` 中至少一类来源或约束
### 角色行动 beat 额外必填
- 角色当时知道什么；
- 角色目标；
- 可用手段；
- 为什么选这个行动；
- 代价或风险。
这五项是“降智检查”的主干。叙事规划研究长期强调两件事：情节要有因果连续，角色行动要能被自己的目标和认知解释。[Narrative Planning: Balancing Plot and Character](https://arxiv.org/abs/1401.3841)
### 信息揭露 beat 额外必填
- 世界真相是什么；
- 哪个角色知道；
- 读者在 beat 前知道什么；
- 本 beat 新增什么；
- 仍隐藏什么；
- 是否允许误导，以及误导依据是什么。
### 互动选择 beat 额外必填
```yaml
choice_spec:
choice_id: CH-016-01
decision_owner: player_as_CHAR-001
preconditions:[STATE-77, RULE-11]
options:
-option_id: O1
label: 公开令牌
immediate_effects:[PE-1610]
state_deltas:[ST-D-91]
risk: 引来宗门追查
-option_id: O2
label: 继续隐瞒
immediate_effects:[PE-1611]
state_deltas:[ST-D-92]
risk: 同伴信任下降
convergence_policy: soft_converge_after_2_beats
canonical_status: noncanonical_branch
```
Ink 与 Yarn Spinner 等互动叙事工具都用变量、条件和选择控制流程，说明你的中枢应把“状态、前置条件、选择、效果”做成结构化字段，而不是只产对白脚本。[Ink](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)｜[Yarn Spinner](https://docs.yarnspinner.dev/write-yarn-scripts/scripting-fundamentals/flow-control)

## 5. 剧情卡和分镜卡怎样生成
### 一张卡不等于一条事实
推荐的卡片单位：
- 一个清晰可视动作；
- 一个角色决定；
- 一次状态变化；
- 一次信息揭露；
- 一个选择点。
纯背景事实、内心长期状态、规则说明可以附着在卡片侧栏，不必单独占卡。
### `projection_card_v1`
```yaml
card_id: CARD-016-03
source_beat_id: B016-02
card_type: action_dialogue
viewpoint_ref: CHAR-001
location_ref: LOC-009
characters_on_screen:[CHAR-001, CHAR-006]
visual_state:
CHAR-001: 右手按住受伤肋部
CHAR-006: 挡在门前
primary_action: 主角把令牌推到桌面中央
spoken_line_ref: LINE-DRAFT-22
subtext: 主角用公开部分真相换取同伴协助
reader_reveal: 主角确实持有令牌
conceal: 令牌来自谁
state_delta_refs:[ST-D-77]
next_card_condition: always
asset_refs:
CHAR-001: ASSET-CHAR-001-FRONT
CHAR-006: ASSET-CHAR-006-3Q
camera_hint: medium_two_shot
motion_hint: 令牌入画；说话角色轻微上移
```
你描述的“上传角色图，像 PS 一样放到画面里，谁说话就轻微移动”完全可以由这些字段驱动，不需要图像生成成为主链依赖。
### 多视角投影
同一 beat 可生成：
- 上帝视角卡；
- 主角视角卡；
- 配角视角卡；
- 反派视角卡。
但每张卡只能读取该视角允许的 `known_by／believed_by`。世界真相可用于审计，不能自动泄漏到角色旁白。

## 6. 长篇线怎样落到本章
建议每条故事线保留：
```yaml
line_id: LINE-03
status: active
current_phase: convergence
last_major_change_ref: A-082
open_ports:[A-091, ISSUE-33]
next_required_move: 让两名调查者交换各自掌握的半条线索
deadline:
max_chapters_remaining:2
continuation_constraints:
- 不能把二人写成已经互相信任
- 不能让反派知道密信原文
priority: high
```
本章计划只引用 active 线，不复制全线历史。程序沿 A 因果链、B 触发器、C 读者承诺、D 规则回取必要节点。
### 收线检查
- 是否新增了与收线无关的开放口；
- 计划中的 beat 是否减少未决，还是只换了场景继续拖；
- 到期线是否有具体 `next_required_move`；
- 多线合流后是否真的共享因果端点，而不是人物碰面就算合流。

## 7. 爽点、冲突和困境怎样进入大纲
不要用“加一个爽点”“增加冲突”这种空指令。应写成可检验变化：
### 爽点
```plain text
压制来源 → 主角可用但被限制的能力 → 触发条件 → 反转动作
→ 对手损失 → 旁观者认知变化 → 后续代价
```
### 阻碍
```plain text
角色目标 → 当前最优路径 → 阻碍从哪里来 → 阻碍为什么合理
→ 角色改用什么次优路径 → 新成本
```
### 情感爆发
```plain text
长期压抑项 → 本章触发 → 角色公开／隐性选择
→ 关系状态变化 → 是否可逆 → 下一章余波
```
这些结构既能生成正文，也能投影为卡片，还能由程序检查“太顺”“太平”“只有结果没有代价”。

## 8. 查询与回读索引
每条 fact、plan_event、beat 至少挂这些索引：
- `entity_refs`
- `chapter_id`
- `scene_id`
- `storyline_ids`
- `state_slot`
- `issue_id`
- `trigger_id`
- `reader_promise_id`
- `rule_id`
- `causal_parent_ids`
- `story_order`
- `discourse_order`
- `actuality`
- `known_by`
- `reader_visibility`
常见查询可以直接变成结构化请求：
- “主角最近一次资源减少是什么时候？”
- “反派目前知道主角身份到哪一步？”
- “两章内必须收的线有哪些？”
- “这个世界规则之前在哪些事件里实际生效？”
- “当前仍未兑现的读者承诺有哪些？”
- “第 16 章这个决定，角色当时有没有足够信息？”

## 9. 章节执行包的推荐结构
```yaml
schema_version: chapter_execution_packet_v1
chapter_plan_ref: PLAN-C0016-V4
contract_ref: EC-016-V2
entry_snapshot:
character_states:[...]
world_states:[...]
active_logic:
causal_nodes:[...]
triggers:[...]
reader_promises:[...]
rules:[...]
selected_history:
facts:[...]
omitted_bridges:[...]
ordered_beats:[...]
forbidden_assumptions:
- 不得把 BEL-155 当成 world_truth
- 不得让 CHAR-021 知道 F-1438 的原文
output_contract:
prose_target: 3200-3800 Chinese chars
preserve_beat_order:true
allow_local_scene_expansion:true
new_long_term_fact_requires_flag:true
```
### 包大小
v0.2 的 1,500 tokens 可作为普通章目标，不建议写成无条件硬顶。关键章可能有多条活动线和复杂知情差异，强截会损伤正确性。
建议：
- 默认目标：1,500 tokens；
- 软上限：2,000；
- 质量硬顶：2,500；
- 超过 1,500 必须有 `overflow_reason`；
- 任何单条事实的 actuality、必要限定和知情字段不可被截断；
- 超预算时整条低优先故事线淘汰，不截半条。
这个数值仍需用真实章节标定，不能直接转为现役阈值。

## 10. 最小可用版
不必一次把所有字段做完。第一版只要：
1. `canonical_fact_store`；
2. `plan_event_store`；
3. 人物状态快照；
4. A/B/C/D 四账；
5. `chapter_plan_v2` 的 beat、视角、目标、结果、揭露、引用；
6. `chapter_execution_packet_v1`；
7. `plan→prose` 实现对账；
8. 一种剧情卡投影。
这样已经能支撑续写、一致性检查、静态分镜和简单互动选择，后续再加镜头、资产和复杂分支。
