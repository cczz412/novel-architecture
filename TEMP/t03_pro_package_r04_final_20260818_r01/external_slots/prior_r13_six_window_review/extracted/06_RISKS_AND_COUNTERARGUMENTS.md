## 最强反对意见 1｜“A 已经知道缺哪些字段，直接实现最省时间”

### 反方论点

当前设计稿已经提到 versions、needs_recheck、锚迁移；先改代码，后面再修合同，比停下来讨论 owner 更快。

### 审查回应

这个方案会同时制造三个第二真源：C1 current revision、C10 identity revision、M4 fact stale。A 的反例不是“少字段”，而是“谁有权认同一章、谁确认替换证据底座、旧 confirmed fact 还算不算真值”。这些选择会改变 C4 枚举、M6/M7 查询、planstore 引用与历史迁移。若先写代码，后续合同只能追着既成实现走，风险高于短期收益。

### 条件分支

若 CZ 明确拍定 owner、restore-as-new、stale 语义和 anchor 基准，可以立即转正式合同／施工；否则只做 TEMP 候选。

## 最强反对意见 2｜“D 4/4 都是机械不变量，B 改 writer 不会影响，没必要重跑”

### 反方论点

B 只改事务入口，D 测的是无损、隔离、权限和只读，逻辑上正交。

### 审查回应

正交是推测，不是当前字节证据。D 的四张 fixture 全部把旧 `store.py` 列为输入，READY-03/04 还锁定旧 C4。重放成本是零 API、固定夹具、固定 42 断言；不重放却会让“当前字节通过”的说法失去可审计性。正确做法不是宣布旧 PASS 作废，而是保留历史 PASS 并补 current-byte receipt。

### 条件分支

若逐文件差分证明 B 修改与某票执行路径完全无交集，也应把这个证明写进重放回执，不能靠口头判断跳过。

## 最强反对意见 3｜“C 已经 13/14，直接开 C9 比等 A/T03 更有效”

### 反方论点

豆包 7/7、DeepSeek 6/7 足以做容错；先落 C9，再把 REAL-03 当模型差异。

### 审查回应

C9 不只是 Prompt。它要定义包内对象身份、版本水位、遗漏回执、回捞入口、消费者和原始结构。当前没有章节 revision 水位，也没有 unresolved bundle 的正式对象；豆包原始输出仍是 fence，DeepSeek 是 bare JSON，产品 parser 未验。现在落 C9 会把实验 Prompt 形状冻结成合同，并可能把旧章事实或未决遗漏系统化。

### 条件分支

可以提前做纯 TEMP 的 C9 schema alternatives，但 C 窗当前继续运行会与 A/T03 的候选形状互相抢定义。更稳的是有意空闲，等三项新停点。

## 最强反对意见 4｜“T03 11/11 至少部分覆盖，已经没有完全漏项”

### 反方论点

对未决发现而言，部分送达也能提醒作者，完全缺失 0 已经可用。

### 审查回应

部分送达可能比完全缺失更危险：它会截掉限定词、反对意见、未表态者或当前能力边界，让一个开放问题看起来像已决定。T03 自己的例子包括“只送最终提案，漏掉空房、反对和未表态”。因此 full/partial 必须分账；完整 6/11 与负控 19/55 都没过门。

### 条件分支

若产品明确把 partial 只显示为“材料碎片，禁止形成命题”，可以研究一个更低风险的辅助入口；这仍不是 C3/C4 正式未决对象。

## 最强反对意见 5｜“B writer 统一后，暗稿默认已发生就可以直接入账”

### 反方论点

R13/设计索引已有“暗稿默认已发生”，B 又保证只有作者 action 才能 confirmed，所以工程链已经具备授权。

### 审查回应

“作者点了哪个 action 才算签字”“暗稿能否成为 AUTHOR_ATTESTATION”“能否带动下一章”“收工与关章关系”仍是包内明确红线。B 只保证一个合法 action 进来后怎样原子写，不决定什么 action 合法。把事务安全扩成权限合法是典型层级偷换。

### 条件分支

CZ 明字冻结暗稿 action、签字回执、作用范围和下一章条件后，B 可再开实现；此前 idle。

## 最强反对意见 6｜“单一共享页面只要格式严格就不会串线”

### 反方论点

WINDOW_ID、CYCLE_ID、SHA 和 lease 都有了，模型只需按头部处理。

### 审查回应

这些字段能抓运输错误，不能清空模型已有对话上下文。页面历史仍可能影响回答，尤其旧权限、旧写集和同名模块。严格协议只能让本地验证拒绝异常，不能证明模型内部没有串线。必须把页面视为不可信顾问，权限永远在本地，正式字节变更后冷启动。

### 条件分支

若 CZ 更看重操作方便，可接受残余风险并采用协议 v2；若要求可证明隔离，改用六页／独立会话。

## 少数意见与可逆分支

### 少数意见 A｜C 可做一个无 API 的 C9 envelope 草案

这在技术上可行，也不必等模型。但当前 C 窗最容易把 envelope 写成半正式 C9，并与 A/T03 同时抢字段。推荐默认 idle。只有总控明确把写集限制为 TEMP、禁止字段定案、禁止 API 时，才可作为备选分支。

### 少数意见 B｜M10 可以比 M9/M11 更早施工

M10 是投影出口，只要 plan object 和来源回执稳定，V0 场景卡可以不等 unresolved 全部完成。它不在本轮六窗任务里，但后续排期不应把它机械绑在 M11 之后。风险是 C8 尚未落、插件/资产 owner 未定，需单独合同工单。

### 少数意见 C｜T03 可保留“碎片提醒”而不建命题

如果作者界面把它明确显示为未经聚合的原文片段，并禁止任何真值／状态推断，partial coverage 可能有辅助价值。它应作为另一个产品假设，不得用来替未决命题过门。

## 未证明的否定事实清单

下面几类句子必须禁止：

- “没看到签字，所以没有签”；
- “没看到接受，所以邀请未接受”；
- “未检出冲突，所以没有冲突”；
- “未读取旧版，所以旧事实已失效”；
- “竞品／模块没有字段，所以没有能力”；
- “D 没发现回写，所以所有路径都只读”；
- “旁路 writer 扫描为 0，所以未来插件不可能旁路”。

安全写法应带范围和证据：

- 原文明说“尚未接受”；
- 当前覆盖范围内未找到接受动作；
- 在本次固定入口和静态扫描范围内旁路 writer 为 0；
- D 的四条夹具未观察到未授权写入。

## 什么证据会推翻本回包建议

| 当前建议 | 可推翻证据 |
|---|---|
| A 先设计后施工 | CZ 已冻结 owner/语义，且现行正式合同已有未被本包收录的 revision contract |
| D 必须重放 | 有可审计差分证明四夹具执行路径与 B 改动完全无交集，并由当前字节结果票确认 |
| C idle | A/T03/D 新停点已齐，或 CZ 明确授权只做 TEMP C9 envelope |
| B idle | CZ 明字拍暗稿／关章／下一章 action，并指定 B 写集 |
| T03 不继续同 Prompt | 新的冻结未见数据证明同 Prompt 在独立样本上同时过 full≥90% 与 false trigger≤10%，且无分母变化 |
| 单页不可证明隔离 | 平台提供真正的会话分区／上下文隔离证明，并能由本地协议验证 |

## 决策风险底线

即使为了速度做条件分支，也不能牺牲三条：

1. 计划、未决、推断、投影不能冒充已发生真值；
2. 旧证据版本不能在无水位／无回执时静默继续驱动下游；
3. 外审建议、模型 PASS 和页面回复永远不能自生权限。
