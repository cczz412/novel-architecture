# 外发调查 Prompt｜Agent 工具、管线进度、停点与生成前检查（2026-08-14）

身份：**调查题，不是施工合同。** 给 ChatGPT（建议开深度调查）逐条复制。7 题互相独立，**不要带附件、不要同一窗连发**。回包只作证据与候选先验，不自动改 R10、不自动改代码。

产品语义以本地正式背景板 **R10** 为准。下面每题里的「已拍」是约束，调查时不要推翻；缺的是：**业界怎么做、失败长什么样、我们该把哪一层做成什么形状。**

## 怎么用

1. 新开一个 ChatGPT 对话（深度调查更好）。
2. 只粘下面某一题从「请做独立深度调查」到该题结束。
3. 7 题分 7 窗。回来后再对照 R10 消化，不要边回边改正式稿。

现在的 `python3 cli.py` 是检修口，不是作者产品。调查要回答的是：同一套管线，怎样暴露成 Agent 会用的工具，又怎样让作者看得见、控得住。

## 题 1｜工具面：产品该暴露哪些工具，形状怎样才让模型会选

```
请做独立深度调查。不要假设你能读到我们的内部文件。下面「已拍」是约束，不要推翻或改写成另一种产品。

我们在做给网文作者用的「故事真源引擎」：导写＋核对，不代写正文。后台有账本（已发生事实、人物/世界状态、知情、规划、义务、世界规则）。现在只有管理员命令行，能查各站交接物。作者看不懂这些零件。下一步不是再做一套作者 CLI，而是：

- 网页/手机：作者点画布、确认、选出题；
- 聊天里的主 Agent：作者用人话，底下调同一套能力；
- 外部 Agent（Claude 等）：只读已确认事实＋交修改提案，不能写正史。

已拍、不要推翻：
- 写入正史永不开放给外部工具。作者签字才入账。
- 聊天框先暴露已有能力；意图要分开：探讨 ≠ 真改 ≠ 查询。冲突走质检，不靠聊天直接改账。
- 插件/理论不自动冒出来，走卡牌；同一套内容按场景分层取用。
- 业务不绑某一家模型。今天的模型很会选工具（function calling / MCP），我们要把「组件」暴露成工具。

请调查并回答：
1. 长篇创作/编辑类产品（或相邻的 IDE、文档 Agent、游戏导演工具）怎样把「管线各站」做成工具清单？粒度怎样才合适（太粗＝一步做完乱跳；太细＝模型选错）？
2. 命名、描述、入参出参怎样写，模型才不容易选错工具？有哪些公开失败案例（工具爆炸、同义工具、副作用藏在查询里）？
3. 「管理员检修工具」和「作者/主 Agent 工具」要不要两套清单？若要分开，权利边界通常怎么划？
4. 工具返回值怎样才适合模型消费（短结构化回执 vs 长文本）？和「给作者看的句子」是否必须两套投影？
5. 给出一份建议的工具分层（只读查询 / 提案 / 开工编译 / 禁止项），每层举 8～15 个工具名级别的例子，并标明不该做成工具的事。

请给可核对来源（产品文档、论文、工程博文、事故复盘）。分不清已验证与推测时写明。不要给我们写代码，不要发明我们的字段名去冒充已拍合同。
```

## 题 2｜管线进度：怎样告诉 AI「现在走到哪一步」，防止跳跃和误关工作

```
请做独立深度调查。不要假设你能读到我们的内部文件。下面「已拍」是约束，不要推翻。

产品是网文作者的导写工作台。日常续写有明确步骤，例如：选当前故事线 → 编辑本章章纲（装配单）→ 处理卡片出题 → 作者确认选项 → 才谈关章/去写作区。系统不把抽取、记忆、章纲、生成揉成一次模型调用；每步留下可检查的工件。

已拍、不要推翻：
- 章纲阶段可以只编章纲、不产正式稿。
- 触发条件满足时默认只亮灯，不自动开卡；是否开卡由作者决定。
- 停点预先埋位，可设：自动通过 / 提醒不停 / 必停。小白默认少停，高级作者才频繁停。停点放行 ≠ AI 可写真值。
- 防乱：聊天与卡片是同一对象的两种输入；AI 产出必须固定落位，禁止随机弹窗把作者当前工作关掉或换走。
- 硬冲突红灯才能挡住「静默关章」；没检到只能说「当前覆盖范围内未检出」，不能写「确定无冲突」。

痛点画面：作者正在编辑大纲，跟 AI 聊着聊着，系统毫无征兆把大纲关掉并宣布「已经结束」。这不允许。管理员命令行以后也要按同一条管线走，作者思考时该停能停。

请调查并回答：
1. 带 Agent 的工作流产品怎样维护「当前步骤／当前工作对象／允许的下一动作」？常见机制：状态机、会话模式、工具按状态门控、显式 cursor。各有什么翻车方式？
2. 怎样防止模型跳跃（跳过确认、提前关章、把探讨当成真改）？有哪些可执行的护栏（服务端拒绝、工具不可见、二次确认、把非法动作变成提案）？
3. 「作者正在编章纲」时，聊天允许什么、禁止什么？怎样用指示器让作者和模型看到同一份进度（完成度、未关闭的工作、下一步）？
4. 停点三档（放行/提醒/必停）怎样接到 Agent 工具层，而不是只做 UI 开关？小白自动走推荐时，怎样留下可撤销痕迹、又不让模型以为已经签字？
5. 给出一份「管线游标」最小设计建议：状态有哪些、谁能改、聊天和点选必须读同一游标、非法动作的失败回执长什么样。

请给来源。不要写我们的代码。不要建议取消停点或让模型代签真值。
```

## 题 3｜双通道：聊天自动调工具，和一步一步点选，怎样同一权利、不越权

```
请做独立深度调查。不要假设你能读到我们的内部文件。下面「已拍」是约束，不要推翻。

我们要同时服务两种作者，而且是同一本账、同一套管线：
A. 小白：跟人聊天，主 Agent 自动选工具、推进；默认少打断，先看到效果。
B. 掌控型：一步一步点卡片生成，系统不主动替他做下一步；他要能看懂每一块是干什么的，故事始终在自己手里。

已拍、不要推翻：
- 产品定位导写＋核对，不代写。一键成文只是后续可选模块。
- 画布是交互中心，不是第二本账。聊天产出落画布，不另起真值。
- 小白默认停点放行；高级才频繁停。真值签字（事实入账、改史、Bible、来源认领）任何档位都要作者显式动作。
- 高影响事件（死亡/秘密揭示/物品转手等）不可随批量默认，要单签。
- 外部 MCP：只读＋提案。网页作者本人才有全功能。CLI 只是检修口。
- 意图三分：探讨 ≠ 真改 ≠ 查询。

请调查并回答：
1. Copilot / 工作流画布双通道产品（IDE、设计工具、低代码、游戏关卡编辑）怎样保证「聊天能做的」不超过「按钮能做的」？有哪些越权事故（聊着就把文档关了、自动提交、静默改主数据）？
2. 「不主动替他做」怎样工程化：默认只提案、只高亮、只生成选项，等点击才生效？和「小白自动走推荐」怎样用同一套权利表配置，而不是两套业务逻辑？
3. 作者友好的一步一步，最小要让他看见哪几类东西：当前任务、可选动作、已生效约束、未决冲突、完成度？哪些数字（例如「219 条候选」）不该上主屏？
4. 主 Agent 自动调工具时，怎样向作者展示「我正在用哪一步、为什么停、你还可以改」——可感知、可撤销，而不是黑箱一串调用？
5. 给出建议：一张「动作权利表」模板（动作 × 聊天是否可直接执行 × 是否必须作者点 × 失败时落到提案还是拒绝），覆盖：改章纲、选出题、关章、确认事实、豁免黄灯、关闭当前工作。

请给来源。不要建议做第二套作者 CLI 当主界面。不要让聊天绕过真值签字。
```

## 题 4｜这章编大纲时：怎样挑上下文、狠狠压缩，缺料时再去读

```
请做独立深度调查。不要假设你能读到我们的内部文件。下面「已拍」是约束，不要推翻。

场景：作者在编「第 N 章章纲／出下一章选项」。账本可以很细（上百章事实、状态、规划），但喂给模型的执行包必须瘦。脱离共同前提（不可逆变化、本章欠账、禁做、人物当前状态）剧情会走飞；全塞进去重点被稀释，还贵。

已拍、不要推翻：
- 「瘦」＝最小充分＋可扩张，不是越小越好。
- 账本可以细，执行包必须瘦。概念进产品与进执行包是两道门。灵感可以「存而不喂」。
- 压缩：当前完整、近期展开、远期一句且带覆盖编号和过期状态；不可逆长期留；换线先接回该线上次现场。压缩不能顶替证据，原文在冻结书稿里按需回捞。
- 检索对象应是账本对象（事实、计划、状态），不是把正文切碎当真值。正文按证据锚少量回取。
- 缺料时不要静默从全库追加；应暂停、让作者或受控回取看见缺了什么再重编。
- 整卷/整书宽窗口只作为大书重建、全书体检、低置信兜底的候选路由，不是默认。

请调查并回答：
1. 编译器式「按任务编译输入」、RAG、Agent 多轮 retrieve，各适合什么？长篇叙事里哪种失败最多（丢不可逆、召回噪音、重复摘要）？
2. 生成选项之前，「及时去读必要资料」怎样做成显式步骤而不是模型自己做梦补设定？预算和轮次怎样封顶？
3. 主模型是否只该看到编译后的包，把「去账本核对」交给子程序/子 Agent？业界有哪些 OK/缺料/冲突 的短回执格式？
4. 针对「编本章大纲」给一份分区建议（任务、铁律、本章禁做、近章、本线状态、望远索引、可回取目录）。说明每区为什么在，以及超预算时先降档还是先踢出（踢出必须仍可回取）。
5. 列出最不该从包里丢掉的 10 类条目，和最不该默认塞进来的 10 类。

请给来源。不要把向量库写成故事真值。不要假设可以无限制加上下文。
```

## 题 5｜生成「看似正确的选项」前要做哪些检查；哪些用规则，哪些用子 Agent 只回 OK

```
请做独立深度调查。不要假设你能读到我们的内部文件。下面「已拍」是约束，不要推翻。

目标：出题/生成方案前做大量检查，让主 Agent 不必自己读海量上下文。子检查只回报：OK / 缺什么 / 冲突是什么。检查过了，主模型才生成选项。

已拍、不要推翻：
- 红灯：两端都能回验的已确认硬冲突。黄灯：节奏、手法、情绪、模板偏离。隐含/多跳/证据未闭合 → 待复核线索，不是红灯。
- 没检到不能写「确定无冲突」，只能写覆盖范围内未检出。
- 读者知情硬账至少：已知道 / 不知道 / 被误导（记下误解成什么），带原文锚。软猜测（读者大概猜到多少）不进真值。
- 人物心理标签只作软先验，不能单独当硬约束。行为判断靠事实、目标、关系、情境、历史选择。
- 生产模型不能自签质量绿票；抽取和质检不应用同一家模型。
- 触发满足默认亮灯进执行包，不自动开卡。

我们初步分类（请批评和补全，不要当成已实现）：
A. 规则/字段匹配：人物状态字段是否对得上；秘密是暴露/公开/误信/怀疑/完全不知道。
B. 事实句关键字：这个动作是否撞上某条已确认事实里的关键词。
C. 世界规则：不能把全部规则塞进提示。规则应带触发器，只检查被触发的那些。
D. 可能仍要小模型/子 Agent：动机是否降智、方案是否机械套技巧。

请调查并回答：
1. 游戏引擎、叙事引擎、政策引擎、代码 linter 里，「生成前守卫」怎样分层（纯规则 / 检索核对 / 小模型）？延迟和漏报通常怎么取舍？
2. 子 Agent「只回 OK/问题清单」的可靠做法？如何防止子 Agent 编造 OK？需要证据指针吗（事实编号、原文片段）？
3. 针对「生成下一章剧情选项」，给出检查清单：每项用规则还是模型、输入是什么、输出回执字段建议、失败时阻止生成还是带黄灯仍可出题。
4. 关键字匹配的陷阱（同名、否定句、已痊愈的伤）。字段状态机（知情多态）怎样避免组合爆炸？
5. 哪些检查必须在生成前；哪些可以生成后、作者看到选项时再跑？

请给来源。不要让检查器拥有签字权。不要建议把 200+ 条事实一股脑给主模型当检查。
```

## 题 6｜世界规则、Hook、义务、作者规划：触发器格式怎样统一，作者怎样看见「正在生效」

```
请做独立深度调查。不要假设你能读到我们的内部文件。下面「已拍」是约束，不要推翻。

长线账里有：故事线、因果、义务、规则、触发条件。Hook（作者埋的钩子/规划）和故事内义务要分表，不要混成一种东西。触发应绑故事内事件或故事内时间，不硬绑章号。章号字段合同未冻结，方向是优先故事内事件/时间。

已拍、不要推翻：
- 触发满足：默认亮灯＋进入本次执行包，提高相关材料优先级；不自动开卡。
- 计划事件不是已发生事实。选中计划 ≠ 已经在故事里发生；「安排了」和「实际兑现」是两层。
- 作者要能感知工作流里什么在生效。画布接的是底部账本的投影（完成度、节奏、哪对哪不对）。
- 管理员命令行以后也按同一管线读这些指示器，方便作者思考时停下来。
- 例子：某宝物落到谁身上，触发隐藏条件；作者规划的 hook 要能被准确拿到，而不是大海捞针扫全部世界规则。

请调查并回答：
1. 规则引擎、游戏 quest、INK/Twine、商业叙事工具里，触发器的最小字段通常有哪些（条件、范围、一次性/可重复、预热、冷却、谁可见）？
2. 把世界规则、义务、hook、未来规划做成「同一套触发器外壳、不同载荷」是否可行？何时必须分表（我们已倾向 Hook 与义务分表）？统一外壳能避免什么乱，会引入什么错？
3. 「触发器」怎样写才既能被程序匹配，又能投影成作者能看懂的一条：「现在生效的是……因为……」？
4. 预热提醒（快到了但还没触发）怎样做才不像垃圾通知？和停点、黄灯如何分工？
5. 给出一份触发器外壳建议（字段级建议即可，标明是建议不是我们的已冻合同）：条件类型、匹配输入（刚发生的事件/当前状态）、输出（亮灯/入包/禁止某动作）、作者可见文案、调试/CLI 可见字段。并给 4 个例子：世界规则、义务到期、作者 hook、宝物易主。

请给来源。不要把触发器绑死章号。不要让触发自动改真值或自动开卡。
```

## 题 7｜画布指示器：完成度、节奏、对错，以及节奏不对时怎样选理论/插件

```
请做独立深度调查。不要假设你能读到我们的内部文件。下面「已拍」是约束，不要推翻。

作者主界面是按章的一张工作流画布（任务卡、连线、红黄灯、接收区）。时间轴是分开的预览，不是同一张主画布。底部是账本数据；画布只投影作者该看见的。聊天先暴露工具能力，点哪问哪。

已拍、不要推翻：
- 红灯＝硬事实冲突（可回验）。黄灯＝节奏/手法/情绪。待复核线索另账。
- 节奏监控可以是规划画布拉到最远的视图，尽量零自有账本。
- 理论/技巧（救猫咪、英雄之旅、打脸爽点等）走插件卡牌，不自动往上冒。同一插件分层：出题时短、写法指导更细、分镜再下一层；分层标准要能告诉用户（他们也可能自己做插件）。
- 要点汇聚屏是插件提醒的集散地，分组折叠、来源标注。
- 写作指导是出题副产品，不另开一次 API。
- 产品不产正文；不做「降 AI 率」承诺。

请调查并回答：
1. 专业工具（视频时间线、DAW、IDE 诊断、项目管理）怎样把「完成度 / 健康度 / 节奏」做成一眼能懂的指示器，而不把内部计数（候选 219 条）甩给用户？
2. 「节奏不对」怎样从可计算信号变成作者能懂的一句话＋一个下一步？哪些信号可规则化（钩子间隔、欠账堆积、连续无兑现），哪些必须模型看？
```
