# 上下文配方

这个目录主要解决“几份材料怎样拼成模型消息”的问题。你可以直接理解成：配方只写装配规则，不负责联网，也不负责真正调用模型。

一份配方会用路径和 SHA256 锁住三份上游材料：

- API 合同包；
- 提示词清单；
- 任务输出 Schema。

配方还会点名一个模型调用档、一个合成输入槽，以及严格的两条消息顺序。当前合同只允许先放系统消息，再放用户消息；不能多塞消息，不能给内容加前缀或后缀，也不能做提示词变量替换。

旧的合成探针输入槽只接收不超过 4096 字节的 JSON 对象。根层必须有 `probe_id`
和 `payload`，`payload` 必须有 `label` 和 `values`，`values` 最多 16 项。

小说事实抽取 v2 另走整章配方：用户消息由 P3 背景卡、背景卡使用边界、文件名和
完整章节逐字拼成。这里没有 4096 字节短探针限制，因为它模拟的就是真实整章请求。
背景卡自己的来源另用来源索引绑定真实文件和 SHA-256；目标章节不能成为背景卡的
唯一来源。

能力边界全部写死在配方里：只准离线解析，不准联网、不准读取密钥、不准发送请求、不准调用模型，也不准写 Notion。

具体配方实例和 Schema 分开放：Schema 管通用结构，实例只登记本次选择及上游
文件 SHA。旧实例引用的任一零件发生变化时，应重新登记新修订，不能原地洗掉旧 SHA。

小说事实抽取 v2 的三个零件是：

- `novel_fact_p3_context_card_v1.schema.json`：规定背景卡只放题材、主角别名和金手指；
- `novel_fact_p3_source_index_v1.schema.json`：登记背景资料真实路径与 SHA-256；
- `novel_fact_v2_user_message_template.md`：把背景卡和完整章节拼成用户消息。
